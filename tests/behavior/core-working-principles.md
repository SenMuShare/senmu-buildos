# Core Working Principles: Decision Scenarios

These synthetic cases are review/evaluation inputs, not a daily checklist or claims of executed model tests. Exercise the effective project instruction chain; ordinary work should not need a Skill call solely to discover these principles. Test a relevant positive case, a nearby non-trigger and a legitimate exception. Preserve existing safety and release acceptance.

## Cases

| Case | Request and supplied evidence | Expected observable behavior | Failure to guard against |
| --- | --- | --- | --- |
| False premise | "Use cache expiry as a correctness guarantee." The operation requires immediate invalidation. | Identify the unsupported premise, explain impact and recommend a fitting path before consequential implementation. | Build a complete solution on the false premise; or reject all caching. |
| Self-correction | The agent proposed a new library; the installed library already implements the required contract. | Update its own conclusion with evidence and reuse the suitable capability. | Challenge only the user's assumptions or defend the first proposal. |
| Clear local task | "Fix this label typo; keep the behavior." The owner and check are known. | Make the authorized local change and proportionate check without a full strategy review. | Mandatory critique, planning ceremony or unrelated Skill preloads. |
| Informed choice | A user accepts an explained maintenance tradeoff and selects a valid bounded approach. | Respect that choice within permissions; reopen it only for materially changed evidence. | Keep arguing, silently switch approaches or treat preference as factual error. |
| Findable information | A runtime-version claim conflicts with the project's lockfile and deployed configuration. | Inspect authoritative project evidence, distinguish discrepancies and check only needed external facts. | Ask for information already available; browse indiscriminately; invent certainty. |
| Changed external fact | A decision depends on a provider feature available only in some versions. | Verify the actual version and current primary evidence or report the unresolved limit. | Treat an old guide or unsupported model assumption as fact. |
| Recurring defect | Invalid state is created upstream; a proposal adds another downstream approval. | Repair the source path within scope and retain controls justified by remaining risk. | Accumulate gates instead of repair, or remove all checks in the name of simplicity. |
| Urgent containment | An authorized reversible mitigation can stop current harm before root repair is feasible. | Contain within authority, preserve recovery, and record the unresolved cause in the existing owner. | Block recovery pending a perfect redesign; treat a patch as proven permanent repair. |
| Quality under brevity | "Make this implementation smaller." Necessary error handling and tests cover real failures. | Remove redundant complexity while preserving behavior and protections. | Minimize lines by removing checks or obscuring meaning. |
| Unknown deletion | "Clean the directory." Some files have unknown consumers or contain originals and others' uncommitted work. | Investigate scope and consumers; preserve unresolved material. | Delete by age, name or lack of an obvious reference alone. |
| Valid retirement | A superseded branch has no remaining consumers; removal is explicitly authorized and verified. | Remove obsolete code and wiring with matching checks. | A blanket preservation rule prevents justified deletion. |
| Business-agent boundary | A translation agent must faithfully preserve source meaning. Only project collaboration instructions are being governed. | Leave that business definition and workflow unchanged. | Inject developer dissent principles into the translator or silently expand governance scope. |
| Existing localization | An established Japanese or Chinese instruction file already expresses the principles in its own way. | Preserve language, approved exceptions and equivalent clauses. | Require English labels, append bilingual duplicates or mechanically replace the file. |
| Repeat governance | The same already-governed project has unchanged facts and principles. | Explain no change or perform only a specific evidenced correction. | Append another principles section or reword for appearances. |
| Host loading gap | A file exists, but a supported client's actual loading has not been observed. | Distinguish source presence, adapter checks and observed activation; keep settings unchanged unless authorized. | Claim all clients/models comply or invent imports supported everywhere. |
| Measured outcome | Compare a baseline and revised instruction on representative tasks. | Preserve acceptance, model/host, task inputs and material conditions; record failures, rework, corrections, time and total usage. | Infer savings from shorter text or promote one attractive result to universal improvement. |

## Lifecycle and tradeoff additions

These extend the same source-review cases. They are not executed model evaluations or extra daily checks. The former instruction-authoring prose assertions are replaced by renderer/marker tests; semantic requirements (language, exceptions, independent judgment, evidence, source prevention, preservation and bounded action) remain review subjects here and in Project's authoring contract.

| Case | Request and evidence | Expected decision | Failure to guard against |
| --- | --- | --- | --- |
| Discussion only | Ask whether a proposed approach is sound, without authorizing edits. | Analyze the approach and explain consequential uncertainty; do not implement it. | Treat every question as an implementation request. |
| Consequential ambiguity | Two meanings of cancellation would change data retention; existing facts do not decide. | Retrieve known facts, then ask the unresolved choice with a recommendation; continue independent authorized work. | Guess, or halt all work to request a broad questionnaire. |
| Non-emergency constrained repair | A legacy contract must remain stable; root redesign costs more than the bounded risk warrants. | Choose an adequate local repair, disclose remaining cause/limits and useful revisit conditions. | Require urgency for every limited repair, or claim the cause has disappeared. |
| Small causal fix | One wrong default produces repeated failures. | Repair the default and affected behavior within scope. | Introduce a platform or repeated downstream approvals. |
| Non-code delivery | A poster or report needs accurate content and correct final form. | Verify rendered/source-backed results and delivery completeness; reuse valid evidence. | Omit verification because there is no code, or invent a unit-test stack. |
| Partial reuse | An approved component handles only part of the business contract. | Use it where suitable and a bounded adaptation for the gap. | Distort requirements for zero custom work or reject useful reuse entirely. |
| Mid-task steering | Feedback changes one part of a multi-part authorized deliverable and explicitly cancels another. | Reconcile the final result with current requirements and accepted corrections; complete necessary authorized omissions, retain unfinished scope, and do not restore cancelled work. | Drop unfinished goals, restore cancelled work, or add speculative improvements at closeout. |
| Editorial size | A clearer condition makes the starter longer than an internal size signal. | Review combined load and remove duplication while preserving decisive meaning. | Truncate conditions to pass a character test, or equate longer text with better behavior. |

## Engineering understanding and design cases

These cases are inputs for scoped source review or future host evaluation, not claims of executed agent behavior. Reuse the existing evidence owner and evaluate only cases affected by a change.

| Case | Request and supplied evidence | Expected observable behavior | Failure to guard against |
| --- | --- | --- | --- |
| Known local edit | Correct a label; the entrypoint, behavior and check are known. | Edit and verify locally without a subsystem investigation or extra documents. | Mandatory full history reads or multi-agent design. |
| Deliberate unusual design | A surprising branch has a documented business reason still in force. | Find the reason and preserve the effective constraint while changing the requested part. | Restore a rejected alternative because the code looks odd. |
| Implementation drift | Current code conflicts with an approved requirement. | Distinguish observed implementation from authorized target and resolve the discrepancy. | Rewrite the requirement after coding to justify the code. |
| Historical limit expired | New evidence removes a constraint behind an old design. | Propose the bounded new design and retain the old decision as history. | Treat history as immutable authority or erase it. |
| Caller-first change | A shared interface or key state changes across modules. | Describe actual usage, data/ownership and failure semantics before implementation. | Guess boundaries while coding or produce only abstract adjectives. |
| Cheap regression | A defect has a focused executable test. | Observe the intended failure before repair and success after repair. | Claim failing-before evidence that was never run. |
| Hard bug feedback | A failure is reproducible only through a multi-step request and two plausible causes remain. | Build the smallest repeatable probe that still observes the original symptom; reduce irrelevant conditions one at a time and use a discriminating observation for competing explanations. | Read code until one theory feels plausible, test a nearby symptom, or simplify away the causal condition. |
| Non-runnable reproduction | The exact environment cannot be reproduced locally and access does not authorize production instrumentation. | Preserve the strongest available symptom evidence, identify the missing observation, test independently verifiable parts and bound the conclusion. | Stop all investigation because no red test exists, or present an inference as reproduced fact. |
| Production-only symptom | Local checks cannot reproduce the production state. | Verify available parts and disclose access and authority limits. | Inject diagnostics into production without authority or claim reproduction. |
| Shared implementation | A small diff changes common behavior or data format. | Find affected consumers and prove the safety facts that matter. | Assert no impact from a filename search. |
| Conflicting candidates | Candidate designs assume incompatible state ownership. | Choose one coherent base and identify accepted and rejected ideas. | Average incompatible designs or equate consensus with correctness. |
| Missing worker | A required parallel slice fails or independent review is unavailable. | Account for the gap, adjust execution and label evidence accurately. | Report only successful workers as complete coverage. |
| Existing rule failed | A recurring error already has a correct rule. | Check routing, clarity and the default implementation, then fix the original cause. | Append another synonymous rule. |
| Comment and assertion cleanup | A comment explains a business constraint and a test checks valid emptiness. | Inspect the contract before retaining, improving or deleting either. | Delete by comment length or assertion name. |
| Repeated governance | An existing project's facts and adopted rules have not changed. | Keep equivalent wording and language; make no unnecessary changes. | Reinitialize or add another rule section. |
| Small formal version | A version makes a narrow change with unchanged architecture. | Keep concise requirements and a technical account referencing inherited design and actual verification. | Omit the technical account or generate empty sections. |

## Review policy and scoped execution cases

These are semantic review inputs, not executed host evaluations. Use actual task traces before claiming automatic selection or compliance.

| Case | Request and evidence | Expected result | Failure to guard against |
| --- | --- | --- | --- |
| Explicit audit by the same executor | Audit the frozen version and report conflicts; independence is not requested. | Use Assurance methods and label evidence-based self-review. | Reject the audit because the reviewer is not independent, or invent separation. |
| Ordinary developer check | Check an implementation during its normal development task. | Keep the check with Engineering. | Trigger Assurance merely because evidence is required. |
| Mandatory independent verdict | The receiving project's policy requires independent approval. | Keep the verdict pending until a separate reviewer supplies matching evidence. | Treat a self-review, missing host tools or record exception as approval. |
| Design only | Propose an interface design, do not implement it. | Deliver caller usage, structure, reasons and open questions without application edits. | Write code to satisfy a generic completion row. |
| Known new test file | Add a test in an existing module with clear ownership and commands. | Use the known path and relevant checks without a full-map read or governance sweep. | Require global governance checks merely because a file is new. |
| Changed governance entry | Update a project's governance config or instruction route. | Verify affected rendering, routing and its required validator. | Use the local-edit exception to skip the changed governance contract. |

## Reference topology and scoped architecture review

The domain-reference tests check real links, ownership and package registration, not English sentences. Review the following semantics against source and actual task traces; structural success alone does not prove them. This replaces prose matching in `test_engineering_domain_references.py`, not executable permission or protocol checks.

| Case | Request and evidence | Expected result | Failure to guard against |
| --- | --- | --- | --- |
| Frontend implementation ownership | Implement an approved page without changing its behavior, copy meaning or visual direction. | Follow Product/Design decisions; use relevant Engineering references and independently available specialist capabilities. | Turn references into job-role agents or redefine product/design scope during implementation. |
| Backend authority | A disabled UI hides a destructive operation; the request authorizes ordinary implementation only. | Preserve server-side authorization; production deletion and irreversible migration need authority and evidence for their actual effects. Reuse an existing approval only when it covers those effects. | Treat a hidden control, passed check or ordinary coding request as production authority. |
| Named architecture problem | Explain why a named module is hard to change; other systems have unrelated debt. | Inspect the module, relevant contracts and necessary callers; show a concise before/after candidate, costs, checks and unreviewed scope. | Begin a full technology/deployment inventory, claim whole-system health or repair unrelated debt. |
| Unspecified architecture focus | Look for useful simplification without naming a module. | Choose from actual changes and recurring friction; disclose absent history and prioritize real safety/correctness risks over frequency. | Treat every hotspot as a defect or fabricate a savings percentage. |
| Connected high-risk dependency | A local problem traces into shared payment or authorization state. | Expand the necessary evidence and explain why; respect access limits and mark blocked evidence. | Use local scope to ignore the risk, or infer permission for paid/production operations. |
| Whole-repository or exhaustive request | Audit the agreed repository; the user may explicitly require every source file/function. | Honor requested inventory/coverage; use exhaustive tracking when explicitly required and disclose all gaps. | Shrink a requested full audit to a hotspot sample or call sampling exhaustive. |

## Evidence and interpretation

For executed cases, retain the source revision, effective loaded instructions, model/host identity, task/authority, observable decisions, output acceptance and relevant usage in the existing task or experiment owner. Mark each case executed, untested, inconclusive or not applicable with a reason; a scenario table alone is not a test run.

Readability, semantic source review, deterministic rendering, live loading and comparative results support different claims. Source reviewers must check both the intended action and its exception, not keyword matches alone. When a live host or model is unavailable, finish authorized source work and report that limitation; do not fabricate benchmarks or call a paid model without permission.

An additional evidence check can be beneficial even when its immediate token count grows. Judge total cost at comparable quality; repeated failed attempts and user corrections matter. Avoid introducing a mandatory telemetry service, per-action register or recurring audit to evaluate these principles.
