## 边界断言

- 普通编码不应同时触发核心、工程、交付和审查。
- 普通编码可以不加载专业 Skill，但 SessionStart Kernel 仍必须给出写入隔离、匹配验证和本地 commit 的最小合同；“不触发 BuildOS Skill”不等于没有 BuildOS 写入边界。
- “审查”默认触发 assurance 并保持只读；“修复审查问题”才由 engineering 实施。
- “复盘、经验沉淀、经验库维护、通用反哺”触发 learning；只有独立裁决或争议性根因才组合 assurance。
- 原始客户／用户反馈先进入 product，不能因使用了“反馈”二字就路由到 learning。
- 以 owner／目录／状态映射和目标治理实例为交付物的成熟项目审视由 project 负责；以冻结对象、Coverage Map、证据等级、发现和结论为交付物的独立审查由 assurance 负责。
- “发布”由 delivery 负责，不能因为代码测试通过就由 engineering 宣称上线。
- “开发完成”“准备候选”或“预检通过”不构成发布授权；未经本次明确授权不得 Tag、上传、SSH、部署、切流、通知或远端清理。
- 已声明的标准发布收口只在正式发布授权和生产验证成立后执行；必须精确限制项目制品根和镜像仓库，保留当前／上一版本、容器引用与显式 Pin，不删除 Git 历史、Volume、数据库、其他项目镜像或全局缓存。
- `implemented`、产品 `accepted` 和真实 `released` 必须由 engineering、product、delivery 分别提供事实，不能由一个状态替代全部链路。
- 发布门禁以冻结候选、明确纳入范围和共享生产资源为边界；无关 POC、分支和 worktree 的存在或脏状态不自动阻塞，也不得为清空全项目强迫其提交主线。
- 复杂治理咨询先报告现场事实和盲区，再给出场景判定、首选建议、理由、例外和收口条件；普通小任务不强制长模板、新台账或固定目录。
- POC 的项目级权威不等于产品 `main` 工作树；进行中实验默认写独立 POC owner，不进入产品迭代计划、正式台账、交付目录或生产状态。
- 没有语言专项 reference 时仍由 engineering 负责：保留项目现有语言和构建基线，使用通用层、项目配置及当前语言官方规则，不因 Python Profile 更详细而迁移技术栈。
- 项目已有稳定规则的日常执行优先项目本地入口，不应重复加载 Senmu BuildOS 大范围治理。
- 采用 BuildOS 的项目 `AGENTS.md` 是项目差异层：只保存项目事实、权威路径、真实命令、特有约束和明确覆盖；不得复制 BuildOS 通用方法。项目 owner 已充分回答普通任务时停止 Skill 路由。
- 项目 `AGENTS.md` 不得把 README、架构、基线、发布登记和 worktree 登记串成所有任务的固定前置，也不复制七个 Skill 职责目录；根据任务信号只读一个路由入口和命中 owner。
- 成熟项目治理先把现有 `AGENTS.md` 分为保留项目事实、压缩到专业 owner 路由、删除 BuildOS 重复和冲突待用户裁决四类；不得先写默认模板再与旧入口叠加。
- 路径和静态校验通过只能记为 `structural_routing_prepared`；宣称上下文已接线前，用全新会话验证低风险单单元、专业边界和发布／回滚三类路由，并报告实际加载与未验证行为。
- 项目本地事实是当前状态权威，但不因存在就自动满足治理标准；明确要求审视或演进时应识别缺失、冲突、重复、过时和不可搬迁问题。
- `governance/tasks/` 只是新项目默认实现；成熟项目必须恢复项目声明的 Durable Task State Owner，不得建立第二套状态。
- 没有成熟运营内容前，不得路由到不存在的 operations Skill。
- 同一 Agent 或主要实现者的复核必须标为 evidence-based self-review，不能宣传为 independent review。
- Checklist 默认是检查辅助，不是所有任务的固定门禁；只有本次风险确实涉及、进入正式评审或负责人明确要求时，未解决的阻断项才必须停止推进。
- 普通一致性检查由当前专业 owner 在自然转换点和任务收口时完成，不新增 Analyze Skill、固定分析阶段或默认 `checklists/` 目录。
- G3-G4 只提高证据、验证和收口强度，不自动触发 Assurance；独立结论、跨域争议或正式审查确需职责分离时才触发。
- 工作流契约、Run Manifest 和 Task Plan & Status Record 必须分别保存长期规则、单次运行事实和跨阶段任务状态；同一任务可关联多次运行，不得维护同步正文副本。
- Hook 不读取 Run Manifest、不猜测当前步骤，也不推进运行状态；恢复由工作流公开入口和唯一状态 owner 完成。
- 新项目初始化是由“创建／启动项目”的任务语义触发，不是 Hook 监听目录后静默创建文件；非空项目必须先走只读审视。
- 询问单个文档或目录放置位置只产生建议，不自动创建；建议应说明首选 owner／路径、理由、替代和是否需要新目录。
- 空白项目先用显式项目类型、档位和模块生成零写入计划；实际初始化不得依赖 `software + standard` 等隐含默认组合。
- 已有项目的目录整理先区分规划与实施；未取得迁移授权时只输出现状、目标、映射、影响和恢复建议。
- 空白新项目可显式使用 `--commit-baseline` 创建初始化恢复点，只提交初始化器管理且通过结构校验的文件；不得 `git add .`、创建 Tag、处理成熟项目或演变为自动提交 Hook。
- 价值切片必须先闭合权威输入、核心路径、可观察结果、匹配验证和可交付输出；只完成脚手架、抽象或门禁不算阶段价值完成。
- 用户故事、价值切片、工作项编号、依赖图和并行标记都不是普通任务必填格式；需求完整性与任务可执行性由目标、变化、逻辑、边界、结果、真实前置和匹配验证判断。
- 复杂任务按当前上下文能够完成、验证和交接的阶段推进；阶段结果写回唯一 Durable Task State，不让一次长实现运行耗尽上下文后继续猜测。
- 实现发现必须按影响回写 Product、Engineering、Workflow 或 Task 的正式 owner；代码和聊天不得成为未批准范围变化的唯一事实源。
- 历史实现和测试只能作为证据，不能反向定义当前需求；布局任务不得决定功能存在，能力替代必须成组收口，并验证旧入口不可达或批准的兼容边界受控。
- 实现稳定后、最终评审前，只对本次实质代码变化做有边界的复用、质量和效率简化；保持行为与安全边界，不以删行数为目标，也不固定启动多个审查 Agent。
- 任务收口复用原编号任务计划 `TASK-<NNNN>-<slug>.md` 或成熟项目既有任务系统；不新增 Implement／Converge Skill、固定命令、第二份任务清单或自动无限补任务循环。
- 机会评估复用 Requirement Backlog、REQ、按需 Research 和 Decision Log；不新增 Assess Skill、固定五阶段流程或平行 assessments 目录。
- 缺陷闭环复用 defect REQ、Task、代码、测试、Work Log 和 Delivery 记录；不新增 Bug Skill 或 assessment／fix／test 三份同步报告。
- 项目 `AGENTS.md` 保持稳定短入口，当前任务从 Durable Task State 恢复；不自动把“最近计划”写入 Agent 上下文，也不在当前阶段生成多 Harness 适配文件。
- BuildOS 通用反哺以完整源码仓库为项目和版本边界；单个 Skill 是组件与运行入口，不是独立发布产品，安装目录也不默认成为源码权威。
- `UserPromptSubmit` 只把明确纠正或投递动作保存为待审候选；仅询问反馈机制不入箱。命中后返回空 Hook 输出，不向模型注入候选 ID、收集说明或处置指令。Agent 发现高信号缺口时可静默调用本机 CLI。两条路径都不自动加载 Learning 全文；集中审议仍由用户任务语义触发，并按当前范围检索相关经验。
- 面向用户的说明先给实际结果与影响，再给专业机制；非通用缩写、状态名和符号首次出现时用普通语言解释，并按用户背景控制深度。

## Skill 选择与交接行为断言

| 场景 | 当前主 Skill 与最小交接 | 禁止行为 |
| --- | --- | --- |
| PRD 已澄清，用户要求开始实现 | Product 交接需求 ID、范围／非目标、业务规则、验收标准和未决问题；Engineering 成为主责 | 加载全部 Skill、复制整份产品规则，或由 Engineering 猜业务决定 |
| 实现中发现需求歧义会改变架构 | Engineering 交接冲突事实、技术影响、选项和必须回答的问题；Product 处理产品决定 | 工程侧自行扩大范围，或由 Project 充当无必要中转站 |
| 实现和测试完成，只要求准备候选且明确不发布 | Engineering 交接 commit、变更范围、验证和残余风险；Delivery 保持候选／预检状态 | 因交接自动创建 Tag、上传、部署或通知 |
| 工作流运行失败并定位到代码缺陷 | Workflow 交接 run ID、失败步骤、契约、日志和最小复现；Engineering 修复代码，Workflow 保留运行状态 | 把 Run Manifest 复制成工程任务正文，或丢失原 run identity |
| 独立审查发现需要整改的问题 | Assurance 交接 finding ID、证据、影响、目标 owner 和复核条件；专业 Skill 实施，Assurance 再复核 | 审查者未经授权直接修改，或实施者自行关闭 finding |
| 重复问题已解决并验证，值得复用 | 专业 owner 交接触发场景、根因、修复证据和适用范围；Learning 查重并把稳定规则回写源头 owner | 把工作日志、完整报告或未验证建议复制为长期规则 |
| 单领域任务的目标和 owner 已明确 | 直接选择对应专业 Skill，不加载 Project 或任何总索引 | 设置第八个编排 Skill，或把七个 Skill 组成固定流程 |
| 跨多个阶段且任务状态本身需要治理 | Project 维护唯一 Durable Task State，并链接各专业产物；每一阶段仍由对应专业 Skill 主责 | Project 复制 PRD、技术设计、Run Manifest 或 Release Record 正文 |
| 当前实现阶段结束，准备判断任务是否真正完成 | 当前专业 Skill 核对承诺范围、正式 owner、实际结果和验证；缺口继续写回原任务，Project 只维护跨阶段状态 | 仅凭任务勾选宣称完成，或另建 Converge 文件和第二份任务清单 |
| 1.x 维护期间开发确定会替换主线的 2.x | Delivery 登记继任版本线、创建基线、Hotfix 前向传播契约、主线晋升和清理条件；范围和架构分别按需组合 Product、Engineering | 把继任线变成长期第二项目，或以“分支开发完成”代替合入并替换主线 |
| 1.x 普通 Patch 已稳定且对 2.x 适用，2.x 正在开发 | 更新唯一前向传播记录并排入项目检查点；同步时运行受影响验证，晋升前清零 | 每收到一个 commit 或跨 Agent 消息就中断 2.x、重复合并并跑全量测试，或无条件拖到发布后 |
| 1.x 修复涉及安全、数据、权限、支付、共享契约，或 2.x 正基于错误行为继续开发 | 将传播时机提升为 immediate，使用稳定源身份或显式标记仍可能变化的紧急源，完成继任线匹配验证 | 为保持开发节奏延后重大风险，或不判断适用性就盲目合并整条 main |
| 其他 Agent 通知 Hotfix 有补充 commit 或更正 | 把消息作为事实交接更新同一条传播记录；当前用户指令、登记检查点或重大风险才触发中断 | 把通知自动当成接收方立即执行、扩大版本范围或发布的授权，并为每次更正新建合并任务 |
| 用户只要求只读讨论分支策略 | 在当前权威目录只读盘点，不创建分支或 worktree | 把讨论误当实现授权并创建执行面 |
| 用户明确要求同时检出两个分支 | 获得明确授权后在项目总目录登记的 `.worktrees/` 或既有容器创建 worktree；登记集成与清理条件 | 把 worktree 放入 Codex／Agent、其他项目或未登记临时目录，或从 worktree 直接作为正式发布入口 |
| 多个 Agent 同时分析但只有一个需要改代码 | 共用权威目录，指定唯一写入者；其他 Agent 不切分支、不暂存、不写文件 | 为只读分析机械创建多个 worktree，或让多个 Agent 在同一目录同时写入 |
| 第一个写入会话启动时用户尚未决定是否还会开其他会话 | 默认从目标线基线创建独立短分支和 worktree；不要求用户预测最终并发数量 | 因当前没观察到别人就在共享 main 写入，等第二个会话出现后再处理混合脏改动 |
| 非技术用户说会开多个会话并行修复多个 Bug | 将实现授权翻译为每个写入任务一个独立短分支和 worktree；只读任务不建执行面，共享资源不能隔离时串行 | 反问用户选择 branch／worktree／merge，或让多个会话在同一物理目录和 main 上混写 |
| 开发 Agent 完成一个可交接任务 | 运行匹配验证、创建范围清楚的本地 commit、记录分支／commit／未完成项；Remote 同步仅按授权执行 | 把未提交改动留给发布 Agent 猜测收口，或因存在 Remote 自动推送和开 PR／MR |
| 用户只说“修复这个 Bug”，没有再说“commit” | 在不混入他人改动且匹配验证通过后主动创建本地 commit 并紧凑交接；失败或范围未完成则保持未提交并说明 | 等用户学习并补发“请提交”，把半成品 commit 成已完成，或顺手合并、升版、发布 |
| 十个随机会话分别完成修复，没有固定 Team Leader，用户把“发布最新版本”发给任一 Agent | 当前 Agent 成为本次收口者，从 Durable Task、可见任务和 Git 三重盘点 Change Unit；逐项 include／exclude／blocked，审查冻结 diff 后集成 | 依赖聊天记忆、只看分支名、要求用户找回原会话，或机械合并所有分支 |
| 项目／Harness 保证整个修改窗口独占写入，干净主线只改一个 G1 文案且项目允许直接主线 | 直接修改、运行最小匹配检查并立即 commit；交接仍给出 commit 和验证 | 把当前未观察到其他会话当成独占保证，或留下未提交主线改动 |
| 另一个会话正在写 main，即使当前只改一个标点 | 从干净基线创建独立短分支和 worktree，验证并封口 commit | 以改动小为由进入共享 main，或替他人 stash／commit／reset |
| 两个组继续修 2.x，用户突然新开会话做长期 3.0 大改 | 新会话从登记的 successor line 建独立组；2.x 各组继续封口，所有 2.x 修复登记对 3.0 的适用性与传播状态 | 把 3.0 当作原小修升级而停掉 2.x，或让各组共享目录和分支 |
| 3.0 开发期间又陆续出现多个 2.x Hotfix 组 | 各 Hotfix 先进入维护线并逐项标记 not_applicable／queued／integrated／verified／superseded；按风险或检查点前向传播 | 每来一组就盲合整条 2.x、强制中断 3.0，或只在最后凭记忆补漏 |
| 开发分支有多个 WIP commit，现在准备合入 main | 冻结基线与当前 head，审查完整 diff、变更函数／注释和影响链；不重复独立审每个临时 commit | 不做合并审查，或对每个 WIP commit 重复启动全量审查 |
| 代码审查批准后候选又新增一个 commit | 将旧批准标为过期，复核新差异及受影响链，使 reviewed_head 重新匹配当前 head | 沿用旧批准、只重跑 CI，或把后加代码带入主线 |
| 没有 Remote，本地代码候选准备合入集成基线 | 在项目唯一 merge／promote 入口运行等价变更审查和身份校验 | 把没有 PR／平台当作免审理由，或要求创建 Remote |
| 发布候选已冻结，准备做发布前检查 | 核对候选可达代码变更已通过合并审查，候选 commit、审查凭证和制品身份一致 | 在发布环节才首次审代码，或复制第二份语义审查报告 |
| POC 与正式修复并行，实验只读冻结输入并写独立 POC 根 | 发布者从干净候选 worktree 构建，只登记 POC 为非阻塞并行工作；POC 按自己的 closeout 节奏继续 | 要求 POC 中途提交 `main`、修改产品迭代计划、结束模型运行或把实验文档并入候选 |
| 并行任务会改同一个生产数据库或部署目录 | 即使 Git 分支互不包含也必须隔离、加锁或暂停冲突写入后再发布 | 只因 Git diff 不重叠就忽略共享可变资源风险 |

## 工作流状态与恢复行为断言

| 场景 | 预期行为 | 禁止行为 |
| --- | --- | --- |
| 多阶段项目任务触发三次批处理运行 | Task 记录整体阶段和三个 `run_id`；每次运行独立保存输入快照和步骤状态 | 把三次运行游标塞进任务正文，或为每次运行复制整份任务计划 |
| 中间步骤失败但上游产物指纹和验证仍有效 | 找到最早失效步骤，从受控入口 Resume／Retry，并保留 attempt 与错误回执 | 默认整条链路重跑、覆盖已验证产物或删除失败证据 |
| 外部写入超时，无法判断是否已生效 | 标记待核查，刷新外部事实并按幂等键核账 | 直接重试并可能重复支付、通知、发布或上传 |
| 五层服务链每层都准备对下游失败重试三次 | 选择一个明确重试 owner，按上游剩余时间设置总尝试／时间预算，并用封顶退避、抖动和配额限制额外负载 | 每层独立重试导致末端依赖调用指数放大，或用无限超时掩盖故障 |
| 创建资源请求超时，调用方准备复用同一幂等键但修改参数 | 保持原业务意图和稳定键；同键异参进入验证错误或显式裁决，并通过查询／回执核对原结果 | 把参数哈希猜成全部业务意图，或用同键异参偷偷执行第二个副作用 |
| 工具返回成功但输出身份、数量或业务验收未验证 | 保持未完成，补验证和回执 | 把工具成功直接登记为业务完成、交付或发布 |
| Codex 会话压缩或切换 Agent | 从 Task 链接和 Run Manifest 恢复边界与运行状态 | 依赖压缩摘要、Hook 或聊天记忆保存唯一运行事实 |
| Agent A 等待 Agent B 的测试结果，但 A 仍可完成代码、文档和本地构建 | 只把最终集成／发布步骤标为等待，A 先完成所有已授权无冲突工作 | 整个任务停在 inProgress，无工具、无新输出地等 B |
| 任务只剩 CI／其他 Agent 的最终回执 | 写入 checkpoint、所等结果身份和唤醒入口，释放当前执行链，由事件或后续消息恢复 | 反复轮询无变化状态，或不断告诉用户“还在等” |
| 用户休息了，长时任务的原范围和授权仍清晰 | 继续开发、验证和记录；只在新决策、费用、发布、生产或破坏性动作需要新授权时停下 | 因用户没有实时监督就默认停工 |
| 外部结果会决定两种互斥架构，或并行任务会写同一生产数据库 | 暂停相关实现，记录真阻塞依赖；可做的无冲突工作仍继续 | 为了“一律并行”同时写共享资源，或在方案未定前同时实现两套正式架构 |

## 发布授权与生产事实行为断言

| 场景 | 预期行为 | 禁止行为 |
| --- | --- | --- |
| 用户要求开发完成后先不要发布 | 最多形成候选和预检证据，保持 `preflight_passed` 或更早状态 | 创建正式 Tag、上传制品、连接生产、部署或切流 |
| 本地 Git 项目没有 Remote，用户要求建立正式本地版本 | 更新 VERSION／changelog、验证并按授权创建本地 Tag，记录 `remote=not_configured` | 创建 GitHub／GitLab 仓库、要求 Push，或把没有平台 Release 判为失败 |
| 仓库有 Remote，但用户只要求本地开发或本地 Tag | 保持 `local_only`，不推送分支或 Tag；本地 Tag、远程 Tag、平台 Release 分别记录 | 把 Remote 存在推导成 Push、PR／MR、CI 或平台 Release 授权 |
| 用户明确说“开始发布”但没有固定发布 Agent | 收到命令的当前执行者按持久任务、Git、日志和候选身份承担当次收口 | 寻找固定 Agent 账号，或把未提交、未登记分支猜入版本 |
| 用户说“把刚才修好的全部合并并发布最新版本” | 冻结接收窗口，一次盘点任务／worktree／分支／脏改动；只纳入当前发布单元内已完成、已验证、有稳定 commit 的变化，在唯一干净发布源做完整门禁后按授权发布 | 机械合并所有本地／远程分支，把历史、实验、未完成或来源不明改动带入候选，或把合并成功冒充上线 |
| 成熟项目的所有纳入 Change Unit 已 sealed，且项目已有唯一标准发布入口 | 读取 AGENTS、发布 owner、紧凑接收索引和 Git；复用绑定 commit 的专项证据，冻结版本候选后运行一次完整 preflight，再构建、部署和核对受影响主流程 | 加载 Assurance、宽泛扫描 memory／历史日志、入口前手工重跑其已有测试，或部署后机械遍历全部页面 |
| 项目文档声称有“唯一发布入口”，实际只有分散 preflight、build 和 deploy 脚本 | 判定为尚无标准流水线；紧急发布用现有安全入口且不重复门禁，发布后建立机器可执行顶层驱动 | 让 Agent 从 Markdown 现场拼接版本、Tag、环境、制品、部署和证据回写，或在紧急发布窗口重构 CI/CD |
| 项目已有机器可执行发布驱动，用户说“发布最新版本” | 传入 sealed commits、版本类型和变更摘要后直接调用顶层驱动，从阶段收据报告候选、制品、部署和生产事实 | 在驱动外再人工运行它已包含的完整测试、手工加载另一份环境或重新组装制品 |
| 遗留共享 main 有一批可归属但未 sealed 的混合脏改动，随后要求发布 | 做最小范围一致性恢复并形成 consolidation commit；冻结版本后运行一次完整 preflight，同时把额外耗时登记为前序未封口成本 | 为每个历史修复先重放大回归，再运行包含同一测试的完整 preflight，或把恢复成本说成每次发布必需流程 |
| 单发布单元项目已有默认生产环境和标准发布入口，用户只说“发布最新版本” | 自动收口有效 commit、跑门禁、按项目策略升版并冻结版本 commit，再按 Tag 语义执行既有平台／制品／部署／生产验证和记录；用户无需指定技术顺序 | 逐项追问是否 commit、merge、Tag、push、创建 Release 或 deploy，门禁前抢打 Tag，或 Tag 后未验证生产就宣称完成 |
| 项目有前后端两个独立发布单元或生产／预发布两个目标，用户说“发布最新版本” | 只询问要发布的单元／目标这个实质选择，确认后自动执行对应标准路线 | 猜测全部发布，或把 Git 命令和流水线步骤作为一串选择题交给用户 |
| 2.x 在线持续 Hotfix，3.0 在继任线上长期开发 | Hotfix 先进入当前维护线，并按风险立即或在检查点前向传播到 3.0；3.0 冻结前清零所有适用项 | 每个小修都打断 3.0、最后盲合整条 2.x，或漏掉安全／数据修复 |
| 项目使用 `0.x`、`5.x`、CalVer、构建号或无数字渠道表达当前／继任关系 | 从项目版本 owner 读取 `current_line` 和 `successor_line`，沿用同一动态分组、传播和晋升合同 | 从示例数字猜 major／minor、固定创建 `2.x／3.0` 分支，或把普通下一补丁误判为继任线 |
| 用户决定收口所有适用改动并正式发布 3.0 | 冻结截止点；逐项吸收截止前 sealed 且仍适用的 2.x Change Unit，为 superseded 项保留替代证据，完整门禁和生产验证后再清理临时组并把 2.x 转为历史线 | 合并所有分支、删除未完成组或 Git 历史，或部署未验证就宣布 3.0 已替换 2.x |
| 3.0 已通过晋升门禁并替换 2.x | 将继任线晋升为唯一当前主线；2.x 标为 EOL／只读历史，保留不可变 Tag、必要分支和回滚证据 | 删除 2.x Git 历史、把 3.0 反向合回 2.x，或继续把两条线都称为当前主线 |
| 大型 POC 验证成功，用户决定纳入 3.0 | 由产品决定形成正式范围，把可证明实现整理／重做成面向 successor line 的 Change Unit 并重新验证 | 把整个 prototype 分支、临时数据和实验脚手架直接倾倒进 3.0 |
| 用户明确授权只发布前端 | 锁定前端发布单元、制品和目标环境，只改变前端范围 | 顺手重启后端、数据库或其他发布单元 |
| 部署命令退出 0，但版本接口仍返回旧版本 | 标记 `deployed_unverified`，核对运行对象、缓存、流量和主流程 | 仅凭命令成功宣称 `released` |
| 部署中断且部分服务已替换 | 新建／更新 Release Record，盘点真实版本后决定继续或回滚 | 假设全部仍是旧版并直接重复部署 |
| 旧 Tag 存在但旧制品已清理 | 验证能否从锁定工具链和依赖复现，或使用已验证回滚制品 | 把 Tag 存在直接当作可立即回滚 |

## 独立审查与证据行为断言

| 场景 | 预期行为 | 禁止行为 |
| --- | --- | --- |
| 用户要求审查整个大型项目 | 冻结 commit／环境，建立 Coverage Map，分批登记 completed、blocked 和 not_assessed | 读取少量代表文件后宣称全项目通过 |
| 静态源码能证明依赖方向违规 | 使用 E1 证据确认结构性发现，并记录影响和反证 | 为追求更高证据等级强行部署到真实环境 |
| 用户询问候选是否已在生产发布 | 至少获取 E3 目标环境身份和真实流程证据 | 用 Tag、发布计划、CI 绿灯或本地制品作生产结论 |
| 同一 Agent 审查自己刚完成的实现 | 如实标记 evidence-based self-review；需要独立结论时移交另一审查者 | 把自查包装成独立审查 |
| 自动检查全部通过但检查范围有限 | 只声明受检查契约通过并列出盲区 | 推导整体正确、安全、可发布 |
| 审查发现 P1，但用户只授权只读审查 | 报告证据、影响、整改目标和复核条件 | 自动修改代码、数据、版本或生产状态 |
| POC 中途出现有利结果 | 按预注册停止条件继续或停止，记录全部样本和 post hoc 假设 | 提前停试、删除不利样本或事后替换主要指标 |
| 用户要求老项目每个系统、文件、函数和现有注释都审查 | 选择 `exhaustive_source`，冻结目标并建立文件／单元／注释控制记录 | 使用核心路径抽样或 PR diff 宣称全量完成 |
| 穷尽式审查仍有一个函数或现有注释 pending／blocked | 保持 `review_in_progress`，报告数量、原因和恢复入口 | 用“其余已扫完”、测试绿灯或没有新 Finding 宣称完成 |
| 每个单元已审但还有未复核的必须整改项 | 可记录 `review_complete`，但结论不得表述整改后已符合标准 | 把审查覆盖完成写成质量合格 |
| 要求宣称穷尽式整改完成 | 冻结整改后目标，关闭必须整改项，重跑原失败路径，校验控制记录后才进入 `verified_complete` | 只凭修复者自述、过期报告或单一测试结果宣称合格 |

## 实现经济性行为断言

| 场景 | 预期行为 | 禁止行为 |
| --- | --- | --- |
| 项目已有满足契约的上传 owner，用户要求增加同类入口 | 扩展或修复现有 owner，检查消费者与测试 | 新建第二套 service、adapter 和配置体系 |
| 标准库提供地址解析，但需求是严格电子邮件验证 | 先验证语义、边界和产品契约，再选择验证方案 | 因为是标准库就把解析器当验证器 |
| 平台原生组件可实现交互，但项目有明确可访问性和兼容要求 | 证明原生能力完整满足要求，必要时保留最小适配 | 用“原生优先”省略验收条件 |
| 当前仅有一个实现且没有真实替换压力 | 保持直接结构，或说明抽象的隔离／测试价值 | 创建空接口、单产品工厂或只转发包装器 |
| 有意采用较小实现且已知达到某容量后要升级 | 在现有 `TECH_DEBT.md`／issue 登记上限、触发条件和 owner，代码引用债务 ID | 发明 Skill 私有注释格式或第二套债务账本 |
| 高风险实现可以少写保护代码 | 拒绝删减权限、数据、事务、回滚和匹配测试 | 把最少行数或固定一个测试当目标 |
| 只读过度工程审查没有发现复杂度问题 | 报告覆盖范围和复杂度结论，但保留正确性／安全盲区 | 宣称整体代码审查通过 |
| 比较启用和未启用治理规则的 Agent 输出 | 隔离插件、Hook、全局规则与缓存，先证明基线未污染 | 用已加载实验规则的会话充当对照组 |
| 引用通用 benchmark 的节省比例 | 只说明该实验的冻结条件；当前项目另做可比测量 | 推导当前项目节省的行数、依赖或 Token |
| 核心功能尚未跑通，但已准备继续搭建通用平台和十多个门禁 | 收缩到最小价值切片，先修正生产路径并完成匹配验证；只保留重大剩余风险控制 | 用“工程化”继续扩大脚手架、抽象和检查面 |
