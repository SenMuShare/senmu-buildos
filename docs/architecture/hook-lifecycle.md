# Hooks 生命周期设计

## 目标

Hooks 解决长会话、恢复、上下文压缩和子 Agent 启动后短治理边界丢失的问题，并以低噪声方式收集可复用的改进候选。它们不承载专业知识库，不自动读取整个项目，也不替代确定性门禁或人工治理判断。

可以把 Hook 理解成“在特定时刻自动塞进会话的一张短便签”。它与 Skill 的分工是：

```text
Hook 便签：无论当前岗位是什么，都不能忘的少量底线
Skill 手册：根据当前正在做的工作，按需拿取的一本专业指南
```

因此，写代码时不应由 Hook 注入产品管理和项目治理全文；当前请求匹配 `senmu-build-engineering` 时，只加载软件工程 Skill。做需求管理时则加载 `senmu-build-product`。Hook 只提醒“先看真实项目和项目／框架／平台现有能力、不要越权、复用仍有效证据、只取得缺失或变化的规则／源码／输出范围、优先修正问题生产源、门禁只覆盖重大剩余风险、留下验证和真实状态”。

## SessionStart

在宿主支持的 startup、resume、clear、compact 场景注入固定短通用底线：项目事实优先、范围和风险校准、现有能力优先、有效证据复用、有界取得规则／源码／输出、源头治理、必要高风险门禁、可恢复执行、验证与真实完成状态。

插件使用 Codex 原生 `PLUGIN_ROOT` 定位脚本，并通过 `additionalContextLimit` 与脚本内字符预算双重限制输出。Codex 已自动发现 `AGENTS.md`，因此 Hook 不读取或复制其正文。

## SubagentStart

向子 Agent 注入更短的委派边界：不得扩大任务、不得越过项目权威和授权、优先复用现有能力与证据、有界取得缺失信息、返回证据与未完成项、不得绕过高风险门禁。

## UserPromptSubmit

该 Hook 只执行本机、确定性的反馈信号检测与候选落盘。无论是否命中，都向 Harness 返回空对象，不使用 `additionalContext` 向当前模型注入收集结果或处置提示；用户原始请求仍是本轮唯一新增语义输入。

只对明确的纠正、返工、回退或流程不合理信号做确定性匹配。结构化 prompt 先提取用户本轮真正写下的请求与批注，排除引用会话、选中的 Assistant 文本、附件包装和宿主生成建议；命中后也只保存该用户片段，而不是整段包装内容。候选经过去重、脱敏并保留来源指针后写入用户本机反馈箱。普通请求、讨论和偏好不会入箱。Hook 不调用模型、不联网、不修改项目文件，也不把候选直接升级为经验或规则。

## Agent 后台提交

Agent 自己发现高信号治理缺口时，在本地 CLI 可用的前提下使用 `feedback-cli.js submit --quiet` 静默写入候选。正常面向用户的答复不显示内部标记、候选 ID 或收集回执；CLI 不可用时跳过该次后台收集，不回退到可见标记。只有用户显式要求记录或查询反馈时，才返回相应的简短确认或结果。

## 失败策略

- Hook 输出失败不得阻塞普通会话启动。
- Hook 失败时应尽量提供可见状态，不静默伪装为已注入。
- 安全、生产数据、权限、支付、发布完整性和破坏性操作不得只依赖 Hook；项目脚本和 validator 才是可执行门禁。
- 反馈 Hook 或后台 CLI 失败时不得阻塞正常对话；失败不等于候选已保存，集中审议时以本地反馈箱为准。
- 安装或更新插件后，Codex 仍要求用户 review and trust 当前 Hook 定义；源码测试通过不代表本机插件运行时已经启用。

## 当前实现限制

- 不保存完整会话、工具日志或 transcript 正文，只保存不超过 800 字符且经脱敏的触发片段和来源指针。
- 不自动统计、聚类、复盘、生成规则或修改 Skill。
- 不维护隐藏的全局项目事实。
- 不根据目录猜测并自动加载某个专业 Skill。
- 不注入 `SKILL.md` 全文。
- 不维护已读文件、内容哈希或全文缓存；上下文是否保留和何时压缩仍由 Harness 决定。
- 动态项目摘要留待后续独立评审，不进入当前实现。

## 当前专业 Skill 如何选择

当前实现不让 Hook 猜岗位。Codex 根据用户当前请求和七个 Skill 的 description 选择主 Skill：

```text
项目初始化／目录／整体治理  → project
需求／PRD／路线图／迭代     → product
Harness／Agent／物料／流程   → workflow
架构／编码／测试／重构       → engineering
Git／版本／部署／发布        → delivery
POC／独立审查／债务盘点      → assurance
复盘／经验沉淀／经验库维护    → learning
```

一个任务只先确定一个主 Skill；只有任务真的跨越职责边界时才组合第二个。反馈 Hook 和后台 CLI 只收集候选，不把当前任务切换到 Learning。只有用户明确要求集中处理反馈、复盘或治理经验时，才加载 Learning 完成查重、证据核对和晋级判断。

## 后续可讨论的“记住当前岗位”

如果真实使用证明长任务在 compact 后会忘记当前专业领域，可以再选择一种显式状态方案：

1. 项目声明的 Durable Task State Owner 登记当前主 Skill、边界和恢复入口；只有真实测试证明有必要时，SessionStart 才读取并注入极短摘要。事实可见、可审计，但项目需要维护状态。
2. 用户或 Agent 显式切换当前模式，例如 engineering／product；实现简单，但可能忘记切回。
3. 每次用户消息都由 Hook 猜测领域；自动化最高，但容易误判、增加延迟和上下文噪声，当前不推荐。

在没有真实漂移证据前，保持“短通用 Hook + 按请求选择 Skill”是当前成本最低、最不容易误注入的方案。

当前已经定义任务登记与执行记录，但 Hook 仍不自动读取、总结或改写任务文件。先用项目入口、任务记录和工作日志验证连续性，再决定是否启用短任务恢复摘要。
