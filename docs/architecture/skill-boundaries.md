# Skill 边界与协作关系

## `senmu-build-project`

Project Management，负责单项放置建议、空白项目规划／初始化、成熟项目结构审视／演进，以及项目形态、G0-G4、权威项目根、目录、文档、状态源、项目地图、legacy 边界、项目内移交和跨生命周期协调。建议和规划默认零写入；迁移需要独立实施授权。它的审视结果是治理实例的 owner／目录／状态映射、缺口和演进边界，不是独立证据裁决，也不是其他专业 Skill 的父级。

## `senmu-build-product`

负责需求从收集到验收的产品事实，包括需求池、PRD、路线图和迭代承诺，并负责这些产品产物之间的普通一致性自查。它不决定技术实现，也不宣称代码或部署已经完成。

## `senmu-build-workflow`

负责工作流、Agent／Harness 契约、数据和物料角色、输入输出、过程状态、附件与交付物。它不替代软件架构规范或正式发布治理。

## `senmu-build-engineering`

负责技术路线、架构、实现、测试、重构、依赖、语言与框架专项规则，并负责需求、设计、任务、实现和测试之间的普通技术一致性自查。它不负责版本放行、部署、发布回执或独立治理审查结论。

## `senmu-build-delivery`

负责 Git、仓库与发布单元、版本、制品、部署、上线、回滚和发布证据。它可以把已经发生的交付工作追加到项目统一 Work Log，但不拥有第二份协作日志，也不重写需求或工程 owner 的规则。

## `senmu-build-assurance`

负责独立、证据化的实验、冻结对象审查、债务盘点和争议性因果核验，输出证据等级、覆盖、发现和结论；普通一致性自查仍由 Product／Engineering 自己完成，只有明确要求独立结论、跨域争议或 G3-G4 正式审查时才由 Assurance 主责。治理实例的 owner／目录／状态映射与演进仍由 `senmu-build-project` 负责。默认只读；除非用户另行授权，不应用审查中发现的修复，也不直接拥有经验台账或通用规则晋级。

## `senmu-build-learning`

负责组织学习与持续改进：集中审议本机反馈候选，执行复盘、经验捕获、查重、晋级、检索、替代、退役，以及跨项目候选向 Senmu BuildOS 源码项目的反哺。网页、PDF、书、仓库和第三方 Skill 等外部工程知识也由 Learning 作为不可信教材建立临时蒸馏批次，经合并、替代、新增、项目特有、待证据或拒绝六类裁决后，只把稳定规则写回专业 owner。Hook 收集到的单条反馈只是待审信号，不是需求、事实或规则；Learning 拥有 Lessons Learned Register 的语义、schema 和生命周期，但稳定规则仍写回 Product、Workflow、Engineering、Delivery 等源头 owner。根因需要独立裁决时由 Assurance 提供证据；项目目录和跨生命周期任务状态仍由 Project 负责。

当治理对象是 Senmu BuildOS 自身时，Learning 面向完整 Git 仓库执行整仓影响分析。某次改进最终可以只修改一个 Skill 或一份文档，但插件清单、全部 Skills、Hooks、文档、脚本、测试、迁移和版本共同构成一个产品与发布单元。

## `owner` 的三种语义

| 类型 | 拥有什么 | 不得冒充 |
| --- | --- | --- |
| 专业事实 owner | Product 拥有需求／PRD／产品验收，Engineering 拥有技术设计、实现与工程测试，Workflow 拥有运行事实，Delivery 拥有版本／发布事实，Assurance 拥有独立审查结论 | 一个 Skill 接管全部生命周期正文 |
| 语义／运行 owner | 同一业务规则、数据、状态、副作用或业务不变量的唯一权威实现 | PRD、技术设计、代码和测试采用同一物理 owner |
| Durable Task State Owner | 跨阶段进度、决定摘要、证据链接、未完成项与下一步 | 复制或改写各专业事实正文 |

跨产物一致性通过稳定需求 ID、验收合同、接口和证据链接建立，不通过合并 owner 建立。不得把“让 PRD、技术设计、实现和测试对齐同一条已批准需求”压缩成“把它们统一到同一个 owner”；讨论稿、旧代码和旧测试仍只作为候选证据，不能因此获得产品事实权威。

## 组合原则

- 一个任务先确定主 Skill；只有跨越真实职责边界时才组合其他 Skill。
- 默认只加载能直接产出当前结果的一个主 Skill。“与某专业相关”、“最终可能提交”、“对用户可见”或“代码里存在步骤”都不构成组合理由。
- 支持 Skill 只在当前回合需要它的独立决定或产物时加载：业务行为／验收变化才交 Product，流程契约／可恢复运行状态变化才交 Workflow，Git／版本／发布决定成为当前结果才交 Delivery。交接是职责转换，不是每次修改的固定流水线。
- G1 的契约保持型局部变更由 Engineering 单独主责；判断依据是产品、运行和交付契约是否保持，而不是枚举按钮、颜色、文案等表面对象。项目本地规则可直接指导执行时，不为重述通用原则继续加载 BuildOS Skill。安全、隐私、权限、支付／计费、生产数据、破坏性操作和正式发布仍按真实边界升级。
- 专业 Skill 之间传递项目事实和证据，不复制对方的规范正文。
- 只有真正的项目初始化、治理修复或跨生命周期任务才由 `senmu-build-project` 校准范围；单领域任务直接加载对应专业 Skill。
- 项目已经有稳定本地规则时，日常执行优先使用项目本地入口，不强制调用 Senmu BuildOS。
- 需要分步骤、分阶段、跨 Agent 或跨会话的工作共用项目声明的 Durable Task State Owner；`governance/tasks/TASK-<NNNN>-<slug>.md` 只是 standard/release 新项目默认实现，core 可沿用 README、Issue 或外部任务系统。主 Skill 负责推进当前结果，支持 Skill 只写本域事实和证据。

## 选择与交接机制

Senmu BuildOS 不设置第八个“总导演”Skill，也不要求 Agent 先读取总索引再决定路由。Codex 先根据七个平级 Skill 的 `description` 和用户期望结果选择主 Skill；用户也可以显式指定。`SKILL.md` 正文只在对应 Skill 已被选择后，按需指向本域 reference 和跨域交接对象。

Handoff 不是固定流水线，也不是把整个上下文交给下一个 Skill。发生真实职责切换时，当前主 Skill 只传递最小任务包：任务／需求／run／finding／release 标识、当前阶段、范围与非目标、权威入口、已确认事实与证据、未决问题、下一项预期结果，以及仍然有效的授权边界。接收方成为下一结果的主责；原 Skill 只继续拥有自己的专业事实。

只有当项目治理实例、跨阶段任务状态或多领域责任边界本身就是当前结果时，`senmu-build-project` 才承担协调。单领域任务不需要经过 Project 中转。若以后真实行为测试证明声明与 Handoff 无法稳定支撑某个高频、确定性流程，再评估独立 Workflow；在此之前不建立编排 Skill、根级流程目录或固定执行链。

## 证据取得与复用

渐进披露不只约束“第一次读多少”，也约束后续是否重复取得同一证据。Agent 第一次需要某个事实时读取足以支持当前判断的最小范围；已经取得且来源身份、内容、适用范围与当前授权仍有效时，直接复用，不再次全文读取同一 Skill、reference、项目文档、代码文件或命令输出。

- 只缺一个细节时，优先搜索、定位行范围或读取局部；源码或规则刚刚变化时，优先看 diff 与受影响周边。只有全局语义、结构或验证确实需要时才重新取得全文。
- 最小充分证据同时约束输出范围：先取目录、命中位置、差异摘要、失败项或有界状态，再按决定需要展开。不得把多份长 reference、源码、diff、日志或检查结果拼成一次可能截断的输出；确需全文时按决策顺序分别取得。
- 被截断的结果只能证明当前可见部分，不能支持全局结论。后续只补取缺失区间或未覆盖对象，不从头重放已经取得的内容；工具允许过滤、分页、范围或紧凑模式时优先使用。
- 用户新增消息会触发当前请求的重新路由，但消息本身不证明旧证据已失效。宿主要求本轮重新读取已选择的 `SKILL.md` 时服从宿主；已经取得且仍有效的 project/reference 证据仍按最小范围复用。
- 上下文压缩、resume、clear、Agent／Harness 交接、来源版本变化、运行状态变化或问题范围扩大后，原细节不再可靠时，重新取得当前判断需要的最小证据；不假装能够读取另一 Agent 的隐藏上下文。
- 不建立 `read_files.json`、全文缓存、Skill 私有已读台账或 Hook 注入的动态摘要。会话历史与压缩由 Harness 负责；跨会话必须保留的任务边界和外部副作用继续写入项目声明的 Durable Task State 或运行 owner，而不是保存工具 transcript。

这项纪律不限制真实跨域任务读取多份必要 reference，也不把“一个 Skill + 一个 reference”机械变成 Hard Gate。目标是消除重复获取，不是省略会改变判断、权限、状态、失败处置或完成声明的证据。

## 项目本地产物

任务状态与专业产物的统一落点见 [项目产物与目录责任地图](project-artifact-map.md)。任何 Skill 新增项目本地文件前先按该地图寻找 owner；已有项目采用不同但明确的权威位置时，遵守项目现状并更新项目地图，不平行复制。

## Skill 粒度判断

岗位可以帮助理解职责，但不按公司职位表机械创建 Skill。只有同时满足以下条件才继续拆分：

1. 用户任务能够清楚地区分并稳定触发。
2. 已经存在足够独立的方法论、输入输出和验证方式。
3. 单独加载能明显减少无关上下文。
4. 拆分后不需要在多个 Skill 重复同一套核心规则。

当前 Software Engineering 虽然包含架构、开发、测试和重构，但入口只负责路由，详细内容按 reference 渐进加载；测试已有独立的专业 reference 和项目模板，但仍服务于工程实现、产品验收与交付证据之间的共同链路，暂时拆出独立 Testing Skill 会增加路由和 owner 冲突。等测试形成稳定的独立任务语料、工具入口和跨项目资产后，再评估拆为 Quality Engineering 或 Software Testing。

“成熟项目先确认现有语义 owner、不得泄漏默认目录”是单领域 Skill 直接调用时仍必须成立的写入安全边界，因此允许在七个 `SKILL.md` 短入口中显式重复；详细目录规则和示例仍只由 Project reference 唯一维护。

## Skill 文本设计与瘦身

- `description` 只负责让 Harness 判断何时加载；`SKILL.md` 保存目标、路由、始终有效的边界和交接契约；条件式步骤、模板和大段方法进入命中时才读取的 reference。
- 需要某条 reference 才能正确执行的规则，应在实际决策或动作附近明确要求读取；只在入口远处列一次文件名，不足以保证使用。
- 一个规则只保留一个正文 owner。把内容从入口移入 reference 后，要删除入口中的同义过程描述；入口只保留在 reference 尚未读取前也必须生效的停止条件和安全边界。
- Skill 负责结果条件，脚本或专业 Skill 负责自己拥有的执行机制。调用方说明“必须满足什么”和无法确认时的安全方向，不复制被调用方的完整命令与状态机。
- 瘦身以决策覆盖、路由准确、真实行为和验证证据为准，不以字节数或文件数为目标。测试中固定的文字只有在承载真实契约或已验证事故时保留；偶然措辞应改为语义不变量。
- 信息密度优先于最低 Token：保留会改变判断、权限、状态、失败处置或完成声明的非显然信息；只删除通用常识、同义重复、未承担决策的长例子和已有可靠 owner 的副本。压缩前后按行为不变量核账，不能用格式校验或字数下降证明效果更好。
- 只有当重复且确定性的计算、校验、导出或文件处理能显著提高可靠性或效率，且现有工具与短指令不足以稳定完成时，才增加 `scripts/`。脚本要评估灵活性损失、维护和输出上下文成本；其结果不得代替语义、授权或真实环境证据。
- 脚本按用户工作流路由：入口只暴露高频、通用且会直接帮助当前结果的执行入口；专项 validator 由命中的 reference 路由；生命周期底层实现和 helper 可由上层命令间接拥有，不为了“可发现”全部写入 `SKILL.md`。Agent 通常执行入口而不加载实现源码，只有调试或修改时才读取实现。
- 包校验同时约束字符数和保守的混合中英文上下文单位，并为“入口 + 最大单份 reference”及“入口 + 两份最大 reference”设置路由包上限。静态组合预算不授权运行时把多份长文件拼入一次工具输出；预算只是防止无意膨胀的上限，不是缩减目标，不是假装精确的 tokenizer，也不授权删除有效信息；超限时先判断唯一 owner、语义覆盖和渐进路由。
- 使用 `tests/behavior/skill-entry-invariants.md` 反向核对入口压缩前后的有效决策；这份表不是第二份规则 owner。
