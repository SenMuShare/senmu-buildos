# 代码管理与合并规范

本规范面向工程项目的代码治理，规定项目分支、代码合并、PR／MR、合并清单、多 AI 协作和发布前代码检查规则。

## 本页导航

1. 分支管理；2. 标准流程与 Bug/Hotfix、需求一致性、权威工作区门禁、继任版本线；3. 合并清单；4. 多 AI 协作；5. 发布前代码检查。

## 1. 分支管理

本地 Git 是分支、提交、合并、Tag 和历史恢复的基础；Remote、PR／MR、CI 与 GitHub／GitLab 等托管平台均为可选执行面。先读取仓库现有规则并检查 Remote 是否存在，不因缺少 Remote 判定项目不完整，也不为已有项目强行引入另一套分支模型。项目尚未定义时，可以选择以下角色：

```text
main       默认集成／正式发布基线
develop    可选的独立集成基线
feature/*  人工开发分支
codex/*    AI 开发分支
```

如果项目有多个产品或子系统，分支必须带 scope：

```text
codex/website/<topic>
codex/app/<topic>
codex/admin/<topic>
codex/platform/<topic>
codex/backend/<topic>
codex/frontend/<topic>
codex/repo/<topic>
```

规则：

- `main` 可以是日常持续集成主线，但共享项目默认不直接在其工作区修改或绕过门禁推送；使用短分支和项目已有检查进入主线。
- 小型、个人或高频交付项目优先 `main + 短分支`；只有真实存在独立集成、稳定候选或多版本维护需求时才增加 `develop`、`release/*` 或 `next/*`。
- 新需求、修复、文档治理都从集成基线拉短分支。
- 分支名要表达影响范围。
- 一个分支只做一个主题。相互独立且可分别验证、回退的变更应拆成不同短分支，分支内的 commit 也保持隔离且完整；某一项等待评审、测试或准备时，不得拖住其他无依赖变更。只有共同契约、原子迁移或不可分验收确实要求同一候选时才绑定。
- 不同产品、官网、后台、部署、文档治理不要随意混改。
- 发布前必须合入正式发布基线。
- 没有远程仓库时，以本地分支、commit、tag、版本文件和 changelog 保持完整可追溯；不得擅自创建 Remote 或要求发布到托管平台。

开始修改前必须检查：

```bash
git branch --show-current
git status --short
git log --oneline --decorate -10
```

## 2. 标准执行流程

以下步骤是双基线模型示例；项目使用单主线、trunk-based、release branch 或其他成熟模型时沿用现状并记录等价门禁：

1. 从项目登记的集成基线开始，例如 `develop`。
2. 创建短生命周期分支，例如 `codex/admin/entity-list`。
3. 在分支中完成需求、技术文档、代码和测试。
4. 按项目 AI 入口、代码质量规范、架构契约和实际语言／框架规则完成自查与统一质量命令。
5. 合并前跑合并清单。
6. 合回 `develop` 做集成验证。
7. 发布前再由 `develop` 合入 `main`。
8. 开发执行者完成验证和 commit；存在 Remote 且获得同步授权时再推送分支并创建或更新 PR／MR。
9. 从登记的发布基线锁定候选；只有取得发布授权后才创建正式 Tag、上传、部署或切流。

建议命令：

```bash
git switch develop
git pull --ff-only
git switch -c codex/<scope>/<topic>

# 完成后
git switch develop
git merge --ff-only codex/<scope>/<topic>
git switch main
git merge --ff-only develop
```

如果没有 Remote，跳过 `git pull --ff-only`，并记录当前以本地分支和 Tag 为准；Remote 存在也不等于已授权推送。`pull --ff-only` 是安全更新方式，不是唯一合并策略；项目应在 squash、rebase 或 merge commit 中声明一致策略。命令失败时不强行覆盖，先检查分叉和冲突。

### 教练式现场判定

用户询问分支、worktree、并行协作或清理策略时，先从真实 Git 和项目入口确认权威仓库、目标分支、当前写入者、已合并关系、未提交改动、非 Git 状态资产、发布入口和 Remote 现状。复杂场景的最小建议包含：

1. 已确认现场事实和未确认盲区；
2. 当前对象是普通短分支、Hotfix、POC、继任版本线、发布入口还是历史残留；
3. 建议合并、排队、保留、迁移或清理的理由、风险和完成条件；
4. 当前授权只允许建议、只读检查还是已覆盖实施。

分类是从 Git 和项目事实即时推导的建议，不要为它另建一套必须持续同步的状态台账。可使用 `scripts/inspect_git_workspace.py` 生成只读候选分类，但 `merged_cleanup_candidate` 只表示 Git 条件可能成立，不代表已获删除授权，也不能代替对被忽略资产、运行进程和业务 owner 的语义核对。

### 短分支与 worktree 生命周期

- 普通短分支完成验证和提交后交给集成目标；合并不等于收口，还要在目标分支运行匹配验证并确认没有独有事实。
- 每个临时分支和 worktree 在创建时明确用途、基线、集成目标、保留条件和清理条件；完成时必须得到“已安全清理”或“有理由保留并登记退出条件”之一，不能成为无人负责的第三套当前代码或长期残留执行面。
- 临时 worktree 已合并、目标验证通过、工作树干净，且没有独有的未跟踪／忽略资产、运行环境、状态 owner 或交付物后，才成为清理候选。
- 经授权清理时，先停止依赖该目录的进程并以明确路径移除 worktree，再从权威仓库用非强制方式删除已合并本地短分支；只在 Remote 存在且授权覆盖远程同步时删除远程分支。
- `git branch -d` 拒绝时先重新判定合并目标、squash／rebase 关系和独有 commit；不得把 `-D`、`git worktree remove --force` 或直接删目录作为默认清理方式。
- `git worktree prune` 只清理已经不存在的工作树元数据，不代替活动目录的安全收口。
- `main`、受保护集成线、运行中 POC、未晋升的继任线和有独有事实的分支不能因数量多而删除。历史由 commit、Tag、制品和发布记录保留，不长期依赖大量临时目录作回滚手段。

## 2.1 Bug/Hotfix 分支门禁

用户临时要求修 Bug、线上故障、回归问题或 Hotfix 时，也必须识别分支和发布边界，不能因为范围小就直接在当前工作区改完并宣称上线。修复授权不自动包含发布授权。

开始修复前必须确认：

- 当前分支、工作区和最近提交。
- 受影响发布单元、当前 `VERSION` 和最新正式 tag。
- 当前线上版本或发布基线，以及可用回滚点。
- 是否存在未发布改动；如有，先判断是否属于本次修复范围。
- 本次修复应进入哪个候选版本；是否发布由用户另行授权，不发布时写明原因和后续收口点。

修复验证通过后，进入合并或发布前必须再次检查：

- Bug 修复提交是否只包含本次问题相关改动。
- 与影响范围匹配的测试、构建或真实流程验证是否完成。
- 如果修复改变了业务状态流、用户文案、接口契约、存储保留策略、第三方服务调用或失败重试逻辑，需求文档和技术设计是否已同步；不能以“只是修 Bug”为理由跳过文档收口。
- 版本号、changelog、工作日志和发布计划是否已完成或明确不适用。
- 本地分支、远程分支、tag 和制品的同步责任是否明确。

## 2.2 需求-技术-代码一致性门禁

凡是新增功能、改变业务逻辑、改变状态流转、改变用户可见文案、改变接口字段、改变数据保留/清理策略、接入或调整第三方服务，必须先确认需求文档和技术设计的对应章节。

执行规则：

- 改代码前先定位 PRD 和技术设计中的对应条目；如果没有条目，先补文档或在本次分支内同步补齐。
- 需求文档负责回答“用户看到什么、规则是什么、状态如何流转、边界和验收标准是什么”。
- 技术设计／架构契约负责回答“模块职责、依赖方向、数据所有权、接口、数据模型、异步任务、存储清理、权限、安全、第三方服务和失败处理如何实现”。
- 代码、测试和验收必须能回指到需求文档与技术设计；如果实现与旧文档不一致，应在同一分支更新文档并写清楚取舍。
- 同一分支把代码、PRD 和测试改成一致，只证明候选内部一致，不能证明产品授权来源成立。凡改变用户动作、可见状态、生效／持久化时机、撤销／恢复或验收结果，合并时还须核对先前已批准行为、本次获确认的变化和候选实际行为；实现分支自己的文档与测试改动不能作为唯一授权依据。
- 只有纯格式化、错别字、注释修正、内部重命名且不改变行为的改动，可以说明“不涉及需求/技术文档同步”。

## 2.3 权威工作目录与 worktree 收口门禁

分支是同一 Git 仓库中的逻辑历史，worktree 是某个分支的临时物理检出。用户说“拉分支”时，
默认含义不是新建第二个长期项目目录；确需 worktree 隔离开发时，必须把它声明为临时执行面，
不能静默升级为新的日常入口、台账拥有者、交付目录或发布来源。

执行面按以下顺序选择：

- 默认一个权威目录、多个短分支、一次一个写入者；前一任务完成验证、commit 和交接后再切换分支。
- 多个 Agent 可以同时分析，但共用目录时只能有一个写入者，其他执行者不得切分支、暂存或修改文件。
- 多个执行者必须同时写不同分支，或必须同时运行、比较不同版本时，才评估独立 worktree；未获明确授权则改为串行。
- 创建前评估源码规模、依赖安装、构建缓存、submodule、数据库、模型、媒体和其他非 Git 资产的时间、磁盘与收口成本；收益不足时继续串行。

文字声明不能替代物理身份。项目使用 Git worktree 时，应通过项目入口和 Git 身份共同区分：

- `current_checkout_root`：当前源码检出目录；
- `repository_primary_worktree`：由 `git rev-parse --git-common-dir` 推导的仓库主工作树；
- `project_authority_root`：负责人登记的项目总边界，可包含多个仓库、发布单元和独立 POC 根；
- `release_source_root`：本次候选唯一构建／交付来源；
- `is_external_worktree`：二者是否不同。

不得只用“从当前源码向上寻找 Makefile、package.json 或项目标记”的方式识别权威根；该算法会让每个
worktree 都自认权威。涉及业务台账、POC 事实、Git 忽略运行资产、交付或发布的项目，应提供非零退出的
项目级 `workspace-authority-check`，并用反例测试证明从外部 worktree 调用会失败。新增项目门禁时可以从
从 `senmu-build-project` 的 `scripts/workspace_authority.py` 复制最小实现，再按项目登记需要扫描的状态目录；不得让 Skill
外部脚本成为项目日常运行依赖。

在任何 worktree 中首次写入状态型 POC 资产前，还必须解析项目登记的 `project_authority_root`、唯一
`POC_ROOT`、`tracking_mode` 和可能并行的 `release_source_roots`。源码 diff 可以留在独立 POC 分支／worktree；
实验账本、输入、模型、缓存、输出和报告只能写入登记的 POC owner，不得因“权威根”回写产品 `main`、
`ITERATION_PLAN.md`、正式业务台账或发布目录。解析失败、路径越界或发现第二个活动 POC 根时必须非零退出，
不能回退到当前目录、Codex 管理目录、clone、`/tmp` 或个人缓存。临时 scratch 在 POC closeout 前迁入、
按策略删除或登记保留理由；它不构成无关产品发布的阻塞项。

G3-G4 的集成、迁移、主线替换、正式交付和发布任务必须在开工时登记：

```markdown
### 工作区收口契约
- 项目权威根：负责人日常进入和查找项目成果的总边界
- Git 仓库根：本次分支实际所属仓库
- 开发分支：本次隔离修改所在分支
- 集成目标：最终必须接收修改的分支和 commit
- 候选 commit：本次发布冻结的精确提交
- 本次纳入：明确进入候选的分支／提交／需求
- 并行排除：继续运行但不进入候选的 POC、分支和 worktree
- 共享资源：数据库、配置、端口、对象存储、部署目录及锁；没有则写无
- 正式交付入口：发布脚本、制品或交付文件必须读取的唯一位置
- 临时 worktree：路径、用途、保留条件和清理条件；没有则写无
```

完成前执行以下 Hard Gate：

1. 在 `release_source_root` 检查 `git status --short`、当前分支、候选 HEAD 和最近 tag，并用 `git worktree list` 盘点并行执行面；盘点不等于要求全部干净。
2. 只把“本次纳入”的分支／提交按项目规则合入集成目标；不得因为其他分支已经完成、属于同一仓库或同一发布单元就自动扩大版本范围。
3. Git 忽略或未跟踪且属于本次正式运行的配置、数据库、台账、媒体、回执和制品，必须通过项目正式导入、迁移、同步或原子覆盖入口进入发布源；无关 POC 资产不得迁入候选。
4. 只从干净且锁定候选 commit 的 `release_source_root` 运行完整质量、构建、台账、同步、交付和真实发布前检查；其他 worktree 的局部通过不能替代该结果，其无关脏状态也不能否定该结果。
5. 从权威交付入口核对用户会实际打开或上传的文件、版本、SHA、数据库状态和远端回执，防止“代码是新版、交付物仍是旧版”。
6. 在工作日志中记录权威根、集成 commit、交付路径、回滚 tag、仍保留的 worktree 及原因。
7. 本次纳入的临时 worktree 已合并且没有独有未提交事实后，先保存必要 patch/快照，再按明确路径移除；仍在运行的排除项保持非发布入口并给出后续收口责任，不为本次发布强制提交、结束或删除。
8. 枚举 `git worktree list --porcelain` 后按候选可达性和资源影响分类。只有候选代码／正式资产存在唯一副本、
   另一个目录仍被称为发布入口，或并行任务会修改本次共享生产资源时才非零阻断；其余登记为非阻塞并行工作。
9. 涉及 POC 时确认候选不包含未批准的 POC 提交，POC 不写共享生产资源，发布脚本也不读取 `POC_ROOT`。
   POC 根的完整残留归零属于 POC closeout 或项目级迁移／清理门禁，不属于每次普通发布门禁。

以下任一情况都不得宣称任务完成：

- 最新代码、台账或交付物只存在于临时 worktree、复制目录或个人缓存。
- 负责人认定的原项目目录仍指向旧分支、旧 commit、旧数据库或旧制品。
- 同一发布单元存在两个都被称为“当前”“正式”“V2”或“可上传”的活动目录。
- 发布、上传、部署或自动化仍可能从临时 worktree 取文件。
- 候选包含未批准生产化的 POC 代码／台账，或依赖尚未形成结论的 POC 输出。
- 并行任务可能修改本次使用的生产数据库、配置、对象、部署目录、端口或其他共享可变资源，且没有隔离或锁。
- 只凭 tag 可回滚就长期保留第二套活动目录；回滚应由 commit、tag、bundle、数据库备份和制品记录承担。

以下事实本身不得阻断发布：另一个 POC 仍在运行；排除在本次范围外的分支已完成或未提交；无关 worktree
存在改动；实验资产位于已登记且发布脚本不会读取的 `POC_ROOT`。发布者必须记录排除理由，不能要求实验执行者
为“清空全项目”把快照提交到 `main`，也不能把无关完成分支自动并入当前版本。
发布可记录某一时刻的 POC branch／HEAD 作为排除证据，但不得为了获得“稳定 HEAD”要求已隔离 POC 暂停、提交、改分支或等待发布结束；排除判定依据候选可达性、发布源和共享资源隔离，不依赖另一个任务静止。

| 并行事实 | 发布判断 |
| --- | --- |
| POC 提交是候选 commit 的祖先，且尚未批准生产化 | 阻断；重新选择候选或移除该变化 |
| POC／其他分支会写本次生产数据库、配置、对象或部署目录 | 阻断；先隔离、加锁或停止冲突写入 |
| 发布脚本、构建上下文或制品会读取 POC 根／其他 worktree | 阻断；修正唯一发布源 |
| POC 在登记的独立根运行，候选不包含其变化，生产资源也隔离 | 非阻塞；记录为并行排除项 |
| 其他分支／worktree 有无关未提交改动或已完成功能 | 非阻塞；保留原状，另定版本范围 |

G0-G2 的短期探索可以使用登记的 POC 根或临时 worktree 而不执行完整发布门禁；只有该 POC 本身准备交付、
替换主线、更新正式台账或生产化时才升级到 G3-G4。另一个无关发布开始，不会改变该 POC 的治理等级。

禁止只验证“规则可从文档发现”就声称门禁已完成。worktree 收口规则至少要有一个真实或临时 Git 仓库的
正例和反例：主工作树通过、外部 worktree 被拒绝、迁移后逐文件或关键文件 SHA 一致、残留扫描归零。

## 2.4 继任版本线：例如 1.x 维护期间开发 2.x

当下一代版本已经明确会替换当前主线时，把它定义为 **Successor Version Line（继任版本线）**，而不是第二个长期项目。执行面继续沿用 2.3 的判定：默认在权威目录切换分支；用户只说“拉／开分支”或“旁路开发”时，不得推导为已授权 worktree、clone 或第二个目录。只在获准且必须同时写入／运行两条版本线，或构建、依赖和环境无法安全切换时增加 worktree。它仍只是共享同一 Git 历史的临时执行面，不拥有第二套治理、台账、发布入口或“当前版本”身份。

获准创建 worktree 时，先从负责人确认的 `project_authority_root`、实际 Git 仓库和项目既有约定选择受管容器；可以是项目总边界内的 `.worktrees/<branch-slug>/`、仓库相邻目录或项目登记的其他位置，不强制一种物理布局。当前位置恰好在 Codex／Agent 管理目录中不自动合法或非法：只有它本身已被确认是该项目的权威边界或受管容器时才可使用。禁止仅凭当前工作目录猜位置，也不得落入系统临时目录、下载目录、其他项目或未登记个人路径。容器位于仓库内部时确保不进入版本控制，并在 Project Map、编号任务计划或工作区登记中保存路径、分支、用途、集成目标和清理条件。

同一目录切换分支前必须先检查脏工作树；有未提交修改时不得静默 stash、覆盖或切换，应先确认这些修改的归属并完成提交、转移或负责人认可的保留处理。

只拉分支、继续使用同一目录的典型操作：

```bash
git status --short
git switch main
git pull --ff-only
git switch -c next/2.x

# 需要回到 1.x 时，先确保工作树干净
git switch main
```

只有明确获准同时检出两个版本时，才使用类似操作：

```bash
git status --short
git worktree add .worktrees/v2 next/2.x
git worktree list

# 合并收口时从权威主目录执行
git switch main
git merge next/2.x
# 确认 worktree 无独有事实后再移除明确路径
git worktree remove .worktrees/v2
git worktree list
```

命令只是示例；真实项目必须沿用已有远程、保护分支、PR 和合并策略。任何强制覆盖、删除分支或移除仍有独有修改的 worktree 都不属于默认授权。

推荐角色：

```text
main                         当前正式主线，例如 1.8.x
next/2.x                     下一代长期集成线，目标是晋升到 main
codex/v2/<topic>             从 next/2.x 拉出的短任务分支
hotfix/1.x/<topic>           从 main 拉出的当前版本修复分支
```

项目沿用 `develop`、`release/*` 或其他成熟模型时可以保留原名，但必须明确等价角色。`release/2.x` 通常更适合候选稳定阶段；仍在持续集成开发的下一代版本优先使用 `next/2.x` 或项目既有的下一代集成分支。

继任版本线必须在 `delivery/BRANCHING.md` 或项目等价 owner 中登记：当前正式分支与版本、继任分支与目标版本、创建基线 commit/tag、最终集成目标、Hotfix 前向传播契约、晋升条件、预计切换点、失败恢复方式和清理条件。`product/ITERATION_PLAN.md` 记录版本范围；编号任务计划记录执行状态；技术设计与 ADR 记录架构变化。不要创建 `v1/`、`v2/` 两套长期源码目录来代替 Git 分支。

### Hotfix 前向传播契约

当前正式线继续发布 Patch、继任线并行开发时，必须区分五件事：修复是否适用、是否负有传播责任、何时执行、采用何种集成方式、需要什么验证。不得把“应传播”自动解释为“收到消息后立即中断当前任务合并”，也不得把所有修复无条件拖到发布前一次性处理。

每个可能适用于继任线的已收口 Hotfix，只维护一条可更新记录：

| 字段 | 最低要求 |
| --- | --- |
| 源身份 | 当前正式线的最终 commit、已合并 PR／MR 或正式 tag；重大风险提前通知时标记 provisional，中间提交不是新的传播任务 |
| 目标线 | 需要评估或接收修复的继任分支 |
| 适用性 | `unassessed`／`applicable`／`not_applicable`／`superseded`，后两者记录理由 |
| 状态 | `observed`／`queued`／`integrating`／`verified`；源修复尚未稳定时保持 `observed` |
| 时机 | `immediate`／`checkpoint`／`release_gate`，并登记项目定义的检查点或截止条件 |
| 集成方式 | merge、cherry-pick、等价重做或不适用；按代码关系选择，不预设唯一方式 |
| 验证与回执 | 源线验证、继任线受影响验证、最终集成 commit 和残余风险 |

时机按影响选择：

- `immediate`：安全、权限、支付、数据损坏、共享数据库／接口／协议错误，或继任线继续开发会建立在错误行为之上；显式用户指令也可以提升优先级。
- `checkpoint`：一般适用修复默认排队，在项目声明的干净边界批量处理，例如功能切片完成、集成测试前或约定同步点。不得由 Skill 固定成每日、每周等统一频率。
- `release_gate`：不影响当前开发的低风险修复可以延后，但继任线进入 RC、候选冻结或晋升 `main` 前必须完成适用性判断并清零仍适用的待同步项。

跨 Agent／会话通知只传递源身份、影响、建议时机和证据，默认是事实交接，不是接收方立即执行、扩大版本范围或发布的授权。接收方把它更新到同一条传播记录；只有当前用户指令、已登记检查点、既有任务授权或经证据确认的重大风险可以打断当前开发。源 Hotfix 出现补充提交或纠正时更新原记录，在最终稳定边界明确前不得连续制造多个命令式合并任务。

传播执行遵循以下边界：

- 先在当前正式线完成修复范围内的测试和收口，再以稳定源身份评估继任线；紧急风险确需提前并行时，明确标记源仍可能变化。
- 可以在检查点批量处理多个 Patch，但先逐项判断适用性；不得为省事盲目合并整条 `main` 历史，把仅属于旧线的版本号、发布记录或运维差异带入继任线。
- 源线验证不能替代继任线验证。同步后先跑受影响测试；候选冻结后再从锁定 revision 运行项目要求的完整验证，不因每次通知机械重复全量测试。
- 如果每次 Patch 都在大量稳定文档、版本标题或候选状态上产生相同冲突，应治理事实 owner：把频繁变化的版本事实集中到发布单元的 VERSION、changelog、Release Record 或项目声明的单一状态文件，避免在多份长期文档中重复维护“当前版本”。

执行规则：

1. 从当前确认的最新集成基线创建继任分支，并记录基线 commit/tag。
2. 继任版本的具体任务继续使用短分支，完成后合回 `next/2.x`，不直接在 `main` 开发 2.x。
3. 1.x Hotfix 先在 `main` 收口；按前向传播契约判断其对 2.x 的适用性、风险和同步时机。仍适用的修复必须在登记的检查点或晋升门禁前合并／等价移植到 `next/2.x`；只有重大风险或明确指令要求立即打断开发。
4. `main` 中的 `VERSION` 继续表达当前正式版本；`next/2.x` 可以使用 `2.0.0-dev`，但不得让开发版本冒充已发布版本。
5. 2.x 满足需求、迁移、兼容、测试、部署和回滚条件后，通过项目规定的合并／PR 流程晋升到 `main`。晋升前复核传播记录，处理 `main` 上新增且仍适用的 Hotfix、冲突和未决项；晋升后以新的 main commit、`VERSION`、changelog、制品和生产验证共同确认主线替换完成。
6. 替换完成并度过约定稳定期后，删除或归档 `next/2.x`、短分支和临时 worktree；历史由 commit、tag、制品和发布记录保留，不长期维持两套“当前系统”。移除 worktree 前确认没有独有未提交修改、状态资产或交付物；移除后运行 `git worktree list`，并从权威主目录重新核对分支、HEAD、版本、完整质量命令和正式交付入口。

如果下一代版本尚未被批准替换主线，应标记为 experiment／candidate，不得使用“继任版本线已经完成”的状态。反之，一旦项目已明确它必须替换主线，就必须把最终合并、验证和旧线收口写入任务完成条件，不能以“2.x 分支开发完成”代替项目完成。

## 2.5 代码变更审查合并门禁

代码质量审查属于合并门禁，不等到发布时首次执行。审查单位是准备进入集成基线的完整 `base_commit..head_commit`，不是开发分支上每个临时 commit。直接提交到主线的项目中，每个主线 commit 等价于一个合并候选，必须在写入权威历史前完成等价门禁。

项目已有 PR／MR、分支策略、CODEOWNERS 或审批系统时沿用它们；未配置 Remote 不构成豁免，应在本地合并入口保存等价审查证据并非零阻断。不为了套模板建第二套账本；没有等价 owner 时可从 `assets/delivery-governance/CHANGE_REVIEW_CONTROL.template.json` 建立记录。

合并必须同时满足：

1. 已冻结仓库、集成目标、源分支、`base_commit` 和 `head_commit`，且完整 Git diff 中每个文件都已纳入或有规则允许的排除理由。
2. 第一方代码的变更函数／方法／顶层执行单元和被修改的现有注释均已按 Engineering 标准复核；人工代码不得以文件级摘要、lint 或测试绿灯代替语义审查。
3. G2-G3 代码批准由与作者分离的 peer／人类／审查 Agent 完成，G4 需 independent review。项目特殊情况只能通过有 owner、理由、批准时间和失效时间的显式例外放行。
4. 审查批准绑定当前 `head_commit`；审查后任何新 commit 都使旧批准失效，必须复核新差异及受影响链。
5. 所有项目声明的必需质量检查通过，变更单元 pending／blocked 为零，没有开放 Finding；P0／P1 不得以接受风险绕过。
6. 审查 Finding 整改后重跑原问题路径和匹配回归，由 reviewer 复核关闭；实现者声称修复不能自动关闭。

使用 BuildOS 默认记录时，合并入口执行：

```bash
python3 <buildos>/skills/senmu-build-delivery/scripts/validate_change_review.py \
  --record <change-review.json> --repo <repository> --require-current-head
```

通过只证明当前记录、Git 差异和审查状态自洽，不代替审查者的语义判断。有远程平台时将等价检查设为受保护分支必需状态；无远程时由项目唯一本地 merge／promote 入口调用，不把通用 Skill 脚本当作项目的永久运行依赖。

## 3. 风险匹配的合并核对

合并说明只保留本次范围实际命中的检查，不复制一张跨所有项目和技术栈的固定长清单。以下类别中，Hard Gate 和受影响项必须有结论；明显不相关的项目特有项可以省略，不为“完整”逐条填写不适用：

- **身份与范围**：目标仓库、发布单元、集成基线、允许路径、文件列表和无关改动隔离清楚。
- **工作区与并行**：权威根、写入者、分支和集成目标明确；使用 worktree／继任版本线／POC 时，完成对应授权、登记、前向同步、资产收口和残留检查。
- **产品与文档**：需求、行为、状态、用户文案、部署和用户可见版本变化已回写各自 owner；纯内部且不影响契约时记录不适用理由即可。
- **架构与实现**：读取项目工程入口；核对模块、依赖、接口、schema、第三方服务、legacy、复用、变更预算和技术债，只在触发条件成立时建立 ADR 或额外复核。
- **专项风险**：本次涉及的前端设计系统、数据真实性、数据库迁移、权限、支付、上传、删除、导出、安全、隐私和生产数据保护已经验证；未涉及的专项不加载。
- **代码与验证**：检查语义、异常、副作用、并发／幂等／事务、兼容、注释和敏感文件；运行与风险匹配的格式、lint、类型、测试、架构、构建或统一质量命令。
- **版本与发布**：用户可见或交付变化已处理 VERSION／changelog；Hotfix、正式发布或回滚另行完成 Tag、制品、生产验证、Release Record 和回滚门禁。没有发布授权时保持本地候选状态。
- **接力与学习**：开发执行者留下 commit、验证、未完成项和风险；发生返工或治理缺口时按 Learning 规则判断是否复盘或形成经验，不因普通合并强制复盘。

项目确需可重复的机器／人工清单时，应把稳定检查写入项目自己的 PR 模板或质量入口，并按技术栈和发布单元维护；本通用 reference 只提供选择维度。

## 4. 多 AI 协作

多 AI 或多人协作时：

- 每个写入主题使用独立短分支；只读分析不为形式完整机械创建分支。
- 不同主题不要共用一个分支。
- 同一工作目录同时只允许一个写入者；真正并行写入必须使用获准的隔离执行面。
- 接手前先检查已有未提交改动。
- 不覆盖他人未提交改动。
- 接手其他 AI 的工作前，先读最近工作日志，确认已完成、未验证和遗留风险。
- 收到另一执行者的 commit、PR、测试或状态消息时，先登记稳定源身份、真实依赖点和集成检查点。状态交接不是立即中断命令；候选不可达、共享生产资源会冲突、安全风险或下一不可逆动作必须依赖该结果时才立即停下，否则继续已授权的无冲突工作。
- 开发执行者完成后运行匹配验证、创建范围清楚的 commit，并按 `协作日志与版本日志规范.md` 记录分支、commit、验证、未完成项及本地／远程状态；推送和 PR／MR 只在 Remote 存在且授权覆盖时执行。
- 发布前检查最新 tag 到当前分支的 diff，确认没有旧分支覆盖新内容。
- 如发现分支过旧，先合流或重新开分支。
- 收到明确发布命令的当前执行者临时承担当次版本收口，按任务、分支、commit、PR／MR 和日志恢复范围；不依赖固定 Agent 账号，也不把未提交工作猜入版本。

共享或受保护分支禁止强推。私有短分支确需在已发布历史上 rebase 时，也只能在项目规则允许、确认无人依赖且明确获准后使用限定目标的 `--force-with-lease`；普通 `--force`、`git reset --hard` 和覆盖式 checkout 不得用来“解决”冲突。

## 5. 发布前代码检查

发布门禁不在这一阶段首次开展日常代码语义审查。它核对冻结的发布候选可达变更已通过合并审查、没有绕过受保护入口，且当前候选 commit、审查凭证、质量验证和制品身份一致。候选包含未审变更或审查身份已过期时，退回合并门禁，不在发布环节建第二套审查结论。

代码合并发布时，至少执行：

```bash
git status --short
git diff --check
git log --oneline --decorate -10
```

如项目有 preflight、lint、test、build 脚本，应在发布前执行。没有这些脚本时，AI 助手应建议补齐，而不是长期靠人工判断。

代码项目应优先提供一个由本地、提交前检查和 CI 共同复用的完整质量命令，并纳入项目已声明的架构／依赖门禁。发布前记录实际命令和结果；项目声明为阻断项的检查未通过、未运行或只有口头自查时，不得宣称代码已满足发布门禁。自动检查通过后仍要审查完整 diff 的正确性、安全、兼容、数据、测试、架构影响、技术债和注释，不把 lint 通过等同于语义正确。
