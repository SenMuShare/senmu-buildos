# 代码管理与合并规范

本规范只处理非例行 Git 决策、并行执行面、合并和版本线治理。项目现行分支策略优先；本地 Git 是完整基础，Remote、PR／MR、CI 和平台 Release 只在实际存在且授权覆盖时启用。

## 1. 现场判定

先只读恢复权威仓库／根、Git 状态、集成线、开放批次、发布单元、并行写入、共享资源和授权。按“产品版本归属 → 批次／Change Unit → 写入者／worktree → 交付意图”决定版本线、分支、执行面和阶段；Agent 数量不决定产品版本或分支拓扑。

现有 owner、任务、Git 和上下文足以推断时直接执行；只在选择会改变版本归属、批次截止、费用、数据安全或生产结果时，用产品语言确认一次，不询问 Git 机制。

默认语义如下：

- 当前开放批次中、共同验收且一起发布／回退的连续需求，复用现有 `in_progress` 单元；单项完成不代表批次完成。
- 用户没有表达提测／收口时保持开发中；没有表达发布时保持未发布。实现授权不自动包含封口、合并、完整门禁或发布。
- “提测／本轮收口／准备发布”冻结当前批次并集中形成候选，但不授权生产变更；“收进当前版本”允许集成但不发布；“发布／上线”才开启绑定精确候选的有限发布会话。
- 后续需求只有在进入不同目标版本、独立验收／发布／回退边界，当前单元已经 sealed，或确需并行隔离时才建立新单元。尚未开始实现的未来需求只进入产品 owner，不创建空代码分支。

只读盘点可运行：

```bash
python3 skills/senmu-build-delivery/scripts/inspect_git_workspace.py \
  --repo <repo> --target <integration-branch> \
  --intent <read|write|parallel-write|release-closeout> --compact
```

`write` 使用匹配批次的任务分支：归属一致的开放单元直接续作，否则新建。只有项目／Harness 保证整个窗口独占写入时，才可用 `--exclusive-writer` 复用当前目录；它不允许写集成线，“当前没看到别人”不算保证。

首次源码写入不能只停在建议输出。项目没有自己的写入入口时，使用 Delivery 的确定性 Change Unit 入口：

```bash
python3 skills/senmu-build-delivery/scripts/manage_change_unit.py prepare \
  --repo <repo> --target <integration-branch> \
  --unit <stable-task-or-change-unit-id> --slug <short-scope> \
  --worktree <new-isolated-path>

python3 skills/senmu-build-delivery/scripts/manage_change_unit.py verify \
  --repo <returned-worktree> --unit <same-id>
```

`prepare` 从冻结 commit 创建专属分支／worktree 并在 Git common dir 记录执行身份；记录不匹配、属于其他单元或已 `sealed` 时 fail closed。该记录不替代 Durable Task State；项目有等价入口时直接沿用。

同一任务复用冻结事实，只在 HEAD、工作区、执行面或发布范围变化时重查。复杂 Git 建议给出事实、盲区、理由、例外和收口条件；诊断不授权删除或新台账。日常本地 commit 由 Engineering 主责。

## 2. 分支与提交

一个独立 Change Unit 使用一个短分支，分支身份不属于会话或单项修改。同一目标版本、验收、发布／回退边界的开放批次继续复用并以 checkpoint commit 保存进度；分支已 sealed、边界不同或工作可独立交付时才新建。未知／真实并行再增 worktree。无项目策略时用 `main + codex/<scope>/<topic>`；只有长期替换版本或独立候选根才增 `next/*` 或 `release/*`。不直接写集成线。

- 创建分支前检查当前分支、`git status --short` 和最近提交。
- 合并策略沿用项目现状；命令失败时先解释分叉或冲突，不强制覆盖。
- 修复授权不包含合并、Tag、推送或发布授权。
- 改变用户行为的变更必须回指先前批准行为、本次产品决定和候选实际行为；同一分支把 PRD、代码和测试改成一致不能自证授权。
- 开发执行者在开放批次内完成实现和必要 checkpoint；收到提测／收口请求时冻结范围、运行匹配验证并形成稳定 commit，收到明确发布命令的当前执行者承担当次发布收口，职责不绑定固定 Agent。

项目必须在既有治理 policy 或分支 owner 中声明 `main_mode`：

- `release_ready`：只有完成、验证且满足项目接收条件的 Change Unit 才进入 `main`，主线始终可形成发布候选。
- `integration`：完成且已决定接收的工程切片可以进入 `main`，但生产版本仍由冻结候选、制品和发布事实确定；未完成半成品不得借此进入主线。

未声明时 BuildOS 可以根据仓库事实给出一次建议，但在声明落回项目 owner 前不自动集成。分支名称不能替代语义声明。

### 2.1 版本线拓扑

项目必须把分支角色分为集成线与任务分支，而不是让每个新任务继承上一个任务分支：

- 集成线是项目 owner 登记的 `current_line`、`successor_line`、必要的 `maint/*` 或一次发布窗口的唯一 `release_source_root`。
- 任务分支从目标集成线的冻结 commit 建立，封口后由收口者集成回同一条线。后续同类任务从已经集成的线上建立，不默认从前一个任务分支上串联生长。
- 确实需要依赖尚未集成的父变更时，才建立 stacked unit；必须登记父 Change Unit，父单元先 sealed，子单元交接时声明集成顺序。堆叠是可追踪例外，不是常规版本线。
- 同一目标版本、共同验收和共同发布／回退边界下的连续补充保持当前单元 `in_progress`；不为每次澄清、Bug 或交互调整立即 sealed、合并、运行完整门禁或新建 worktree。

`manage_change_unit.py prepare` 默认把 `--target` 视为集成线；若目标已属于另一 Change Unit 则 fail closed。真实依赖使用 `--target-role stacked-unit --parent-unit <id>`；精确 commit 基线使用 `--target-role frozen-commit`。

跨 Agent、跨会话续作必须传递稳定 Change Unit ID，并恢复原分支与 worktree：

```bash
python3 skills/senmu-build-delivery/scripts/manage_change_unit.py resume \
  --repo <repo> --unit <same-id>
```

`resume` 不创建新分支；登记缺失、单元已封口或执行面冲突时停止。新 `run_id`、新 attempt 或“从头再跑实验”只改变运行事实，不自动创建 Change Unit。

## 3. Worktree 与并行执行面

按以下顺序自动选择，不把 Git 机制选择题交给非技术用户：

| 现场 | 默认执行面 | 原因与例外 |
| --- | --- | --- |
| 只读分析／监控 | 当前权威目录，不建分支 | 没有写入冲突 |
| 默认 Codex 写入；用户稍后仍可能开启新会话 | 每个新独立写入单元使用独立短分支和独立 worktree；同一开放单元复用已登记执行面 | 并发数量事前未知；先隔离新单元可避免中途搬家和归属污染 |
| 项目／Harness 保证整个修改窗口独占写入，且工作区干净 | 在当前目录创建任务短分支 | 省略的是额外 worktree，不是任务分支 |
| 已有多个会话／Agent 并行修复 | 每个写入任务使用独立短分支和独立 worktree | 分支只隔离提交历史；同一物理目录仍会互相切换和覆盖 |
| 当前目录有来源不明或属于其他任务的改动 | 保持原样，转到干净的独立 worktree；若无法确认安全基线则交还 owner | 不自动 stash、reset、提交或混入当前任务 |
| 共享数据库、生成目录、端口或生产资源无法隔离 | 串行、加锁或暂停冲突步骤 | Git 隔离不能解决共享可变资源冲突 |

只读任务不建分支或 worktree。新写入单元自动建任务分支，匹配开放单元则恢复原执行面；未知并行为新单元增加 worktree。项目禁止、复制成本显著、基线不清或会产生第二个状态 owner 时改为串行；只有可验证的独占写入保证才复用当前目录。

创建时登记用途、基线、集成目标、共享资源和退出条件。业务台账、数据库、POC 状态、媒体和回执仍归项目唯一 owner，不随源码 worktree 复制；权威根不明或出现第二个活动 owner 时停止写入。

每个写入者只负责一个开放单元；单一写入者可连续接收同批需求，多写入者各自隔离。确认提测／交接后冻结范围、验证、commit 并 `seal`。待接收视图由 Change Unit 登记与 Git 派生，不建第二套台账；收口者再形成接收矩阵并集成。

使用 Delivery Change Unit 入口的任务在 commit 和匹配验证完成后执行：

```bash
python3 skills/senmu-build-delivery/scripts/manage_change_unit.py seal \
  --repo <worktree> --unit <same-id>
```

`seal` 只在工作树干净且基线后存在 commit 时记录封口 head；封口后同一分支不能再被 `prepare` 恢复。后续同范围返修也从明确基线创建新 Change Unit，再由集成者决定替代或追加关系。

任意后续 Agent 可以读取待接收视图，不必回看全部聊天：

```bash
python3 skills/senmu-build-delivery/scripts/manage_change_unit.py list --repo <repo>
```

脚本把仍为 `sealed` 且尚未进入登记目标线的单元派生为 `pending_integration`，已经可达目标线的派生为 `integrated`。若使用 squash、rebase、cherry-pick 或决定排除／替代，先把最终处置写回项目任务 owner，再使用 `close --disposition <integrated|excluded|superseded> --owner-ref <owner#section>` 登记 Git 执行回执；`integrated` 还必须给出 `--integration-commit`。回执只镜像 owner 决定与 commit 映射，不是第二份任务状态。

新会话先恢复匹配的开放 Change Unit；只有验收、发布／回退边界或写入归属改变时才新建单元。混合脏改动不得自动 stash、reset 或代提交；保持原样并回到可归属的执行面续作。

短分支合并并在目标线验证后，先核对未提交、未跟踪、忽略资产、进程和独有 commit。确认无独有事实且获得授权后，按明确路径移除 worktree，再用 `git branch -d` 删除已合并本地分支；Remote 删除另行授权。不得默认使用 `-D`、`--force` 或直接删目录。

## 4. Hotfix 与继任版本线

Hotfix 开始前确认线上／发布基线、当前版本、回滚点、未发布改动和候选版本。修复后运行原始复现与匹配回归。前向传播按适用性和风险处理：高风险共享根因立即同步；一般修复在登记检查点同步；仍适用的低风险项最迟在 RC／候选冻结或继任线晋升前清零。

传播责任不等于打断另一个 Agent；跨 Agent 通知默认登记事实和检查点。继任版本线是未来替换主线的分支，不是第二个长期项目；它共享治理、状态 owner 和发布入口，按适用性持续吸收当前维护线 Hotfix，晋升后只有一个当前主线并保留旧线历史／回滚证据。

## 5. 合并与审查

- 冻结 base／head、发布单元、需求／缺陷范围和完整 diff。
- 核对每个实质变更函数、接口、状态、副作用、异常、注释和匹配测试。
- 只运行本次风险和技术栈命中的门禁，不执行万能长清单。
- 项目 Hard Gate、质量命令和阻断 Finding 未关闭时不得合并。
- 审查批准绑定冻结 head；新 commit 使旧批准失效。
- 自查不能替代项目要求的职责分离批准，但普通低风险提交不强制独立审查。
- 审查职责绑定本次冻结变更集，不绑定固定 Agent；收到合并／发布命令的当前 Agent 可以完成低风险证据自查，高风险或项目硬门禁要求时才另找独立审查者。

## 6. 发布源与并行排除

正式候选从唯一 `release_source_root` 构建。只有候选可达的未批准变化、本次纳入但未收口的事实、共享生产资源冲突，或发布脚本会读取其他 worktree／POC 根时才阻断。

用户说“发布最新版本”“把刚才修好的都发上去”时，解释为一次发布收口，而不是“合并所有分支”：

1. 冻结接收窗口，读取当前版本唯一 PRD 或等价版本 owner 中的需求与缺陷清单，并盘点活动任务、worktree、分支、未提交改动和项目登记的发布范围；不依赖完整聊天恢复承诺。
2. 清单内属于本版本的每项必须已经验证并有匹配证据，或有明确延后、取消、移出本版本的决定。处于已分析待实施、开发中或已实现待验证的本版本必需项阻断候选；当前版本 owner 已批准且范围明确时先完成，只有是否纳入会改变发布结果且无法从 owner 判断时才询问负责人。
3. 只纳入能够证明属于本发布单元、已完成、已验证并有稳定 commit 的变化；存在依赖时按依赖顺序集成。已合并历史分支、实验／POC、未完成任务、范围不明分支和与本发布单元无关的改动排除，不为“一个不漏”机械合并。
4. 来源不明的脏改动交还原 owner 完成提交或由负责人明确排除，不由发布者代为打包猜测。
5. 在唯一干净发布源完成合并审查、冲突处理、完整预检和版本冻结；只有发布授权覆盖时才继续 Tag、制品、部署和生产验证。

每次发布实例化一份 `RELEASE_CONTROL.template.json` 或项目等价 owner，把范围、接收矩阵、门状态、证据和恢复点写在同一张控制单上，按 `scope_accounted -> integration_complete -> candidate_verified -> release_authorized -> release_verified -> git_execution_closed` 顺序逐项关闭，并运行：

```bash
python3 skills/senmu-build-delivery/scripts/validate_release_control.py <release-control.json>
```

Release Control 管“该查什么、进行到哪、从哪恢复”；Release Record 只记录实际发布、生产验证与回滚动作，不重复控制单正文。开发批次不为中间 checkpoint 重跑完整门禁；候选不变时复用证据，候选变化只补受影响检查并按标准入口决定是否重跑。

### 标准发布快速通道

当项目已有唯一发布单元、默认生产目标和标准发布入口时，按以下预算执行：

标准发布入口是项目 owner 声明的机器可执行顶层命令或 CI/CD workflow，至少统一受理冻结 commit、版本／变更摘要、一次完整 preflight、不可变制品、部署预检／执行、生产身份／健康核对和 Release Record。它应从项目声明的环境 owner 加载配置，支持幂等重试或按收据恢复，并输出机器可读的阶段状态。只写在 Markdown 里的命令顺序、分散的 build/deploy 脚本或“唯一入口”这句话不构成已有流水线。

1. 只读项目 `AGENTS.md`、发布 owner、紧凑 Change Unit／分支闭环索引和当前 Git；不加载 Assurance，不宽泛搜索 memory、历史日志或全部会话正文。
2. 所有纳入单元已 `sealed` 且测试证据绑定其 commit 时，直接集成并只运行冲突影响检查；不重放每个修复组已经通过的专项测试。
3. 完成版本／Changelog 和候选 commit 后，调用项目声明的完整 preflight **一次**。标准入口已经包含的子测试不在入口前手工重复执行。
4. preflight 通过后只构建一次冻结制品；部署后核对运行身份、健康和本次受影响主流程，不机械遍历全部页面。
5. 只有候选代码变化、冲突处理改变行为或门禁失败修复时才重跑受影响检查；纯发布记录追加不使已经通过的候选代码测试失效。

当上述顶层驱动缺失时，项目只能算“有发布脚本”，不算“有标准发布流水线”。紧急发布继续使用现有安全入口，但只做一次必需门禁，不在发布窗口现场设计 CI/CD；发布后把顶层驱动登记为项目自动化债务。

遗留共享主线存在混合脏改动时不具备快速通道。发布者只做足以确认范围一致性的最小恢复检查，形成一个明确的 recovery／consolidation commit，再冻结版本并运行一次完整 preflight；不得先按每个历史修复重放大批测试，随后又执行相同 preflight。这种额外耗时应登记为前序会话未 sealed 的恢复成本，不包装成正常发布成本。

隔离良好、候选不可达且不写共享生产资源的 POC、分支和 worktree 不阻断发布，也不要求暂停、提交、归零或自动合入。发布可记录其时点 branch／HEAD 作为排除证据，但不能为了冻结证据打断对方。

收口记录权威根、集成 commit、发布源、交付路径、回滚点、并行排除项和临时执行面去留。最新事实若只存在于临时目录，或两个目录都被称为当前／正式，则尚未完成。

### 6.1 发布列车与截止点

一次发布收口只保留一个可变集成根。如果选择 `release/*` worktree，所有候选相关修复都必须回到该根并在其上重新预检；不能封口发布分支后又另行推进 `main`。如果选择 `main`作为发布根，则不再建立第二个同时声称是候选的发布分支。

- 截止点是“接收哪些 Change Unit”的快照，不是“以后不能出现新分支”。截止后新建、候选不可达且不争用共享生产资源的任务自动排除；记录其 `branch@HEAD` 即可，不得为更新排除账本改写候选 commit。
- 版本、changelog 和必要候选状态在完整 preflight 前可以作为可变的 release-train 准备提交；只有 preflight 通过后才冻结最终候选。
- preflight 失败产生的修复回到同一发布根，使旧候选失效；重新运行受影响检查和完整 preflight 后再冻结新 head。
- 候选／制品前运行 `verify_release_identity.py`，使已存在的 `reviewed_commit = tested_commit = release_source_head = artifact_source_commit`。正式 Tag 不是候选门禁输入；目标发布验证成功后，项目标准促进入口必须先校验精确发布 commit 的验证回执，再创建并推送 Tag。
