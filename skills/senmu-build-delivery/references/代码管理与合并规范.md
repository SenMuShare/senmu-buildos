# 代码管理与合并规范

本规范只处理非例行 Git 决策、并行执行面、合并和版本线治理。项目现行分支策略优先；本地 Git 是完整基础，Remote、PR／MR、CI 和平台 Release 只在实际存在且授权覆盖时启用。

## 1. 现场判定

先只读确认权威仓库与项目根、当前分支、HEAD、工作区改动、Remote、集成线、发布单元、并行写入者、共享资源和当前授权。再判断对象是普通短分支、Hotfix、POC、继任版本线、发布入口还是历史残留。

复杂 Git 建议应给出已确认事实、盲区、分类、理由、例外和收口条件。诊断分类不是删除授权，也不需要另建长期台账。范围清楚的日常本地 commit 由 Engineering 完成，不触发本规范。

## 2. 分支与提交

默认采用一个权威目录、短分支和一个写入者。项目没有既定策略时可使用 `main + codex/<scope>/<topic>`；只有真实存在独立集成、候选或多版本维护需求时才增加 `develop`、`release/*` 或 `next/*`。

- 一个分支和 commit 只承载一个可独立验证、回退的主题；无依赖工作不因另一项等待而绑定。
- 创建分支前检查当前分支、`git status --short` 和最近提交。
- 合并策略沿用项目现状；命令失败时先解释分叉或冲突，不强制覆盖。
- 修复授权不包含合并、Tag、推送或发布授权。
- 改变用户行为的变更必须回指先前批准行为、本次产品决定和候选实际行为；同一分支把 PRD、代码和测试改成一致不能自证授权。
- 开发执行者完成范围清楚的实现、匹配验证和本地 commit；收到明确发布命令的当前执行者承担当次发布收口，职责不绑定固定 Agent。

## 3. Worktree 与并行执行面

用户只要求开分支时，不推导为 worktree、clone 或第二项目目录。只有多个执行者必须同时写不同分支，或必须同时运行／比较版本且串行代价不合理时，才评估额外 worktree。

创建时登记用途、基线、集成目标、共享资源、保留和清理条件。必须区分 Git 主工作树、项目权威根、本次唯一 `release_source_root` 和额外执行面。业务台账、数据库、POC 状态、媒体和回执仍写入项目唯一 owner，不随源码 worktree 复制。无法解析权威根或发现第二个活动状态 owner 时停止写入。

短分支合并并在目标线验证后，先核对未提交、未跟踪、忽略资产、进程和独有 commit。确认无独有事实且获得授权后，按明确路径移除 worktree，再用 `git branch -d` 删除已合并本地分支；Remote 删除另行授权。不得默认使用 `-D`、`--force` 或直接删目录。

## 4. Hotfix 与继任版本线

Hotfix 开始前确认线上／发布基线、当前版本、回滚点、未发布改动和候选版本。修复后运行原始复现与匹配回归。前向传播按适用性和风险处理：高风险共享根因立即同步；一般修复在登记检查点同步；仍适用的低风险项最迟在 RC／候选冻结或继任线晋升前清零。

传播责任不等于打断另一个 Agent；跨 Agent 通知默认登记事实和检查点。继任版本线是未来替换主线的分支，不是第二个长期项目；它共享治理、状态 owner 和发布入口，晋升后只有一个当前主线。

## 5. 合并与审查

- 冻结 base／head、发布单元、需求／缺陷范围和完整 diff。
- 核对每个实质变更函数、接口、状态、副作用、异常、注释和匹配测试。
- 只运行本次风险和技术栈命中的门禁，不执行万能长清单。
- 项目 Hard Gate、质量命令和阻断 Finding 未关闭时不得合并。
- 审查批准绑定冻结 head；新 commit 使旧批准失效。
- 自查不能替代项目要求的职责分离批准，但普通低风险提交不强制独立审查。

## 6. 发布源与并行排除

正式候选从唯一 `release_source_root` 构建。只有候选可达的未批准变化、本次纳入但未收口的事实、共享生产资源冲突，或发布脚本会读取其他 worktree／POC 根时才阻断。

隔离良好、候选不可达且不写共享生产资源的 POC、分支和 worktree 不阻断发布，也不要求暂停、提交、归零或自动合入。发布可记录其时点 branch／HEAD 作为排除证据，但不能为了冻结证据打断对方。

收口记录权威根、集成 commit、发布源、交付路径、回滚点、并行排除项和临时执行面去留。最新事实若只存在于临时目录，或两个目录都被称为当前／正式，则尚未完成。
