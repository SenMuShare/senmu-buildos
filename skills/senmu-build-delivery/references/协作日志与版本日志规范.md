# 协作日志与版本日志规范

本规范面向公司工程项目的协作留痕、版本留痕和组织学习治理，规定项目中三类记录如何管理：

- 版本日志：面向版本发布、用户可见变化、内部追溯和回滚。
- 协作工作日志：面向多人、多 AI 接力协作，记录每次具体工作做了什么、验证了什么、留下什么风险。
- 经验与防回退台账：面向后续执行，保存已经验证、会重复触发的失败模式、源头修复、正确约束和必要的剩余风险控制。

三者用途不同，不能互相替代。工作日志回答“这次发生了什么”，changelog 回答“这个版本发布了什么”，
经验台账回答“以后遇到什么信号时必须怎样做，如何防止回退”。

Git commit 历史记录逐次代码快照和差异，也不能替代上述三类记录。不要为每个机械 commit 自动复制一段 Work Log 或 changelog：实质任务、合并、发布和中断写 Work Log，进入版本的用户可见或交付相关变化写 changelog。项目可以约定 Conventional Commits 等消息格式，但未配置时不强加；提交信息仍应简短说明意图和范围。

## 本页导航

1. 工作日志价值；2. 推荐位置；3. 版本日志；4. 协作工作日志；5. 经验与防回退台账；6. AI 写日志要求；7. 合并与发布记录；8. 与任务管理的边界；9. 与复盘的关系。

## 1. 为什么需要工作日志

多 AI 或多人协作时，最常见的问题是：

- 不知道上一个 AI 做了什么。
- 不知道哪些改动已经验证，哪些只是写了代码。
- 不知道哪些文件是本次任务改的，哪些是历史遗留。
- 不知道当前分支是否能合并或发布。
- 不知道哪些问题被搁置，下一位接手者从哪里继续。

因此，正式项目应建立协作工作日志。它不需要写成长篇报告，但每次有实质改动、发布、合并、部署、排障或重要决策时，都应留下记录。

工作日志的目标是保证连续性和承诺性：

- 连续性：后面的 AI 即使没有聊天上下文，也能接着做。
- 承诺性：每次记录都要说明已完成、未完成、已验证、未验证和下一步。
- 可恢复性：如果因为断网、上下文丢失、工具失败或任务中断，下一位接手者能知道中断点。

## 2. 推荐日志位置

推荐结构：

```text
governance/
  logs/
    WORKLOG.md
    2026-06.md
  lessons/
    LESSONS_LEARNED.md
  CHANGELOG_RULES.md
projects/
  <app-or-service>/
    CHANGELOG.md
    VERSION
```

小项目仍沿用同一默认位置，可以只保留：

```text
governance/logs/WORKLOG.md
governance/lessons/LESSONS_LEARNED.md
CHANGELOG.md
VERSION
```

Work Log 的 schema 和生命周期由 `senmu-build-project` 负责，Lessons Learned Register 由 `senmu-build-learning` 负责；Delivery 只向统一 Work Log 追加已经发生的合并、构建、部署、发布或回滚事实，并把可复用候选连同证据交给 Learning。多产品／多发布单元项目建议：

- 每个正式发布单元维护自己的 `VERSION` 和 `CHANGELOG.md`。
- 仓库级协作接力记录统一写到 `governance/logs/`。
- 不按 Skill、Agent 或普通子目录建立第二份 Work Log；只有发布单元本身是独立项目、已在 Project Map 登记独立 owner 时，才使用其项目内 Work Log。
- 项目级经验默认集中到 `governance/lessons/LESSONS_LEARNED.md`；只有发布单元的触发条件和门禁完全独立时才拆分。

需要持久状态的任务由项目声明的 Durable Task State Owner 保存当前边界、阶段、进度和恢复入口；采用 BuildOS 新项目默认实例时使用 `governance/tasks/TASK-<NNNN>-<slug>.md`。`WORKLOG` 只按时间追加实际发生的工作。接手者先读任务状态 owner，需要追溯过程时再读工作日志。

## 3. 版本日志规则

版本日志记录“这个版本发布了什么”。它服务于发布、回滚、用户沟通、内部复盘。

每个正式发布单元应维护：

```text
VERSION
CHANGELOG.md
```

如果项目有普通用户和内部维护者，建议拆分：

- 内部 changelog：记录具体实现、接口、数据库、部署、测试、风险、回滚点。
- 用户 changelog：只写用户可理解的新功能、体验优化和笼统修复，不暴露内部实现、安全细节、密钥、成本、价格策略、支付配置和未公开计划。

版本日志必须写：

- 版本号。
- 发布日期。
- 影响范围。
- 新增能力。
- 修复问题。
- 技术/部署变化。
- 测试和验证结果。
- 已知风险。
- 回滚点或上一稳定版本。

Bug/Hotfix 的版本日志不能省略。只要修复进入正式发布单元，就必须记录修复问题、影响范围、验证结果、发布版本、回滚点和是否有未发布改动。用户可见修复应在用户 changelog 中脱敏说明，内部 changelog 保留可追溯细节。

## 4. 协作工作日志规则

协作工作日志记录“某个人或某个 AI 这次具体做了什么”。它服务于接力协作，不替代版本日志。

日志可以由工具预填时间、分支、commit 和文件清单，但“完成了什么、验证了什么、仍缺什么”必须由执行者按事实确认；Hook 不得因普通 commit 自动改日志或生成第二个提交。

以下情况必须写工作日志：

- 完成一次功能开发。
- 完成一次 Bug 修复。
- 修改需求、技术方案、部署方案、版本规则。
- 执行合并、发布、部署、回滚。
- 排查线上或本地问题。
- 接手他人或其他 AI 的未完成工作。
- 发现风险但暂未处理。
- 修复 AI 自己踩坑、项目负责人纠偏的问题、重复返工问题或暴露出的治理漏洞。
- 因断网、工具失败、上下文不足或权限问题中断任务。
- 明确提出“下一步准备做什么”但尚未完成。

Bug 修复验证完成后，即使暂不发布，也必须写工作日志，说明修复停留在哪个分支或提交、为什么暂不发布、后续触发发布的条件、未发布风险和回滚/恢复依据。

工作日志至少包含：

- 时间。
- 执行者：人名、AI 名称、线程名或分支名。
- 分支。
- 治理等级，如果本次达到 G2-G4 或触发发布/复盘门禁。
- 任务目标。
- 修改文件。
- 关键决策。
- 已执行验证。
- 未验证项。
- 遗留风险。
- 下一步建议。
- 文档影响（Doc Impact）：本次修改了哪些权威文档；如果正文无需修改，记录已审阅并校准到哪个发布单元版本。
- 复盘结论，如果本次踩坑、返工或治理漏洞触发了复盘。
- 中断原因，如果任务没有完成。

普通完成、中断和发布三种日志结构见 [Work Log Entry Templates](../assets/delivery-governance/WORKLOG_ENTRY.template.md)。只读取或复制当前场景需要的变体，并按真实 owner、验证和状态裁剪；模板字段不是每次任务的机械必填表。

## 5. 经验与防回退台账

正式名称采用“经验与防回退台账（Lessons Learned Register）”。“踩坑指南”可作为口头称呼，但正式台账必须是
结构化、可判定、可失效的记录，不能变成抱怨合集或无限增长的故事集。

只有同时满足以下条件，才从工作日志／复盘提升为有效经验条目：

- 问题可能重复出现，或已经出现第二次；
- 根因和修复经过证据验证，不只是猜测；
- 能写出明确适用范围、触发信号、必须／禁止动作；
- 至少有可复验检查，重要路径优先形成测试、doctor、validator 或 CI 门禁。

每条经验至少包含：唯一 ID、状态、适用范围、触发信号、症状、已确认根因、源头治理动作、必须、禁止、修复验证、
权威规则落点、来源工作日志、负责人／复核日期和替代关系；存在合理剩余风险时再记录自动检测／门禁及其成本与退役条件。状态使用：

- `candidate`：尚未充分验证，不得当硬规则；
- `active`：后续 AI 开工时必须读取并执行；
- `superseded`：被新条目替代，保留历史并指向新 ID；
- `retired`：触发条件已消失，保留退出依据。

Hard Gate：

- 后续 AI 开工时读取作用域内所有 `active` 条目；命中触发信号时先执行条目的必须／禁止动作和检测命令。
- 同类问题第二次发生时，不得只追加第二段工作日志；必须建立或升级经验条目，并分析缺陷为何仍在生产环节被制造、源头修复为何失效，以及是否确有剩余风险需要门禁。
- 经验条目不能成为第二份 PRD、架构或部署规范。稳定规则写回对应权威文档，经验台账保存失败模式、触发和防回退索引。
- 规则已经机器化后仍保留条目，但把正确的生产入口、默认值和可执行契约作为主要防线；必要的 validator／测试负责回归和剩余风险，不能长期依赖 AI “记得看”。

初始化模板由 `senmu-build-learning` 的 `assets/learning-governance/LESSONS_LEARNED.template.md` 唯一持有。

## 6. AI 写工作日志的要求

AI 助手每次完成实质性工作后，应在最终回复中说明是否写了工作日志。项目已有工作日志规范时，应按规范写入。

如果项目没有工作日志，AI 助手应建议新增：

```text
governance/logs/WORKLOG.md
```

AI 助手写日志时不要记录：

- 密钥、密码、token、私钥。
- 用户真实隐私数据。
- 服务器敏感配置明文。
- 未公开商业敏感细节，除非项目内部文档允许且有访问控制。

AI 助手写日志时必须记录：

- 本次工作做了什么。
- 哪些文件被改。
- 哪些验证已做。
- 哪些验证没做。
- 有没有未完成事项。
- 如果发生踩坑、返工或纠偏，写明根因分类、修复动作和后续约束。
- 如果问题达到经验提升条件，写入或更新 `LESSONS_LEARNED.md`，并在工作日志引用经验 ID。
- 如果任务中断，写明中断点和下一步。

## 7. 合并和发布时的日志要求

合并前检查：

- 工作日志是否记录了本分支主要工作。
- changelog 是否记录用户可见或发布相关变化。
- Bug/Hotfix 是否完成 patch 版本、回滚点、线上验证计划和未发布改动说明。
- 未验证项是否写清楚。
- 遗留风险是否写清楚。
- 权威文档是否完成 Doc Impact 判断；正文无变化时是否仍记录适用版本校准，历史快照是否保持原版本。
- 本次是否命中 `active` 经验条目；相关 validator 是否执行，新增经验是否已分配 ID。

发布后必须补充：

- 发布版本。
- Git commit。
- tag。
- 部署服务。
- 制品版本。
- 线上验证结果。
- 回滚点。
- 未发布改动说明。
- 本地 Tag、Remote、远程 Tag、PR／MR 和平台 Release 的实际状态；不存在或未授权时明确写 `not_configured`、`local_only` 或 `not_authorized`。
- 本次发布涉及的现行基础文档及其适用版本校准结果。

## 8. 日志和任务管理的边界

工作日志不是任务列表，也不是 PRD。

- 待办任务应进入项目任务系统、迭代计划或 issue。
- 需求变化应进入 PRD 或需求文档。
- 技术决策应进入技术方案。
- 发布变化应进入 changelog。
- 工作过程和接力信息进入工作日志。
- 已验证的重复失败模式、触发信号和防回退门禁进入经验台账。

如果一条信息会影响后续需求、架构或发布，不能只写在工作日志里，还应同步到对应正式文档。

## 9. 复盘、工作日志和经验台账的关系

复盘不是独立于工作日志之外的口头总结。只要复盘结论会影响后续 AI 的执行方式，就必须落入工作日志，并按 `senmu-build-learning` 的《项目复盘与组织学习规范》判断是否还要更新项目正式文档或形成 Senmu BuildOS 整仓反哺候选。

工作日志保存本次复盘事实；经验台账只接收已经验证且可能复现的结论。一次性失误可以只留工作日志，项目规则缺口
应同时更新权威文档；重复失败还必须形成经验 ID 和可执行门禁。

工作日志中的复盘至少包含：

- 问题/踩坑。
- 发现方式。
- 根因。
- 修复动作。
- 验证结果。
- 分类：一次性执行失误、项目个性化规范缺口或通用治理缺口。
- 已更新的项目文档或 skill 文件。
- 后续约束。

如果复盘结论建议更新 Senmu BuildOS，应记录跨项目抽象依据，并把维护工作作为 BuildOS 源码仓库中的独立项目任务交给 `senmu-build-learning`；涉及 Skill 入口、结构或触发时再组合 `$skill-creator`。应用项目工作日志不承担 BuildOS 自身的版本历史。
