# 仓库边界与发布单元治理规范

本规范判断多产品、多团队或多 AI 项目的仓库与发布单元边界，并治理版本、制品、接口、迁移和公开贡献回流；它不是普通目录整理指南。

## 本页导航

1. 场景；2. 概念、分层与公开回流；3-4. 仓库／发布单元；5-8. 拆分门禁、迁移和验收；9-10. 接口与协作；11-12. 落地与分工。

## 1. 适用场景

遇到以下情况，应读取本规范并触发仓库边界评估：

- 一个仓库内出现多个产品、子产品、官网、后台、用户端、移动端、开放 API 或共享包。
- 不同团队或不同 AI 并行处理不同子系统，且各自发布节奏不同。
- 发布某个子项目时，频繁需要 stash、排除或绕开其他子项目的未完成改动。
- 同一仓库里存在多个 `VERSION`、多个 changelog、多个 tag 前缀或多个部署脚本。
- 一个子项目已经能独立构建、独立部署、独立回滚，但仍被其他子项目的工作区状态阻塞。
- 项目负责人提出“代码会不会打架”“是不是应该分仓库”“多团队怎么协作”这类问题。

不适用或只需轻量参考的情况：

- 单人早期原型、一次性验证项目、还没有正式发布流程的小工具。
- 同一应用内部的普通模块拆分，例如设置页、列表页、详情页。
- 只是代码目录命名混乱，但发布、团队和版本仍然是同一个单元。

## 2. 核心概念

**产品序列**：同一业务方向下的一组产品或子产品。产品序列可以共享品牌、用户体系、战略路线和部分技术标准，但不一定共享代码仓库。

**仓库边界**：一个 Git 仓库承载的代码、文档、版本和发布职责范围。仓库边界应服务协作和发布，而不是只按业务想象或目录习惯划分。

**发布单元**：可以被独立构建、部署、回滚、打版本和写 changelog 的系统或服务。发布单元可以在 monorepo 内，也可以是独立仓库。

**接口契约**：发布单元之间的 API、事件、SDK、数据库只读视图或文件交换协议。拆仓库后，接口契约必须显式化，不能依赖“同仓顺手改”。

**权威工作目录**：项目负责人确认的日常项目入口。分支、worktree、clone、迁移暂存区和构建目录可以有多个，
但同一发布单元只能有一个被称为当前代码、当前台账和正式交付来源的权威工作目录。

**公开模型**：项目事实进入外部可见范围的方式。至少区分仅私有、原生公开开发，以及私有权威通过受控晋级生成公开投影。第三种模型中的公开仓不是第二个可独立编辑的源码 owner；外部贡献先导入私有权威，再由同一晋级链重新投影。

## 2.1 分层治理策略

不同项目不应套同一强度的仓库治理。先按复杂度分层，再决定目录、分支、发布和拆仓策略。

| 层级 | 典型形态 | 推荐策略 |
| --- | --- | --- |
| L0 单体小项目 | 单应用、单人或早期验证、无正式发布 | 一个仓库即可；README 写清启动、测试和数据不进 Git |
| L1 单产品多目录 | 官网、前端、后端在同一产品内，统一发布 | 可 monorepo；一个 VERSION/changelog 或按服务补充说明 |
| L2 单产品多发布单元 | 官网、用户端、后台、后端可独立构建/部署 | monorepo 可接受，但必须有发布单元登记表、路径边界、独立 VERSION/changelog/tag |
| L3 多子产品共享平台 | 多个平级产品共享账号、登录、支付、后台或数据底座 | 先明确发布单元和数据边界，再按团队、权限、发布阻塞、共享代码与 CI 能力选择 monorepo 或 multi-repo；共享能力通过显式契约治理 |
| L4 多团队/多 AI 高并发 | 不同团队、供应商或多个 AI 长期并行，发布节奏明显不同 | 应拆 multi-repo 或至少使用强路径门禁、CODEOWNERS、CI 路径过滤和独立发布流水线 |

升级信号：

- 一个发布单元的未完成代码反复阻塞另一个发布单元上线。
- 发布时经常需要临时排除目录、stash 或人工解释“这块不要带上”。
- 不同发布单元已经有各自版本号、changelog、tag 或部署脚本。
- 同一个登录/账号/支付底座服务多个平级产品，但产品账本、余额、订单、成本或统计口径必须分开。

降级信号：

- 项目还没有真实发布用户。
- 只有单人维护且发布总是整体发布。
- 所谓子项目只是同一应用内部页面，不能独立部署或回滚。

## 2.2 公开贡献回流私有权威

采用“私有权威 → 脱敏公开投影”的项目，公开 Pull Request 是入站候选，不是第二源码 owner。维护者按以下链路接收：

1. 冻结 PR 的公开基线 commit、贡献 head、文件清单和来源链接；公开 CI 只验证公开面，不持有私有仓凭据。
2. 从公开基线计算语义差异，只把公开白名单路径导入新的内部 Change Unit；投影标记、内部路径、未知路径或敏感内容 fail closed。禁止把公开 `main` 直接 pull／merge 到私有主线。
3. 在内部 owner 解决冲突，完成产品／工程裁决、隐私检查和匹配验证，再形成内部 commit。
4. 从内部 commit 重新生成空暂存面的公开投影，对比其结果是否保留贡献意图；保留作者归属和 PR 链接。
5. 只有取得公开更新授权后才提交公开候选，并用最终公开 commit 回写／关闭 PR；接收贡献、内部合并和公开发布分别登记。

本地后续修改仍只进入私有权威，再走同一投影链。若外部贡献长期成为主要开发方式，应另行评估“公开源码为权威、私有仓只保存内部治理／发布覆盖”的架构迁移；两种模型不得混用。

## 3. Monorepo 与 Multi-repo 的适用条件

### 3.1 适合继续使用 monorepo 的条件

满足多数条件时，可以继续用一个仓库：

- 子系统由同一团队维护，发布节奏接近。
- 有强 CI/CD 能力，可以按路径只测试、只构建、只发布受影响单元。
- 有 CODEOWNERS、分支保护、路径级评审和明确的发布脚本边界。
- 共享代码很多，且共享包变化需要同步验证多个应用。
- 统一版本或统一发布对业务是合理的。
- 团队有能力维护 changeset、workspace、包版本和依赖影响分析。

如果没有这些能力，monorepo 会从“统一管理”变成“互相阻塞”。

### 3.2 适合拆成 multi-repo 的条件

满足多数条件时，应优先考虑独立仓库：

- 子系统有独立团队或合作团队。
- 子系统有独立产品定位、独立路线图或独立客户入口。
- 子系统可以独立构建、部署、回滚。
- 子系统需要自己的版本号、changelog、发布制品和验收清单。
- 子系统之间主要通过 API 或文件协议协作，而不是频繁共享内部源码。
- 发布一个子系统时经常被另一个子系统的未完成改动阻塞。
- 项目负责人需要给不同团队分配不同权限、不同节奏和不同责任边界。

Multi-repo 的代价是接口契约、共享包、跨仓发布和文档索引要更认真；它不是免费变清爽。

## 4. 独立发布单元判断

判断一个子系统是否应成为独立发布单元，至少检查：

- 是否有独立用户入口或服务职责？
- 是否能独立构建？
- 是否能独立部署？
- 是否能独立回滚？
- 是否需要独立版本号和 changelog？
- 是否有独立负责人或团队？
- 是否有独立测试和线上验证路径？
- 是否有独立故障影响范围？

多数为“是”时，应作为独立发布单元。是否进一步拆成独立仓库，取决于团队协作、权限、发布阻塞和共享代码成本。

不要伪造独立发布单元：如果一个模块无法独立部署、无法独立回滚，只是同一应用内部页面，就归入所属应用版本。

## 4.1 发布单元登记表

多产品或多发布单元项目必须维护 `governance/REPOSITORY_AND_RELEASE_UNITS.md`（Repository and Release Unit Register）或项目已登记的等价权威文件。没有登记表时，AI 不应直接判断“顺手一起发”。

模板：

```markdown
| 发布单元 | 产品/子产品 | 代码路径或仓库 | 入口/服务 | 版本文件 | Changelog | tag 前缀 | 构建命令 | 部署/重启范围 | 共享依赖 | 不得混入 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| website | 示例产品官网 | projects/website/ | / | VERSION | CHANGELOG.md | website-v | npm run build | website 服务 | 主题 token、公开 API | app/admin/backend 未完成代码 |
| app | 示例产品用户端 | projects/app/ | /app/ | VERSION | CHANGELOG.md | app-v | npm run build | app frontend | 认证 API、业务 API | website/admin 草稿 |
| admin | 统一后台 | projects/admin/ | /admin/ | VERSION | CHANGELOG.md | admin-v | npm run build | admin frontend | 认证、权限、后台 API | 官网 SEO、用户端实验 |
| backend | 平台后端 | projects/backend/ | /api/ | VERSION | CHANGELOG.md | backend-v | test/build command | backend 服务 | 数据库、队列、支付 | 前端纯样式改动 |
```

登记表必须回答：

- 哪些发布单元共享登录、账号、支付、数据库或后端 API。
- 哪些数据必须按产品分账、分余额、分订单、分消耗、分成本或分统计口径。
- 哪些发布单元可以独立发布，哪些必须联动发布。
- 某个发布单元变更时，默认不涉及哪些路径和服务。

## 5. 仓库拆分触发门禁

出现以下信号时，AI 或研发人员不得只靠 stash、临时排除或口头约定继续推进，应先提示项目负责人做仓库边界评估：

- 同一工作区同时存在多个团队的未完成改动。
- 发布脚本必须临时忽略无关子项目才能上线。
- 同一个 tag 或版本号难以说明到底发布了哪个子系统。
- 一个子系统的 hotfix 被另一个子系统未完成需求阻塞。
- 多个 AI 反复在不同子项目之间切换，导致工作日志、版本号和发布记录混杂。
- 项目负责人多次反馈“代码打架”“怎么又提到另一个子项目”“不同团队节奏不一样”。

这些信号说明问题不只是个人操作失误，而是仓库边界、发布单元或脚本门禁需要升级。

## 6. 迁移策略

仓库拆分应分阶段执行，避免“大爆炸”迁移。

推荐顺序：

1. 先拆低耦合、低风险、独立入口清晰的子项目，例如官网、文档站、独立静态前端。
2. 再拆独立前端但共享后端 API 的子项目，例如后台管理系统前端。
3. 再拆核心业务平台或后端服务。
4. 最后处理共享包、SDK、类型、设计 token 和公共脚本。

不要在第一阶段就抽象大型 shared 包。短期允许少量重复，等边界稳定后再抽公共能力。

## 7. 拆分前检查清单

拆分前必须确认：

- 拆分目标：拆哪个子项目，为什么拆。
- 当前归属：它现在属于哪个产品、哪个发布单元、哪个负责人。
- 目标仓库名、README、VERSION、CHANGELOG、部署文档和测试说明。
- 是否保留 Git 历史；如保留，使用 `git filter-repo`、`git subtree split` 或等价方案。
- 是否存在跨目录 import、相对路径引用、共享脚本或共享配置。
- 环境变量和密钥归属是否明确。
- 数据库、存储、上传文件、支付、权限、登录态是否跨系统共享。
- 发布脚本、制品名、镜像 tag、回滚方式是否准备好。
- 迁移冻结窗口：拆分期间哪些分支或目录暂停开发。
- 回滚方案：拆分失败时如何回到原仓库结构。

## 8. 拆分后验收清单

拆分后必须验证：

- 新仓库能独立安装依赖、构建、测试和启动。
- 新仓库有自己的 README、VERSION、CHANGELOG 和部署说明。
- 原仓库不再保留重复活跃代码，或明确标记为归档/迁移期只读。
- 线上发布和回滚命令能指向新仓库制品。
- CI/CD 或手工发布流程不会误发其他仓库内容。
- 接口契约已经写入文档，并有兼容策略。
- 相关团队知道新仓库地址、分支策略和发布规则。
- 项目级文档索引已经更新。

## 8.1 拆仓治理迁移包

拆仓不是只迁移源码。只移动代码但不迁移治理资料，会导致后续发布继续依赖旧仓库、旧脚本、旧 tag 或聊天上下文。

每个正式发布单元拆出后，必须同步收口一组“治理迁移包”：

- 仓库 README：说明当前仓库定位、启动方式、文档入口和不属于本仓库的范围。
- `VERSION` 与 changelog：延续真实产品版本线，不能为了迁移随意另起 `0.1.x`，除非明确是未上线原型。
- tag 规则：新 tag 前缀、旧 tag 使用规则、是否保留历史 tag。
- 部署文档：构建命令、制品名、部署命令、健康检查、回滚方式。
- 测试文档：本仓库独立 preflight、真实流程验收和未验证风险。
- 工作日志：迁移做了什么、验证了什么、哪些旧路径不再使用、下一步是什么。
- 发布单元登记表：代码路径或仓库、线上入口、版本文件、changelog、tag 前缀、构建命令、部署范围、共享依赖和不得混入范围。
- 归档说明：旧仓库、旧脚本、迁移快照和临时目录放在哪里，是否只读。

拆分后应做一次真实或演练发布，至少验证目标发布单元可以从新仓库独立构建、打包、部署或启动。若只是目录迁移成功但没有验证发布链路，不应宣布仓库治理完成。

## 9. 接口契约要求

拆仓库后，跨发布单元协作必须使用显式契约：

- HTTP API 建议维护 OpenAPI、接口表或等价文档。
- SDK 或共享包必须有版本号、changelog 和兼容说明。
- 事件、消息、异步任务和文件交换必须写清字段、状态、重试和失败处理。
- 不允许前端仓库直接依赖另一个后端仓库的内部源码。
- 不允许多个服务随意写同一张核心业务表；如确需共享数据库，必须写清读写边界。

接口契约变更应先判断兼容性：

- 向后兼容：可随发布单元正常版本发布。
- 破坏性变更：必须有迁移计划、双写/双读或灰度策略。
- 涉及支付、权限、账户、余额、订单、用户数据：按高治理等级处理。

## 10. 多团队和多 AI 协作规则

多团队或多 AI 并行时：

- 每个任务必须声明目标仓库、目标发布单元、允许修改路径和不涉及范围。
- 发布前必须检查是否有其他发布单元的未完成改动混入。
- 不同发布单元的版本号、tag、changelog 和工作日志不能混写。
- 如果必须临时在同仓内协作，优先使用分支、worktree 或明确路径范围，而不是长期依赖 stash。
- 任务开始必须声明权威项目根；外部 worktree 只承担隔离开发，不自动获得项目根、台账或交付权威。
- 拆仓、迁移或主线替换完成时，旧目录要么成为明确只读归档，要么停止作为活动入口；同一发布单元不得长期保留两个“当前项目目录”。
- AI 发现无关子项目、分支、worktree 或 POC 改动时，应保留并隔离，不得擅自回滚、强制提交主线或自动纳入
  当前版本；只有候选可达性、本次范围或共享生产资源证明存在影响时才阻断发布。

任务边界统一写入项目声明的 Durable Task State Owner；采用 BuildOS 新项目默认实例时使用 `governance/tasks/TASK-<NNNN>-<slug>.md`。下列字段是交付领域必须补齐的部分：

```markdown
### 本次任务边界
- 目标产品/子产品：
- 目标仓库或目录：
- 目标发布单元：
- 允许修改路径：
- 明确不涉及：
- 共享依赖或接口：
- 是否需要联动发布：
- 如果发现其他发布单元改动：停止并先报告，不纳入本次提交/发布。
```

发布前阻断规则：

- `git diff --name-only` 或 PR 文件列表出现不在允许路径内的文件时，必须停止发布并解释来源。
- 目标发布单元的 `VERSION`、changelog、tag 前缀、构建命令和部署服务必须一致。
- 如果本次只发布某个前端或官网，不得顺手重启后端、数据库或其他前端，除非任务边界明确包含。
- 如果共享登录、账号、支付、权限或数据库 schema 被修改，治理等级升级，必须重新确认影响的所有发布单元。
- 如果代码、台账、制品或发布脚本仍分别指向不同工作目录，必须停止发布，先按 `代码管理与合并规范.md` 完成权威工作目录收口。
- 私有权威到公开投影的项目必须从空暂存面按公开白名单生成候选，扫描路径、身份、密钥和内部 owner，并把批准绑定候选身份；不得把内部 Git 根整体归档后再依赖黑名单补删。

## 11. 项目文档落地

本规范进入具体项目后，至少应沉淀为项目内文档：

```text
governance/REPOSITORY_AND_RELEASE_UNITS.md
```

项目文档应包含：

- 当前产品序列和子产品关系。
- 发布单元登记表。
- 当前仓库和目标仓库列表。
- 每个发布单元的负责人、版本号、tag 前缀、部署命令和回滚方式。
- 跨发布单元接口契约位置。
- 迁移阶段计划和冻结窗口。

## 12. 与其他规范的分工

- `项目目录与文档规范.md` 负责说明目录怎么组织、每类文档放在哪里。
- `版本制品与发布规范.md` 负责说明版本号、tag、制品、部署和回滚怎么管理。
- `代码管理与合并规范.md` 负责说明分支、合并、评审和未发布改动边界。
- 本规范负责判断仓库边界、发布单元边界，以及单仓迁移多仓的治理流程。

如果只是目录不清楚，先读项目目录规范；如果已经出现团队、发布、版本和工作区互相阻塞，则必须读本规范。
