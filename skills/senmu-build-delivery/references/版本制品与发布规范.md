# 版本制品与发布规范

本规范面向需要版本化或正式交付的工程项目，规定版本号、基线、tag、代码包、制品包、Docker 交付、资源保留和技术路线演进规则。

1. 发布总规则与 Hotfix；1.1 版本时间线；1.2 继任版本线；2. 版本基线；3. 版本号；4. Tag；5. 代码包；6. 制品包；7. 部署、发布单元与收口；8. 技术路线演进。

## 1. 版本与发布总规则

版本治理分三层，不能相互推导授权：

- 本地 Git：commit、分支、VERSION、changelog、本地正式 Tag 和恢复依据；项目采用 Git 时可独立形成完整版本线。
- Remote Git：push／fetch、远程分支和 Tag、PR／MR、CI；只有已配置且用户授权对应同步动作时启用。
- 托管平台或部署：GitHub／GitLab Release、制品上传、服务器或其他目标环境；只按项目既有能力和本次发布授权执行。

没有 Remote 或平台 Release 不构成版本治理缺陷；不得因为项目使用 Git 就创建远程仓库、推送或选择 GitHub／GitLab。

正式项目默认使用语义化版本：

```text
major.minor.patch
```

规则：

- `major`：架构、核心业务模型、数据模型或兼容性重大变化。
- `minor`：新增或调整用户可感知功能、流程、业务规则。
- `patch`：Bug、样式、文案、部署脚本、非破坏性技术调整。

每个正式发布单元应维护：

```text
VERSION
CHANGELOG.md
```

如果项目有普通用户和内部维护者，建议区分：

- 内部 changelog：记录具体实现、接口、数据库、部署、测试、风险、回滚点。
- 用户 changelog：只写用户可理解的新功能、体验优化和笼统修复，不暴露内部实现、安全、密钥、成本和未公开计划。

正式版本、公开源码、部署和独立制品是可组合但互不推导的交付能力。源码型插件可以只有公开仓库、版本、Tag 和 Marketplace 安装；托管服务可以有部署事实但没有用户下载包；容器、桌面应用或包管理器项目才按真实输出启用镜像、DMG／PKG、binary 或 package 的身份、保留和回滚。GitHub 自动生成的源码快照默认不是项目管理的独立制品；只有项目主动构建、签名、发布并由消费者安装或回滚依赖时才进入制品生命周期。

发布流程是阶段模型，不是一次授权的默认动作清单。收到明确发布命令的当前执行者承担这一次收口，从持久任务、Git、版本和日志恢复范围；职责不绑定固定 Agent 身份：

1. 确认版本范围。
2. 更新必要文档。
3. 完成代码。
4. 运行测试。
5. 更新 VERSION 和 changelog。
6. 合并到发布基线。
7. 锁定候选并按需构建制品。
8. 候选包含 Skill、Hook、路由或行为契约变化时，核对当前 Skill 完整性复审记录与冻结表面一致，结论可放行且没有未关闭阻断 Finding；自动结构校验不能替代该复审。
9. 取得明确发布授权后按项目预选语义执行：Tag 表示“不可变候选来源”时先创建；Tag 表示“已验证发布”时等待目标验证成功后创建。
10. 通过项目唯一发布入口执行本次获准层级；只有 Remote／托管平台存在且授权覆盖时才推送 commit／Tag、创建平台 Release 或上传制品。
11. 存在部署目标时，按授权部署并从目标环境完成生产事实验证；纯本地代码／制品发布写明部署与线上验证不适用，并核对本地产物身份。
12. 按预选语义创建、推送或核对不可变正式 Tag，追加 Release Record；失败、部分完成、未推送或回滚也必须记录，Tag 本身不改变实际状态。

详细状态、授权和生产事实判定按[发布授权与生产事实协议](发布授权与生产事实协议.md)执行。用户只要求开发、候选或预检时，流程不得越过 `preflight_passed`。

## Bug/Hotfix 发布门禁

临时 Bug 修复、线上 Hotfix、回归修复和用户临时要求的“小修”默认都属于发布治理范围。不能只完成代码和本地验证就宣布结束。

修复前必须确认：

- 受影响的正式发布单元和版本归属。
- 最新正式 tag、当前 `VERSION`、线上版本和上一个稳定回滚点。
- 是否需要先创建回滚辅助 tag 或备份。
- 当前工作区是否有未发布改动，是否会混入本次修复。

修复后如果要发布，必须完成：

- 提升对应发布单元的 patch 版本。
- 更新内部 changelog；用户可见变化同步用户 changelog 或公开发布说明。
- 从正确发布基线构建制品，制品版本、镜像 tag、Git tag 和 `VERSION` 保持一致。
- 线上验证健康检查、版本号和本次修复路径。
- 记录发布 commit、tag、制品、部署服务、回滚点和未发布改动。

如果修复暂不发布，必须在工作日志或任务系统中写明“不发布”的原因、当前代码位置、验证结果、风险、后续发布条件和本地/远程同步状态。不得留下无法判断是否已经上线的 Bug 修复。

## 1.1 版本时间线和迭代规划

项目应维护一条清晰的版本时间线，让后续 AI 知道当前版本做了什么、下个版本准备做什么、哪些任务尚未收口。

推荐维护：

```text
product/ITERATION_PLAN.md
governance/logs/WORKLOG.md
projects/<app-or-service>/CHANGELOG.md
```

当需求过大，需要拆成 2-3 期时，必须写入版本迭代规划：

- 当前版本纳入什么。
- 下个版本计划什么。
- 哪些需求延期。
- 延期原因。
- 风险和依赖。
- 验收标准。

如果 AI 建议拆期，不能只在聊天里说；必须把拆期结果写入迭代规划或等价文档。

## 1.2 继任版本线与主线替换

当前正式版本继续维护、下一代大版本并行开发时，版本关系必须区分为“当前正式线”和“继任版本线”。继任版本线的目标是通过验证后晋升为新的主线，不是长期复制一个独立项目。

- 当前正式线继续提供线上修复和回滚能力。
- 继任版本线使用开发版本号，例如 `2.0.0-dev`，并保存其创建基线。
- 当前线修复应按适用性前向传播到继任线，避免主线替换后缺陷回归。传播责任与立即执行分离：重大风险立即处理，一般修复在登记的检查点批量处理，低风险项最迟在 RC／候选冻结或主线晋升前清零；具体状态与验证按代码管理规范执行。
- 主线替换必须同时收口需求范围、迁移、兼容性、测试、版本号、changelog、制品、部署、生产验证和回滚点。
- 分支合入 `main` 只是代码晋升；只有版本和生产事实一致后，才能宣布下一代版本已经替换当前主线。
- 替换完成后停止把旧线和继任线都称为“当前”，并按保留策略清理旁路分支与临时 worktree。

具体分支、同目录切换和可选 worktree 规则按[代码管理与合并规范](代码管理与合并规范.md)执行。

## 2. 版本基线管理

项目必须明确“基线”是什么。常见基线包括：

- 需求基线：当前版本承诺实现的需求范围。
- 技术基线：当前版本采用的架构、技术栈、数据库、部署方式和关键第三方服务。
- 代码基线：当前可继续开发或可发布的 Git 分支，例如 `develop` 或 `main`。
- 发布基线：当前线上正式运行版本对应的 commit、tag、VERSION 和 changelog。
- 回滚基线：上一个可回滚的稳定版本。

每个正式发布版本必须能回答：

- 这个版本从哪个需求范围开始？
- 修改了哪些需求或技术方案？
- 对应哪个 Git commit？
- 对应哪个 tag？
- 对应哪个 VERSION？
- 对应哪段 changelog？
- 构建出了哪些制品？
- 部署到了哪个环境？
- 线上验证结果是什么？
- 可回滚到哪个版本？

## 3. 版本号约定

默认采用语义化版本：

```text
major.minor.patch
```

开发中版本可以带后缀：

```text
1.4.0-dev
1.4.0-beta.1
1.4.0-rc.1
```

正式发布版本不应保留 `-dev` 后缀。

多产品或多发布单元项目，应分别维护版本号。例如：

```text
website  -> website-v1.2.0-20260613
app      -> app-v1.5.1-20260613
admin    -> admin-v1.1.0-20260613
backend  -> backend-v2.0.0-20260613
```

是否拆分版本号取决于发布单元是否可以独立构建、独立部署、独立回滚。如果不能独立发布，就不要伪造独立版本。

## 4. Tag 规则

正式发布必须创建不可变 Git Tag。单发布单元优先使用 SemVer 友好的格式，多发布单元再增加 scope；日期只在项目既有规则需要时追加：

```text
v<major>.<minor>.<patch>
<scope>-v<major>.<minor>.<patch>
```

示例：

```text
v1.2.0
website-v1.3.1
backend-v2.0.0
```

规则：

- 多发布单元项目，每个正式发布单元使用自己的 tag 前缀。
- 正式版本优先使用 annotated tag；项目已有签名、格式或发布工具约定时沿用现状。
- tag 必须指向锁定的发布 commit；它表示候选来源还是已验证发布由项目预先声明，实际结果由 Release Record 判定。
- VERSION、changelog、镜像 tag、Git tag 应保持一致。
- 创建本地 Tag、推送远程 Tag 和创建平台 Release 是三个不同状态；后两者分别要求 Remote／平台存在及明确授权。
- 没有 Remote 时，本地 Tag 与版本记录仍构成有效本地版本线；记录 `remote=not_configured`，不擅自补建远程。
- 不能从不包含最新 tag 变更的旧分支直接发布，除非明确做回滚。
- 如需回滚，优先使用经过验证的不可变制品；需要从 Tag 重建时必须证明工具链、依赖和构建输入仍可复现，不把“有 Tag”误当成“已有可立即回滚制品”。

## 5. 代码包管理

代码包指 Git 仓库中的源码、配置模板、脚本、文档和测试。代码包管理原则：

- Git 是代码包的唯一可信来源。
- 代码包不包含真实密钥、证书、上传文件、数据库、运行缓存和生产数据。
- 每次正式发布必须对应一个 Git tag。
- tag 指向的 commit 必须包含对应版本的 `VERSION` 和 changelog。
- 发布后如果发现线上版本和 tag 不一致，必须先停止继续发布，查清来源。

代码包必须包含：

- 源码。
- 文档。
- 构建脚本或构建说明。
- 部署脚本或部署说明。
- 测试脚本或测试说明。
- 配置模板，例如 `.env.example`、`deploy.env.example`。

代码包不得包含：

- `.env`、`.env.*` 真实环境文件。
- 服务器私钥、证书私钥、支付私钥。
- 用户上传文件和生产数据库。
- 本地构建产物、临时包、缓存、日志。

## 6. 制品包管理

制品包指由代码构建出来、用于部署的包，例如：

- Docker 镜像。
- Docker 镜像 tar 包。
- 前端静态构建产物。
- 后端 wheel/jar/binary。
- 压缩发布包。

制品包管理原则：

- 制品来自明确的 Git commit 和 tag。
- 制品版本必须与 `VERSION`、changelog 和 Git tag 对齐。
- 制品包命名必须包含项目、服务、版本、平台和构建时间或 commit。
- 制品只用于发布、部署和短期回滚，不作为长期历史备份。
- 长期可追溯依据是 Git commit、tag、VERSION、changelog 和发布记录。

推荐命名：

```text
<project>-<service>_<version>_<platform>_<yyyymmddHHMM>.tar
<project>-<service>:<version>
```

示例：

```text
crm-frontend_1.4.2_linux-amd64_202606131430.tar
crm-backend:1.4.2
```

制品保留策略：

- BuildOS 默认在本机构建端和生产运行端保留当前已验证版本及一个已验证可回滚版本；“上一个”指最近可用回滚点，不机械等于版本号相邻。
- 用户或项目已明确保留数量、稳定观察期、合规期限、成本边界或 Pin 时，以记录后的项目策略为准。策略减少到无法快速回滚、违反合规或破坏必要证据时，先说明风险并取得相应确认；高风险迁移、灰度、跨大版本或不可逆数据变化可以临时扩大保留集合，并登记退出条件。
- 发布新版本后清理更早的 tar、旧镜像和临时上传文件；只有能精确归属本发布单元时才处理 dangling 镜像。
- Git commit／Tag 只证明源码身份，不单独保证未来可以生成相同制品。更早版本只有在基础镜像 digest、依赖锁、构建工具、平台、外部输入和 provenance 仍可获得时才可声明能重建；否则依赖受控制品库、归档或项目明确接受的恢复等级。

该策略必须进入发布单元唯一部署入口，不依赖操作者或 Agent 临场记忆。BuildOS release 档位提供 `operations/scripts/cleanup-release-assets.sh` 和 `operations/release-retention.env`：项目校准后只允许清理配置声明的制品根和受管镜像仓库，先确认当前／上一版本真实存在，再保留容器引用和显式 Pin，最后精确移除更早对象。

执行顺序固定为：目标环境部署与生产验证通过 → 生产运行端项目级收口 → 本机构建端项目级收口 → 按项目策略执行远程镜像／制品库生命周期 → 收口本次纳入的临时 Git 执行面 → 记录保留集合和结果。`dry-run` 不构成正式收口；apply 需要部署入口在本次发布授权和生产验证成立后显式传入 `RELEASE_CLOSEOUT_AUTHORIZED=1`。任一应执行的收口失败时不得把发布描述为完整结束。

三个资源面必须分别判定，不能以其中一个完成代替其他两个：

- **本机构建端**：开发机、CI runner 或受管构建主机上的版本目录、镜像、tar 和临时上传物；不要求每个开发者机器都成为正式制品库。
- **生产运行端**：目标主机／节点上的受管镜像、发布目录和临时传输物；当前运行对象和回滚对象先按 digest／ID 核对。
- **远程镜像／制品库**：只有项目实际使用且发布授权覆盖时，才按仓库原生生命周期策略或项目脚本处理；不可变 release tag、digest、签名、证明材料和跨环境引用必须纳入保留判断，不能把本地主机清理当成远程仓库已清理。

Git 执行面不由镜像清理脚本删除。发布者按[代码管理与合并规范](代码管理与合并规范.md)确认本次纳入的短分支和临时 worktree 已合并、目标验证通过且没有独有事实后安全清理；并行排除项保持非发布入口，并登记 owner 与退出条件，不为了本次发布强制归零。

以下内容不属于自动制品清理：Git commit／正式 Tag／Changelog／Release Record、数据库与 Volume、其他项目镜像、全局 dangling 镜像和全局 Builder Cache。跨大版本或合规保留使用完整身份 Pin，并记录理由、批准者和退出条件；不能以“以后可能有用”无限期保留。

## 7. Docker 部署建议

大项目、正式 Web 项目、SaaS、后台系统和包含多个服务的项目，优先建议 Docker 化部署。

适合 Docker 的场景：

- 前后端分离。
- 后端依赖较多。
- 需要数据库、缓存、队列、对象存储网关等多个服务。

### 7.1 Docker 目标平台门禁

Docker 镜像构建成功不等于能在生产服务器运行。开发机和生产服务器可能是不同 CPU 架构，例如本地 Apple Silicon 默认构建 `linux/arm64`，而常见云服务器是 `linux/amd64`。

正式发布 Docker 制品时必须明确目标运行平台：

- 构建脚本应支持 `DOCKER_PLATFORM` 或等价参数，并为生产环境设置默认目标平台。
- 手工构建生产镜像时应显式使用 `docker build --platform <os/arch>` 或 buildx 等等价能力。
- 制品目录、manifest 或发布记录应写明目标平台，例如 `linux/amd64`。
- 镜像 tar 命名不应只写 `linux-amd64`，还必须确保实际镜像架构与命名一致。
- 发布后应在服务器侧执行 `docker image inspect` 或等价命令，确认实际镜像 `Architecture/Os` 与服务器匹配。

如果发现目标平台不匹配，应停止发布，重新构建正确平台制品，不要依赖容器运行时“可能兼容”。
- 本地、测试、生产环境需要一致。
- 多个 AI 或多人协作，需要降低环境差异。
- 现场服务器资源可控，需要明确镜像、容器、日志和数据目录。

Docker 交付建议：

- 本地或 CI 构建镜像，不建议长期在低配生产服务器现场构建。
- 镜像 tag 使用版本号，例如 `<service>:1.4.2`。
- Compose 或部署配置中引用明确镜像 tag，不使用不确定的 `latest` 做正式发布。
- 数据库、上传文件、配置和密钥挂载到受控数据目录，不打进镜像。
- 发布时只重启受影响服务，不无故重启数据库。
- 发布完成后通过项目唯一收口入口分别处理运行端、本机构建端和按需远程制品库；主机脚本只清理该主机的受管旧镜像、旧制品目录和临时 tar，不执行跨项目全局 prune。

Docker 项目至少要说明：

- 每个服务的镜像名。
- 每个服务的版本 tag。
- 构建命令。
- 部署命令。
- 数据卷和持久化目录。
- 环境变量来源。
- 日志位置。
- 健康检查。
- 镜像和制品保留数量。
- 回滚步骤。

## 7.1 独立部署单元和制品归属

如果某个子项目可以单独部署，就必须有自己的制品归属：

- 独立 Docker 镜像。
- 独立镜像 tag。
- 独立构建命令。
- 独立部署命令。
- 独立健康检查。
- 独立回滚说明。

示例：

```text
website:
  image: company-website:1.3.0
  artifact: company-website_1.3.0_linux-amd64.tar

app-frontend:
  image: company-app-frontend:2.1.0
  artifact: company-app-frontend_2.1.0_linux-amd64.tar

app-backend:
  image: company-app-backend:2.1.0
  artifact: company-app-backend_2.1.0_linux-amd64.tar
```

不要把多个独立服务混成一个模糊的“代码包”或“部署包”。层级不清会导致迁移、回滚、排障和多 AI 协作都变困难。

## 7.2 上线前分支和待办收口

每次上线前，必须检查历史分支和待处理事项：

- 当前发布分支是否包含最新集成基线。
- 本次发布范围内的功能分支是否都已合并。
- 是否还有本次发布已承诺但未合并的分支／提交；同一发布单元的其他分支必须分类为后续版本或非阻塞并行工作，不能因“已完成”自动纳入。
- 工作日志里是否有未验证项。
- 迭代规划里是否有本版本必须完成但尚未完成的事项。
- changelog 是否覆盖本次用户可见变化。
- 部署文档是否覆盖本次制品和服务变化。

如果发现未收口项，不能直接上线。必须说明：

- 是阻塞发布，还是延期到后续版本。
- 延期原因是什么。
- 后续版本或工作日志中如何记录。

上线核对清单应写入部署文档或发布说明。

## 7.3 发布源目录收口

正式制品只能从发布单元登记的权威工作目录和发布基线构建。分支或 worktree 中“已经做完”不等于
发布源已经更新；在权威目录完成集成、运行资产迁移、台账同步和完整验证之前，不得上传、部署、
交付或打正式完成结论。

发布门禁围绕冻结的候选 commit、明确纳入范围及共享生产资源计算，不围绕整个仓库是否“全部安静”计算。
排除在候选之外且不修改共享生产资源的 POC、分支和 worktree 可以继续运行；它们应登记为非发布入口，
不得被迫提交到主线、提前结束或自动并入当前版本。若需要同时发布，先形成新的范围决定和候选 commit。

发布记录必须同时写明：权威项目根、Git commit/tag、制品或交付固定路径、关键 SHA、台账/数据库
revision，本机构建端／生产运行端／远程仓库的保留结果，以及临时分支和 worktree 的清理或非权威保留状态。用户需要回退时，应依赖已验证回滚制品、tag／bundle、可复现构建证据、数据库备份和制品记录恢复，不通过长期并排保留 V1/V2 活动目录实现回退。

## 8. 技术路线变更的交付影响

技术路线本身由 `senmu-build-engineering` 决策；本节只负责其进入正式版本时的兼容、迁移、部署和回滚影响。每次演进必须有理由、有边界、有记录。

技术路线变化包括：

- 更换前端框架或组件库。
- 更换后端框架。
- 更换数据库。
- 引入 Docker、Kubernetes、Serverless 或云厂商平台。
- 引入缓存、队列、搜索、向量数据库。
- 引入新的第三方 AI、支付、短信、对象存储服务。

演进前必须说明：

- 为什么现有方案不够？
- 新方案解决什么问题？
- 迁移成本是什么？
- 对现有用户、数据、部署、测试有什么影响？
- 是否需要灰度、兼容或回滚？
- 文档、脚本、CI/CD、部署和监控是否同步更新？
