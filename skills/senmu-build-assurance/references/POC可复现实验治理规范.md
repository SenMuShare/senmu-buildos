# POC 可复现实验治理规范

本规范用于需要通过原型、模型对比、技术路线试验、性能测试、算法调参或用户体验对照来支持决策的POC。
目标是让POC像工程实验一样可质疑、可复核、可追加、可重做，而不是只留下“当时感觉这个更好”的聊天结论。

## 本页导航

1. 触发与等级；2. 门禁类型；3. 项目级存储契约；4. 实验结构；5. 立项字段；6. 逐轮追加；7. 人工盲测；8. 结论状态；9. 删除与复现；10. 治理记录边界；11. 最小模板。

## 1. 触发条件与治理等级

命中以下任一条件时使用本规范：

- POC将影响技术路线、模型、供应商、架构或生产参数选择；
- 需要两个以上方案做A/B、基准或消融实验；
- 产物较大、昂贵、敏感或会在实验后删除；
- 结论包含主观听感、画质、交互体验等人工判断；
- 实验时间长、依赖复杂，未来可能需要重跑；
- 项目负责人明确要求保留实验过程、思考和结论账本。

默认属于G2；影响生产关键路线、成本、安全、数据或正式发布时升至G3-G4。轻量探索不要求完整重流程，
但只要对外宣称比较结论，最小变量、输入和证据就不能缺失。

## 2. Hard Gate、Soft Gate与Guidance

### Hard Gate

- 最终结论不得只存在于聊天、临时README或某个AI上下文中。
- 声称A优于B前，必须记录共同基线、计划变量和意外变量；无法公平控制时必须披露。
- 删除唯一临时产物前，必须有稳定账本、结构化manifest和足以重建实验的复现协议。
- 失败运行、警告和反例不得因“不好看”而删除；更正用追加或替代关系，不静默改写历史。
- 人工评价未完成时必须标记待评价，不得把工程偏好伪装成负责人最终决策。
- POC结论与生产批准分离；生产化另走需求、架构、测试、版本、发布和回滚门禁。
- 付费模型、云资源、外部招募或不可逆写入必须在运行前获得对应成本与操作授权；批准实验设计不自动授权无限重跑。
- 涉及密钥、隐私、生物特征或未授权素材时，只记录受控来源和指纹，不把原件复制进通用账本。
- POC 稳定账本、运行资产和负责人可见路径必须位于负责人登记的项目级 `POC_ROOT`；该根属于项目权威
  边界，但不得因“权威”被推导为产品源码仓库的 `main` 工作树或正式发布目录。外部 worktree、clone、
  临时目录或个人缓存只能作为执行面，不能成为实验事实的唯一拥有者。
- 项目必须登记唯一 `POC_ROOT`、`tracking_mode`、保留/备份策略和校验命令。无法解析这些项目级事实时，
  状态型 POC 写入必须失败关闭，不能自行选择当前目录或另建第二套 POC 根。
- POC 与产品开发并行时，不得把进行中的实验账本写入发布工作树、产品迭代计划、正式业务台账或生产状态；
  需要 Git 保存小型记录时使用独立 POC 分支／仓库，直到负责人批准生产化才形成主线迁移提交。
- POC 校验必须验证物理归属，不能接受任意 `--root` 后只检查目录内部自洽。POC closeout 才扫描登记的
  执行面并阻断独有实验事实；无关产品发布不得要求仍在运行且已隔离的 POC 先提交、结束或归零。
- 已隔离 POC 收到跨任务发布或 Hotfix 通知时，默认只记录事实与建议时机，不暂停实验、重写 HEAD 或立即同步。只有当前用户明确指令、已登记检查点，或安全、数据损坏、共享生产资源冲突等有证据的重大风险才允许打断。

### Soft Gate

- 主观对比使用随机编号、固定环境和预先定义维度的盲测。
- 运行器自动输出manifest、计时、SHA、环境和参数，减少事后手填。
- 采用“一个问题一个实验、一个计划变量一个消融版本”；问题改变时开子实验。
- 重要结论至少跨第二输入、第二设备或第二次运行验证其外推性。

### Guidance

- 高频、大模型或媒体型 POC 默认优先采用“统一且 Git 忽略”的项目级 POC 根，使一个实验的方案、脚本、
  运行资产和结论物理聚合；是否备份由保留等级决定。
- 只有项目负责人明确要求用 Git 保存小型实验证据时，才采用“受控证据 + 忽略运行资产”的分离拓扑。
- 已验证的典型拓扑是：独立 POC 根整体 Git 忽略，每个实验自带账本、manifest、复现协议、输入、运行、证据和
  晋级说明；正式源码、业务台账、交付区和生产状态保持只读。这里只复用职责边界，不固定目录编号或名称。
- 目录名属于项目配置，不属于通用 Skill；不要把某个项目的固定目录名复制成跨项目标准。

## 3. 项目级存储契约

项目初始化或首次 POC 前，必须在项目 AI 入口、治理配置或等价权威文件中登记：

```yaml
project_authority_root: <负责人认定的项目总边界>
poc_root: <project_authority_root 内的唯一 POC 状态根>
tracking_mode: untracked | split
release_source_roots: [<可能并行发布的源码／交付根>]
retention_classes: [ephemeral, reproducible, retained]
backup_policy: <按保留等级定义的快照、备份或无备份策略>
validator: <非零退出的项目级校验命令>
```

`project_authority_root` 是负责人从项目入口登记的总边界，可以包含多个仓库、发布单元和一个独立 POC 区；
它不等于某个 Git 仓库的主工作树。`release_source_roots` 用于证明 POC 状态不会污染并行发布源。配置保存可搬迁
定位规则，不要求持久化某台机器的绝对路径。

- `untracked`：整个 `POC_ROOT` 不进入 Git；一个实验的全部事实位于同一实验目录。项目必须用 `.gitignore`
  和 `git ls-files` 反向检查证明没有误跟踪。
- `split`：只在独立 POC 分支、独立治理仓库或项目明确登记的非发布状态 owner 中跟踪小型账本、manifest、
  复现协议和必要源码；大文件位于唯一登记的忽略运行根。两边必须使用同一 `experiment_id` 并互相引用。
- 同一项目只能选择一种当前默认拓扑；例外实验必须逐项批准并登记，不能出现未登记的第三位置。
- `POC_ROOT` 必须位于负责人认可的 `project_authority_root` 内，且并行时不得位于正在发布的源码工作树。
  Codex 管理目录、外部 worktree、clone、
  `/tmp` 和个人缓存不得成为唯一或第二个长期活动 POC 根。
- `untracked` 不等于可随意丢失。每个实验必须声明 `retention_class`；`retained` 必须有经验证的项目外备份，
  `reproducible` 必须具备可重建输入与协议，`ephemeral` 也必须在删除前冻结结论和删除事实。

## 4. 实验结构

### 4.1 聚合实验包

```text
<POC_ROOT>/
  EXP-0001-<slug>/
    EXPERIMENT.md              # 决策问题、假设、边界和成功条件
    PLAN.md                    # 变量、样本、步骤和复现方法
    RESULTS.md                 # 逐轮运行、测量、评价和限制
    DECISION.md                # 采用、拒绝、继续或延期
    experiment-manifest.json  # 输入、环境、run 与输出引用
    scripts/                   # 必要的小型实验代码，按需创建
    evidence/                  # 小型、可审阅证据，按需创建
```

`untracked` 模式把以上记录、输入和运行资产聚合在同一实验目录；`split` 模式才把小型受控记录放入独立
POC Git owner。实验 ID 使用 `EXP-<NNNN>-<slug>`，只增不复用。进行中的实验不需要修改产品
只有负责人决定生产化后，才在目标版本 PRD 和项目任务 owner 中登记正式工程切片。

### 4.2 `split` 模式的独立运行根

```text
02-workspace/experiments/EXP-0001-<slug>/
  inputs/ engine/ models/ cache/ outputs/ reports/
```

大型输入、模型、数据库、缓存和输出不进入 Git。只有采用 `split` 时，才把等价运行根放在项目登记的忽略目录
或对象存储，并让小型记录 owner 与运行根通过同一 experiment ID、路径、版本和 SHA 互相引用；运行根不能
成为唯一历史，小型 Git 记录也不能伪装成完整输出归档。

### 4.3 结论晋级

- 验证成功：把结论晋级到正式需求、技术设计、ADR 或 Workflow Contract。
- 验证失败：保留问题、证据和拒绝理由，避免重复实验。
- 证据不足：记录继续实验的条件，不把阶段观察写成生产结论。
- POC 结论不自动批准生产化；生产化需要独立的正式范围、风险和交付授权。

这里的“独立”是职责和授权边界，不强制每次新建会话或 worktree。负责人批准产品化后，必须先形成晋级契约：源实验与结论、批准范围与非目标、正式需求／技术 owner、当前主线基线、接收或舍弃的 POC 变化、正式集成目标和验证／发布边界。原任务只有在新授权和范围明确时才可继续；否则建立新的持久任务入口。

晋级后不得让目录、分支、任务状态和用途相互矛盾，例如目录仍标记 `poc`、分支却已表示 `productization`。是否新建 worktree 仍由并行写入、环境隔离和收口成本决定；不新建时也必须正式重命名／重新登记执行面，并保留已冻结的 POC 结论。

## 5. 立项字段

开始前至少冻结：

1. `experiment_id`、负责人、执行者、日期和状态；
2. 决策问题、当前生产基线、可证伪假设和适用范围；
3. 成功/失败判据，机器指标与人工指标；
4. 样本、重复次数、方差／不确定性处理和停止条件；探索性实验可以轻量，但必须披露证据强度；
5. 对照组、变体矩阵、不变量、计划变量和已知不可控变量；
6. 输入来源、版本、SHA、授权与隐私边界；
7. 代码commit/diff、模型ID/revision、依赖、设备、随机种子和计时定义；
8. `project_authority_root`、`POC_ROOT`、`release_source_roots`、`tracking_mode`、`retention_class`、备份位置、删除条件和临时 scratch；
9. 谁有权得出最终结论，谁有权批准生产化。

如果真实执行偏离预注册矩阵，记录偏离原因；不要事后把它包装成原计划。

### 5.1 基线冻结粒度

基线按一轮运行或预先声明的检查点冻结，不是要求整个 POC 期间永不更新。上游普通样式、文案或低风险提交默认排队到下一检查点，不得每次通知都中断正在进行的运行。安全、数据完整性、核心契约或实验结论可比性受影响时，可在用户指令或登记触发下升级为立即更新。

更新基线时保留上一轮身份，记录新 commit／版本、触发原因、受影响变量和需要重跑的证据；不用无声 rebase 或覆盖让旧结果看起来仍来自同一基线。

## 6. 逐轮追加规则

每次运行都追加：

- 运行ID、父实验ID、开始/结束时间、执行者、命令和退出码；
- 为什么有这一轮，以及上一轮暴露的问题；
- 本轮唯一计划变量和所有意外差异；
- 输入、Prompt、参数、代码、模型、依赖、设备指纹；
- 原始测量、输出格式/时长/SHA、警告、失败和验证；
- “机器观察”“执行者解释”“负责人评价”三个不同层次；
- 下一轮假设或停止理由。

失败运行同样是证据。修正错误数据时保留原值、修正值、原因和日期，或追加新运行；不覆盖成仿佛错误从未发生。

不得因为中途结果有利就提前停止、只保留最佳样本、事后更换主要指标或删除不利变体。探索中新增假设可以继续测试，但必须标为 post hoc，并用新实验或独立数据验证后再作为正式结论。

## 7. 人工盲测

主观质量至少记录：候选随机编号、评价维度、评分尺度、评价人、日期、设备/环境、时间码或操作步骤、
原始意见和总体选择。先评价再揭盲，避免实现说明诱导听感或观感。

性能指标不能代替质量偏好；主观偏好也不能绕过安全、语义完整性、错误率、成本或兼容性门禁。

### 7.1 Agent、Prompt、Skill 与 Hook 对照实验

比较 Agent 行为、Prompt、Skill、Hook 或插件效果时，额外执行以下门禁：

- 对照组与实验组使用独立配置根和干净会话，隔离全局 `AGENTS.md`、个人 Skill、插件、Hook、缓存、历史摘要和未声明环境变量；不得让实验能力意外进入基线组。
- 开始正式计分前运行最小探针，证明两组实际加载内容、事件输出和目标行为确实不同；发现污染后，受影响运行全部作废并重跑。
- 冻结模型精确版本、推理参数、Harness 版本、工具权限、代码基线、任务顺序和重复次数；模型系列名称不能代替精确运行身份。
- 同时评价语义正确性、风险边界和实现成本。代码更少但违反输入验证、业务契约或安全门禁时，不能判为更优。
- 优先测量实际 diff、文件、依赖、可执行测试和可观察结果；Agent 的解释文本、宣称节省或输出篇幅不能替代产物证据。
- 通用基准只说明其冻结条件下的结果。没有当前项目的可比对照，不得推导“本项目节省了多少行、多少依赖或多少 Token”。

如果一个提示原则在不同模型家族上出现稳定差异，应把适用边界写入结论，不能继续修改措辞直到只留下有利样本。

## 8. 结论状态机

```text
planned -> running -> pending_human_evaluation -> concluded -> archived
          |          \-> blocked
          |          \-> invalidated
          \-> cancelled
concluded -> superseded
```

- 阶段性结论必须写明`interim`，包含证据和未知项。
- 最终结论记录采用/淘汰方案、理由、适用边界、不确定性、签字人和日期。
- 新证据推翻旧结论时，把旧实验标为`superseded`并引用新实验；历史正文不改写。
- 若结论外推到不同数据、硬件、版本或用户群，必须说明是否已复验。
- `invalidated` 表示比较设计、输入污染或关键证据使本轮结果不可用于决策；它不同于假设被证伪，也不能从账本删除。

## 9. 删除与复现门禁

删除大产物前逐项验证：

- 输入可重新取得，且有版本/SHA；
- 代码仓库、commit和本地补丁可重建；
- 模型/依赖有稳定ID、revision或可验证包指纹；
- 非官方算法、Prompt、分段、后处理和验证逻辑保留源码或完整协议；
- 运行矩阵和命令没有依赖个人记忆中的隐式步骤；
- 原始结果摘要、输出SHA、失败和人工评价已进入稳定账本；
- 已声明随机生成、驱动、硬件或上游删除导致的逐位复现限制；
- 删除动作本身记录时间、范围、恢复可能性和执行者。
- 若曾在外部 worktree 运行，先将稳定记录和被忽略的运行资产迁入登记的 `POC_ROOT`，比较文件清单和 SHA；
  只有对账完成、POC 根复验通过、外部独有文件数为零后，才允许移除临时 worktree。
- 临时 scratch 只允许承担已声明的下载、解压或中间计算；完成前必须迁入、按政策删除或登记保留理由，
  并证明 Codex 管理目录、外部 worktree、clone、`/tmp` 和个人缓存中的独有 POC 文件数为零。
- `tracking_mode=untracked` 时，删除前按 `retention_class` 验证备份或可重建性；Git 历史不能充当恢复方案。

只有SHA但没有可取得来源，不可复现；只有环境名但没有精确版本，不可公平比较；只有成功截图但没有原始测量，
不能支撑结论。

## 10. 与其他治理记录的边界

- 实验账本：保存假设、变量、运行、观察、评价和结论。
- 工作日志：保存本次协作修改了哪些文件、验证了什么、还有什么风险。
- ADR/技术方案：保存被批准进入系统的正式技术决策。
- Changelog：保存正式版本实际发布的变化。
- 业务台账：只保存项目定义的正式业务事实，不默认接收POC状态。

实验有结论后，如果决定生产化，必须把批准的结论转译进正式需求、ADR/技术方案、测试与发布文档；不能让日常生产
长期依赖POC账本作为运行SOP。

## 11. 最小模板

使用`assets/poc-experiment-governance/`中的账本与manifest模板落地；项目已有等价结构时适配既有结构，
不要平行创建第二套台账。
