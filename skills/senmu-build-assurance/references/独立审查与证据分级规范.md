# 独立审查与证据分级规范

本规范用于代码、架构、项目治理、工作流、交付准备、生产事实或完整项目审查。它规定如何冻结范围、组织证据、校准问题等级和复核结论；不授权修复、发布、删除或改变生产状态。

## 1. 审查身份

审查开始时明确一种身份：

- **Independent review**：审查者没有参与被审对象的主要实现或关键决策，并能独立选择证据和形成结论。
- **Peer review**：同一团队或相邻领域的审查，具备专业分离但可能共享上下文。
- **Evidence-based self-review**：实现者或同一 Agent 对自己的结果复核，可以有效发现问题，但不得宣传为独立审查。

身份描述的是独立程度，不代表能力高低。无法证明分离时使用 self-review；需要正式独立结论时移交另一执行者，并提供冻结对象而不是预设答案。

Product 和 Engineering 对需求—设计—任务—代码的一般一致性检查属于本域自查，不需要为每次普通变更调用 Assurance。只有负责人要求独立结论、审查者与实现者需要分离、存在跨领域争议，或 G3-G4 正式放行明确要求独立证据时，Assurance 才主责冻结对象、Coverage Map、证据和结论；发现的修订仍回到原专业 owner。

## 2. Review Charter

执行前冻结：

- 审查目标、决策用途、请求方和报告读者。
- 被审对象的路径、仓库、commit／版本、环境、时间点和权威入口。
- in scope、out of scope、允许的抽样和必须完整覆盖的关键路径。
- 只读边界，以及允许执行的静态检查、本地测试、真实环境查询和临时产物位置。
- 适用的需求、架构、测试、发布或业务标准及其版本。
- 问题等级、结论状态和停止条件。

“审查整个项目”应先建立 Coverage Map，按发布单元、模块、数据／权限边界、入口和用户主流程拆分。上下文不足时分批审查并维护覆盖进度，不能以读过少量代表文件代替全项目结论。

### 2.1 审查模式与完整性语义

审查必须显式选择模式，不得在报告中混用：

- `risk_based`：普通变更、PR 或大型项目风险评估的默认模式。可按发布单元、模块、变更和高风险路径抽样，但必须声明未覆盖范围，不能外推为全库每个函数已审查。
- `exhaustive_source`：只在用户明确要求“全量”、“每个系统／模块／文件／函数”、“每条现有注释”或等价完整性时使用。该模式不允许用抽样代替清点，也不允许用“多轮后没再发现问题”代替完整性证据。

`exhaustive_source` 必须产生稳定控制记录，并满足：

1. 冻结仓库、commit／树身份、发布单元、系统和语言；目标变化后旧结论不得沿用。
2. 根据项目跟踪文件和明确排除规则，清点每个第一方源码文件；生成物、vendor、锁文件和外部镜像只能按文件登记排除理由，不得静默消失。
3. 使用匹配语言的符号解析方法清点每个函数、方法、构造器、属性访问器以及具有独立行为的 lambda／顶层可执行单元；每项保留限定名、行范围、内容指纹和审查证据。
4. 每个可执行单元逐项检查职责、抽象层次、输入输出、副作用、异常／资源、依赖／架构、重复／实现经济性、测试、注释／文档；不适用也要记录理由。
5. 每条已存在的注释或文档字符串检查准确性、必要性、时效性和安全性。缺失应有注释的情况通过所属可执行单元的 `comments_docs` 检查登记；不强制为自解释代码添加噪声注释。
6. 将发现与文件、可执行单元或注释双向关联，并分开表示“全部审查完成”和“所有必须整改项已经复核”。

可从 [Exhaustive Source Review Control](../assets/review-governance/EXHAUSTIVE_SOURCE_REVIEW_CONTROL.template.json) 创建控制记录，并执行：

```bash
python3 <buildos>/skills/senmu-build-assurance/scripts/validate_exhaustive_source_review.py --record <control-record.json>
```

校验器只证明记录的结构、状态和交叉引用自洽，不能单独证明符号扫描没有遗漏。审查者还必须登记 inventory method、工具／版本、限制，并把扫描结果与项目跟踪文件、语言清单和入口核账。

## 3. 证据等级

| 等级 | 含义 | 可以支持的典型主张 |
| --- | --- | --- |
| `E0 unsupported` | 只有说法、印象或无法定位的摘要 | 只能登记为待核实假设 |
| `E1 documentary` | 当前版本的源码、配置、schema、文档、静态产物 | 结构、声明、静态约束和潜在风险 |
| `E2 reproducible` | 可复跑命令、测试、构建、查询或确定性检查 | 在冻结环境中的可复现行为 |
| `E3 operational` | 目标环境运行身份、真实数据路径、用户主流程或外部系统回执 | 当前环境或真实链路事实 |
| `E4 corroborated` | 独立复核、重复运行、多个来源或跨输入／环境相互印证 | 高影响结论、外推或稳定性主张 |

等级不是机械打分。静态架构违规通常由 E1 足够证明；生产已发布需要 E3；“长期稳定”“普遍更优”等宽泛主张通常需要 E4。证据必须记录定位、获取时间、对象版本、方法和限制。

截图、日志片段、测试绿灯或工具退出 0 只能证明其直接观察到的事实。被截断输出、过期报告、其他分支结果和历史生产状态不能替代当前对象证据。

## 4. 证据登记与交叉验证

每条关键证据至少登记 `evidence_id`、等级、来源、对象身份、时间、采集方法、支持／反驳的主张和限制。敏感信息只登记脱敏定位与受控查询入口。

证据冲突时：

1. 先核对是否来自同一版本、环境、时间和发布单元。
2. 区分计划／候选文档与动态运行事实。
3. 优先刷新更易变化、且与主张直接相关的权威来源。
4. 无法消解时保留冲突并降低结论强度，不选择更符合预期的一份。

## 5. 发现状态与问题等级

发现状态使用：

- `suspected`：有信号但证据不足。
- `confirmed`：证据足以证明问题及影响边界。
- `disputed`：存在未消解的事实或标准争议。
- `accepted_risk`：owner 明确接受并记录期限或复核条件。
- `resolved_unverified`：已报告修复，但尚未复核。
- `verified_resolved`：对原失败路径完成复核。
- `false_positive`：新证据证明原发现不成立，保留更正依据。
- `superseded`：被后续发现或报告替代。

P0-P3 同时考虑影响、发生可能性、可恢复性、暴露范围和时间紧迫性：

| 等级 | 判定 |
| --- | --- |
| `P0` | 正在发生或极可能导致安全、隐私、资金、不可恢复数据、严重生产事故；必须立即停止或隔离 |
| `P1` | 关键契约、核心流程、发布完整性或高风险控制存在重大缺陷；正式放行前必须解决 |
| `P2` | 有实质影响但存在安全替代路径或可计划治理；不应被“建议优化”弱化 |
| `P3` | 低风险改进、可维护性或清晰度建议；不冒充阻断问题 |

严重度不按文件数量、代码行数、措辞强烈程度或个人偏好决定。技术债若尚未造成缺陷，应记录触发条件和风险，而不是自动升级为 P1。

## 6. 审查执行

1. 读取项目权威入口、当前状态和适用 owner 规则。
2. 建立 Coverage Map 与 Evidence Register，先查高风险边界。
3. 使用搜索、静态分析、测试、运行查询和真实流程等与主张匹配的方法。
4. 对每个候选发现主动寻找反证、既有保护和可能误报。
5. 将发现绑定到路径／对象、证据、影响、严重度理由和最小整改方向。
6. 完成覆盖核账，明确未执行、失败、被阻断和不适用的检查。

只读审查允许读取和运行不会改变项目、外部系统或生产状态的检查；需要生成中间物时使用隔离临时位置。可能写数据库、更新快照、上传、通知、部署、清理或改变外部状态的“测试”必须另获授权。

## 7. 结论状态

领域或整体结论只使用：

- `supported`：范围内主张有匹配证据支持，且没有未解决阻断项。
- `supported_with_conditions`：结论成立，但存在明确条件、P2/P3 或待执行验证。
- `not_supported`：存在 P0/P1、关键证据缺失或事实与目标主张冲突。
- `inconclusive`：证据冲突、时效不足或被阻断，无法可靠判断。
- `not_assessed`：没有纳入或没有实际覆盖。

“没有发现问题”只适用于已声明覆盖范围，不等于项目整体正确、安全或可发布。机器门禁全部通过，也只能证明门禁覆盖的契约。

对 `exhaustive_source`，`review_complete` 只表示冻结范围内的文件、可执行单元和现有注释已逐项得到审查结果，不表示代码已符合目标标准。只有冻结整改后目标、关闭所有未处置发现、重跑原失败路径和匹配回归、再次通过控制记录校验后，才能进入 `verified_complete` 并给出有限强度的整改后结论。

## 8. 整改与复核

- 审查报告提出整改目标、owner、优先级和验收证据，不在未授权时实施修复。
- 修复者更新对应 Product、Workflow、Engineering、Delivery 或 Project owner；Assurance 不建立第二份规范。
- 复核读取原 finding 和新的冻结对象，重跑原失败路径并检查新增回归风险。
- 原报告保持历史；复核追加状态或生成新报告并建立 supersedes 关系。
- 修复验证通过不自动代表产品验收、发布批准或生产上线。

使用 [Assurance Review Report 模板](../assets/review-governance/ASSURANCE_REVIEW_REPORT.template.md) 记录 Review Charter、Coverage Map、Evidence Register、发现和结论。项目已有审计系统时沿用其唯一 owner。
