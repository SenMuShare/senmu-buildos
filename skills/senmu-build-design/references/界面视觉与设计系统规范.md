# 界面视觉与设计系统规范

本规范把用户目标、模糊审美和现有产品事实转成可实现的界面方向。它负责视觉层级、布局、字体、色彩、材质、组件表现、素材策略和响应式设计，不决定产品是否增加功能，也不维护组件库 API。

## 1. 权威顺序与现场读取

按以下顺序裁决：已批准产品行为与内容 > 项目现有设计系统、品牌资产和页面惯例 > 目标平台与组件生态 > 本规范的通用方法。现有 owner 完整且合理时直接沿用；只有缺失、冲突、重复或需要长期改变时才治理它。

开始前取得会改变设计决定的最小事实：

- 这是什么界面：营销官网、产品应用、后台、移动端、桌面端、嵌入式面板或混合表面；
- 主要用户、最重要任务、首要动作与使用环境；
- 当前页面、导航、内容层级、关键状态和真实数据密度；
- 现有 Logo、字体、色彩、图标、照片、视频、产品截图和品牌限制；
- 已安装组件库、设计 Token、响应式约定和目标设备。

不得因用户只说“高级”“大气”“科技感”就让用户补一套专业术语。先把业务和使用场景复述准确，再给二至三个用户能理解、构图和素材策略真正不同的方向；每个方向说明感觉、适用场景、核心资产和主要风险，并推荐一个。已有充分方向时直接进入规格，不强制提问或凑满候选。

## 2. 从感觉到可实施规格

审美词必须落到可观察决定：

- **层级**：首屏／主任务先看到什么，次要信息如何退后，主动作与风险动作如何区分；
- **构图**：容器、网格、对齐、留白、密度、分组、焦点和滚动节奏；
- **字体**：字族角色、字号层级、字重、行高、字距、段落宽度和多语种适配；
- **色彩与材质**：品牌色、语义色、背景层、表面层、边界、阴影、透明度和明暗模式；
- **组件**：导航、按钮、表单、列表、表格、卡片、弹层和反馈的视觉关系；
- **数据可视化**：先明确趋势、比较、分布、组成或关系等问题，再选择图形；标注、图例、数值口径和非颜色表达必须让数据可理解，具体图库 API 交项目／Engineering；
- **素材**：主视觉用真实产品、摄影、插画、视频、三维还是数据；缺失资产要给可行替代；
- **响应式**：内容优先级、重排、折叠、密度和输入方式怎样随空间变化；不能只把桌面等比缩小。

官网与品牌页通常依靠一个强主视觉、清楚的叙事节奏和明确转化动作；工具和后台通常优先任务效率、信息密度、状态可辨识与稳定位置。两类表面可以共用品牌，但不应机械共用同一页面构图。

## 3. 设计系统边界

只有多个页面或长期组件需要共同规则时才建立或调整设计系统。优先修改项目现有 Token、主题、组件和文档 owner，不默认创建 `design-system/MASTER.md`、页面覆盖目录或新的样式数据库。

最小设计系统应只保存会减少真实分歧的内容：

1. 基础 Token：颜色、字体、空间、圆角、边界、阴影、层级和动效语义；
2. 语义角色：主／次动作、成功／警告／错误、表面层和文本层级；
3. 组件状态：默认、悬停、按下、聚焦、选中、禁用、加载、空和错误；
4. 响应式与主题规则：在哪些真实断点或容器条件下改变什么；
5. 允许的局部例外及其 owner、理由和退出条件。

Token 表达角色，不把无上下文的原始色值、间距或时长散落到组件。页面特有变化能用已有 Token 和局部组合完成时，不为“统一”增加新 Token。不同风格机制不得随意混搭；需要打破项目惯例时说明用户收益和一致性成本。

## 4. 面向实现的交付

根据任务大小交付最小充分结果：

- 小型局部设计：直接给现状、目标、具体改动和验证点；
- 新页面或改版：给推荐方向、层级／布局、组件、Token、素材、响应式、关键状态和禁止结果；
- 跨页面系统：更新项目现有设计 owner，并列出迁移范围、兼容边界和验证入口；
- 后续由另一执行者实现：提供自包含规格，但不复制整段对话、外部案例库或隐藏意图。

技术栈从项目事实取得。不得为视觉偏好默认指定 React、Tailwind、某组件库或动画库；选择依赖时只说明真实能力缺口，并交 Engineering 核对兼容性与维护成本。

## 5. 完成检查

交付前确认：第一眼层级是否明确；主任务和主动作是否可发现；内容、视觉与品牌是否一致；真实数据和最长／最短文本是否可容纳；桌面与移动是否各自成立；加载、空、错、禁用和危险状态是否可辨认；素材是否可取得；规格是否足以实施且没有另造第二套 owner。
