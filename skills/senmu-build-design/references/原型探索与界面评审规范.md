# 原型探索与界面评审规范

本规范用于方向不确定、交互风险较高或需要整体 UI/UX 判断的任务。原型帮助发现和比较设计，不自动成为正式产品、生产代码或独立证据。

## 1. 何时需要原型

以下情况可以先做原型：多个方向会实质改变层级或交互；手势、动效、空间关系无法从静态稿判断；高成本实现前需要验证任务路径；用户明确希望先看方案再选择。

局部样式、已有明确设计稿、成熟组件的常规组合或低成本可逆修改直接实现并验证，不为展示流程强制做原型。

## 2. 候选必须真正不同

通常提供二至三个候选，数量由决策需要决定。候选应在信息层级、布局模型、视觉气质、素材策略或交互机制上有清楚差异，不能只换颜色、圆角和阴影假装多个方案。

比较时保持核心内容、数据、目标任务和设备条件一致。每个候选说明：

- 用户首先看到和完成什么；
- 视觉／交互机制及其适用场景；
- 所需素材和技术前提；
- 可访问性、性能、维护和品牌风险；
- 推荐与不推荐的理由。

输入很少时用用户能理解的名称描述方向，并主动推荐一个；用户可以直接选择推荐项。不得把审美问卷转嫁给不熟悉设计术语的用户。

## 3. 原型边界

- 在项目既有原型入口、Storybook、测试路由、独立示例或可删除的隔离工作区实现；不把候选写进生产导航、真实数据或正式发布源。
- 复用项目技术栈、组件和假数据。只有原型问题确实需要且收益大于安装／维护成本时才增加依赖。
- 静态稿只验证构图和视觉；任务路径、手势、焦点、响应式和动效需要可交互原型。不得用静态截图声称交互已验证。
- 原型记录对象、版本、目标视口、假设和未验证项。视觉方向被选择不等于业务需求已批准。
- 选定后把稳定决定写回项目现有设计系统、产品规格或实现 owner；未选候选保持隔离，并按用户授权删除、归档或保留，不让多套主题长期并存。

需要盲测、对照实验、可复现 POC 或独立结论时由 Assurance 冻结对象和证据标准；Design 自己比较方案只能称设计探索或 evidence-based self-review。

## 4. 界面评审范围

先声明评审对象：一个组件、页面、流程、设计系统或跨设备体验。随后按真实任务检查：

1. **理解与层级**：用户能否知道当前位置、主要内容、下一动作和退出方式；
2. **一致性**：同义对象、组件、Token、状态和交互是否复用项目 owner；
3. **任务效率**：常用路径是否直接，信息密度是否适合场景，错误是否可恢复；
4. **状态完整**：加载、空、错误、禁用、选中、危险和长内容是否设计；
5. **响应式与输入**：不同视口、键盘、触摸和精确指针是否各自成立；
6. **可访问性**：语义、焦点、名称、对比、缩放、非颜色表达和减弱动效；
7. **动效与手感**：目的、频率、反馈、空间关系、可中断性和性能；
8. **实现可行性**：是否能复用现有组件，素材和数据是否真实可得，是否引入不必要依赖。

Finding 必须包含具体位置、当前证据、用户影响、建议结果和验证方式。只有偏好差异而没有任务、理解、一致性、品牌或可访问性影响时，标为可选建议，不冒充缺陷。严重度按用户影响和频率排序；少量高置信问题优于冗长的审美清单。

## 5. 收口

完成时分别说明：已决定的设计、仍是候选的内容、已经运行验证的部分、尚未在真实设备／数据／用户中验证的部分，以及写回哪个项目 owner。代码检查、截图和设计自查不能冒充用户研究、独立审查或生产可用性。
