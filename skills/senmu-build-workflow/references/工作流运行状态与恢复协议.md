# 工作流运行状态与恢复协议

本协议用于需要多步骤执行、可重试、可中断、跨 Agent 接力或具有外部副作用的工作流。它规定一次运行如何被识别、记录、验证和恢复；不代替项目任务管理、发布台账或 Codex 会话历史。

## 1. 三类事实必须分开

| 对象 | 回答的问题 | 唯一 owner | 典型位置 |
| --- | --- | --- | --- |
| 工作流契约 | 这条链路长期应如何运行 | workflow definition、schema、config | `workflows/` |
| 运行清单 | 这一次实际运行到哪里、用了什么、产生了什么 | Run Manifest／运行数据库 | `state/`、`data/` 或既有状态系统 |
| 任务计划与状态记录 | 为什么做、如何推进、跨阶段整体进度和下一步是什么 | 项目声明的 Durable Task State Owner | 新项目默认 `governance/tasks/TASK-<NNNN>-<slug>.md`；成熟项目可映射既有计划、数据库或外部系统 |

同一任务可以关联多次运行，同一次运行也可以产生多个交付物。三类对象通过 `task_id`、`run_id`、交付 ID 和证据链接关联，不复制彼此正文。

## 2. 运行身份与输入快照

每次可恢复运行至少记录：

- 稳定的 `workflow_id` 和实际执行的 `workflow_version`。
- 全局唯一且运行期间不变的 `run_id`；重试 attempt 不得伪装成新业务运行。
- 关联的 `task_id`（如有），以及启动时间、执行者和实际公开入口。
- 输入对象的稳定 ID、版本、哈希或不可歧义定位方式。
- 影响结果的配置、代码、模型、工具或运行环境版本。
- 幂等键或去重规则，尤其是支付、通知、发布、上传和数据库写入等副作用。

聊天里的对象描述不是输入快照。输入发生实质变化时，应创建新运行或明确记录失效边界，不能静默改写旧运行事实。

## 3. 状态模型

运行级推荐状态：

| 状态 | 含义 |
| --- | --- |
| `created` | 已生成运行身份，尚未满足执行前提 |
| `ready` | 输入、权限和前置条件已经通过预检 |
| `running` | 至少一个步骤正在执行 |
| `waiting` | 正在等待外部系统、异步结果或人工输入 |
| `paused` | 有意暂停，已有明确恢复入口 |
| `failed` | 当前 attempt 失败，必须记录错误和可恢复判断 |
| `cancelled` | 经授权终止，不再自动推进 |
| `completed` | 契约内步骤与运行级验证已完成 |
| `superseded` | 已由另一运行替代，不再作为当前入口 |
| `archived` | 运行事实转为只读历史 |

步骤级推荐使用 `pending`、`running`、`succeeded`、`failed`、`skipped`、`cancelled`。每一步记录 attempt、输入引用、输出引用、开始／结束时间、验证结果和错误回执。

`completed` 只表示工作流契约内运行完成，不自动代表产品已验收、已经交付或已经发布。这些事实由各自 owner 单独登记。

## 4. 状态转换规则

- 只有唯一状态 owner 可以推进运行状态；日志、聊天和生成目录不得反向覆盖它。
- 状态转换应由公开入口、受控命令或明确事务完成，不通过手工修改数据库／JSON 绕过 owner 流程。
- 工具返回成功后仍需验证输出身份、完整性、数量、格式和业务条件，再把步骤标为 `succeeded`。
- 部分成功必须保留真实步骤状态，不得把整次运行写成成功，也不得抹掉已经确认的有效输出。
- `waiting` 是可恢复状态，不是持续占用执行者的轮询动作。只有依赖该结果的步骤进入 `waiting`；其他 `ready` 步骤继续。整次运行只剩等待时，保存 checkpoint、所等事件／结果身份、超时与唤醒入口后释放 worker；优先事件唤醒，不得无界轮询。
- 外部副作用发生前后分别记录意图、授权、幂等键和回执；无法确认结果时标为待核查，不盲目重试。
- 状态文件若采用 JSON，应通过原子替换、事务或项目等价机制写入，避免中断留下半份状态。

## 5. 恢复决策

恢复前依次完成：

1. 从权威状态源定位 `run_id`，核对工作流版本和输入快照。
2. 刷新外部系统事实，区分“请求已提交”“处理已完成”“结果已验证”。
3. 从上游到下游检查步骤证据，找到最早失效或尚未验证的步骤。
4. 按输入语义、目标版本、真实依赖和产物结果判断可否复用。哈希只提供身份线索；只有它承担产品完整性／精确修订契约，或揭示输入发生实质变化时才阻断复用。纯行政哈希、回执或进度记录缺失／过期，不使已确认有效的产物失效。
5. 选择并登记恢复动作，然后从公开入口执行。

恢复动作必须明确区分：

- **Resume**：从已验证 checkpoint 继续同一次运行。
- **Retry**：在同一运行中重试失败步骤，增加 attempt，并保持幂等。
- **Restart**：输入、规则或环境变化使旧 checkpoint 不可信，创建新运行。
- **Rollback**：撤销已发生的副作用或恢复到已知安全状态；它不等于重跑。
- **Manual reconciliation**：外部结果不确定或无法自动判定时，停止自动写入并人工核账。

默认从最早真实失效层向下最小重跑；如果上游输入语义、目标修订或实际消费者依赖已经改变，才使相应下游产物失效。不得仅因行政记录变化而回退游标、扩大重跑范围、覆盖旧交付物或删除失败证据。

如果标准编排只因行政标记拒绝继续，而目标步骤已有项目授权的受控入口，可直接执行该步骤、核对输出并继续，再修复或降级不合理门禁。这个例外不允许手改状态 owner，也不允许绕过权限、幂等、安全、费用、不可逆副作用或正式发布授权。

## 6. Run Manifest 最小字段

Run Manifest 或等价数据库记录至少能表达：

- schema、workflow、run、task 和当前状态。
- 输入快照、实际版本和执行环境。
- 每一步的状态、attempt、输入／输出、验证和错误。
- 当前 checkpoint、最早失效步骤和下一恢复动作。
- 已发生的外部副作用及其授权／回执。
- 最终输出、验证证据、交付状态引用和归档状态。

可使用 [Run Manifest 模板](../assets/workflow-governance/WORKFLOW_RUN_MANIFEST.template.json) 建立项目自己的 schema。已有数据库或编排系统能完整承担这些事实时，登记其表／对象和查询入口，不再创建 JSON 副本。

## 7. 多 Agent 与 Harness 边界

- Harness 负责会话、工具调用、上下文压缩和生命周期事件；项目运行事实必须脱离单次会话仍可恢复。
- Agent 移交时传递 `task_id`、`run_id`、当前步骤、输入／输出引用、失败证据、授权边界和下一动作。
- 系统提示词定义稳定行为，不能保存动态游标、当前 step 或“已经发布”等运行事实。
- Hook 只恢复短治理底线，不扫描并注入完整 Run Manifest，也不自行猜测或推进运行状态。

## 8. 收口检查

- 能从项目入口定位工作流契约、状态 owner、当前运行和恢复命令。
- 同一运行身份、输入快照和步骤证据相互一致。
- 重试没有重复触发不可逆副作用；不确定结果保持待核查。
- 运行完成、产品验收、交付和发布没有被合并成一个状态。
- 被替代、失败和取消的运行仍可审计，但不会冒充当前入口。
