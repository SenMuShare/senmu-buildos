# 工作流、物料与交付物治理规范

本规范用于脚本自动化、Codex Harness、视频/图片生产、内容加工、批处理和其他“代码 + 状态 + 文件交付”项目。重点不是采用固定目录名，而是让每类资产的职责、可恢复性和交付状态清楚。

## 1. 资产角色

| 角色 | 含义 | 默认治理 |
|---|---|---|
| 源输入 | 用户资料、原始媒体、冻结文案、业务参数 | 保留来源、授权、版本和指纹；不得被中间处理覆盖 |
| 工作区 | 当前任务的拆解、转换和人工审阅内容 | 可修改；与正式交付隔离 |
| 临时/缓存 | 可重新生成的下载、代理文件、渲染缓存 | 默认不进 Git；可以安全清理 |
| 运行状态 | 数据库、manifest、队列、游标、任务状态 | 明确唯一可写权威、备份和迁移规则 |
| 交付物 | 面向用户或下游的候选或正式结果 | 稳定命名、版本/交付 ID、校验和；验收与发布状态另行登记 |
| 证据/回执 | 运行参数、来源引用、检查结果、发布或未发布事实 | 与一次运行和交付物可追溯关联 |
| 归档 | 已结束版本、历史交付和不可再作为当前入口的资料 | 只读或受控恢复；不能冒充当前状态 |

项目可以使用中文或既有目录名，但 README/AI 入口必须能把真实路径映射到这些角色。

表中的“任务状态”只指一次工作流运行的机器状态，例如队列、游标、manifest 或 run state。跨阶段管理进度服从项目声明的 Durable Task State Owner；二者只用 task ID／run ID 关联，不合并成一份状态。

## 2. 工作流与 Harness 契约

长期或可重复执行的链路至少定义：

- 唯一公开入口及输入 schema/config。
- `run_id` 或等价运行身份，以及输入版本/哈希。
- 状态所有者：数据库、manifest、台账或外部系统中只能有一个可写事实源。
- 每一步的输入、输出、失败状态和可重试边界。
- 断点续作、幂等或明确的重新开始规则。
- 目标验收、最终交付位置和运行回执。
- legacy 入口、旧缓存和旧产物何时只能作为历史参考。

工作流契约保存长期规则，不保存某次运行的当前游标。一次运行的步骤、attempt、checkpoint、错误与恢复动作按[工作流运行状态与恢复协议](工作流运行状态与恢复协议.md)进入 Run Manifest 或项目既有状态系统。

聊天记录不能成为运行链路的唯一状态。Agent 应能从项目内入口、状态源和回执恢复当前进度。

### 2.1 人机操作向导

设计或修复包含登录、密钥、验证码、支付、审批、账号归属或只能由人判断的不可逆步骤时，把流程编译成可恢复的人机操作向导：

- Agent 先自动完成当前授权内可做的读取、准备、校验和无副作用步骤，不把整条安装或配置流程原样丢给用户。
- 每次只交付当前必须由人完成的一段，写清打开哪里、识别哪个字段、可填写边界、预期结果、完成后返回什么信号，以及失败时停在哪里。
- 密钥、密码、Cookie、验证码和支付资料由用户在受信任界面直接填写，不要求粘贴进聊天、日志、Git、截图或客户端代码；Agent 只核对脱敏状态和结果。
- 已完成步骤保存可验证 checkpoint；恢复时先读取真实状态，重复执行必须幂等或明确说明会产生的新副作用，不让用户从头重做。
- 删除、付款、提交审核、发送通知、切换生产或其他不可逆动作前单独展示对象、影响和最后确认点；准备完成不等于获得执行授权。
- 项目已有原生向导、标准 CLI 或平台流程时直接复用并补缺失边界，不建立第二套长期步骤 owner。

本节拥有向导契约，不接管现有向导的日常执行。用户只要求按项目已有可靠步骤完成一次配置时，直接遵守项目入口；只有入口缺失、步骤不可恢复、秘密边界不清或不可逆确认设计有缺口时，才加载 Workflow 修复原契约。

## 3. 目录规划

按角色规划，而不是机械照抄名称：

```text
project-root/
  README.md / AGENTS.md       入口和权威顺序
  scripts/ 或 src/            可维护代码
  workflows/                  流程契约、schema、配置
  sources/ 或 inputs/         原始/冻结输入
  work/ 或 staging/           当前工作区
  data/ 或 state/             数据库、Run Manifest、运行游标
  outputs/ 或 deliveries/     最终交付物
  evidence/ 或 receipts/      验证和回执
  archive/                    历史版本和已关闭任务
```

小项目可以合并目录，但不得让源输入、中间文件和最终交付物互相覆盖。系统临时目录只用于可丢弃数据；需要接力、审阅或恢复的内容必须回到权威项目根。

## 4. Git 与大文件边界

- Git 默认管理代码、配置、schema、流程文档、小型清单和必要的可复现实例。
- 大型媒体、运行数据库、缓存和可重建中间物默认不直接进入 Git；使用项目认可的存储位置，并在 Git 中保留索引、manifest、哈希或恢复说明。
- 最终交付物是否进入 Git 由体积、隐私、许可、恢复成本和发布方式决定，不能因为“是最终文件”就默认提交。
- `.gitignore` 不能成为数据治理说明；被忽略资产仍需有权威位置、保留周期和恢复方式。

## 5. POC、生产与交付边界

POC 输出先进入实验或 staging 区。只有满足明确的质量、成本、许可和可重复性条件后，才能升级为正式工作流、生产输入或最终交付。

生成完成不等于交付完成；交付完成不等于已发布。项目必须分别记录：生成结果、验收结果、交付位置，以及适用时的发布状态和发布回执。

## 6. 收口检查

- 当前入口、状态源和运行进度可从项目内恢复。
- 源输入、临时内容和最终交付未混放或互相覆盖。
- 最终物料有交付 ID/版本、来源、验证，以及独立的验收／交付／发布状态引用。
- 未发布、未验收、失败或中断状态保持真实。
- 可清理内容与必须归档内容有明确边界。
