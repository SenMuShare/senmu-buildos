# Business Agent Content Governance

Use for content review or authorized improvement of existing business agents, reusable prompts and model-backed workflow nodes. Creation uses the Agent Framework; routine execution follows the adopted project definition. This is not root AGENTS maintenance, business redesign or permission to run the workflow.

## Preserve Meaning Before Improving Expression

Find the approved outcome and the effective prompt, not just a plausible Markdown file. Follow the existing register, call sites, configuration, prompt store and assembly code as applicable. Identify the actual system/developer instructions, scenario overlays, run variables, examples, output parser and tool/model request. Read only the scope needed; do not export secrets or customer inputs into BuildOS.

For a requested whole-project review, inventory all in-scope active agents and shared fragments before claiming coverage. Group by business responsibility and actual provider/model/endpoint/mode; shared fragments need one review but every affected consumer must be accounted for. Use the existing task/register to distinguish changed, reviewed-no-change, blocked and unassessed items. Samples can support a finding, not a hidden claim of exhaustive governance. Historical, third-party, generated and protected copies are not default write targets.

Establish the preserved contract in the existing task or review notes, without a new mandatory ledger:

- Business objective, responsibility, approved requirements, terms, creative intent and exceptions.
- Required/optional inputs, variable names, delimiters and interpolation/escaping; output fields, types, enum values, count, language and downstream parsing.
- Workflow sequence, branching, state ownership, missing/conflicting-input behavior, failure handling, handoffs and human acceptance.
- Provider, exact model, endpoint, task mode, settings, budgets, retry limits, tool access, privacy and external-effect authority.

Approved contracts define intended behavior; code and traces show actual behavior. Do not enshrine a known defect or silently resolve a disputed business choice. Carry out independent authorized improvements and report the precise unresolved choice. If the brief is only an audit, make no edits. An audit-and-optimize request covers scoped expression repairs, not automatic production activation or paid evaluation.

## Reconcile Content in Place

1. Trace each material instruction to its business meaning and consumer. Separate permanent instructions, scenario rules and per-run data; preserve the existing assembly mechanism and interfaces.
2. Make the role, outcome, inputs, decisions, outputs, constraints and failure behavior discoverable. Reorder prose for readability without reordering business steps. Merge genuine duplication; retain intentional emphasis, business examples and edge cases that affect decisions.
3. Repair ambiguity or contradictions only from confirmed requirements. Keep must/prefer/may strength and scope intact. Do not invent defaults, examples, input fields or stricter requirements merely to fill a template. Shorter text is not inherently better.
4. Preserve established document and runtime prompt languages, exact output copy and technical identifiers unless explicitly authorized otherwise. New definitions follow project collaboration language, then request language, then English when neither is known. The English starter is an outline, not a replacement. Existing multilingual structure may be intentional.
5. For an actual image-generation/editing responsibility, apply [Image Agent Guidance](image-generation-agent-guidance.md) and only the matching model profile. Other agents retain the common content method; an unknown model requires current primary evidence, not a guessed neighboring profile.
6. Review the assembled prompt and its changed consumers after editing. Update the original source, version evidence and affected references together. Keep recoverable history through the project's existing version mechanism, not Agent.new/old or duplicated active definitions.

Model guidance may improve how an existing requirement is conveyed; it may not add an unrequested aesthetic, task, output or decision. A prompt-writing-only agent remains prompt-writing-only: do not turn it into generate-review-regenerate. Model replacement, endpoint/settings changes, extra images, retries, post-processing, new confirmation steps, publishing or wider writes are separate proposed changes unless already authorized. Keep sound existing wording; repeated governance of unchanged facts should make no semantic changes.

## Verify Contracts Separately from Effects

Before/after checks cover variables and their rendering, output schema and downstream use, required constraints and exceptions, call modes/settings and affected handoffs. Use existing fixtures, representative assembled requests and contract/parser tests. A parser passing does not establish business equivalence; a prose review does not establish runtime behavior. Do not weaken checks to accommodate an accidental contract change.

When authorized runtime evaluation is available, compare the old and new prompt on the same representative normal, edge and known-failure inputs, actual model/version, settings and acceptance rules. Repeat where variability matters. Check each affected responsibility and shared consumer, not only an attractive output. Prompt-only agents are evaluated on their prompt contract; image quality requires a separately authorized renderer. Keep evaluation data within its permitted boundary.

Report two conclusions: (a) content/contract reconciliation and remaining ambiguity; (b) observed outcome quality, regressions and coverage. Structural checks or deterministic template rendering cannot prove semantic equivalence, correct model routing or better generated outputs. Without paid-call/runtime authority, finish permitted source work and state that effects remain unverified. An existing execution loop or approval boundary is not changed merely to evaluate a candidate. Retain rollback and activate through the project's approved lifecycle.

Output only the useful coverage summary, material edits and preserved meanings, checks/results, unresolved issues and separately proposed business changes. Do not produce a per-rule scorecard. No-change is a valid result.
