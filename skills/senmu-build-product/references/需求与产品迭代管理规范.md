# 需求与产品迭代管理规范

本规范维护从需求进入、澄清、决策、规划、迭代承诺到产品验收的单一事实链。它回答为什么做、为谁做、做什么、何时承诺以及如何验收；技术实现、任务进度、版本制品和真实发布分别由 Engineering、Project 和 Delivery 的权威事实负责。

## 1. 产品事实与文档职责

| 文档 | Professional Name | 唯一职责 | 不负责 |
| --- | --- | --- | --- |
| `REQUIREMENT_BACKLOG.md` | Requirement Backlog | 保存需求条目、来源、生命周期、决策与追踪关系 | 承诺版本或记录开发流水 |
| `PRD.md` | Product Requirements Document | 定义已确认的问题、用户、范围、业务规则、成功标准和验收 | 保存全部候选想法或技术设计 |
| `ROADMAP.md` | Product Roadmap | 按结果和阶段表达产品取舍、顺序与条件 | 冒充正式版本或发布日期 |
| `ITERATION_PLAN.md` | Iteration Plan | 保存当前迭代目标、已承诺切片、变更和验收收口 | 复制需求正文、任务进度或未批准生产化的 POC 运行状态 |

复杂或需要独立追踪的需求使用 `product/requirements/REQ-<NNNN>-<slug>.md`；全局 PRD 只保存产品共同范围和稳定业务契约。关联编号任务计划保存加工进度和关键取舍摘要；正式需求评审记录归 Product review owner，评审通过后更新正式需求 owner。

同一事实只保留一个主记录，其他文档通过 `REQ-xxxx`、Task ID、发布单元和证据链接关联。已有项目使用外部产品系统时，可将外部对象作为 owner，但项目入口必须记录系统、对象 ID、读取方式和离线恢复边界。

## 2. 需求对象模型

每条需求至少包含：

- 稳定 ID、标题、类型、来源、提出者和日期。
- 问题或机会、目标用户／场景、期望结果和影响。
- 范围、非目标、约束、依赖、风险和待确认问题。
- 可验证验收标准或进入探索的证据目标。
- 生命周期状态、决策、优先级方法、目标阶段和下一步。
- 关联 PRD、路线图、迭代、Task、工程实现、测试、发布和验收证据。

ID 从 `REQ-0001` 起只增不复用。需求被拒绝、取消或替代后仍保留原 ID、原因和替代关系。

推荐类型用于路由，不用于决定优先级：

| 类型 | 含义 | 典型 owner 边界 |
| --- | --- | --- |
| `problem` | 待解决的用户或业务问题 | Product 定义问题与结果，不预设功能 |
| `feature` | 已确认的产品能力 | Product 定义行为和验收，Engineering 决定实现 |
| `defect` | 已交付行为偏离产品契约 | Product 记录用户影响；工程缺陷证据链接 Engineering |
| `research` | 需要发现或验证的问题 | 产品研究结论留在 Product；决策型技术 POC 由 Assurance 管理证据 |
| `enabler` | 为后续产品结果提供条件的技术使能 | Engineering 提供必要性、成本和债务边界，Product 决定投入顺序 |
| `compliance` | 法务、隐私、安全或监管要求 | 保留来源和不可协商边界，高风险按 G3-G4 处理 |

### 2.1 机会评估与产品发现（按需）

需求池负责接住所有想法，但不是所有想法都应直接进入正式需求或研发。出现投入较大、证据薄弱、问题尚不明确、机会成本高、存在成熟替代，或失败后难以回退的情况时，先做机会评估；低成本、可逆且能快速获得真实反馈的小改动可以直接形成最小需求或实验，不为流程延迟验证。

机会评估至少回答与本次决策有关的内容：

- 问题是否真实、谁受到影响，以及当前证据和置信边界；没有来源的判断标为假设。
- 最有力的反对证据、现有替代、既有能力、成熟产品／开源方案，以及什么都不做的代价。
- 可选方向至少包含最小可行方案；适用时比较不做、复用、购买或合作，不默认自行开发。
- 愿意投入的时间／资源上限、主要风险、范围失控点和必须验证的假设。投入上限用于约束探索，不伪装成精确工期承诺。
- 最终决定、理由、未决问题和重新评估条件。

普通想法直接保存在 Requirement Backlog。需要多轮研究与取舍时，在关联编号任务计划中保存问题、证据、候选、取舍和下一步摘要；正式结论仍回写 REQ／Backlog，不创建第二套 assessment 目录或五阶段流水线。状态映射如下：

| 评估结论 | 产品状态 |
| --- | --- |
| 信息不足，需要继续验证 | `clarifying`，或以 `research` 类型登记证据目标 |
| 值得进入需求决策 | `ready`；形成路线图决定后才进入 `planned` |
| 当前不做但条件可能变化 | `deferred`，记录重评条件和 owner |
| 已决定不做 | `rejected`，保留决定依据和替代关系 |

重大、争议性或需要独立证据裁决的机会评估可由 Assurance 提供只读证据结论；Product 仍负责产品取舍。不得要求所有想法达到同一证据等级，也不得因为已经投入研究成本就强行给出推进结论。

## 3. 生命周期与状态转换

推荐使用一组可解释的状态，不把优先级、版本、发布状态塞入生命周期：

| 状态 | 含义 | 允许进入条件 |
| --- | --- | --- |
| `inbox` | 已记录，尚未完成整理 | 有来源和最小问题描述 |
| `clarifying` | 正在澄清用户、范围、证据或约束 | 明确下一项待确认信息 |
| `ready` | 信息足够，可以参与产品决策 | 问题、结果、范围和验收方向可判断 |
| `planned` | 已进入路线图，尚未形成当前迭代承诺 | 有阶段、顺序或重评条件 |
| `committed` | 已进入当前迭代承诺 | 切片、验收、依赖和容量已确认 |
| `in_progress` | 已开始产品／工程执行 | 有 Task 或实现入口 |
| `implemented` | 实现声称完成，等待产品验收 | 有实现和测试证据，但不代表发布 |
| `accepted` | 产品验收通过 | 验收标准逐项有证据和结论 |
| `deferred` | 暂缓 | 有原因、重新评估条件和责任人 |
| `rejected` | 决定不做 | 有决策依据，不等于需求不存在 |
| `cancelled` | 已承诺或执行后终止 | 有影响、收口和后续处理说明 |

允许回退状态，但必须记录原因和日期。`implemented`、`accepted`、`released` 是不同事实：代码完成由 Engineering 提供证据，产品验收由 Product 记录，真实发布由 Delivery 记录。Product 不创建 `released` 生命周期状态，可通过关联发布证据形成查询视图。

## 4. 澄清与准备度

进入产品决策前，确认：

1. 问题和目标用户是真实需求，不只是预设方案。
2. 期望结果和成功判断可观察。
3. 范围、非目标、业务规则、异常路径和数据／权限影响已说明到足以决策。
4. 依赖、不可逆风险和关键假设已暴露。
5. 验收标准描述可观察行为，不规定无必要的实现细节。

这不是要求每条小需求填写完整 PRD。可逆的小改动只需最小需求条目；跨角色流程、状态机、权限、计费、数据、合规或多个发布单元的变化应进入正式 PRD。

对状态型、编辑型、多入口或跨视图能力，需求只记录与验收有关的行为不变量：动作何时对其他入口生效、何时持久化、哪个状态是唯一当前事实，以及退出、刷新、版本切换、失败恢复、草稿、撤销或人工提交如何处理。并非每项都必须存在；不存在同样应在可能产生歧义时写清。低风险小改动不展开内部保存、缓存或事务细节。

### 4.1 从自然语言形成需求草案

用户提出想法后，Product 在现有需求 owner 中完成加工，不创建平行的 `specs/` 目录或“当前 feature”状态指针：

1. 先进入需求池并取得稳定 REQ ID；需要多轮讨论时关联现有或新建编号任务计划。
2. 从原始描述提取问题、目标角色、触发、期望结果、范围、数据、约束、依赖和验收方向。
3. 把低风险且有充分项目依据的默认选择记为“假设”，不反复追问；不得以模糊的“行业标准”替代数据保留、认证、安全、支付、权限或合规决定。
4. 只询问会实质改变范围、产品行为、验收、数据、权限、成本或风险的问题。相互独立的问题可一轮提出，通常不超过三个；前一答案会改变后续问题时逐个询问。
5. 每个已确认答案立即更新需求草稿并删除失效或冲突表述；任务级取舍摘要进入关联编号计划，正式 REQ／PRD 只保留当前有效事实。
6. 需求达到本节准备度后进入 `ready`；G3-G4、正式评审或负责人明确要求时，还必须完成 Requirement Review 才能交接 Engineering。

澄清扫描按项目实际范围检查：角色与行为、数据和状态、主要流程与失败路径、权限与隐私、外部依赖、约束与取舍、术语一致性、验收可测试性以及未解决占位符。没有重要歧义时直接说明可以进入下一阶段，不为凑流程制造问题。

### 4.2 场景与价值切片

复杂需求可以在正式 REQ 中增加按需的“场景与价值切片”，每个切片说明角色／触发、行为或交付、可观察结果、独立价值和独立验收方式。切片用于帮助 Product、Engineering 和验收围绕端到端结果协作，不替代 Task、技术设计或测试计划，也不要求把自然需求强制改写成用户故事。需求目标、变化、业务逻辑、边界和验收已经完整清楚时，不为格式继续切分。

- 软件产品：用户场景、行为和可观察结果。
- 工作流：触发、输入、处理结果、失败与恢复。
- 媒体／内容：目标受众、素材边界、成品标准、审核与交付。
- POC：问题、假设、证据目标和晋级条件。
- 一次性交付：交付范围、质量标准和接受条件。

小改动无需填写该模块；不得为了形式把同一需求拆成没有独立价值的页面、接口、脚手架或技术层任务。

## 4.3 需求评审与晋级

需要多轮讨论或会影响多个阶段的需求使用以下链路：

```text
关联编号任务计划中的加工进度与关键取舍
→ Product owner 下的 REQUIREMENT_REVIEW
→ 处理评审意见
→ approved
→ product/requirements/REQ-<NNNN>-<slug>.md 或 PRD
```

每轮评审必须冻结评审对象的路径与版本／commit，记录意见、影响、处理决定、owner 和状态。`approved` 只表示需求可进入后续规划，不表示技术方案、实现、验收或发布已经完成。

重要产品取舍必须记录候选方案、最终选择、放弃理由和重新评估条件；任务级上下文留在编号任务计划，长期产品事实写入正式需求。

## 4.4 需求一致性自查

普通需求准备和实现前自查由 Product 主责，比较正式需求／PRD、验收标准、迭代承诺和关联 Task，重点识别重复、歧义、遗漏、术语漂移、相互冲突、不可验证标准和没有任务覆盖的已承诺需求。自查结果写入关联的 `REQUIREMENT_REVIEW.md` 或项目既有产品评审 owner，不另建第二份需求。

Product 自查只能声明当前覆盖范围内的一致性，不得包装成 independent review。负责人要求独立结论、跨领域争议裁决或 G3-G4 正式放行审查时，由 Assurance 冻结对象、覆盖和证据后形成独立报告；修订仍回到 Product owner。

## 5. 优先级与产品决策

优先级表示相对取舍，不表示严重度，也不自动形成承诺。项目可以使用排序、Now/Next/Later、MoSCoW 或自定义评分，但同一产品线应保持一种主要方法，并说明：

- 用户／业务价值和受影响范围。
- 紧迫性、风险降低或机会窗口。
- 依赖、成本级别和不做的代价。
- 证据置信度和关键假设。
- 决策人、日期和重新评估条件。

评分只辅助决策，不能伪造精确性。高分需求仍需经过范围、容量、依赖和风险判断；紧急故障可先止血，随后补齐产品影响和取舍记录。

## 6. PRD 与多产品边界

PRD 至少覆盖：产品背景和目标、用户与场景、范围与非目标、需求与业务规则、关键流程／状态、异常边界、权限／数据／合规、依赖与假设、成功判断、验收标准和未决问题。成功指标应说明可用的基线、目标、测量方式和时间窗口；没有证据基础时使用可观察的成功判断，不为每个小需求编造百分比或伪精确指标。

一个项目包含多个产品线、工具或明显不同的用户体验时：

- 顶层 PRD 只维护共同定位、共享能力和产品矩阵。
- 每条产品线使用独立 PRD 或明确章节，拥有独立范围、用户流程、验收和商业规则。
- Roadmap 决定当前阶段进入哪条产品线，不让顶层愿景静默扩大当前迭代。
- 共享登录、账户或平台能力可以统一，但订单、余额、账本、统计和发布节奏等产品事实必须明确归属。

## 7. Roadmap 与迭代承诺

Roadmap 以目标结果和阶段组织，不做无条件功能清单。每个阶段说明目标结果、成功标准、纳入的需求 ID、依赖、风险、置信度和进入／退出条件。日期和版本只有在获得真实承诺时才填写；否则使用 Now/Next/Later 或阶段名称。

迭代计划从 Roadmap 选择当前承诺，并区分：

- `committed`：容量、依赖和验收已确认的承诺范围。
- `stretch`：不影响承诺完成的候选范围。
- `out`：本迭代明确不做的范围。

临时插入必须先取得需求 ID，并记录新增、替换、缩减或延期了什么。迭代执行状态写入项目声明的 Durable Task State Owner；采用 BuildOS 新项目默认实例时使用 `governance/tasks/TASK-<NNNN>-<slug>.md`。迭代计划只保存产品承诺和范围变化。

## 8. 验收与收口

验收标准优先使用可观察行为：给定前置条件，当用户或系统执行动作时，应出现什么结果；同时覆盖关键异常、权限、数据和兼容边界。不要把“代码已提交”“测试通过”或“接口返回 200”单独当作产品验收。

最小追踪链为：

```text
来源 -> REQ-xxxx -> PRD/业务规则 -> Roadmap -> Iteration
     -> Task/实现与测试 -> 产品验收 -> 发布单元/真实发布证据
```

收口时逐项记录：验收标准、证据、结果、未通过项、例外确认和残余风险。`accepted` 只代表产品验收完成；是否发布、发布到哪里以及是否可回滚，读取 Delivery 的真实记录。

## 9. 变更与漂移治理

需求变化优先更新其事实 owner：

- 问题、用户、范围、业务规则或验收变化：更新 PRD 和需求条目。
- 优先顺序或阶段变化：更新 Roadmap。
- 当前承诺变化：更新 Iteration Plan，并记录影响。
- 执行边界或进度变化：更新编号任务计划。
- 技术方案变化：更新 Engineering 权威。
- 版本、部署或发布变化：更新 Delivery 权威。

不得只在聊天、Work Log、代码注释或提交信息中保存会影响后续工作的产品决定。Work Log 记录“发生了什么”，不能取代当前产品事实。

表现层等价变更默认不是 PRD 变更，由设计系统、组件实现、可见回归或项目已有设计规范承载。其判据是产品语义、信息层级、交互可供性、可访问性、品牌硬契约和明确验收结果保持不变，而不是修改对象属于某个样式属性、文案字段或布局参数；任一契约发生变化时，更新最小产品事实。

现存实现、历史页面、旧测试和旧文档是产品证据，不是当前需求 owner。用户可见能力是否新增、保留、恢复或移除，必须回指当前有效的需求与验收记录；小项目可使用负责人确认的最小需求记录，不强制完整 PRD。

技术方案可以决定如何实现，但若为了性能、一致性、兼容或实现便利而新增或删除用户动作、可见状态，改变生效／持久化时机、撤销／恢复方式或验收结果，就已经形成产品契约变化。Engineering 必须提交原行为、技术问题、用户影响和尽量保持原行为的替代方案，由 Product 更新并确认需求；不得用实现分支随后补写的 PRD 或测试反向证明该变化本来就是需求。

## 10. 按项目形态裁剪

- 持续产品：使用完整 Backlog、PRD、Roadmap 和 Iteration 链路。
- 一次性交付：可将 Roadmap 合并为阶段计划，但必须保留范围、验收和变更依据。
- 小脚本或内部工具：通常只需最小需求条目和验收标准，不强制完整产品体系。
- POC／探索：在实验 owner 中记录问题、假设、证据目标和运行状态；未验证结论不得进入正式产品承诺，
  已验证结论也只有在负责人决定生产化后才形成新的需求／迭代切片。
- 复合项目：按产品线或交付单元拆分范围与验收，共享事实只保留一个 owner。
