# 需求与产品迭代管理规范

本规范只管理产品文档怎样产生、流转、冻结和回写。具体写哪些内容由对应模板提示；技术实现、任务进度、版本制品和真实发布分别由 Engineering、项目任务 owner 和 Delivery 负责。

## 1. 文档职责与流转

```text
可选用户需求
    ↓ 负责人决定进入某个版本
版本产品需求文档（PRD）
    ├─ 按需版本技术设计
    ├─ 按变化和风险形成测试用例
    └─ 使用契约变化时更新并走查现有用户文档
    ↓ 开发与验收
当前产品规格书
    └─ 存在长期技术事实变化时，更新系统技术规格书
```

| 文档 | 何时存在 | 唯一职责 | 模板 |
| --- | --- | --- | --- |
| `product/USER_REQUIREMENTS.md` | 可选 | 接住值得保留的零散想法和反馈，在条目旁记录状态与处理版本 | `USER_REQUIREMENTS.template.md` |
| `versions/<version>/PRD.md` | 一个产品版本进入开发时 | 定义本版本的目标、变化、产品行为和验收，是开发与测试依据 | `PRD.template.md` |
| `versions/<version>/TECHNICAL_DESIGN.md` | 技术选择或实现边界确需长期说明时 | 说明本版本怎样实现 | `TECHNICAL_DESIGN.template.md` |
| `versions/<version>/TEST_CASES.md` | 需要保存版本级测试设计时 | 从 PRD 提取匹配风险的测试用例 | `TEST_CASES.template.md` |
| `product/PRODUCT_SPECIFICATION.md` | 项目需要持久产品全貌时 | 保存当前完整、有效的产品事实 | `PRODUCT_SPECIFICATION.template.md` |
| `engineering/SYSTEM_TECHNICAL_SPECIFICATION.md` | 长期代码项目需要持久技术全貌时 | 保存当前完整、有效的系统技术事实 | `SYSTEM_TECHNICAL_SPECIFICATION.template.md` |

项目已有等价文档或外部产品系统时，映射现有 owner，不建立第二套事实。

Get Started、教程、用户手册、CLI／SDK／API Reference 等用户文档继续由项目现有文档 owner 维护，不加入上述产品文档层级。它们在安装、配置、公开调用或操作路径改变时成为受影响的产品表面；Product 只在 PRD 中声明必须保持的使用契约、验收入口和当前正式文档位置，不复制文档正文，也不要求没有长期用户入口的项目新建文档站。

公开产品的 README、官网、应用商店页或代码托管项目简介属于现行产品表面。正式版本准备时，Product 按本次实际变化复审定位、目标用户、核心问题、能力、设计理念、边界和安装／使用入口；受影响正文与已有语种同步更新，不把版本号替换冒充内容复审，也不复制内部任务、参考来源或未经证明的效果。项目应在一个现有产品 owner 中记录本版本审阅结果；没有语义变化时记录已复核及依据，不为此制造平行宣传文档。

## 2. 模板使用规则

创建文档时复制对应模板，再按事实填写：

1. “必要内容”只表示：已经决定创建这份文档后，这些信息通常要足以识别文档、范围和结果；它不表示每个任务都必须创建该文档。
2. “按需内容”只在当前产品形态、变化、歧义或风险确实涉及时保留；不涉及就删除标题和提示。
3. 模板中的注释是写作提示，完成后删除；不保留空表、`待确认` 或成排的“不适用”。
4. 可以改名、合并或重复内容模块，但不能丢失本次实现和验收真正依赖的事实。
5. 小改动只写最小充分内容。不得因为模板存在页面、接口、权限、性能等提示就逐项扩写。

统一的是文档职责和大体组织方式，不是标题数量、字段数量或篇幅。AI 应像使用作文提纲一样使用模板，不把它执行成 schema、校验器或审批流。

## 3. 用户需求到版本 PRD

用户需求池不是强制入口。负责人可以先记录想法，也可以直接讨论并形成一个版本 PRD。

讨论深度由当前不确定性和影响决定，不设所有需求共用的审批仪式：

- **探索式讨论**：方向、用户问题或价值仍不确定时，先比较目标、证据、反例、替代和停止条件；输出候选与未知，不伪造已冻结范围。
- **边界式讨论**：目标明确、变化局部且风险有限时，只澄清会改变范围、行为、验收、数据、权限、成本或风险的事项，直接形成最小充分产品结论。
- **架构式讨论**：跨角色流程、状态机、权限、计费、核心数据、迁移或多个发布单元发生变化时，先说明端到端流程、不变量、异常恢复、非目标和可观察验收，再交 Engineering 设计。

已有 owner 和上下文已足够时不为了“完成讨论”重复提问或等待单独批准；未知项只有会静默改变结果时才阻断。讨论过程留在任务 owner，PRD 只保存当前有效结论。

接收准备实现的需求时，先从产品 owner 和当前上下文判断它属于当前开放版本、后续版本还是尚未承诺的需求池。已有开放版本且新需求与其目标、验收和交付时间一致时直接纳入，不逐项向负责人重复确认；不同归属会改变范围或交付时间且无法从现有事实判断时，只确认这一项产品选择。尚未开始实现的后续需求只记录版本意图，不为规划本身创建代码分支。

版本号遵循项目现行策略和已批准变化。修复、兼容新增和不兼容变化可以形成补丁、次版本或主版本候选，但不得只根据当前版本数字自动决定；讨论中范围变化时先保留“当前补丁批次／后续功能版本／继任版本”等产品角色，范围稳定后再锁定准确版本。

需求池存在时，状态和处理版本直接写在条目旁；不建立关系表、追踪矩阵或复杂状态机。只有确实需要长期独立追踪时才增加稳定 ID。投入大、证据薄、方向不确定或失败难回退时，才按需补充机会评估；低成本可逆调整不为流程延迟验证。

每个进入开发的产品版本只有一份 PRD。PRD 至少要让产品、开发、测试和 AI 对本次变化与验收没有实质歧义，具体内容直接使用 `PRD.template.md`：

- 页面型产品按页面、功能和具体需求组织；
- 无页面能力按能力／流程及其触发、规则、结果、异常和验收组织；
- 前端和后端只描述用户可观察或业务必须完成的产品行为，组件、函数、表结构和部署方案进入按需技术设计。

一个字段、文案或局部行为变化可以只保留版本信息、具体变化和验收。跨角色流程、状态机、权限、计费、数据、合规或多个发布单元的变化，应按真实风险展开模板中的相关模块。

若修改只是让实现恢复到当前产品规格，产品契约没有变化，则更新代码和匹配测试即可，不新建 PRD。

负责人明确说某项功能“不要了”“删除”“取消”或“永久下线”时，默认产品结果是**永久退役**：所有用户、系统和外部调用方都不应再触发该能力，验收同时说明需要保留的替代行为、历史数据读取／迁移和合规边界。只有负责人明确要求临时隐藏、暂停、灰度关闭或保留回滚／兼容面时，才把隐藏或开关停用当作目标，并记录适用范围和退出条件。永久退役不自动授权销毁历史业务数据、审计记录或回滚证据；这类破坏性处置必须单独决定。

## 4. 开发、测试与验收

PRD 是实现和测试的产品输入，但不负责技术方案或实时任务状态：

- 需要技术设计时，由 Engineering 复制 `TECHNICAL_DESIGN.template.md`；框架参数、文案或局部字段即可完成的变化通常不创建。
- 需要版本测试用例时，由 Engineering 复制 `TEST_CASES.template.md`，沿用 PRD 的页面／功能／能力结构，并只覆盖匹配风险。
- 任务拆解和进度写入项目声明的 Durable Task State Owner，不复制进 PRD。

进入实现前只确认当前范围真正需要的准备度：目标、变化、关键规则、失败／权限／数据影响和可观察验收足以实现与测试；未知项不会静默改变范围或验收。低风险小改不建立独立评审或完整文档链。

PRD 或项目等价产品 owner 必须声明本次 **Acceptance Authority**：谁有权把精确候选从 `implemented` 判为 `accepted`，哪些客观检查可以委托给 Agent／测试，哪些产品语义、体验取舍或业务风险必须由负责人判断。执行验证可以委托，验收权威和发布授权不能由实现者、测试绿灯或文档自述自行取得。验收结论绑定实际候选身份；代码、配置、产品行为或受影响用户文档变化后，只使对应范围的旧验收失效并重新核对，不机械重验无关能力。

当本版本改变安装、配置、用户操作、公开 API、CLI、SDK 或故障恢复路径时，PRD 同时列出受影响的现行用户文档入口和可观察结果。验收至少从代表性起点按现行文档走通一个受影响核心任务；命令、代码示例和结果必须与候选一致。静态构建、链接可达或文案看似完整只证明局部质量，不能替代 walkthrough。没有外部用户、没有长期使用入口或一次性探索时，按项目形态裁剪，不为满足模板制造教程或站点。

实现完成、测试通过、产品验收和真实发布是四个不同事实，不能互相冒充。

## 5. 验收后的当前规格

产品验收通过后记录 Acceptance Authority、绑定候选与实际证据，并冻结该版本 PRD 和已存在的技术设计／测试用例：

- 把实际生效的产品变化合入 `PRODUCT_SPECIFICATION.md` 对应位置，并删除被替代的旧逻辑；
- 存在长期技术事实变化时，把它合入 `SYSTEM_TECHNICAL_SPECIFICATION.md`，并删除被替代的旧事实；
- 历史通过 Git 和版本文档回溯，不在当前规格书中累计历代正文；
- 是否已部署、生产生效或可回滚，仍读取 Delivery 事实。

大型产品或系统可以把当前规格书拆成索引和页面／模块子文档，但逻辑上仍各自只有一个当前 owner。

## 6. 新项目与成熟项目

新项目使用下列相对路径作为默认职责映射，但初始化不为未知版本创建空目录或空版本文档：

```text
product/
  USER_REQUIREMENTS.md              # 可选
  PRODUCT_SPECIFICATION.md          # 当前产品事实
versions/<version>/
  PRD.md                             # 本开发版本产品依据
  TECHNICAL_DESIGN.md                # 按需
  TEST_CASES.md                      # 按需，依据 PRD
engineering/
  SYSTEM_TECHNICAL_SPECIFICATION.md # 当前技术事实
```

成熟项目先盘点现有产品文档、页面、代码、接口、测试和运行事实，再映射现有 owner。缺少当前全貌时，先基于证据重建产品规格书和系统技术规格书，区分确认事实、合理推断、冲突和未知；不伪造过去的需求池或版本 PRD。后续版本再采用统一流转，不为目录整齐一次性搬迁全部资料。

目录、流转和模板都不得成为制造空文档、重复正文、审批等待或无意义上下文的理由。
