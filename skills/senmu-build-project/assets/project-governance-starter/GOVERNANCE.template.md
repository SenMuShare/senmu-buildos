## 核心原则

### 1. 权威事实优先

以负责人当前明确指令、项目入口和可验证的代码、配置、数据、运行与交付事实作为决策依据。聊天记忆、候选模板、历史副本和未验证推断不得覆盖当前权威事实。

### 2. 一个事实一个 Owner

需求、技术设计、任务状态、运行状态、版本、交付和经验分别由唯一责任主体维护。其他文档只保存稳定标识和链接，不建立需要同步的平行副本。

### 3. 最小价值切片

优先完成从权威输入到可运行结果、匹配验证和可交付输出的最小闭环。脚手架、抽象、平台化和门禁不得长期先于核心价值完成。

### 4. 源头治理优先

优先修正产生问题的需求、职责、架构、接口、数据模型、默认值、实现和运行流程。检查、清单和审批只控制仍无法从源头消除的重要剩余风险。

### 5. 治理强度与风险匹配

可逆的 G0-G2 工作保持轻量；发布、生产、安全、权限、支付、数据、迁移和破坏性操作按 G3-G4 执行可验证、可恢复且失败关闭的控制。

### 6. 授权、证据与可恢复

开发、验收、发布和生产状态必须分开表达。任何外部写入、发布、删除或不可逆操作都需要匹配授权；完成结论必须有证据，重大变更必须有恢复依据。

## 权威顺序

1. 项目负责人当前明确指令。
2. `AGENTS.md` 或等价 AI 入口。
3. 当前启用模块的需求、技术、工作流、实验、交付规范及项目 policy。
4. 代码、配置、数据库、源物料、运行状态、测试和交付事实。
5. policy 声明的最近工作日志与有效经验条目（如存在）；二者不能覆盖更高层权威事实。

## 开工与完工

- 开工：确认当前目标、权威项目根、运行/状态入口、最终交付定义和本次需要的治理模块；需要分步骤、分阶段、跨 Agent 或跨会话时，使用 policy 声明的 Durable Task State Owner。`core` 未启用专用任务体系时沿用 README、Issue 或外部任务系统，不自行补建空台账。
- 新建前：先查 `governance/PROJECT_MAP.md`（如存在）、既有实现、共享能力和 legacy 边界；能够归入现有责任主体时不得另建平行目录、组件、流程或版本。
- 执行：按任务风险选择 G0-G4；保留输入、实现/运行、验证和结果之间的对应关系。
- 完工：运行匹配的质量/验收命令和项目 validator；只更新真正受影响的需求、流程、状态、交付、版本或工作日志。
- 交付/发布：记录最终位置、接受状态和恢复依据；只有项目实际存在版本、部署或发布时才更新相应事实。
- 踩坑：先修正产生缺陷的需求、架构、接口、默认值、实现或操作流程并验证；policy 已声明经验 owner 时才登记可重复问题，`core` 不为单次经验自动建立台账；仅对无法从源头消除且影响显著的剩余风险补最小机器门禁。

## 章程修订与例外

- 本章程是项目级长期治理 owner。需求、技术设计、任务状态和发布事实分别进入各自专业 owner，不在本文件复制正文。
- 修改核心原则、权威顺序或不可放弃的治理边界时，必须说明原因、影响范围、迁移方式和验证办法，并更新治理版本。
- `MAJOR`：删除原则、重新定义权威关系或做不兼容治理变更；`MINOR`：新增原则或实质扩展治理能力；`PATCH`：澄清、纠错或不改变语义的调整。
- 例外必须记录适用原则、理由、批准者、范围、期限／失效条件、风险和验证方式。G3-G4 不允许用未记录例外绕过安全、权限、数据、发布完整性或恢复门禁。
- 当前任务中的临时要求如果应长期适用，必须晋级为章程修订或对应专业规则；如果只适用于当前任务，保留在编号任务计划，不污染长期章程。
