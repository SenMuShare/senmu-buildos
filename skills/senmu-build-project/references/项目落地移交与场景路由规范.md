# 项目落地移交与场景路由规范

本规范用于避免 Senmu BuildOS 在项目落地后变成日常开发的额外负担。BuildOS 是按需调用的通用治理基线；项目入口是该基线上的差异层。项目只沉淀真实项目事实、权威入口、可执行命令、特有规则和明确覆盖，不复制 BuildOS 已有正文。

## 本页导航

1. Skill 生命周期；2. 项目形态与模块；3. 落地移交产物；4. 落地后的调用边界；5. 场景路由；6. 最小交付物；7. 项目内规范优先级；8. 可执行契约移交；9. 反臃肿维护。

## 1. 项目处境与生命周期入口

先按项目当前处境选择入口，不把四种处境拆成四套 Skill：

| 项目处境 | 正确入口 | 禁止行为 |
| --- | --- | --- |
| 新项目尚未开始 | 先确认目标、形态和真实交付方式，零写入生成初始化候选；用户批准后建立最小项目 owner | 未确认范围就生成整套目录、文档、分支和发布设施 |
| 新项目已进入正常开发 | 读取项目已落地的需求、代码、质量和交付入口，按当前任务调用一个匹配专业 owner | 每个需求都重新初始化或回读整套 BuildOS |
| 已有项目继续开发 | 继承现有项目事实、当前开发版本和已登记任务／分支；规则足够时直接完成增量工作 | 因项目“老”就自动重做目录、Git、文档或治理体系 |
| 已有项目整体治理 | 先只读盘点权威、结构、质量和交付事实，再按用户批准的范围演进原 owner；跨多阶段时使用成熟项目接管专项 | 用默认模板覆盖现状，或把治理和普通功能需求混成一次无边界改造 |

初始化完成后，把项目事实和项目特有契约写入现有 README、AI 入口、代码／架构、需求、流程和交付 owner；与 BuildOS 相同的通用方法不复制。日常开发只按项目入口执行，规范缺失、冲突、过时或用户明确要求整体治理时才回到 BuildOS 校准。

## 2. 项目形态与模块选择

项目形态用于选择默认模块，不用于限制项目。先选主形态，再补充次要模块：

| 项目形态 | 默认模块 | 通常不必强制 |
|---|---|---|
| 软件产品/服务 | 需求规划、架构代码、Git、测试、发布部署 | 媒体物料目录 |
| 脚本/CLI/自动化 | 输入输出、代码质量、Git、可重复验证 | PRD、路线图、迭代 |
| 工作流/Codex Harness | 流程契约、状态源、运行身份、恢复、回执、物料交付 | 产品版本号，除非对外发布 |
| 视频/图片/内容生产 | 来源、staging、审阅、最终物料、发布状态、归档 | 软件架构文档，除非代码复杂度需要 |
| POC/研究 | 实验问题、冻结输入、证据、决策、升级/归档 | 正式发布流程 |
| 混合项目 | 组合相关模块，并划分发布/交付单元 | 全项目共用一个含糊版本 |

当项目实际包含代码、数据库、媒体、外部素材或正式发布时，分别叠加对应模块。模块是否启用由真实风险和交付方式决定，不由目录名称决定。

## 3. 落地移交产物

初始化完成后，项目至少应有一个项目内入口，告诉后续 AI 去哪里找规则。

采用 BuildOS 的项目中，`AGENTS.md` 或等价入口是 **Project Delta Layer（项目差异层）**，不是 BuildOS 的项目副本。它必须能定位项目事实和命令，但无需在 BuildOS 未安装时复现整套治理方法；项目选择移除 BuildOS 时，应先把仍需保留的规则迁移到新的权威基线。

推荐落点：

```text
AGENTS.md 或等价 AI 入口
README.md
engineering/CODE_QUALITY.md
engineering/SYSTEM_TECHNICAL_SPECIFICATION.md、现有等价架构 owner 或按需 TECHNICAL_DESIGN.md 中的技术契约
engineering/TECH_DEBT.md（存在真实债务时）
engineering/languages/<LANGUAGE>.md
governance/GOVERNANCE.md
.senmu-buildos/config.json
governance/tasks/TASK_REGISTER.md
.senmu-buildos/templates/TASK.md
delivery/BRANCHING.md
delivery/RELEASE_PLAN.md
governance/logs/WORKLOG.md
governance/lessons/LESSONS_LEARNED.md
operations/DEPLOYMENT.md
engineering/TESTING_STRATEGY.md
```

小项目可以合并为更少文件，但必须能回答：

- 项目是什么，当前范围是什么？
- 需求和技术方案在哪里？
- 代码质量、当前语言规范和统一检查命令在哪里？
- 模块职责、依赖方向、数据所有权、架构检查和技术债在哪里？
- 本地启动、测试、部署怎么做？
- 分支、版本、changelog、发布和回滚怎么做？
- POC 放在哪里、是否进入 Git、如何保留/备份、由哪个命令校验？
- 最近做了什么、哪些失败模式不得重复、对应检测命令是什么？
- 后续 AI 接手时先读哪些文件？
- 当前有哪些需要持续跟踪的任务、每项进行到哪里、从哪里恢复？

## 4. 落地后的调用边界

项目 owner 已经给出当前任务所需事实、规则和命令时，直接按项目执行并停止治理路由；“先读项目”不是再把 BuildOS 全文读一遍。

只有当前工作需要建立或改变长期治理决定，而项目规则缺失、冲突、明显过时，或负责人明确要求治理／审查时，才加载一个匹配 Skill 及其必要 reference。高风险事项已有清晰且有效的项目控制时继续服从项目；控制缺失或冲突时只补对应专业缺口，不自动组合全部 Skill。

普通实现、Bug 修复、代码解释、单条文案、局部样式和既有流程执行默认不调用 BuildOS。实施中发现产品、工程、流程、交付或项目契约确有缺口时，再切换到下表中的唯一主责 Skill。

## 5. 需要 BuildOS 时的专业路由

| 需要建立或改变的结果 | 主责 Skill | 适用边界 |
| --- | --- | --- |
| 项目初始化、结构、权威映射、治理迁移或跨阶段状态 owner | `senmu-build-project` | 只处理项目治理实例；现有任务系统的日常使用不触发 |
| 持久产品范围、版本归属、优先级、验收或跨页面内容标准 | `senmu-build-product` | 单条契约保持型改写和普通澄清不触发 |
| 工作流契约、项目 Agent、物料流转、回执或可恢复运行状态 | `senmu-build-workflow` | 执行已经明确的流程不触发 |
| 工程契约、架构、测试策略、技术债或重构规则 | `senmu-build-engineering` | 只在项目规则缺失、冲突、变化或明确要求治理时触发 |
| POC、独立审查、复现或争议原因裁决 | `senmu-build-assurance` | 需要证据化独立结论时触发，不负责实施修复 |
| 开放开发批次、非常规 Git 边界、版本、制品、部署、回滚或生产状态 | `senmu-build-delivery` | 已治理批次内的普通实现不触发；未明确发布时保持不发布 |
| BuildOS 使用反馈审议、正式复盘、经验晋级或外部规则蒸馏 | `senmu-build-learning` | 普通用户纠正和项目业务需求不进入反馈箱 |

上述场景只要跨越多个依赖步骤、阶段、Agent 或会话，均按《任务执行与状态管理规范》登记到项目声明的 Durable Task State Owner；采用 BuildOS standard/release 默认实例时才写入 `governance/tasks/`，core 沿用已声明的轻量 owner。场景专业文档保存领域事实，任务状态保存当前边界、进度、证据链接和恢复入口，两者不得互相替代。

## 6. 最小交付物矩阵

| 等级 | 最小交付物 |
| --- | --- |
| G0 | 回答依据、关键假设、下一步建议 |
| G1 | 改动点、影响范围、验证或未验证说明 |
| G2 | 改动、匹配测试、必要文档同步、必要工作日志 |
| G3 | 版本、changelog、发布/部署记录、线上验证、回滚点 |
| G4 | 风险处置、验证证据、复盘、规范更新或不更新原因 |

## 7. 项目内规范优先级

当项目内规范和 Senmu BuildOS 不一致时：

- 项目真实运行／交付证据和 active 专业 owner 决定项目事实；项目明确覆盖项优先于 BuildOS 通用默认。
- 同义规则不形成冲突：删除项目副本，只保留 BuildOS 基线；项目入口可保留权威路径或真实命令。
- 项目规则疑似过时、多个项目 owner 互相矛盾，或项目覆盖会降低 BuildOS 声明的不可放弃 Hard Gate 时，Agent 不自行猜测，向用户列出具体冲突、证据、影响和建议，由用户裁决。
- 裁决后只更新一个项目专业 owner，并在项目差异层保留必要导航或覆盖；不得同时修改多份同义正文。

## 8. 可执行契约移交

对重复生产、发布、数据处理、内容生成、素材加工等长期链路，项目内文档不能只停留在“人读懂”的 SOP。若同一链路已经发生多次 AI 返工或负责人纠偏，应把项目规则移交为可执行契约。

对代码项目，源代码质量和架构边界也按同一原则移交：用短 AI 入口路由到项目权威规范，用架构契约、技术债台账、语言生态标准配置和统一质量命令表达机器事实，并让本地、提交前检查和 CI 复用同一契约。

最小移交形态：

- 一个公开入口或清晰的项目类型分流入口。
- 一个机器可读 policy/config/schema，记录当前标准和版本。
- 入口脚本、数据库/台账、中间 manifest 或发布计划写入该 policy/config/schema 的 ID。
- 一个 doctor 或 validator 命令，能检查入口、配置、脚本、台账和产物字段是否互相一致。
- 涉及 POC 时，policy 还必须登记唯一 `POC_ROOT`、`tracking_mode`、保留等级、备份策略和禁止写入的位置；
  validator 必须从外部 worktree 反例验证物理归属并扫描历史残留。
- 一条 legacy 规则，说明旧脚本、旧缓存、旧产物、旧 Demo、旧发布版本在什么场景下只能作为历史参考，不能作为新任务默认样板。

只有当链路具备这些要素时，才可以认为规则已经从“聊天/文档记忆”移交为“后续 AI 可稳定执行的项目能力”。

## 9. 反臃肿维护规则

维护 Senmu BuildOS 时：

- 优先补现有 reference；只有新主题无法自然归入现有 reference 时才新增文件。
- 新增 reference 必须从 `SKILL.md` 直接可发现。
- 不要把项目私有 SOP、客户信息、服务器路径或商业细节写进通用 skill。
- 不要把 BuildOS 通用正文复制进项目 `AGENTS.md`、项目业务 Agent 或专业文档；项目只保留差异、事实、路径和命令。
- 技术栈深水区和 vendor 文档应作为按需附件，不应进入入口主流程。
- 已接入官方 MCP/CLI 的生态（如 Ant Design）优先使用官方工具；ECharts、播放器、编辑器等 vendor 资料只保留小型摘要、meta 或项目外快照。更适合长期拆成专业 frontend/admin skill 时，可以只在 `senmu-build-engineering` 保留原则和路由。
- 每次版本更新后检查：是否让入口变重、是否重复已有规则、是否能通过治理等级限制触发范围。
