# 项目落地移交与场景路由规范

本规范用于避免 Senmu BuildOS 在项目落地后变成日常开发的额外负担。它的核心定位是：项目初始化、治理校准和重大治理事件的母版；项目落地后，应把规则沉淀为项目内文档，由项目内文档接管日常执行。

## 本页导航

1. Skill 生命周期；2. 项目形态与模块；3. 落地移交产物；4. 落地后的调用边界；5. 场景路由；6. 最小交付物；7. 项目内规范优先级；8. 可执行契约移交；9. 反臃肿维护。

## 1. Skill 的生命周期定位

Senmu BuildOS 不应成为每次日常开发都必须回读的大手册。

默认生命周期：

1. 初始化期：用 Senmu BuildOS 建立项目目录、文档、分支、版本、部署、测试和协作规则。
2. 落地期：把通用规则改写成项目自己的 README、AI 入口、CODE_QUALITY、ARCHITECTURE／TECHNICAL_DESIGN、必要的 TECH_DEBT、语言专项规则、PRD、DEPLOYMENT、TESTING_STRATEGY、VERSION_AND_RELEASE、BRANCHING、WORKLOG 等。
3. 日常期：AI 优先读取项目内文档和最近工作日志，不再默认调用 Senmu BuildOS。
4. 校准期：当项目规范缺失、冲突、过时或发生重大治理事件时，再回到 Senmu BuildOS 校准。

## 2. 项目形态与模块选择

项目形态用于选择默认模块，不用于限制项目。先选主形态，再补充次要模块：

| 项目形态 | 默认模块 | 通常不必强制 |
|---|---|---|
| 软件产品/服务 | 需求规划、架构代码、Git、测试、发布部署 | 媒体物料目录 |
| 脚本/CLI/自动化 | 输入输出、代码质量、Git、可重复验证 | PRD、路线图、迭代 |
| 工作流/Codex Harness | 流程契约、状态源、运行身份、恢复、回执、物料交付 | 产品版本号，除非对外发布 |
| 视频/图片/内容生产 | 来源、staging、审阅、最终物料、发布状态、归档 | 软件架构文档，除非代码复杂度需要 |
| POC/研究 | 实验问题、冻结输入、证据、决策、升级/归档 | 正式发布流程 |
| 混合项目 | 组合相关模块，并划分发布/交付单元 | 全项目共用一个含糊版本 |

当项目实际包含代码、数据库、媒体、外部素材或正式发布时，分别叠加对应模块。模块是否启用由真实风险和交付方式决定，不由目录名称决定。

## 3. 落地移交产物

初始化完成后，项目至少应有一个项目内入口，告诉后续 AI 去哪里找规则。

推荐落点：

```text
AGENTS.md 或等价 AI 入口
README.md
engineering/CODE_QUALITY.md
engineering/ARCHITECTURE.md 或 TECHNICAL_DESIGN.md 中的架构契约
engineering/TECH_DEBT.md（存在真实债务时）
engineering/languages/<LANGUAGE>.md
governance/GOVERNANCE.md
.senmu-buildos/config.json
governance/tasks/TASK_REGISTER.md
.senmu-buildos/templates/TASK.md
delivery/BRANCHING.md
delivery/RELEASE_PLAN.md
governance/logs/WORKLOG.md
governance/lessons/LESSONS_LEARNED.md
operations/DEPLOYMENT.md
engineering/TESTING_STRATEGY.md
```

小项目可以合并为更少文件，但必须能回答：

- 项目是什么，当前范围是什么？
- 需求和技术方案在哪里？
- 代码质量、当前语言规范和统一检查命令在哪里？
- 模块职责、依赖方向、数据所有权、架构检查和技术债在哪里？
- 本地启动、测试、部署怎么做？
- 分支、版本、changelog、发布和回滚怎么做？
- POC 放在哪里、是否进入 Git、如何保留/备份、由哪个命令校验？
- 最近做了什么、哪些失败模式不得重复、对应检测命令是什么？
- 后续 AI 接手时先读哪些文件？
- 当前有哪些需要持续跟踪的任务、每项进行到哪里、从哪里恢复？

## 4. 落地后的调用边界

项目已经有稳定规范后，日常任务优先读项目内文档。

仍然需要调用 Senmu BuildOS 的情况：

- 新项目初始化或老项目补治理骨架。
- 项目内规范互相冲突，需要重新校准。
- 项目负责人要求检查架构、技术债、代码是否逐步失控或版本治理是否混乱。
- 新增发布单元、重做目录结构、重定版本/分支/部署规则。
- Hotfix、生产发布、回滚、安全、支付、权限、数据迁移等高风险事项缺少项目内门禁。
- AI 踩坑、返工或复盘后判断属于通用治理缺口。
- 已有项目文档和工作日志仍无法阻止同一正式链路反复回到旧流程，需要做可执行契约收敛。
- 项目负责人明确要求按 Senmu BuildOS 重新审视项目。

不需要调用 Senmu BuildOS 的情况：

- 项目已有清晰规则，且只是按项目规则完成普通日常开发。
- 纯代码解释、轻量文案修改、局部样式调整。
- 项目内文档已经明确回答了本次问题。
- 项目本地 AI 入口、代码质量规则和实际语言／框架规范已经明确回答普通编码或评审问题。

## 5. 场景路由表

| 用户场景 | 治理等级 | 先读什么 | 最小交付物 |
| --- | --- | --- | --- |
| 先讨论需求/范围 | G0-G2 | README、PRD、项目内工作日志；必要时读项目实践指南 | 需求边界、疑问、是否需要改文档 |
| 初始化新项目 | G2 | 项目实践指南、项目目录与文档规范、技术路线规范、源代码工程质量规范 | 项目目录、核心文档、AI/治理入口、质量命令、下一步计划 |
| 普通功能开发 | G2 | 项目内 AI 入口、CODE_QUALITY、适用语言规则、PRD、TECHNICAL_DESIGN、相关代码、测试说明 | 代码/文档同步、质量命令和测试结果、必要工作日志 |
| 轻量修改 | G1 | 相关文件和项目内约定 | 改动说明、验证或未验证说明 |
| 普通 Bug 修复 | G2 | 项目内 AI 入口、CODE_QUALITY、适用语言规则、问题上下文、相关代码、测试说明、工作日志 | 修复、回归测试、质量验证、必要工作日志 |
| 脚本/自动化项目 | G1-G3 | README/AI入口、输入输出契约、代码和 Git 规则 | 可重复命令、输入输出样例、验证和版本/交付说明 |
| 工作流/Harness 建设 | G2-G4 | 流程契约、schema/config、状态源、物料与交付规范 | 公开入口、run identity、状态恢复、回执、最终交付路径 |
| 视频/图片/内容生产系统 | G2-G4 | 来源/授权、工作流、staging、验收、交付和发布规则 | 来源可追溯、过程可恢复、最终物料和真实发布状态 |
| POC/技术路线实验 | G2-G3 | 项目 AI 入口、POC policy、权威根规则、实验治理规范 | 唯一 POC_ROOT、tracking_mode、实验账本/manifest、validator 与残留检查 |
| Hotfix/正式发布 | G3 | 项目内 VERSION/CHANGELOG/DEPLOYMENT/WORKLOG；必要时读发布规范 | 版本、changelog、制品、线上验证、回滚依据 |
| 生产事故/安全/支付/权限/数据 | G4 | 项目内安全/部署/日志；必要时读部署、安全、复盘规范 | 止血、验证、复盘、项目规范更新 |
| AI 踩坑或负责人纠偏 | G2-G4 | 工作日志、`senmu-build-learning` 复盘规范；争议证据按需组合 Assurance | 根因分类、修复验证、项目经验或 BuildOS 整仓反哺判断 |
| 正式链路反复回到旧流程 | G3-G4 | 项目入口、需求/技术/SOP、工作日志、复盘台账、现有脚本和台账字段 | 可执行契约收敛：入口、policy、台账字段、validator、legacy 边界 |
| 老项目治理补齐 | G2-G3 | README、现有 AI/质量规则、工具配置、现有 docs、项目目录与文档规范、源代码工程质量规范 | 缺口清单、质量基线、最小文档集、优先级 |
| 成熟项目长期接管治理 | G2-G4 | 项目入口、任务状态 owner、运行／发布基线、成熟项目接管治理专项规范 | 可恢复专项任务、冻结基线、Coverage Map／Finding、用户决定、整改波次、复核与临时内容去留决定 |
| 工程治理与技术债审查 | G2，发现高风险后可升级 | 项目入口、技术设计／架构契约、代码质量、测试、版本发布、工作日志、架构与技术债治理规范 | 证据化审查报告、P0-P3 问题、质量／债务基线、分阶段整改建议；默认不改业务代码 |

上述场景只要跨越多个依赖步骤、阶段、Agent 或会话，均按《任务执行与状态管理规范》登记到项目声明的 Durable Task State Owner；采用 BuildOS standard/release 默认实例时才写入 `governance/tasks/`，core 沿用已声明的轻量 owner。场景专业文档保存领域事实，任务状态保存当前边界、进度、证据链接和恢复入口，两者不得互相替代。

## 6. 最小交付物矩阵

| 等级 | 最小交付物 |
| --- | --- |
| G0 | 回答依据、关键假设、下一步建议 |
| G1 | 改动点、影响范围、验证或未验证说明 |
| G2 | 改动、匹配测试、必要文档同步、必要工作日志 |
| G3 | 版本、changelog、发布/部署记录、线上验证、回滚点 |
| G4 | 风险处置、验证证据、复盘、规范更新或不更新原因 |

## 7. 项目内规范优先级

当项目内规范和 Senmu BuildOS 不一致时：

- 项目明确规则和真实状态是当前事实权威，不得被默认模板覆盖。
- BuildOS 是治理标准；已有规则存在缺失、冲突、重复、过时或不可搬迁问题时，应提出并在授权后实施演进，而不是永久保留现状。
- 安全、密钥、隐私、生产数据、支付、权限和正式发布的 Hard Gate 不应被项目随意降级。
- 如果项目规则落后或互相矛盾，应先指出冲突，再建议按 Senmu BuildOS 校准。
- 校准后必须更新项目内文档，不能只在聊天里说明。

## 8. 可执行契约移交

对重复生产、发布、数据处理、内容生成、素材加工等长期链路，项目内文档不能只停留在“人读懂”的 SOP。若同一链路已经发生多次 AI 返工或负责人纠偏，应把项目规则移交为可执行契约。

对代码项目，源代码质量和架构边界也按同一原则移交：用短 AI 入口路由到项目权威规范，用架构契约、技术债台账、语言生态标准配置和统一质量命令表达机器事实，并让本地、提交前检查和 CI 复用同一契约。

最小移交形态：

- 一个公开入口或清晰的项目类型分流入口。
- 一个机器可读 policy/config/schema，记录当前标准和版本。
- 入口脚本、数据库/台账、中间 manifest 或发布计划写入该 policy/config/schema 的 ID。
- 一个 doctor 或 validator 命令，能检查入口、配置、脚本、台账和产物字段是否互相一致。
- 涉及 POC 时，policy 还必须登记唯一 `POC_ROOT`、`tracking_mode`、保留等级、备份策略和禁止写入的位置；
  validator 必须从外部 worktree 反例验证物理归属并扫描历史残留。
- 一条 legacy 规则，说明旧脚本、旧缓存、旧产物、旧 Demo、旧发布版本在什么场景下只能作为历史参考，不能作为新任务默认样板。

只有当链路具备这些要素时，才可以认为规则已经从“聊天/文档记忆”移交为“后续 AI 可稳定执行的项目能力”。

## 9. 反臃肿维护规则

维护 Senmu BuildOS 时：

- 优先补现有 reference；只有新主题无法自然归入现有 reference 时才新增文件。
- 新增 reference 必须从 `SKILL.md` 直接可发现。
- 不要把项目私有 SOP、客户信息、服务器路径或商业细节写进通用 skill。
- 技术栈深水区和 vendor 文档应作为按需附件，不应进入入口主流程。
- 已接入官方 MCP/CLI 的生态（如 Ant Design）优先使用官方工具；ECharts、播放器、编辑器等 vendor 资料只保留小型摘要、meta 或项目外快照。更适合长期拆成专业 frontend/admin skill 时，可以只在 `senmu-build-engineering` 保留原则和路由。
- 每次版本更新后检查：是否让入口变重、是否重复已有规则、是否能通过治理等级限制触发范围。
