# 项目工程治理实践指南

本指南是项目从进入、初始化、执行到发布和复盘的二级导航。它说明生命周期和决策顺序，不重复各专项规范。具体细则从 `SKILL.md` 的索引按需读取。

## 1. 定位与适用边界

把 Senmu BuildOS 当作跨项目治理母版，不当作具体项目的 PRD、技术方案或日常执行手册。它适用于软件、脚本、工作流/Harness、媒体生产、POC 和混合交付项目；不同项目只选择实际需要的模块。

- 项目已有清晰规则时，先把它们作为当前事实入口；存在缺失、冲突、重复、过时或不可搬迁问题时，仍需按 BuildOS 治理标准演进原 owner。
- 项目缺少、冲突或过时的规则，或发生结构性、高风险治理事件时，用本指南校准。
- 校准结束后，把长期规则写回项目内权威文档；不要让项目长期依赖本 Skill。
- 技术栈、目录和交付方式可以变化，目标与来源、责任边界、状态、验证、交付证据和恢复方式不能消失。

## 2. 入场顺序

按以下顺序建立事实，不凭聊天记忆猜测：

1. 确认任务目标、允许修改范围、明确不涉及范围和完成定义。
2. 从 README/AI 入口确认项目形态、当前目标、真实路径、状态源和交付物；不要先假设它是软件产品。
3. 选择当前任务需要的治理模块，再读取对应的需求、技术、工作流、Git、POC、交付或运行资料。
4. 工作包含多个依赖步骤、阶段、Agent 或会话时，使用项目声明的 Durable Task State Owner 维护边界、进度、证据和恢复入口；standard/release 新项目默认使用 `governance/tasks/`，core 可沿用 README、Issue 或外部任务系统。
5. 检查权威项目根、Git 根、分支/工作区、发布或交付单元和当前运行入口。
6. 搜索既有实现、共享能力、公开契约、数据/物料所有者和 legacy 入口。
7. 依据风险和可逆性确定 G0-G4；发现新风险时升级。
8. 判断是否命中负责人确认或安全、生产、发布、数据、权限、破坏性操作门禁，再提出方案、审查或实施。

只有未解决的选择会实质改变范围、架构、部署、维护成本或风险时才暂停询问。其余情况应说明依据后推进。需求、计划、开发和发布事实分别写入各自权威文档。

## 3. 通用工作回路

```text
确认目标与权威 -> 识别项目形态 -> 选择治理模块
-> 实施/运行 -> 验证 -> 交付/发布/归档 -> 复盘与移交
```

不同项目可展开为不同链路：

| 项目形态 | 典型链路 |
| --- | --- |
| 软件产品 | 需求 -> 产品规划 -> 迭代 -> 技术设计 -> 开发测试 -> 版本部署 |
| 脚本/自动化 | 输入输出契约 -> 实现 -> 可重复验证 -> Git/版本或交付 |
| 工作流/Harness | 流程/schema -> 状态与运行身份 -> 执行/恢复 -> 回执与交付 |
| 视频/图片/内容 | 来源与冻结输入 -> 生产/staging -> 审阅验收 -> 最终物料 -> 发布/归档 |
| POC | 问题 -> 冻结输入 -> 可复现实验 -> 证据 -> 决策 -> 升级或归档 |

所有链路都必须回答：权威入口在哪里、什么是当前状态、哪些内容可重建、完成如何验证、最终结果放在哪里、失败后如何恢复。

项目变大后，不要求 AI 读取全库才允许工作；应提供短入口和 `PROJECT_MAP`，让它先定位责任模块、权威路径、状态源、公开接口与交付单元，再只读取当前任务切片。上下文节省来自结构清晰和事实唯一，而不是省略必要证据。

## 4. 初始化模块骨架

初始化不只是创建代码目录。先按项目形态选择模块：产品型项目建立需求和规划；代码型项目建立技术、质量和 Git 规则；工作流/媒体项目建立输入、状态、staging、交付和回执边界；POC 建立实验账本和升级/归档条件。文件可以合并，但职责和入口关系必须可发现。

`standard` 和 `release` 档位建立 `governance/PROJECT_MAP.md`。它只做导航与归属索引：列出模块/流程、权威路径、责任、状态源、公开入口、交付单元和 legacy 边界；详细规则仍由对应需求、架构、工作流或发布文档负责。新增文件、模块、组件、流程或平行版本前先查项目地图和既有实现，避免因 Agent 上下文不同而形成第二套事实。

初始化时把“工作对象、生命周期意图、交付模式、组合方式”分别记录。软件、工作流、媒体或研究是工作对象；POC、试点、生产、迁移或一次性交付是生命周期意图；持续产品、源码分发、版本化制品、托管服务、项目制成品或内部流程是交付模式；复合项目只表示多个工作对象或交付单元的组合，不再把 POC 或 mixed 当作互斥的单一项目类型。

## 5. 初始化架构门禁

新项目、独立发布/交付单元、重要子系统、长期 Harness 或技术路线重构，在实现前先按 `架构约束与技术债治理规范.md` 完成原则检查。至少确认：边界是否清楚，模块是否高内聚，跨模块耦合是否必要且显式，依赖方向和数据/物料所有权是否唯一，设计复杂度是否与质量属性相称。

项目本地技术设计或架构契约至少记录：模块表、允许／禁止依赖、公开接口、数据所有权、副作用边界、业务不变量、运行与发布边界、关键质量属性、变更触发条件、检查命令和已接受技术债。

架构图不是目的。无法从真实路径、配置、依赖或测试验证的图，不能代替架构契约。

## 6. 技术路线决策

按问题选择技术，不按偏好套框架：

1. 先识别产品形态、运行环境、交付方式、团队能力、质量属性和既有约束。
2. 先复用项目现有能力，再评估成熟标准、框架、组件、SDK 或服务。
3. 以契合度、维护性、互操作性、安全、许可、生态、可观测性、迁移和退出成本比较候选。
4. 小脚本、CLI、一次性自动化或边界清楚的离线任务可以使用标准库和少量依赖；不要为形式完整强加应用框架。
5. 主框架或主组件体系确认后作为架构基线；局部缺口优先兼容扩展，替换基线必须有影响、迁移和回滚方案。
6. 只有证据不足且选择影响重大时才做最小 POC，并保留可复现实验记录。

框架名称和产品名称只能是候选示例，不能成为通用规则。已选生态的具体用法进入项目本地专项规范或条件式 reference。

## 7. 治理与交付强度

- G0-G1：保留依据、影响范围和目标验证，避免制造无关流程。
- G2：同步受影响文档，执行匹配的代码质量、架构和测试检查，必要时写工作日志。
- G3：补齐架构影响、完整验证、版本、变更记录、制品、线上确认和回滚依据。
- G4：在 G3 基础上覆盖真实风险路径、审计证据、复盘和规则更新。

Hard Gate 不满足时不得宣称完成。Soft Gate 不执行时说明不适用原因。Guidance 可按项目事实调整。

## 8. 项目内移交

空白新项目先运行零写入规划：

```bash
python3 <senmu-build-project>/scripts/init_project_governance.py \
  --mode plan-new \
  --root <project-root> --project-name <name> \
  --project-type <software|script|workflow|media|poc|mixed> \
  [--lifecycle-intent <exploration|pilot|production|migration|one_off>] \
  [--delivery-model <continuous_product|source_distribution|versioned_artifact|managed_service|project_delivery|internal_process>] \
  [--publication-model <private_only|public_native|private_authority_public_projection>] \
  [--release-channel <channel> ...] [--artifact-kind <kind> ...] \
  [--composition <single_domain|composite>] \
  [--modules <product|workflow|code|architecture|git|poc|delivery|agents> ...] \
  --profile <core|standard|release>
```

确认候选结构后，复用完整命令和同组显式参数，把 `--mode plan-new` 改为 `--mode initialize-new`；确有对应需求时再增加 `--with-agents` 或 `--commit-baseline`。

项目类型和档位必须显式提供；不写 `--modules` 时使用该项目类型的推荐模块，显式提供时以该列表为准，单独写 `--modules` 可生成不含专业模块的基础实例。`initialize-new` 拒绝向已有内容的成熟项目生成默认目录。已有项目先运行 `assess_project_governance.py --root <project-root>` 完成零写入审视，再按《项目治理实例与演进规范》经授权演进原 owner。新项目生成后先用结构校验确认骨架，再校准占位字段、把 policy 状态改为 `active`，
最后运行项目内复制的 `python3 .senmu-buildos/validate.py --root . --strict`。小型探索使用 `core`：默认只建立 README、AGENTS、治理章程、机器 policy 和一个验证入口，不预建任务、日志、经验与专业文档；这些职责先合并到现有入口，需要持续协作时再升级为 `standard`。
准备正式发布、部署或稳定交付的项目使用 `release`；目录和文档仍需按真实项目裁剪，不能把模板当成已完成设计。

`--commit-baseline` 仅用于空白新项目或初始化器自己的 draft 恢复：先运行非严格结构校验，再只暂存初始化器管理的已知文件并创建治理骨架基线 commit。它不执行 `git add .`、不创建 Tag、不处理已有项目，也不通过 Hook 自动提交。Git 身份未配置或索引已有暂存内容时跳过提交并报告原因，避免夹带其他改动。

`--with-agents` 只在项目确实维护自有 Agent／系统提示词时使用。它增加 Agent Register、定义模板和校验器，但不会虚构业务 Agent；普通软件、脚本或内容项目不因使用 AI 开发就自动启用该模块。

初始化或校准完成后，项目内应能直接发现以下事实；文件可以合并，但职责不能消失：

- 项目形态、当前目标、权威入口、状态源和最终交付定义。
- 如果启用需求模块：需求池、规划/迭代和验收关系。
- 如果生产文件或媒体：源输入、工作区、临时文件、运行状态、最终物料、回执和归档边界。
- AI／新人读取入口和文档权威顺序。
- 如果启用 Agent 模块：项目 Agent 登记表、稳定 Key／版本、唯一 Agent 定义、运行入口与 Workflow／Harness 关系。
- 技术设计、架构契约、技术债和决策记录。
- 源代码质量、实际语言／框架规则和统一检查命令。
- Python、TypeScript、Go、Java 使用 Engineering 的对应语言 Profile；多语言项目只加载当前任务涉及的专项，其他语言沿用项目工具配置和官方生态。
- 如果启用 Git/代码模块：仓库、代码边界、分支/worktree、质量和合并规则。
- 如果启用正式交付/发布模块：交付单元、版本/交付 ID、制品、部署/交付验证和恢复规则。
- 当前工作日志、未决事项和交接说明。
- 由 `senmu-build-learning` 管理的有效经验与防回退条目，以及对应的检测／validator。

优先使用短入口路由到权威文档、机器可读配置和统一 validator；不要复制多份长规范。

## 9. 完成定义

交付前确认：

- 结果位于权威项目和正确发布单元，不只存在于临时目录或聊天中。
- 当前启用模块中的输入、规则、实现/运行、状态、验证和交付物之间没有未说明的冲突。
- 已运行与风险匹配的验证，并记录实际结果、未运行项和残余风险。
- 正式交付/发布具备可追溯交付 ID 或版本、结果、验收/线上验证和可执行恢复依据。
- 项目特有经验只更新项目规范；真正跨项目、可抽象且不会增加普遍负担的规则，才由 `senmu-build-learning` 形成 BuildOS 源码项目反哺候选。
