# 项目目录与文档规范

本规范用于选择项目根、目录角色、文档 owner 和项目地图，不要求项目采用同一外形。成熟项目优先映射现状；候选名称不能成为建立平行目录的理由。

## 1. 先确定边界和角色

目录规划前确认权威项目根、Git 仓库和子项目／外部工作区；工作对象、生命周期、交付模式和发布单元；源输入、运行状态、中间物、交付物、证据与归档；现有专业 owner；真实构建、测试、部署、恢复和发布入口。

代码、媒体、数据库、制品和运行状态可以位于不同物理根，但必须由短项目地图关联。不得用向上搜索 `Makefile` 或 `package.json` 猜权威根。

## 2. 可选布局

软件或多服务项目可以从以下角色起步：

```text
project-root/
  README.md / AGENTS.md / .senmu-buildos/
  product/ engineering/ workflows/ governance/
  delivery/ operations/ projects/ scripts/ tests/
```

子项目只有在能独立构建、部署、回滚并具有独立职责时才成为发布单元。前后端共享节奏时共同版本；能独立发布时分别登记制品、命令、健康检查和回滚。

内容、媒体、数据或混合项目可以使用：

```text
project-root/
  project-system/  # 唯一 Git 项目系统
  sources/         # 不可覆盖输入
  workspace/       # 中间物和运行状态
  deliveries/      # 已验收交付
  archive/         # 历史与关闭内容
```

已有中文编号目录、`inputs`、`staging`、`outputs` 或 `receipts` 可以原样保留，只需映射角色。大型媒体、生产数据库、缓存和成品不因项目系统使用 Git 而提交。小型项目可合并文件；未确认模块不预建。

## 3. 入口和项目地图

- `README.md`：项目身份、启动方式、主要应用／服务和关键入口。
- 根 `AGENTS.md`：采用 BuildOS 时只保存项目差异、真实命令、权威路径和明确覆盖；不复制 BuildOS 或专业正文。子目录可提供更具体的差异层。
- `.senmu-buildos/config.json`：治理实例身份、布局、模块和可搬迁定位。
- `governance/PROJECT_MAP.md` 或等价入口：只导航 owner、状态源、命令、发布单元和 legacy 边界，不复制正文或当前可变状态。
- 项目自有 Agent 只有真实启用时才建立 Register 和唯一定义；Skill 的 `agents/openai.yaml` 不是业务 Agent。

冲突时，项目运行证据和最近作用域的 active 专业 owner 决定项目事实；项目明确覆盖优先于 BuildOS 默认。时效不明、多个项目 owner 冲突或试图降低不可放弃 Hard Gate 时交用户裁决。

## 4. 专业 owner

| 事实 | 默认 owner |
| --- | --- |
| 用户、需求、业务规则、路线图、验收 | Product |
| 架构、技术设计、代码质量、语言、测试、技术债 | Engineering |
| Workflow Contract、Run Manifest、物料和恢复 | Workflow |
| Git、版本、Tag、制品、部署、生产事实和回滚 | Delivery／Operations |
| 跨阶段计划与恢复入口 | 项目现有 Durable Task State Owner |
| 审查 Finding、POC 证据和复核 | Assurance |
| 反馈候选、经验生命周期和规则晋级索引 | Learning |

Project 只选择 owner、路径和索引关系，不复制专业写作规则。已有等价 owner 时更新原处；没有真实内容时不创建空台账。

## 5. 最小文档责任

长期项目应能发现项目入口和真实命令、当前需求／目标与验收、架构／实现边界与质量入口、工作流输入状态输出与恢复、发布单元与生产回滚，以及跨阶段任务的范围、进度、证据和下一入口。不要求每项独立成文件。

计划、候选、冻结参考、历史快照和现行文档不得互相冒充。文档状态、适用发布单元、适用版本／交付 ID 和最近校准依据应与用途相称。纯局部修复只审阅受影响 owner，不为了前移版本批量改写无关文档。

版本、commit、候选／生产状态、策略 ID、最近校准时间等高频变化事实应由一个机器可读 owner 维护。其他文档只引用该 owner、保存本页独有解释，或由声明的生成／校验入口形成可重建投影；不得为同步重复页头而手工批量改写无关正文，也不得让投影反向成为第二个事实源。

文档同步按契约变化决定：用户行为和验收回 Product；模块、接口、数据、依赖、基础设施、权限和安全回 Engineering；运行步骤与恢复回 Workflow；版本、部署、生产与回滚回 Delivery。只改变内部实现且契约不变时，更新测试、必要注释和项目要求的最小记录。

## 6. 安全与公开边界

Git 不保存真实密钥、生产数据、用户上传、运行数据库、缓存或未授权材料。配置提交模板，真实值进入项目批准的本机或秘密管理入口。

私有权威到公开仓使用单向白名单投影。公开仓是可重建发布面，不是第二个可独立编辑 owner；内部任务、日志、客户数据、运行状态、绝对路径和私有资产不得进入公开面。公开修订只能由内部权威按生命周期重新生成。

最终方案必须能回答权威根、每类事实 owner、当前任务只需读什么、真实命令、交付入口和恢复入口。无法回答时，目录还没有完成治理。
