# 项目目录与文档规范

本规范提供目录角色、文档 owner 和可选预设，用于回答“放在哪里合适”、规划空白项目或整理已有项目；它不规定所有项目必须采用同一物理结构。

## 本页导航

1. 推荐目录结构；1.0 工作区根目录收敛；1.1 大项目与子项目分层；1.2 非软件与混合项目；2. 目录职责；3. 必要文档；4. 专业内容边界。

## 1. 可选目录预设

缺少既有结构的软件产品或服务可从以下预设讨论；脚本、工作流、媒体、POC 和混合项目按 1.2 节选择角色，不要照抄完整软件目录。给单项文档推荐位置时，优先复用已有 owner，不为匹配本树而新建整套父目录：

```text
project-root/
  .senmu-buildos/                BuildOS 机器配置、validator 与项目模板
  AGENTS.md
  agents/                        项目自有 Agent／Prompt（按需）
    AGENT_REGISTER.md
    <agent-key>/
      AGENT.md
  README.md
  product/
    requirements/
      PRD.md
      REQUIREMENT_BACKLOG.md
      ROADMAP.md
      REQ-0001-<slug>.md         按需创建
    ITERATION_PLAN.md
    design/
      DESIGN_NOTES.md
    assets/
    legal/
  engineering/
    ARCHITECTURE.md
    TECH_STACK.md
    CODE_QUALITY.md
    TESTING_STRATEGY.md
    TECH_DEBT.md
    designs/
      TD-0001-<slug>.md          按需创建
    decisions/
      ADR-0001-<slug>.md         按需创建
    languages/
      PYTHON.md
    frameworks/
    FRONTEND_GUIDE.md
    SECURITY_GUIDE.md
  governance/
    tasks/
      TASK_REGISTER.md
      TASK-0001-<slug>.md
    GOVERNANCE.md
    logs/
      WORKLOG.md
    lessons/
      LESSONS_LEARNED.md
  delivery/
    BRANCHING.md
    RELEASE_PLAN.md
    CHANGELOG_POLICY.md
  operations/
    DEPLOYMENT.md
    deploy.env.example
    scripts/
  tests/
    backend/
    frontend/
    browser/
    fixtures/
  scripts/
    <quality-command>
  projects/
    <app-or-service>/
      README.md
      VERSION
      CHANGELOG.md
      frontend/
      backend/
  data/                          默认不进入 Git
```

目录不是死规定，但必须满足。初始化时应先记录工作对象、生命周期意图、交付模式和组合方式，再按实际启用模块生成目录；不要因为项目是 POC 就套用与生产软件相同的完整目录：

目录规划使用能力评估而不是类型套树。先依据需求和当前／预期架构分别确认治理档位、公开模型、发布渠道、制品类型和路径角色；`release` 只提高正式发布门禁，不自动创建部署、镜像、安装包、制品目录或清理脚本。没有真实消费者、独立构建输出或回滚依赖时，制品能力保持未启用，并登记首次出现容器镜像、DMG／PKG、包注册表、签名压缩包或等价交付契约时重新评估。架构或渠道变化后只增量补齐新 owner 和目录，不重建无关结构。

- 需求和业务规则有明确位置。
- 技术方案有明确位置。
- 模块职责、依赖方向、数据所有权、公开契约和 legacy 边界有明确位置。
- AI 编码入口、源代码质量规则、实际使用的语言规范和质量命令有明确位置。
- 项目若维护自有 Agent／系统提示词，必须区分 Codex 入口、业务 Agent 定义、运行状态和 Skill 展示元数据。
- 部署方案有明确位置。
- 测试策略有明确位置。
- 运行数据、密钥、证书、用户上传文件不进入 Git。
- 多产品/多子系统必须明确目录边界和发布归属；如果团队、版本或发布节奏已经分化，还应进一步按 `仓库边界与发布单元治理规范.md` 判断是否继续适合单仓库。
- 可独立部署的子项目必须明确自己的前端、后端、版本、changelog 和部署制品归属。
- `governance/PROJECT_MAP.md` 是目录、模块、流程、状态源和交付单元的唯一导航索引；它不复制 PRD、技术方案、工作流契约或发布规则正文。
- 跨阶段任务必须有唯一 Durable Task State Owner；`governance/tasks/` 是 BuildOS standard/release 新项目默认实现，core 可沿用 README、Issue 或外部任务系统。成熟项目已有可信任务包、数据库或外部系统时应登记其定位和恢复方式，不得再建立第二份进度表。
- `product/`、`workflows/`、`engineering/`、`governance/`、`delivery/` 与 `operations/` 的模板和规则必须有唯一 owner；初始化器可以统一调用，但不能让 Project 物理拥有所有领域模板。

## 1.0 工作区根目录收敛

项目治理不仅包括代码目录，也包括本地工作区目录。大型迁移、拆仓、重构或发布治理任务开始前，必须先确认项目总目录和当前主线目录，避免把长期工作成果散落在桌面、下载目录、系统临时目录或项目根目录外。

推荐思想：

```text
project-root/
  README.md
  current/ 或 current-v<major>/     当前主线代码、运维、制品和治理文档
  archive/                          旧版本、旧仓库、迁移快照，只读参考
  docs/ 或 governance/              项目级治理文档
```

如果项目决定使用 `current-v<major>` 这类目录名，必须在版本文档中说明它是正式版本基线，还是仅为内部工程代号。若它代表正式主线，`VERSION`、changelog、tag、制品和线上版本必须同步表达同一基线；若它只是工程代号，必须避免让项目负责人、研发或后续 AI 误解为产品版本。

同一软件产品从 1.x 开发 2.x 时，默认继续使用一个仓库和一个正式项目目录，通过 Git 分支隔离代码线；“拉分支”本身不要求创建 `v1/`、`v2/` 两套目录。用户只说拉分支时，不得推导为创建 worktree。在同一目录切换分支即可满足串行开发。只有用户明确授权，并且必须同时运行、比较、修改两个版本或多人／多 Agent 并行时，才创建共享同一仓库历史的临时 worktree。

获准使用 worktree 时，应放在项目总目录登记的容器中，例如 `.worktrees/`，禁止放入 Codex／Agent 自有目录、其他项目目录或未登记的临时路径。继任版本明确要替换主线时，目录规划不得把 worktree 或复制目录固化为第二个长期项目；最终代码、治理、交付和发布入口必须收口到新的主线，合并后清理没有独有事实的临时 worktree。

POC 与正式开发可能长期异步，目录规划必须把“项目总边界”“产品发布源”和“POC 状态根”分开。默认在项目
总目录内登记一个独立、可备份且不属于任何发布源的 POC 根；高频、模型或媒体实验可整体 Git 忽略，让每个实验
物理聚合账本、manifest、复现协议、输入、运行资产、证据和晋级说明。需要修改候选源码时才使用独立 POC 分支，
并行写入时再按授权使用 worktree。实验未被批准生产化前，不修改产品迭代计划、正式台账、交付目录或生产状态；
项目已有等价实验区时沿用，不强制采用固定目录名。

迁移或拆仓任务不得把以下内容长期放在项目根目录外：

- 当前可继续开发的仓库。
- 生产部署脚本和运维说明。
- 发布制品和校验文件。
- 迁移结果说明和复盘文档。
- 后续 AI 需要读取的治理规则。

临时目录可以短期放在系统临时路径，但交付前必须移动、归档或删除，并在项目文档中说明当前主线入口。项目负责人已经明确项目总目录时，所有当前工作入口都应收敛到该总目录内。

## 1.1 大项目和子项目分层

大项目在单仓库内可先按“仓库级治理 + 子项目运行单元”的方式组织：

```text
project-root/
  governance/                 仓库级治理、版本规划、协作日志
  product/                    仓库级或产品线级需求和设计
  engineering/                仓库级技术方案和共用工程规范
  delivery/                   仓库级版本和发布规则
  operations/                 仓库级部署说明和运行脚本
  projects/
    official-website/         官网，独立发布单元
      frontend/
      VERSION
      CHANGELOG.md
    app-platform/             应用平台，独立发布单元
      frontend/
      backend/
      VERSION
      CHANGELOG.md
    admin-console/            如能独立部署，则独立发布；如共享平台，则写清归属
      frontend/
      backend/
```

判断一个子项目是否应独立成发布单元：

- 是否能独立构建？
- 是否能独立部署？
- 是否能独立回滚？
- 是否有独立用户入口或服务职责？
- 是否需要独立版本号和 changelog？

如果答案大多为“是”，应作为独立发布单元；如果只是同一平台内部模块，不要伪造独立版本，应归入所属平台的版本和制品。是否进一步拆成独立仓库，不由本文件单独决定，应结合团队边界、权限、发布阻塞、共享代码成本和接口契约成熟度，按 `仓库边界与发布单元治理规范.md` 评估。

前后端分层规则：

- 前端代码放 `frontend/` 或项目既有前端目录。
- 后端代码放 `backend/` 或项目既有后端目录。
- 共享类型、SDK、脚本或公共包应放在明确的 `packages/`、`shared/` 或项目约定目录，不要散落在业务目录。
- 前端和后端共享同一发布单元时，版本号和 changelog 归属必须写清楚。
- 前端和后端可独立部署时，制品、镜像 tag、发布命令和回滚方式也必须分别写清楚。

## 1.2 非软件与混合项目

工作流、视频／图片、内容生产、运营和 POC 默认使用“项目总目录 + 唯一 Git 项目系统”结构：

```text
project-root/
  00-project-system/           唯一 Git 仓库
    .senmu-buildos/
    README.md / AGENTS.md
    agents/                    项目自有 Agent／Prompt（按需）
    governance/                项目地图、编号任务计划、日志和经验
    product/                   目标、需求和规划（按需）
    workflows/                 流程契约、schema、配置和操作入口
    engineering/               脚本、代码和工程规则（按需）
    delivery/                  版本、交付、发布和回滚规则（按需）
    operations/                平台、账号、部署和运营规则（按需）
    experiments/               实验登记与 Git 内实验包（按需）
    scripts/                   自动化与校验脚本
  01-sources/                  原始或冻结输入，不进入 Git
  02-workspace/                中间文件、运行状态和实验输出，不进入 Git
  03-deliveries/               已验收交付物，默认不进入 Git
  04-archive/                  历史与关闭内容，不进入 Git
```

`workflows/` 是 `00-project-system/` 内的专业模块，不是独立 Git 仓库。大型媒体、运行数据库、缓存和成品不因项目系统采用 Git 而被提交。已有项目可以保留 `00_项目系统`、`inputs`、`staging`、`outputs`、`receipts` 等原名称，在 Project Map 中映射标准角色，不强制迁移。

目录必须能回答：

- 哪些是不可覆盖的源输入，哪些中间文件可以重建或清理？
- 唯一可写运行状态在哪里，如何恢复中断任务？
- 哪些文件已经验收并成为最终交付，哪些仍是 staging/POC？
- Git 管哪些代码、配置、清单和小型证据；大型媒体与数据库由哪里保存和索引？
- 已交付、已发布、未发布、失败和归档状态如何保持真实？

详细规则见 `工作流、物料与交付物治理规范.md`。混合项目应同时保留代码边界和物料边界；两者发布/交付节奏不同则拆成独立单元。

## 2. 各目录职责

- `README.md`：项目入口。写项目是什么、当前有哪些应用/服务、如何本地启动、关键文档在哪里、当前维护规则是什么。
- `AGENTS.md` 或等价 AI 入口：保持简短，写 AI 开工读取顺序、适用作用域、禁止事项、统一质量命令和完成输出；引用权威文档，不复制整套规范。monorepo 可在子目录放作用域更窄的入口，但不得与根规则冲突。
- `agents/AGENT_REGISTER.md`：只在项目确实维护自有 Agent／系统提示词时建立，作为 Agent Key、名称、版本、状态、定义路径、Owner 和 Workflow／Harness 关系的唯一索引；不复制 Prompt 正文。
- `agents/<agent-key>/AGENT.md`：单个项目业务 Agent 的唯一角色与 Prompt 契约。`agent-key` 使用小写 kebab-case，定义至少覆盖角色、目标、职责、输入、输出、工具、流程、约束、质量门禁、异常移交与版本审计。
- `.senmu-buildos/templates/agent/AGENT.md` 与 `.senmu-buildos/validate_agents.py`：启用 Agent 模块时提供的创建模板和确定性结构校验器，不是生效 Prompt，也不保存运行状态。
- Skill 包内的 `agents/openai.yaml`：只属于 Codex Skill 展示元数据，不复制进应用项目，也不登记为业务 Agent。
- `product/`：产品和业务事实。写用户、需求、业务规则、设计资料、价格策略、法务材料、品牌素材。不要放运行代码。
- `product/requirements/PRD.md`：需求主文档。写项目定位、用户角色、核心流程、业务对象、权限、计费、状态、边界、验收标准。
- `product/requirements/REQUIREMENT_BACKLOG.md`：需求池。登记所有零散想法、反馈、缺陷、研究项和技术使能项，使用稳定的 `REQ-xxxx`，记录生命周期、目标版本、迭代和证据链接。
- `product/requirements/ROADMAP.md`：路线和阶段计划。写本期做什么、下期做什么、哪些延期、哪些暂不纳入。
- `product/design/DESIGN_NOTES.md`：产品设计说明。写页面信息架构、模块父子关系、列表/详情/弹窗/抽屉边界、设计稿链接或无设计稿时的默认方案。
- `product/assets/`：品牌、截图、设计稿、素材。必须区分源文件和 Web 可用文件，真实用户数据不得混入。
- `product/legal/`：用户协议、隐私政策、备案、合规说明等。没有法务需求时可以为空或不建。
- `engineering/`：工程判断。写技术方案、架构、技术栈、前端规范、安全规则、第三方服务接入规则。
- `engineering/designs/TD-<NNNN>-<slug>.md`：评审通过的技术设计。写架构、数据模型、接口、权限、安全、异步任务、存储、第三方服务和风险；任务进度留在关联编号计划，正式技术评审记录归 Engineering review owner。
- `engineering/ARCHITECTURE.md`：正式或持续迭代项目的架构契约。写系统边界、模块登记、依赖方向、数据所有权、业务不变量、副作用、公开契约、发布边界和 legacy 边界；小项目可以作为 `TECHNICAL_DESIGN.md` 的一节。
- `engineering/TECH_STACK.md`：技术选型文档。写为什么选这个前端/后端/数据库/组件库，为什么不用其他方案，后续升级规则。
- `engineering/CODE_QUALITY.md`：跨语言源代码质量主文档。写规范适用范围、约束强度、中文注释规则、可执行质量命令、评审输出和例外流程。
- `engineering/TECH_DEBT.md`：已知技术债、影响、责任归属、偿还触发条件和验证证据；没有真实债务时不要求创建空文件。
- `engineering/decisions/`：架构决策记录。只记录模块、依赖、公共契约、数据、基础设施等长期决策，不把每个实现细节都升级成 ADR。
- `.senmu-buildos/templates/ADR.md`：启用架构模块的 standard／release 新项目获得的按需模板；它不是实际决策，也不要求初始化时创建 `engineering/decisions/` 或空 ADR。
- `engineering/languages/`：只保存项目实际使用语言的专项规则，例如 `PYTHON.md`；不要预建所有语言文件，也不要复制整份外部规范。
- `engineering/frameworks/`：只在项目确实需要额外框架约束时保存专项规则，例如 Django、FastAPI 或 Spring；通用语言规则不要在这里重复。
- `engineering/FRONTEND_GUIDE.md`：前端实践文档。写项目已选设计系统、组件复用顺序、信息架构、可访问性、响应式、可视化和专项交互规则；具体生态规范按项目选型加载。
- `engineering/SECURITY_GUIDE.md`：安全边界。写密钥管理、权限校验、上传访问、支付/订单、审计、敏感文件禁止提交。
- `governance/`：项目治理。写治理章程、项目地图、跨阶段任务状态、协作工作日志和经验索引；产品迭代、Git 与发布正文仍由各自专业 owner 负责。
- standard/release 默认 `governance/tasks/TASK_REGISTER.md`：任务登记表。列出需要持久状态的任务、状态、主 Skill、负责人和任务文件，不复制任务正文；core 不预建该台账。
- standard/release 默认 `governance/tasks/TASK-<NNNN>-<slug>.md`：单个任务的持久计划与状态记录。保存目标、边界、阶段、进度、关键决定摘要、证据链接和恢复入口；不为普通任务建立独立目录。
- standard/release 的 `.senmu-buildos/templates/TASK.md`：项目本地编号任务计划模板，只用于创建新任务，不保存活跃状态。
- `product/ITERATION_PLAN.md`：迭代计划。每次完整功能开始前写目标、范围、延期项、风险和验收。
- standard/release 的 `governance/logs/WORKLOG.md` 或 `governance/logs/<yyyy-mm>.md`：协作工作日志。写每次 AI/研发做了什么、验证了什么、没做什么、下一步是什么。
- standard/release 的 `governance/lessons/LESSONS_LEARNED.md`：经验与防回退台账。写已验证、可能重复的失败模式、触发信号、必须／禁止动作、检测门禁和替代关系；不复制工作日志全文。core 不为单次经验创建空台账。
- `delivery/BRANCHING.md`：分支策略。写 `main`、`develop`、`feature/*`、`codex/*` 怎么用，scope 怎么命名，怎么合并。
- `delivery/RELEASE_PLAN.md`：版本与发布。写版本号、tag、构建、发布、线上验证、回滚和发布后收口。
- `delivery/CHANGELOG_POLICY.md`：更新日志规则。写内部 changelog、用户 changelog 如何区分，什么内容不能暴露。
- `governance/GOVERNANCE.md`：项目治理章程。写核心原则、权威顺序、治理版本、修订与例外，以及项目级长期边界，给 AI 和新人入场使用。
- `governance/PROJECT_MAP.md`：项目短地图。登记模块/流程/物料的唯一归属、权威路径、状态源、公开入口、交付单元和 legacy 边界；只做索引，不复制 PRD、架构或部署正文。
- `delivery/`：交付管理。写 Git、版本、changelog、制品、发布、验证和回滚，不放需求或技术设计正文。
- `operations/`：部署和运行。写环境、变量、运行手册、部署脚本、健康检查和运维边界，不放业务需求。
- `operations/DEPLOYMENT.md`：部署主文档。必须包含本地启动、正式环境、环境变量、构建命令、部署命令、健康检查、制品清理、发布后 Checklist。
- `operations/deploy.env.example`：部署变量模板。只能放示例值和说明，不放真实密钥。
- `operations/scripts/`：启动、部署、备份和恢复脚本。脚本要能被文档引用，不要只有脚本没有说明。
- release 档位初始化 `operations/scripts/cleanup-release-assets.sh`、`test-release-retention.sh` 和 `operations/release-retention.env`。项目校准后由唯一部署入口在生产验证通过后按各资源面的依赖顺序收口；默认保留当前已验证版本、一个已验证回滚版本及明确 Pin，项目显式策略优先。不得把版本号相邻误当成可回滚证明，也不得改成跨项目全局 prune。
- `tests/`：测试和验收。写单元测试、接口测试、浏览器流程、真实素材说明。
- `engineering/TESTING_STRATEGY.md`：测试策略。写测试分层、测试代码目录、命令、mock 边界、真实流程和未验证风险；`tests/` 主要保存测试代码和 fixtures。
- `tests/fixtures/`：测试素材。默认不进入 Git；如需提交，必须脱敏、小体积、授权明确。
- `scripts/<quality-command>`：项目统一质量入口。调用语言生态标准配置，并由本地、提交前检查和 CI 复用；脚本名称和形式可按项目工具链调整。
- `projects/`：真正运行的应用、服务、官网、后台或子项目。每个正式发布单元应有自己的 `README.md`、`VERSION`、`CHANGELOG.md`。
- `projects/<app-or-service>/frontend/`：子项目前端。使用的 UI 框架、构建命令和部署制品归属应在子项目 README 或部署文档中说明。
- `projects/<app-or-service>/backend/`：子项目后端。接口、数据库迁移、任务队列、环境变量和服务制品归属应在技术方案或部署文档中说明。
- `data/`：本地运行数据、数据库、上传文件、缓存。必须进 `.gitignore`，不能提交。

上述名称都是相对目录候选。Skill 和初始化器持久化的是角色、定位协议及相对关系，不得写死用户名、用户主目录、客户名、业务父目录或某台机器的卷名；真实绝对路径只允许运行时解析或进入 Git 忽略的本机配置。成熟项目已有等价目录时映射现状，不为匹配候选名称创建平行目录。

如果项目很小，可以合并部分文件，但信息不能消失。例如早期 MVP 可以只有 `README.md`、`PRD.md`、`TECHNICAL_DESIGN.md`、`DEPLOYMENT.md` 和 `TESTING_STRATEGY.md`；正式上线后必须补齐分支、版本、发布、安全和 changelog 规则。

## 3. 必须生成或维护的文档

正式或长期项目至少应能发现以下职责；是否独立成文件由项目形态决定：

- `README.md`：项目入口、本地启动、关键文档索引。
- AI 工程入口：告诉后续 AI 先读什么、加载哪些语言／框架规则和架构契约、运行哪些质量命令以及怎样报告完成。
- 启用 Agent 模块时：Agent Register、每个 Agent 的稳定 Key／版本与唯一定义、实际 Workflow／Harness 入口及运行记录关联方式。
- 项目入口与当前状态：目标、范围、权威根、真实运行/状态入口、最终结果和下一步。
- 多步骤／多阶段任务：任务登记表，以及当前任务的边界、进度、证据、下一步和恢复入口。
- 启用需求模块时：需求、业务规则、验收、规划和迭代关系。
- 启用代码模块时：技术/架构、源代码质量、依赖、测试和统一命令。
- 生产文件或媒体时：源输入、工作区、临时文件、运行状态、最终交付、回执和归档边界。
- 技术债登记：正式或持续迭代项目存在真实技术债时，记录债务 ID、影响、接受原因、责任归属、偿还触发条件和验证方式。
- 部署文档：环境、变量、构建、部署、健康检查、回滚、发布后核对清单。
- 测试说明：测试分层、命令、真实测试数据、mock 边界。
- 版本与发布说明：版本号、changelog、tag、发布流程。
- 协作工作日志与经验台账：分别承担时间线接力和长期防回退，不能只保留其中一个。

如果项目很早期，可以先合并为一两份文档，但不能没有这些信息。

文档和代码必须保持同步：

- 新增功能或改变业务逻辑时，需求文档必须同步用户流程、状态、提示文案、边界和验收标准。
- 改变接口、异步任务、数据模型、第三方服务、存储保留/清理、权限或安全策略时，技术设计必须同步实现约束。
- Bug 修复如果改变了状态流转、失败处理、重试规则、数据保留策略或用户可见行为，也视为业务逻辑改动，必须同步需求和技术文档。
- 同时启用需求和代码模块时，合并前必须能从改动说明中看出“需求 -> 技术设计 -> 代码 -> 测试/验收”的对应关系；其他项目使用“输入/目标 -> 工作流或实现 -> 验证 -> 交付”的对应关系。
- 修改代码质量规则、语言版本、格式、类型、测试或统一质量命令时，必须同步项目 AI 入口、质量文档、机器配置和 CI；不能只改其中一处。
- 新增模块、改变依赖方向、公共契约、数据所有权、数据库 schema、基础设施或 legacy 边界时，必须同步架构契约；达到项目决策触发条件时新增 ADR。
- 引入临时补丁、长期忽略或兼容分支且会持续增加维护成本时，必须新增或更新技术债登记，不能只留一个无收口条件的 TODO。

### 3.1 文档权威与适用版本

启用版本化发布模块的正式项目，其现行基础文档必须声明以下元数据，避免需求、技术方案和实际实现长期脱节。非版本化项目可以用交付 ID、流程版本或最后校准依据表达同一职责：

```markdown
> 文档状态：现行
> 适用发布单元：共享后端、客户端、运营后台
> 适用版本：共享后端 `2.3.0`；客户端 `2.4.1`；运营后台 `1.8.0`
> 最近校准：2026-07-14，对照发布标签或 commit
```

字段含义：

- `文档状态`：现行、规划、冻结参考、历史快照、已废弃。
- `适用发布单元`：明确文档约束哪些应用、服务、客户端或治理仓库，不能只写一个含糊的全局版本。
- `适用版本`：表示维护者已经用该发布单元版本的实际代码、配置、迁移、测试或发布记录核对过文档。
- `最近校准`：记录核对日期和依据；未完成核对时不得只改版本号制造已同步的假象。

每次正式发布必须做文档影响判断：

- 需求、用户行为、状态、计费或验收变化：更新 PRD 正文和适用版本。
- 架构、接口、数据、部署、权限或安全变化：更新技术正文和适用版本。
- 纯 Bug、样式或兼容修复且契约未变：正文可以不改，但必须审阅受影响基础文档并前移适用版本和最近校准。
- 只影响一个发布单元：只更新该单元和共享契约相关文档，不伪造其他发布单元升版。
- 发布记录、QA 报告、事故报告、历史计划和冻结原型：保留原始版本；可以追加后续结果，但不能洗成当前状态。

G2-G4 项目应维护一份项目内权威文档登记表，列出路径、职责、状态、适用发布单元和更新触发条件。G3-G4 发布应增加自动检查，至少验证现行基础文档包含上述四个字段，并与各发布单元 `VERSION` 不冲突。未版本化原型可以写“规划中/未版本化”，但仍要记录最后校准依据。

## 4. 专业内容边界

Project 负责确认事实类型、唯一 owner、首选路径、可接受替代、索引关系和是否值得拆成独立文件，不在目录规范中复制专业写作或技术选型规则：

- 需求池、REQ、PRD、路线图、迭代和产品验收由 `senmu-build-product` 负责；Project 只登记其路径及与 Task 的关系。
- 技术设计、架构、技术栈、数据库、存储、代码质量和测试策略由 `senmu-build-engineering` 依据真实需求、现有系统和官方生态决定；Project 不按项目类型预设数据库或框架。
- Git、版本、制品、部署、发布和回滚由 `senmu-build-delivery` 负责；Project Map 只登记发布单元和入口。
- 工作流、物料、run identity、恢复和交付回执由 `senmu-build-workflow` 负责；Task 只保存跨阶段进度和链接。

用户同时要求目录规划和专业正文时，Project 先确定 owner／路径，再由相应专业 Skill 编写内容；已有项目继续优先映射和演进原 owner。
