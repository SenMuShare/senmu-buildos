# 项目规范发现与按需加载规范

本规范用于帮助 AI 在成熟项目中找到真正有效的项目规则，并在当前任务中只读取相关部分。它不创建 BuildOS 私有的项目知识库，也不把个人偏好、偶然写法或聊天印象提升为项目规范。

## 1. 两个不同产物

- **正式规范 owner**：保存项目特有的完整规则、理由、例外和验证方式，例如项目已有的 CONTRIBUTING、CODE_QUALITY、ARCHITECTURE、TESTING_STRATEGY、WORKFLOW、DEPLOYMENT 或工具配置。采用 BuildOS 时，根 `AGENTS.md` 是差异与路由入口，不是专业正文 owner。
- **项目规范索引**：只保存规范领域、适用信号、一句话决策摘要和权威路径，帮助 AI 快速选择；不复制正式规范正文。

`governance/PROJECT_MAP.md` 是 BuildOS standard／release 新项目的默认索引承载位置。成熟项目如果已有等价入口，应映射并沿用；不要为了统一文件名再建一个 `standards/`、`rules/` 或第二份 Project Map。core 项目没有独立索引也可以直接从短 AGENTS、README、治理章程和工具配置路由。

## 2. 什么时候需要发现规范

- 接手一个已有代码库、工作流、内容生产系统或复合项目。
- 项目规则分散，AI 经常重复询问、违反惯例或读错入口。
- 规范文档与真实实现可能漂移，需要确认当前有效做法。
- 准备初始化或治理项目，但不能确定哪些 BuildOS 默认规则适用。
- 某类任务反复依赖少量项目特有约束，却每次都要全文搜索。

普通小任务已经能从项目入口找到清楚规则时，不再执行完整发现流程。

## 3. 发现流程

1. 确认权威项目根、目标发布／交付单元、当前任务范围和只读／写入授权。
2. 先读短入口和已有 owner，再选择能代表真实生产路径的实现、配置、测试、运行或交付证据；不扫完整仓库来换取虚假确定性。
3. 先按一句话实际约束的对象分流，不靠文件名、`spec` 字样或关键词整体搬迁：
   - 告诉 Agent 怎样行动、何时读取什么：项目 `AGENTS.md` 或等价 AI 路由入口。
   - 规定系统当前必须满足的接口、安全、兼容、数据、质量或运行不变量：Engineering 或项目已有现行工程 owner。
   - 规定用户／业务结果、范围、验收和产品决定：Product owner。
   - 保存架构方案、实现路线、取舍和决定理由：技术设计／决策 owner；当前约束变化时同步更新现行工程 owner，但不把完整决策历史复制过去。
   - 保存流程、交付、任务状态、发布事实或学习证据：分别进入 Workflow、Delivery、Durable Task State 或 Learning owner。
4. 使用两种不同准入标准：持久 Agent 指令应当是非显而易见、项目特有，且反复需要或一次违反会造成重大伤害；现行工程约束只要当前有效、稳定、面向实现且可验证即可成立，不要求先有失败历史。个人偏好、一次性任务上下文和未确认判断不进入项目长期 owner。
5. 给每个候选保留证据路径，并区分正式规则、稳定实践、待确认候选、legacy 和偶然写法。混合文件可以保留原物理位置，但章节职责、唯一权威和历史／现行边界必须清楚；无法可靠分类时只报告候选，不让关键词脚本自动搬迁。
6. 理由或例外会影响行为且无法从证据确认时，再向负责人提出一个具体问题；不要求用户逐条解释显然事实。
7. 获得写入授权后，把完整规则更新到原有专业 owner；没有 owner 时才选择最贴近职责的现有文档或配置，不默认创建新目录。
8. 在项目规范索引登记短入口；未确认候选不得写成强制规则。

成熟项目的 `AGENTS.md` 还要逐项裁决：项目事实、真实命令、权威路径和明确覆盖项 `retain`；项目特有但已有专业 owner 的正文 `compress_to_route`；与 BuildOS 相同的通用方法 `remove_duplicate`；相互矛盾或时效不明的内容 `conflict_for_user_decision`。治理过程不得先写一份 BuildOS 模板再与旧入口叠加。

代码与工程规范的证据选择和判定方法由 `senmu-build-engineering` 的《项目工程规范发现方法》负责。产品、工作流、交付和学习领域仍由各自 owner 判断本域规则是否成立。

## 4. 项目规范索引契约

每条索引至少回答：

- 这是什么领域的规范。
- 当前任务出现什么信号时需要读取。
- 它影响哪一类决策。
- 完整规则和可执行配置在哪里。
- 当前是 active、candidate、legacy 还是 retired，以及最近何时校准。

索引中的“一句话决策摘要”只用于选择，不足以代替正文执行。规则发生变化时先更新正式 owner，再同步索引状态或入口；不得让索引反向成为专业正文的第二份版本。

同一权威正文可以有多个不同的适用信号或入口，它们帮助不同任务找到同一个 owner，不构成多份事实源；完全相同的索引行只增加噪声，应合并。采用 BuildOS Project Map 时，active 行的项目内路径使用相对权威根的代码路径，或使用相对 Project Map 的 Markdown 链接，以便 validator 确定性核验。validator 只证明已声明入口可达、未越界和结构无确定性破坏；它不要求所有 Markdown 都进入索引，也不证明规则语义正确、没有冲突或仍然有效。

项目治理 validator 的错误用于确定性结构破坏，警告用于完全重复索引行或无法机器核验的 active 入口等人工复核候选。纯警告不改变合规退出码；`--json` 回执提供稳定的 `code`、`path`、`message`、`severity` 和统计信息。把该命令接入 CI 或其他真实执行点前，仍需按项目风险明确批准；脚本存在不等于已经形成持续门禁。

## 5. 当前任务如何按需加载

1. Codex 已自动加载当前作用域的 `AGENTS.md`。只在任务所属模块或交付单元仍不明时，再选择一个最短的项目路由入口；不得把 README、项目地图、架构、基线、发布登记和 worktree 登记串成所有任务的固定前置链。
2. 先根据当前请求选择最小规范集合：版本、候选、发布、生产身份或回滚信号才读基线与发布 owner；分支、并行目录或实施基线信号才读 Git／worktree owner；身份、计费、安全或特定业务信号才读对应专业 owner。
3. 项目 `AGENTS.md` 可给出项目特有的触发信号与 owner 路径，但不得复制当前安装中全部 Skill 的职责目录或通用交接流程。只有真实业务 Agent、流程契约或运行状态成为当前对象时，才转交 Workflow。
4. active 项目规范已充分回答时停止；只有缺失、冲突、治理演进或明确 BuildOS 请求才读取一个当前专业 Skill 的必要 reference 和相关有效经验。
5. `candidate` 只能提示调查，不能作为门禁；legacy 只能用于兼容、迁移或历史解释。
6. 遇到冲突时以当前项目的正式 owner 和真实运行证据为事实基础；项目明确覆盖通用默认。时效不明、项目 owner 互相冲突或可能降低不可放弃 Hard Gate 时，列出证据和影响并请求用户裁决。

## 6. 路由接线如何验证

路径存在、Markdown 链接有效、assessor 无冲突或模板通过静态校验，只能证明结构已准备，不能单独宣称“新 Agent 已接上项目上下文”。当治理目标包含实际路由或上下文减负时，用全新会话按风险至少验证：

- 一个低风险单单元任务：应直接进入目标 owner，不加载全局基线、发布登记、worktree 登记或 Project／Workflow 治理。
- 一个专业边界任务：应命中对应契约和必要基线，不扩展到无关领域。
- 一个发布或回滚任务：应命中候选身份、发布单元、授权、生产证据和恢复入口。

未执行这类独立路由验证时，状态最多记为 `structural_routing_prepared`，并明确列出未验证行为。

## 7. 收口标准

一次规范发现只有在以下条件满足时才算完成：证据和适用范围清楚；完整规则进入唯一专业 owner 或明确保持候选；短索引可把后续 AI 路由到该 owner；重复、过时或 legacy 入口已经标注；没有把外部范例、个人偏好或一次性任务状态伪装为项目长期规范。
