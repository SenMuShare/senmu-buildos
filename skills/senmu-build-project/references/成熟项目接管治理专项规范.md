# 成熟项目接管治理专项规范

本规范用于接管历史代码、文档、目录、任务、分支或发布事实混乱的已有项目。目标不是一次“打扫干净”，而是在不丢失业务事实、运行能力和恢复路径的前提下，将项目演进为可理解、可修改、可验证、可交接的治理实例。

Project 只统筹项目根、范围、任务状态、owner 映射和授权检查点。Product、Workflow、Engineering、Delivery 修正各自事实；Assurance 负责冻结审查、Finding 与复核。不新建“治理架构”来复制专业正文。

## 1. 启动条件与两段授权

当用户要求“接管、治理、规整、系统审计、逐步整改”一个成熟项目，且工作可能跨多阶段、多会话或多领域时启动本专项。普通 Bug、单个重构、一次目录放置建议或只读问答不启动。

授权分两段：

1. **审计授权**：允许只读盘点、运行不改变项目或外部状态的检查、建立基线和整改候选。不允许候选反向成为项目事实。
2. **实施授权**：用户看过基线、Finding、目标图、整改波次、影响和恢复点后，明确批准具体范围才能修改。一次批准不自动授权后续扩围、发布、删除、数据迁移或生产操作。

如果用户在启动时已明确授权“审计并在安全范围内整改”，仍要在基线形成后暴露会改变用户行为、数据、权限、发布边界或破坏恢复能力的决策点；不用宽泛授权掩盖重要取舍。

## 2. 唯一状态与本地工作区

整个专项使用[任务执行与状态管理规范](任务执行与状态管理规范.md)选定的唯一 Durable Task State Owner；本页只补充目标、授权、Finding、证据和复核入口，不为成熟项目另建第二套任务实现。

审查需要大量中间物时，在项目现有临时／工作区 owner 中登记一个有界位置，记录用途、owner、Git 跟踪策略、敏感性、保留期和恢复方式。只有项目没有等价 owner 且用户批准时才建新位置。终局由用户或项目策略选择 `retain`、`archive` 或 `delete_authorized`；未决定时保持 `pending_user_decision`，Agent 不自动删除。

BuildOS 文件型默认实现可使用 [接管治理任务模板](../assets/mature-project-governance/TAKEOVER_TASK.template.md) 和 [控制记录模板](../assets/mature-project-governance/GOVERNANCE_CONTROL.template.json)。它们是可选实现，不是成熟项目必须采用的目录命令。

## 3. 执行协议

### A. 冻结基线

- 确认权威项目根、Git／worktree／子仓库、发布单元、当前版本、运行对象和已验证恢复点。
- 记录审计时间、commit／数据 revision／环境身份和证据时效；脏工作区和并行任务不会被静默改写。
- 先运行 `assess_project_governance.py` 的零写入盘点，再语义确认需求、技术、任务、运行、质量、交付和恢复 owner。

### B. 建立覆盖图与 Finding

- 按发布单元、核心用户流程、模块、数据／权限边界和可运行入口建立 Coverage Map；未覆盖领域标为 `not_assessed`。
- 各专业 Skill 对自己的 owner 形成现状事实、目标、保留／合并／移动／新增候选、影响、恢复点和验收证据。
- Finding 使用稳定 ID，记录证据、P0-P3、状态、业务／技术影响、责任 owner、最小整改目标和复核条件。审计只产生候选，不自动授权修改。

产品文档缺失时，不补造历史需求池或过去版本 PRD。先由 Product 根据现有页面、功能、代码、接口、测试、运行和用户确认重建当前 `PRODUCT_SPECIFICATION.md` 或等价产品规格；再由 Engineering 重建当前 `SYSTEM_TECHNICAL_SPECIFICATION.md` 或等价技术规格。确认事实、合理推断、冲突和未知必须区分，后续新版本才使用统一版本 PRD、按需技术设计和测试用例结构。

### C. 用户裁决与整改波次

每个 confirmed Finding 必须获得一个明确决定：`remediate`、`accept_risk`、`defer`、`false_positive` 或取消专项。决定记录批准者、时间、范围和重评条件。P0-P1 不能用 `defer` 模糊搁置；接受风险必须有明确 owner 和证据。

整改按可验证的结果波次组织，而不是按文件数、固定 Sprint 或“先把所有目录整理完”组织。优先顺序是：防止不可恢复损害→恢复权威与主链路→消除重复事实源与高扩散耦合→改善局部可理解性。每波必须关联 Finding ID、实施任务、变更身份（commit／发布单元／数据 revision 或非 Git 等价回执）、验证和恢复点。

### D. 验证、复核与收口

- 实施者完成匹配验证后，Finding 只能进入 `resolved_unverified`；复核者重跑原失败路径、检查回归和冻结对象后，才能进入 `verified_resolved`。
- 每波完成时更新任务状态，记录已完成、未完成、新增风险、恢复入口和唯一下一步；长任务不依赖聊天记忆继续。
- 最终复核重新冻结目标版本，核对批准范围、未处理 Finding、正式 owner、主链路、质量命令、发布／回滚状态和残余风险。
- 在整理期产生的报告、快照、临时脚本和中间数据依用户决定保留、归档或授权删除。删除前确认正式事实已进入原 owner，临时物不是唯一恢复依据。

## 4. 可验证控制记录

项目选择 BuildOS 文件实现时，将校准后的控制记录放在已登记的任务／审查 owner 中，并运行：

```bash
python3 <buildos>/skills/senmu-build-project/scripts/validate_mature_project_governance.py \
  --record <project-control-record.json>
```

校验器只校验关联和收口不变量，不判断技术方案是否专业，不自动修复、创建分支、发布或删除临时记录。项目使用其他状态系统时，可在其原生 schema／自动化中实现同等不变量，无需导出第二份 JSON。

专项进入 `completed` 前必须同时满足：基线已冻结；审计覆盖与盲区已说明；confirmed Finding 均有决定；获批整改具有任务、变更和匹配验证；P0-P1 无未复核阻断项；最终复核已绑定目标身份；临时内容去留已决定；发布和生产事实仍由 Delivery 单独证明。
