# 项目治理实例与演进规范

Senmu BuildOS 是跨项目复用的治理方法、判断标准、默认实现和专业手册，不是任何具体项目的需求、技术方案、任务状态或发布事实。每个项目都应形成自己的 **Project Governance Instance（项目治理实例）**，把适用原则落到项目现有或新建的权威入口、owner、状态源、质量命令和交付证据中。

## 1. 两类权威

- **事实权威**：项目本地代码、文档、数据库、任务系统、运行状态和发布回执描述项目现在是什么。BuildOS 不得凭默认模板否认真实项目事实。
- **治理标准**：BuildOS 用于判断现有事实链是否完整、清晰、可恢复、可验证和可演进。已有规则不因存在就自动正确；缺失、冲突、重复、过时或不可搬迁时，应治理原 owner。

尊重项目事实不等于冻结项目现状。发现缺口后，先提出目标实例和迁移影响；获得授权后更新、合并或替换原 owner，不建立长期并行事实源。

## 2. 实例统一语义，不统一外形

项目治理实例必须能够发现目标与范围、需求与验收、技术路线、任务状态、运行状态、质量入口、交付／发布事实和恢复方式中实际存在的职责，但不要求所有项目拥有相同文件名或目录。

- 新项目在明确职责和模块后，可以采用 BuildOS 的 `governance/`、`product/`、`engineering/` 等预设，也可以合并或改用更符合项目形态的路径。
- 成熟工作流可以继续以任务包、数据库、manifest、Makefile 和回执作为 owner。
- 外部需求或任务系统可以作为 owner，但项目入口必须记录系统、对象 ID、读取方式和离线恢复边界。
- 小型脚本可以把多个职责合并到 README、测试和版本记录中，只要事实唯一且可发现。

Python、前端框架、通用代码质量等跨项目稳定知识保留在 BuildOS 中按需查询；项目只保存已选技术栈、实际约束、入口、例外和验证命令，不复制整本通用手册。

### 放置建议不是目录命令

用户询问某个文档、目录或新职责“放在哪里合适”时，先判断它属于哪个语义 owner，再结合现有结构给出：首选路径、理由、可接受替代、与现有文件的关系，以及是否真的需要新目录。建议可以引用本 Skill 的预设作为比较，但不得把预设说成唯一正确路径，也不得因咨询自动创建或迁移文件。

用户明确要求新建具体文档时，可以在已确认 owner 中创建；若新文档会建立新的长期事实源、改变项目根或引发批量迁移，应先展示目标地图和影响。用户要求整理混乱目录时，应区分“提出规划”和“执行迁移”：前者只交付现状、目标、映射、顺序、兼容与恢复建议，后者需要明确实施授权。

## 3. 三种能力

### Initialize New Project

用于空白或明确的新项目。先从需求、预期技术架构、运行方式和真实用户获取方式分别判断生命周期意图、组合方式、公开模型、发布渠道、已确认制品、治理档位与模块，使用 `--mode plan-new` 查看零写入候选；用户要求实施后，使用同组显式参数运行 `--mode initialize-new`。项目类型只提供初始候选，不能代替上述维度；`release` 表示正式发布治理，不自动证明存在部署目标、容器、安装包或制品保留需求。若确认的目标路径不同于脚本预设，不得为使用脚本而扭曲规划；按目标地图建立最小 owner，并把路径角色与相对关系写入 policy。默认目录只是可选实现，不是所有项目的强制标准。

### Assess Existing Project

用于已有项目，默认严格只读，并分成两个阶段：

1. **Authority-first Inventory**：从评估根、项目导航、发布单元／工作树登记、当前基线和 Git 仓库候选开始，盘点项目地图、policy 与候选 owner，并把缓存、备份、归档、退役和 linked worktree 单独排除。Git root 只能形成仓库候选，worktree 不等于新仓库或发布单元；权威登记引用的 worktree 以 `authority_reference_not_scanned` 单独展示，只有语义确认当前基线后才作为实施入口读取。受支持的 `repositories.json` 显式声明可以确认发布单元、ledger 与退役证据；单次任务实例、POC／实验和第三方运行缓存不得冒充项目级任务、质量或生产 owner。真实交付边界必须由项目登记和运行事实确认。`assess_project_governance.py` 承担这一确定性阶段；默认输出有界摘要，只有 `--verbose` 展开完整清单。
2. **Semantic Assessment**：Agent 读取入口正文和真实项目证据，逐发布单元确认需求 owner、技术 owner、Durable Task State Owner、Run State Owner、质量命令、生产事实和恢复路径，再输出已确认映射、冲突、缺口、重复与迁移风险。

评估结果不应只是文件清单或“通过／不通过”。复杂问题要区分现场事实、治理判定、首选演进方案、可接受替代、需要保留的例外、风险和授权边界。发现大量分支或 worktree 时，Project 先确认项目根、正式入口与身份漂移，再把合并可达性、独有事实和安全清理交给 Delivery；不为了“目录整齐”把它们自动视为垃圾。

文件名命中只能形成候选，不能自动确认语义 owner；多个地图、数据库或任务文件也不能仅凭数量判为冲突。两个阶段的写入操作都必须为零。

### Evolve Existing Project

审视后按授权演进原项目。需求、技术架构、安装方式、部署目标、公开策略、发布渠道或制品类型变化时，先重新评估受影响能力和目录角色，再给增量目标地图；新增 Dockerfile、Xcode 工程或打包脚本只能形成候选信号，存在真实消费者、发布契约或回滚依赖后才启用制品生命周期。优先修复产生问题的需求、职责、目录、接口、数据 owner、默认路径和工作流；补齐缺失职责，合并重复 owner，迁移不可搬迁路径，并保留恢复点。完成后由项目自己的入口、policy、schema、工具和证据接管日常执行。

若演进需要多领域审计、多波整改、跨会话恢复和最终复核，按《成熟项目接管治理专项规范》组织。该专项映射已有 Durable Task State Owner，不替代本节的事实优先、两段授权和原 owner 演进原则。

## 4. 状态 owner

跨阶段或跨会话工作必须有明确的 **Durable Task State Owner**，但其实现由项目实例决定。BuildOS 为 standard/release 新项目提供 `governance/tasks/` 默认实现；core 可沿用 README、Issue 或外部任务系统，已有项目可以映射到项目任务包、数据库或外部系统。

Task State 记录跨阶段目标、边界、进度和恢复入口；Run State 记录某次运行的 step、attempt、checkpoint 和输出；产品、工程、交付与审查文档保存各自专业事实。它们通过稳定 ID 和链接关联，不复制正文。

## 5. 可搬迁定位

提交到项目的治理实例不得以某台机器的绝对路径定义项目身份。优先使用 Git toplevel、仓库 ID、领域 ID、包含固定 `.senmu-buildos/config.json` 的项目根、工作区路径角色和相对关系。新项目 policy 使用 `root_locator.kind=git_toplevel|governance_policy_root` 与相对路径 `.`；私有权威根、公开投影根、运行数据根、暂存根、交付根和归档根都先登记角色，再映射项目自己的相对路径。绝对路径只能是运行时解析结果或本机未提交配置，初始化器生成内容不得因执行机器、用户名或父级业务目录不同而变化。

## 6. 经验回流

项目特有事实和 SOP 留在项目实例。只有经过复现或跨项目验证、能够改变通用决策且不会普遍增加负担的经验，才由 Assurance 提议反哺 BuildOS。反哺后仍由具体项目决定何时升级自己的实例。
