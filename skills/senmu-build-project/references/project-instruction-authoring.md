# Project Instruction Authoring

Explicitly adopted team working principles may be shared across projects; complete methods stay with their specialist owners. The goal is better decisions and effective delivery, not the shortest entrypoint.

## Dual-Track Instruction Authoring

Governance has two parallel outcomes: reconcile existing instructions and adopt missing applicable principles. Inventory or stale-version removal alone is insufficient. These are project collaboration instructions, not business-agent definitions.

1. Identify effective ancestors, overrides, host entrypoints, active worktrees and writable scope. Distinguish file discovery from observed loading. Preserve global settings, protected/history scopes and others' work.
2. Reconcile in place: preserve approved behavior, real commands and exceptions; merge equivalents and resolve conflicts at current owners. Route volatile task/release facts to their sources; remove unconditional preloads, not valid technical-version constraints.
3. Adapt the [AGENTS starter](../assets/project-governance-starter/AGENTS.template.md), not its literal layout. Apply the principles below and omit software-only clauses for non-code work. No vendor, framework or business domain is universal.
4. Combine principles with confirmed project facts and conditional routes. Never invent scripts, owners, approvals or results. Contracts define intent; observed defects do not become policy. Unresolved business changes remain proposals.
5. Localize under the policy below. Keep useful decision summaries in the effective entrypoint and detailed methods with specialists. Applying an adopted principle requires no new Skill call, copied manual or parallel policy.
6. An audit-and-optimize request includes scoped edits and needed reference/validator repairs. Audit-only remains read-only. Report actual changes, equivalent coverage, checks and gaps, not just a verdict.

Use one effective shared body; nested files add scope differences. Check actual global/ancestor/Kernel inputs before duplicating text. Brief safety overlap is acceptable; do not inject the whole template through Hooks, invent deduplication machinery or remove permissions. Independently opened worktrees need reachable rules; filenames and host-specific imports do not prove loading elsewhere.

Repeated governance of unchanged facts must be a semantic no-op. Preserve useful wording; merge equivalent meanings, not identical headings. No fixed clause count, project line/token budget, new ledger or wholesale rewrite is required.

The initializer selects software-only clauses by modules and emits an English draft. Calibrate facts, routes and language before adoption. Existing projects are never reinitialized to force a layout. Plugin updates do not rewrite projects. Do not propagate development principles into business prompts or redefine a translation/classification agent's assignment.

## Distill Core Working Principles

Keep durable preferences that change decisions before specialist selection, not slogans or per-action rituals. Merge existing meaning; the starter carries summaries, not copied specialist methods.

- **Independent judgment:** distinguish goals from proposals; question consequential assumptions, including your own. Explain material errors, costs and alternatives without flattery or reflexive opposition. Respect informed choices; revisit only when evidence changes. Clear authorized local work needs no new review ceremony.
- **Evidence:** use code/configuration/runtime evidence for project facts and reliable sources for external facts; refresh volatile facts. Separate observations, inferences and unknowns. Retrieve available facts before asking. Investigate outcome-changing gaps, not every imaginable possibility; avoid universal browsing.
- **Source prevention:** improve requirements, responsibilities, interfaces, data or paths so correct behavior is easier. Do not substitute endless patches, checks or approvals for root repair. Retain necessary protections. Urgent authorized containment may precede root repair; track the remaining cause in the existing task/debt owner.
- **Implementation and preservation:** retain suitable reuse, the approved stack, readability and minimum sufficient change. Least code is not the goal. Trace consumers before deletion; protect unknown data and others' changes. Content governance grants no redesign authority.
- **Proportionate delivery:** finish authorized work, verify by risk, reuse valid context/evidence and report important results and limits. Ask only for unresolved material choices or authority; brevity must not conceal necessary explanation or uncertainty.

Judge value by correct delivery, wrong turns, rework, user corrections and total task cost at comparable acceptance, not rule/read counts. Prune duplication, not decision-changing meaning. Refine ineffective wording through observed use without imposing recurring audits.

## Project Instruction Language

BuildOS methods and starters use English; project instructions need not.

- An explicit user instruction about document language takes precedence.
- When maintaining a file, preserve its established language and intentional multilingual/per-scope arrangements. Chat language alone does not authorize translation.
- New files follow project collaboration language, then the initialization request's language. Use English only when there is no language signal, including a context-free script draft.
- Do not infer language from nationality, location or product market. Do not append bilingual copies by default.
- Preserve meaning, scope, must/prefer/may, exceptions and permissions. Keep filenames, paths, commands, configuration keys, code identifiers and established technical names unchanged. Code-comment, product-content and response languages remain separate decisions.

Ask about language only when a material choice remains unresolved. Localization is not evidence of better model performance or fewer tokens.

## Scoped Authoring Checks

Review routine work, a consequential decision and a release/rollback exception when applicable; check real routes, language, exceptions and no full-Skill preflight. [Core-principle scenarios](../../../tests/behavior/core-working-principles.md) support review, not daily execution.

Test software/non-code drafts, scope selection, original-owner preservation and repeat rendering. Structural fixtures do not prove an AI performed semantic reconciliation, localization or fresh-session loading. Claim runtime activation or token savings only with corresponding observations of scope, sources, results and limits. Controlled comparisons preserve acceptance and relevant model/host/task conditions; source self-review, runtime adherence and measured improvement remain separate conclusions.
