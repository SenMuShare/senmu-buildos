# Project Instruction Authoring

**Read as needed:** [Authoring](#dual-track-instruction-authoring) · [Principles](#distill-core-working-principles) · [Updates](#adopting-a-buildos-update) · [Verification](#verification-policy-adoption) · [Language](#project-instruction-language) · [Checks](#scoped-authoring-checks)

Own project collaboration, not business-agent definitions. Shared principles may span projects; specialists retain full methods. Optimize correct delivery and total cost, not entry length.

## Dual-Track Instruction Authoring

Reconcile existing instructions and adopt missing applicable principles; inventory alone is insufficient.

1. Identify effective ancestors, overrides, host entrypoints and writable scope. Record linked/unread entrypoints rather than treating them as absent; import candidates are not loaded files. The assessor supplies review dimensions, not mandatory deletion or rewriting. Discovery does not prove loading. Protect global settings, history and others' work.
2. Reconcile original owners, preserving meaning, commands and exceptions. Merge equivalents; route volatile facts to their source and remove unconditional preloads, not justified constraints.
3. Adapt the [AGENTS starter](../assets/project-governance-starter/AGENTS.template.md), not its headings. Retain general principles for non-code projects and only applicable software clauses.
4. Add confirmed facts and conditional routes. Never invent commands or authority, or treat observed defects as policy. Keep decisions in the entry and methods/configuration with their owners; adopted principles need no extra Skill call.
5. Complete authorized scoped repairs and consumers; audit-only stays read-only. Report changes, coverage, checks and gaps.

Use one shared body with scoped differences. Inspect ancestor, global and Kernel inputs; necessary safety overlap is acceptable, whole-template Hook injection or persistent deduplication machinery is not. Preserve worktree reachability. Files and imports prove neither cross-host loading nor permission.

## Distill Core Working Principles

Review coverage, not a mandatory lifecycle. Add no per-action form, plan, approval, Skill call or report. Put exceptions beside defaults.

| Decision | Meaning to retain | Owner |
| --- | --- | --- |
| Understanding | Mode, goal, scope, completion and approved reasons; facts before clarification. | Product / Project |
| Judgment | Evidence, both parties' assumptions, tradeoffs and informed choice. | Product / Assurance |
| Cause repair | Source repair, bounded repair or containment under actual constraints. | Engineering / Workflow |
| Selection | Existing sufficiency, semantic fit, reuse and usable minimum delivery. | Design / Engineering |
| Preservation | Meaning, reasons, consumers, data, others' work and recovery; justified retirement. | Project / Workflow / Delivery |
| Verification | Real outcomes, risk, valid evidence and stop conditions, including non-code work. | Engineering / Design / Assurance |
| Completion | Unfinished scope; distinguish produced, verified, accepted and released. | Project / Delivery |
| Learning | Reassess repetition; repair the rule, route or default implementation. | Learning |

Preserve outcomes, authority and protections. Root repair is not rewrite authority; small scope does not excuse inadequate repair. Bounded repair need not be an emergency. Recommend action on material remaining causes, limits and revisit conditions, not speculative risk lists. Track continuing limitations at the existing task/debt owner; govern authorized rules there, never bypass them.

For software, trace unfamiliar/cross-module flows, recover reasons before design changes and design caller usage before key interface/state/data changes. Clear low-risk edits proceed directly. Engineering owns the [methods](../../senmu-build-engineering/references/source-code-quality-and-ai-collaboration.md#5-ai-implementation-debugging-and-review-loop); Product owns version documents. Missing routes remain explicit.

## Adopting a BuildOS Update

Plugin updates do not rewrite projects. During authorized initialization or reconciliation, compare changes with effective project rules, stack, risks and host loading.

- Unused languages and equivalent rules need no edits. Preserve language, exceptions and working imports.
- Put technical/security changes at their professional owner. AGENTS receives short decisions, real commands and conditional routes, not copied profiles.
- Record `adopted`, `no_change_needed` or `gap_open`, with owner and evidence, in the existing task/governance record. Add no second state system.
- Initializer `adoption_checks` define pending checks; `adoption_record_owner` locates outcomes. An `active` scaffold and strict structural validation do not prove adoption or safety.
- Verify the changed route through real implementation and a matching check. Observe changed host loading in a fresh session when available; otherwise retain the gap without blocking unrelated authorized source work.

Repeated governance is a semantic no-op for unchanged facts. Do not reinitialize existing projects for layout or change business-agent lifecycles. Calibrate drafts before adoption.

## Verification Policy Adoption

Use Engineering's [Testing](../../senmu-build-engineering/references/software-testing-and-quality-verification.md#0-minimum-sufficient-verification). Identify focused commands, expansion triggers and CI/release owners. Reconcile redundancy within authority or disclose it without bypassing checks. Preserve output/schema/security contracts; avoid bulk test deletion, compulsory full-suite inventories and universal frameworks.

Non-code work uses rendered output, source accuracy, completeness or final delivery evidence, not a software stack. Put concise decisions in AGENTS and details at existing owners; keep unknowns explicit.

## Project Instruction Language

Methods/starters use English. Explicit document-language requests prevail; otherwise preserve established and intentional scoped languages. New files follow collaboration language, then request language; English is the no-signal fallback. Nationality, market or chat language alone does not authorize translation or bilingual copies.

Preserve meaning, scope, must/prefer/may, exceptions and authority. Keep commands, paths, keys and identifiers unchanged. Code-comment, product-content and response languages remain separate. Ask only about consequential unknowns.

## Scoped Authoring Checks

Review targets, nearby non-triggers and legitimate exceptions using [decision scenarios](../../../tests/behavior/core-working-principles.md). Include clear/ambiguous tasks, bounded repair and non-code acceptance. Test rendering, scope, original-file preservation, placeholders and markers; prose matching is not intent proof.

Separate storage, resident inputs and task reading. Inspect ancestors, imports, Kernel and references; imports may not reduce loaded context. Remove duplication without dropping conditions or safeguards. Context units are estimates, not official limits or measured tokens. Add no universal cap, ledger or wholesale rewrite.

Fixtures do not prove reconciliation, localization or adherence. Activation needs observation; improvement claims need comparable acceptance, model, host and tasks. Distinguish source review, actual behavior and measured savings.
