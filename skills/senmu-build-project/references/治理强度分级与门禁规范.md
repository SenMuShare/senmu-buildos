# 治理强度分级与门禁规范

本规范用于决定一次任务需要多重的项目治理。目标是避免两种极端：小任务被重流程压垮，重大修复、发布或高风险改动又因为“只是改一点”而绕过门禁。

## 0. 宜疏不宜堵：源头治理优先，门禁兜底

默认采用“质量内建（quality built-in）”而不是“缺陷产生后不断叠加检查”。先定位缺陷在哪个生产环节被制造，再优先修正需求、职责归属、架构、接口、数据模型、默认值、实现或操作流程，让正确路径成为最容易、最默认的路径。

测试、validator、清单、提示词、审批和发布门禁用于发现回归或控制无法消除的剩余风险，不能代替根因修复。不得仅因一次失败就默认新增门禁，也不得用“门禁已补”宣称问题已解决。

新增或加强门禁前，至少判断：

1. 已验证的根因和产生缺陷的环节是什么；能否直接消除或降低缺陷产生概率。
2. 修正生产环节后还剩什么风险，其影响、可逆性和发生概率是否值得设门禁。
3. 判断是否确定、稳定、重要或频繁，能否从真实执行入口机器判定并保持低误报；纯语义猜测、提示词或长清单是否可能因上下文、模型能力或执行成本而失效。
4. 门禁的运行、Token、时间、维护和误报成本是否与风险相称，能否只覆盖关键路径。
5. 门禁由谁维护，何时复核、降级或退役，避免临时补丁永久累积。

新增或改变确定性门禁时，至少验证一个真实违反案例、一个合理例外或明确无例外案例，以及一个相邻但无关的案例。门禁反复误报时先缩窄或移除，不把误报成本继续转嫁给后续 Agent。

安全、隐私、支付、权限、生产数据、破坏性操作、正式发布完整性等不可接受风险仍保留必要的 fail-closed 门禁。这里限制的是用门禁替代工程修复和在低风险处过度设防，不是取消必要验证。

### 0.1 自查、正式评审与独立审查

- 普通自查由当前专业 owner 完成：需求由 Product 自查，技术设计、实现与测试由 Engineering 自查，工作流和发布分别由 Workflow、Delivery 自查。发现问题直接回到原 owner 修正，不另建审查流程或报告。
- 正式评审只在项目流程、治理等级或负责人明确要求时进行，并复用现有需求评审、技术评审、发布核验等 owner；检查项按本次风险裁剪，不为形式完整补齐无关内容。
- 独立审查只在明确要求独立结论、存在跨域争议，或正式审查确实需要职责分离时交给 Assurance。G3-G4 只提高证据、验证和收口强度，不自动触发 Assurance。
- 一致性检查安排在自然转换点：需求进入设计／实现前、设计进入实现前、实现进入验收／发布前，以及任务收口时。普通文件修改或每个小步骤不重复执行整套检查。
- 默认不创建 `checklists/` 目录或一次性 Checklist 文件。只有检查会反复发生、风险显著、内容稳定、现有 owner 无法承载，并且已经明确维护人、复核周期和退役条件时，才建立长期 Checklist；否则把发现写入当前任务或现有评审记录。

## 1. 先分级再执行

AI 入场后，应先判断本次任务属于哪个治理等级。等级可以随着排查结果升级，不能为了省事降级。

| 等级 | 典型任务 | 最小要求 |
| --- | --- | --- |
| G0 轻量问答/阅读 | 解释代码、回答流程、整理想法、不改文件 | 说明依据；不写工作日志，除非形成项目决策 |
| G1 契约保持型局部变更 | 产品、运行和交付契约保持不变的局部实现或内容调整 | 检查契约与影响范围；运行目标范围可用的质量检查或说明未验证 |
| G2 普通工程任务 | 新增小功能、普通 Bug、局部重构、只读工程治理审查、文档补齐 | 读相关 reference；运行格式、lint、适用类型检查和匹配测试；架构审查先出证据，不自动扩展为重构；必要时写工作日志 |
| G3 发布或结构性任务 | Hotfix、正式发布、跨模块架构变化、公共契约或数据结构变化、部署、版本、回滚、线上验证 | 先做架构影响说明；项目完整质量、架构、测试、构建和 CI 通过；发布时必须走版本、changelog、工作日志、tag、制品、线上验证和回滚门禁 |
| G4 高风险/组织学习任务 | 安全、支付、权限、数据迁移、生产事故、重复踩坑、跨 AI 返工 | 必须做复盘；必要时更新项目规范；符合条件时形成 BuildOS 整仓反哺候选 |

如果任务同时命中多个等级，按最高等级处理。

## 2. 门禁类型

每条规则应尽量归入三类之一。

### Hard Gate

不满足就不能宣称完成，除非项目负责人明确豁免并记录原因。

典型 Hard Gate：

- 正式发布必须有版本、changelog、tag、线上验证和回滚依据。
- Hotfix 必须确认发布单元、当前版本、回滚点和未发布改动边界。
- 生产数据、支付、权限、删除、导出、上传必须有后端校验和验证记录。
- 涉及真实密钥、用户隐私或生产数据时，必须阻止写入 Git 或公开日志。
- 项目已声明为合并或发布阻断项的格式、lint、类型、测试和构建检查必须通过；无法运行或豁免时必须由负责人明确确认并记录风险。
- 项目已声明的禁止依赖、循环依赖、跨发布单元内部引用和破坏性公共契约变化必须阻断；需要改变规则时先更新架构契约并记录影响和批准。
- G3-G4 新增模块、公共接口、数据库 schema 或基础依赖时，必须有影响说明、匹配测试和回滚／兼容依据。
- 正式发布必须完成权威文档影响判断：正文有变化时同步修改，正文无变化时确认适用版本，历史快照保持原版本。
- G3-G4 使用分支、worktree、clone 或迁移暂存区时，源码、运行资产、台账、交付物和验证必须回到负责人登记的
  各自正式 owner；临时目录中的完成状态不能替代。项目级 POC 根可以独立于产品发布源，POC closeout 负责其
  残留归零，普通产品发布只检查候选和共享资源影响。
- 需求／技术检查项默认是评审辅助，不是所有任务的固定门禁。当 G3-G4 变更确实涉及该检查领域、进入正式评审或负责人明确要求时，未解决阻断项才阻止进入下一阶段；G0-G2 按风险裁剪并记录未覆盖项，不为形式完整制造额外流程。
- 影响技术或产品决策且临时成果可能删除的POC，删除前必须形成稳定实验账本、结构化manifest和足以重建实验的复现协议；人工评价未完成时不得宣称最终结论。

### Soft Gate

默认要做；如果不做，必须说明为什么不适用或暂缓。

典型 Soft Gate：

- 普通功能完成后写工作日志。
- 需求或技术方案随业务规则变化同步更新。
- 前端页面优先使用成熟组件库。
- 重复性生产、媒体合成或代码生成链路先完成主路线选择和可复用能力审计；未复用时记录无匹配或不适用原因。
- 重要 UI 变化做浏览器可见验证。
- 新增或修改代码同步有价值的注释、类型和匹配测试；不适用时说明理由。
- 新增模块、依赖、抽象层、跨模块状态或第二套同类能力前，先搜索既有实现并说明架构影响；超过项目变更预算时拆分任务或增加独立复核。
- 已知临时补丁、长期忽略和结构热点登记技术债 ID、影响与收口条件；不因本次无关任务强行清零。

### Guidance

建议性最佳实践。AI 应优先采用，但允许因项目阶段、技术栈或负责人要求调整。

典型 Guidance：

- 优先评估与项目既有技术基线兼容的成熟组件生态。
- 按数据规模、一致性、运行环境和团队能力选择存储，不用项目类型替代论证。
- 按交付、隔离、可观测和运维约束选择部署形态，不把容器化当作所有项目的硬要求。

## 3. 分级执行表

| 等级 | 读文档 | 代码质量 | 写日志 | 更新版本 | 复盘 | 线上验证 |
| --- | --- | --- | --- | --- | --- | --- |
| G0 | 按问题需要 | 通常不运行 | 否 | 否 | 否 | 否 |
| G1 | 读相关代码/文档 | 目标范围检查 | 通常否 | 否 | 仅踩坑时 | 通常否 |
| G2 | 读相关 reference | 格式、lint、适用类型、匹配测试；结构审查按证据报告 | 通常是 | 用户可见或发布时 | 返工/踩坑时 | 按影响范围 |
| G3 | 必须读架构或发布/日志/部署/分支规范 | 完整质量、架构、测试、构建和 CI | 是 | 发布时必须 | 重大问题时 | 发布或风险路径必须 |
| G4 | 必须读风险相关规范和复盘规范 | G3 加安全、数据、权限或真实路径复核 | 是 | 按发布归属 | 是 | 按风险路径 |

## 4. 降噪规则

- 不要为了轻量任务新增无关文档、版本号或发布记录。
- G1 使用 Engineering 契约保持型变更快速通道：默认不组合 Product、Workflow 或 Delivery，不修改 PRD／ADR／Changelog，不写 Work Log，只保留受影响实现与一个目标范围检查。项目明确规定或实际契约／风险升级时除外。
- 开发批次和测试时点由 Engineering 测试规范决定；治理等级不因每次小改机械触发完整门禁。
- 不要为每个已修复缺陷新增一条提示词、清单或 validator；先证明仍有需要控制的剩余风险。
- 不要在最终回复中罗列整套 PMO 清单；只说明本次命中的关键门禁。
- 不要把“建议”说成“必须”，也不要把 Hard Gate 当成可选建议。
- 如果任务等级升级，应说明升级原因，例如发现生产影响、数据风险或重复踩坑。

## 5. 最小输出

最终回复至少说明：

- 本次实际治理等级，或隐含说明为什么是轻量任务。
- 已完成的关键验证。
- 未完成或不适用的门禁。
- 如果有复盘或文档更新，说明落点。
