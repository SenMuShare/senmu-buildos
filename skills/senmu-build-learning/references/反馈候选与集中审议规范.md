# 反馈候选与集中审议规范

本规范负责 BuildOS 组织学习的“进料口”：让 Agent 在真实项目中使用 BuildOS 遇到的高信号问题进入 BuildOS 本机收纳箱，再由用户触发集中审议。它不是用户需求池、业务项目收纳箱、看板、统计系统或第二套项目台账，也不自动修改 Skill。

## 1. 捕获什么

候选必须指向 BuildOS 提供的 Skill、reference、模板、脚本、Hook、规则或运行引导，并至少命中一类真实影响：

- 内容错误、冲突或误导 Agent，造成错误决定、回退或返工。
- 写得抽象、空泛、难理解或无法落实到真实项目，Agent 需要额外猜测或重新研究。
- 规则、流程或默认产物让 Agent 多做无效工作、过度实现或明显降低效率。
- Skill 与真实项目、框架或平台能力冲突，只能绕开 BuildOS 才能完成任务。
- 模板或规格指导导致产物不清楚、不完整或不可直接执行。
- 同类 BuildOS 使用问题再次出现，说明上次没有修到真正 owner。

普通业务需求、功能 Bug、项目特有事实、用户对产品方案的修改、一般写作偏好、单次命令拼写、尚未验证的猜测和日常进度不投递。只有能够说明“哪个 BuildOS 内容造成了什么影响”时，项目中的问题才可作为 BuildOS 候选。

## 2. 唯一捕获路径

反馈由正在使用 BuildOS 的 Agent 判断并主动提交，不从用户每条消息中自动猜测。用户指出 BuildOS 不好用时，Agent 先处理当前请求，再判断是否满足上面的 BuildOS 指向和真实影响；满足时通过 Learning 路由调用：

```text
node <plugin-root>/hooks/feedback-cli.js submit \
  --component "<BuildOS Skill/reference/template/script/Hook>" \
  --summary "<problem>" \
  --impact "<error, confusion, extra work, inefficiency, or poor output>" \
  --project-root "<source-project-root>" \
  --evidence "<evidence-reference>" \
  --quiet
```

`--component` 和 `--impact` 是必填边界，防止把业务需求冒充 BuildOS 反馈；`--evidence` 可以是会话、文件、命令结果或绕行说明。`--quiet` 不输出候选 ID 或回执。CLI 不可用时不冒充已保存。用户显式要求查询或处理 BuildOS 收纳箱时，才返回最小必要结果。

## 3. 本机意见箱

BuildOS 收纳箱默认位于 `~/.senmu-buildos/feedback/`，可用 `SENMU_BUILDOS_DATA_DIR` 改到指定本机数据根。来源项目只作为问题发生位置；候选本身始终是对 BuildOS 的意见。它不在业务项目创建 README、台账或治理结构，不上传网络，不修改 Git。

每条候选为独立 JSON 文件，以稳定指纹防止同一事件重复写入。只保存：

- 候选 ID、时间、来源 Harness 和信号类型。
- 本机项目根、session ID 和可用的 transcript 引用。
- BuildOS 组件、具体影响，以及经长度限制和常见密钥模式脱敏的短摘要。

文件和目录在支持 POSIX 权限的系统上分别使用 `0600` 和 `0700`。脱敏只是降低风险，不是完整 DLP；不应在反馈摘要中写密钥或客户数据。

## 4. 集中审议

用户要求“处理／整理 BuildOS 意见箱”时：

1. 从已加载 Skill 定位插件根，先运行 `node <plugin-root>/hooks/feedback-cli.js pending --summary` 取得数量、BuildOS 组件、来源项目和时间范围；再用 `--json --limit <n> --offset <n>` 分页取得当前审议需要的候选，不默认把整个收纳箱一次装入上下文。
2. 按根因、适用范围和专业 owner 查重聚类，不按表面措辞或数量直接晋级。
   若现行 Skill 已覆盖该决策，同时检查实际 Harness、项目入口、脚本、validator 和行为测试是否消费它；“规则已写但行为仍错”默认是执行源缺口，不是再写一遍规则的证据。
   若候选来自对话或基于讨论形成的报告，最终总结只算候选证据；按当前判断需要取得相关原始轮次，核对前提、用户纠正、被比较方案和证据，再与项目或运行事实交叉验证。用户陈述是重要输入但不自动成为已核证事实；不机械读取整段会话，也不只看最终答案。
3. 对每组只提出一个分类建议：`discard`、`project`、`buildos_candidate` 或 `needs_evidence`，并说明理由。
4. 先与用户确认分类和抽象；未授权时不修改项目、BuildOS、安装实例或发布状态。
5. 确认后用 `feedback-cli.js decide` 写入独立决策回执；原候选保留，不靠删除改写历史。

最小命令：

```bash
node <plugin-root>/hooks/feedback-cli.js pending --summary
node <plugin-root>/hooks/feedback-cli.js pending --json --limit 10 --offset 0
node <plugin-root>/hooks/feedback-cli.js decide --id <FB-id> --disposition <value> --note "<reason>"
```

## 5. 晋级后的边界

- `discard`：一次性、噪声、已有规则且只是未遵守，或无法形成可判定动作。
- `project`：审议后确认只是来源项目自身的问题，回到其需求、架构、实现、流程或交付 owner；BuildOS 收纳箱不复制正文。
- `needs_evidence`：记录需要哪个复现、验证或第二项目样本，不当长期规则执行。
- `buildos_candidate`：作为 BuildOS 源码项目的独立输入，再按整仓影响分析、测试和发布授权实施。

可选定时任务只可读取待处理候选并生成审议建议；不得无人审议地修改或发布 BuildOS。
