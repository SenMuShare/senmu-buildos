# 技术架构与组件选型方法

本规范提供项目无关的技术路线决策方法。它不维护永久框架白名单，也不把某个语言、厂商或组件库当作所有项目的默认答案。

## 1. 先定义问题，再选技术

编码前按任务规模确认：

- 产品形态、用户和核心业务流程。
- 运行环境、交付方式、规模、延迟、可用性、安全和合规要求。
- 项目既有语言、框架、组件、部署、数据和团队维护能力。
- 本期范围、可逆性、时间预算和预期寿命。
- 哪些能力属于业务差异，哪些属于通用基础设施。

语言只是实现媒介，不是完整架构。应用框架也不是所有任务的必选项：小脚本、CLI、一次性自动化、离线处理和边界清楚的单文件工具，可以优先使用标准库与少量成熟依赖。

### 1.1 独立判断与事实来源

用户提供目标、约束、偏好和授权边界，不自动提供当前系统事实或正确技术答案。讨论产品技术方案、架构、实现和缺陷时，明确区分已确认事实、推断、未知项与建议，结合需求契约、项目证据、反例、替代方案、维护成本和失败边界独立判断；不成立时直接说明不建议、原因及什么条件下可以成立。

回答“当前系统是否这样实现／运行”时，只要真实项目能够合理查证，就先检查最低成本且足以回答问题的权威证据，例如现行需求／设计、调用链、代码、配置、测试、数据或运行结果。不得把用户措辞、历史文档、目录名、流畅解释或通用经验当成当前事实；尚未检查或证据不足时标为假设或条件性建议。

外部技术状态、标准、安全要求、版本能力或成熟实践会实质影响结论时，查询适用的官方资料、标准或一手技术证据，说明时效与适用边界；外部资料不能替代项目现场。证据强度与风险匹配：普通概念讨论可以简短作答，高成本、难回退、安全、数据、权限、支付、生产或争议性决定需要更强证据和候选比较。

### 1.2 技术规划按影响分流

技术规划的目标是让实现前的重要决定清楚，不是让每个任务生成一套文件：

- 边界明确、单步骤、可逆的小改动，直接实现并做匹配验证，不创建 TD、Research 或 ADR。
- 多步骤、跨文件或需要恢复接力的任务，先由项目声明的 Durable Task State 保存范围、进度、约束和下一步；只有方案需要被解释、评审或长期引用时才创建 TD。
- 存在会改变技术方案、成本、交付、维护责任或风险的未知项时，先在编号任务计划中登记；证据、候选比较或试验复杂到不适合保留为摘要时，才创建正式 Experiment Package 或对应专业研究产物。
- 研究结论必须晋级到 TD、ADR、REQ 或其他正式 owner。任务计划中的研究摘要不能成为第二份技术方案，也不能以“研究完成”代替负责人确认、技术评审或生产批准。
- 只有长期影响模块职责、依赖方向、公共契约、数据所有权、基础设施或发布边界的决定才建立 ADR；普通实现细节留在 TD 或代码中。

技术设计开始前读取需求、项目治理章程、现行架构和既有能力；设计完成后再检查一次范围、复用、复杂度、产品影响、成本和生产风险。G0-G2 使用最小必要自查，G3-G4 或难以逆转的选择再强化评审，不把这套分流变成所有任务的固定命令链。

## 2. 用架构原则约束候选

用 `架构约束与技术债治理规范.md` 的原则和审查问题筛选候选，不在本文件重复定义。会制造双主框架、循环依赖、跨层直连、共享可变状态、所有权冲突或第二套相同能力的候选，默认淘汰；确需采用时记录收益、隔离边界、验证和退出计划。

## 3. 选择顺序

按以下顺序解决能力缺口：

1. 复用项目已有且仍受支持的能力。
2. 使用语言或平台标准能力。
3. 采用与现有架构兼容的成熟框架、组件、SDK 或服务。
4. 对无法由成熟方案覆盖的业务差异编写小范围自有代码。
5. 只有现有基线无法满足核心要求时，评估更换主框架或重构架构。

“成熟方案优先”不是禁止自研。通用基础设施优先复用；真正承载竞争差异、特殊规则或无法合理适配的部分可以自研，但必须有清晰边界、测试和维护责任。

## 4. 候选评价矩阵

至少比较以下维度，按项目风险调整权重：

| 维度 | 核心问题 |
| --- | --- |
| 需求契合 | 能否覆盖核心流程和质量属性，是否需要大量逆向适配 |
| 架构契合 | 是否符合模块边界、依赖方向、数据所有权和发布边界 |
| 成熟度 | 维护状态、稳定性、文档、测试、生态和问题响应如何 |
| 维护成本 | 团队是否能调试、升级、观测和长期接手 |
| 互操作性 | 是否容易接入现有身份、数据、构建、部署和监控体系 |
| 安全与合规 | 权限、隐私、供应链、许可证和数据位置是否可接受 |
| 性能与容量 | 是否满足真实负载，是否存在可验证的瓶颈 |
| 可测试与可观测 | 关键行为、故障、性能和外部调用是否可验证 |
| 迁移与退出 | 数据、接口、制品和业务是否能迁移或回滚，锁定成本多高 |
| 总拥有成本 | 开发、运行、培训、升级、许可和返工成本是否合理 |

不要为每个轻量任务制作大表。G1-G2 可以写简短判断；G3-G4、长期基线或难以逆转的选择应保留正式决策记录。

## 5. 主基线与增量扩展

主框架、主组件体系、主要存储或关键运行平台经确认并写入项目文档后，视为稳定架构基线。

- 先复用基线已有能力。
- 对真实缺口只引入一个职责清楚、边界兼容的专用能力。
- 避免多个库共同拥有同一职责或主题、状态、路由、持久化和鉴权规则。
- 新依赖记录用途、版本策略、许可证、替换条件、验证方式和维护责任。
- 基线更换必须说明驱动因素、受影响契约、迁移步骤、双轨期、数据处理、测试和回滚。
- 不因个人熟悉度、新版本热度或 AI 偏好改变稳定基线。

## 6. 复用与组件审计

在实现常见 UI、认证、上传、编辑、媒体处理、图表、队列、缓存、日志、监控、部署或测试基础能力前：

1. 搜索项目已有实现和批准的共享能力。
2. 查询官方标准、官方 SDK、项目已选生态和成熟社区方案。
3. 只加载命中的文档、示例或组件，不把整套厂商资料塞入通用 Skill。
4. 验证版本、许可证、安全、可访问性、性能和维护状态。
5. 记录采用、适配或拒绝原因。

重复性生产链路还应确认组件来源、参数契约、输入输出、确定性、视觉或行为回归、升级策略和 legacy 边界。未复用时，说明没有匹配项还是适配成本高于自研。

## 7. POC 与负责人确认

只有以下情况需要先做 POC 或负责人确认：

- 候选会显著改变产品形态、架构边界、部署方式、成本或长期维护责任。
- 关键质量属性无法从文档、仓库证据或已有基准判断。
- 迁移难以回滚、会产生数据锁定或跨发布单元影响。
- 多个候选的书面比较无法区分真实效果。

POC 使用同一代表性场景和验收标准，记录变量、失败、测量、人工评价、结论状态和复建方法。实验结论不自动等于生产批准。

当不确定性来自算法、状态机、业务流程或数据转换时，优先做逻辑原型：用隔离的可执行 harness 暴露输入、状态、转换、输出、错误和二至三个代表场景，让同一场景能够重复运行和对比。逻辑原型不为显得完整而搭建生产导航、视觉外壳或真实数据写入；界面构图与交互方向由 Design 原型处理，需要正式可复现结论时由 Assurance 冻结 POC 对象和证据。

## 8. 项目内技术决策产物

把选型结果写入项目本地技术设计、技术栈说明或 ADR，至少包括：

- 问题、约束和关键质量属性。
- 现有能力与候选方案。
- 选择、理由、放弃项和证据。
- 模块边界、依赖方向、数据与副作用所有权。
- 自研边界和禁止并行建设的能力。
- 固定版本或兼容范围、升级与退出条件。
- 验证命令、运行观测、迁移和回滚方式。
- 决策负责人和最近校准时间。

具体生态的 API、组件范式和版本规则进入项目专项文档或条件式 reference；不要反向复制到本通用方法中。
