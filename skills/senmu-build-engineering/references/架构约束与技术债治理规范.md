# 架构约束与技术债治理规范

本规范用于防止 AI 在连续交付局部功能时，把项目逐步推向职责混乱、依赖失控、重复实现、补丁叠加和版本治理失真的状态。它关注的是系统长期可修改性，不把“格式整齐、测试通过、页面能运行”误判为架构健康。

本规范适用于项目初始化、现有系统工程治理审查、跨模块功能、局部或全局重构、新增公共接口或数据结构、重复 AI 返工、技术债治理和架构门禁校准。普通 G1 文案、样式或无行为变化的小修不默认加载。

## 本页导航

1. 治理对象；2. 架构设计原则；3. 触发条件与治理等级；4. 项目本地架构契约；5. 架构变更触发契约；6. 变更预算与任务拆分；7. 架构与退化门禁；8. 测试与架构保护；9. 技术债登记与偿还；10. 现有系统审查；11. 整改闭环；12. 降噪与例外。

## 1. 治理对象

把以下概念分开治理：

- **代码质量**：命名、函数职责、类型、异常、测试、注释和局部可读性。
- **架构契约**：模块职责、依赖方向、数据所有权、公开接口、业务不变量、副作用边界和运行边界。
- **技术债**：已知存在、短期接受、但会增加后续修改成本或风险的实现与治理缺口。
- **工程治理**：权威项目根、发布单元、版本、changelog、tag、质量命令、CI、工作日志和发布证据是否一致。

代码质量合格不等于架构健康；测试通过也不等于没有跨层依赖、重复实现或版本混乱。审查时必须分别给出证据和结论。

## 2. 架构设计原则

项目初始化和结构性变化必须把原则转成可检查的边界，而不是只写口号：

| 原则 | 实践要求 | 审查问题 |
| --- | --- | --- |
| 高内聚 | 围绕一个清晰业务能力或技术职责组织规则、状态和行为 | 修改同一能力是否总要跨多个无关模块？一个模块是否承担多类变化原因？ |
| 低耦合 | 通过最小稳定契约协作，避免共享内部实现和可变全局状态 | 消费者是否知道对方私有字段、表结构或初始化顺序？ |
| 单向依赖 | 依赖指向更稳定的策略和核心，基础设施实现不控制核心规则 | 核心逻辑能否脱离具体 UI、存储或厂商 SDK 测试？是否存在循环依赖？ |
| 信息隐藏 | 公开接口只暴露消费者所需能力，内部结构可独立变化 | 内部重构是否会迫使大量消费者同步修改？ |
| 单一所有权 | 数据、状态、副作用和业务不变量各有一个权威拥有者 | 是否存在多个入口分别定义同一规则、状态或数据事实？ |
| 关注点分离 | 区分业务策略、流程编排、外部适配和运行机制 | 业务规则是否散落在控制器、UI、SQL、脚本或部署配置中？ |
| 可替换与可测试 | 在有价值的边界隔离外部依赖，失败可观察，契约可验证 | 关键路径能否做单元、契约和集成测试？替换外部实现需要改多少核心代码？ |
| 适度设计 | 只为当前质量属性和已知演进建立抽象 | 新层次是否解决真实变化压力，还是只为假设性未来增加复杂度？ |

原则冲突时，按项目质量属性和风险记录取舍。例如性能可能要求减少边界，但不能静默破坏数据所有权或让跨层依赖失控。

## 3. 触发条件与治理等级

出现以下任一情况时，应读取本规范并做架构影响判断：

- 新增模块、服务、共享包、后台任务、公共接口或第三方依赖。
- 修改数据库 schema、核心状态机、权限、计费、订单、文件归属或跨服务数据流。
- 同一需求跨越多个模块、发布单元或前后端边界。
- 引入新的抽象层、框架、状态容器、缓存、队列或持久化方式。
- 同类能力已存在但准备新增第二套实现。
- 一个问题经过多次补丁仍反复出现，或多个 AI 对同一模块采用不同结构。
- 文件、函数、依赖或 diff 的规模明显超过项目正常范围。
- 项目负责人要求检查“代码是否越来越乱”“是否形成屎山”“技术债是否失控”或版本治理是否混乱。

治理等级默认如下：

| 场景 | 默认等级 | 最小动作 |
| --- | --- | --- |
| 只读工程健康审查 | G2 | 读取真实代码和治理文件，运行已有只读检查，形成证据化报告，不修改业务代码 |
| 单模块架构校准或局部重构 | G2 | 更新架构契约，补匹配测试，验证依赖和完整 diff |
| 跨模块、公共接口、数据库或发布单元变化 | G3 | 先做影响说明或 ADR，运行完整质量与架构门禁，独立复核 |
| 支付、权限、生产数据、安全或大规模迁移 | G4 | G3 加真实风险路径验证、回滚依据和复盘 |

## 4. 项目本地架构契约

正式代码项目必须在 `engineering/designs/TD-xxxx-<slug>.md` 或 `engineering/ARCHITECTURE.md` 中保存当前技术设计与架构契约。小项目可以合并文档，但以下事实不能消失：

1. **系统边界**：项目解决什么问题，哪些能力明确不属于本系统。
2. **模块登记表**：模块名称、职责、代码路径、公开接口、数据所有权、允许依赖、禁止依赖和发布单元。
3. **依赖方向**：UI、应用服务、领域逻辑、数据访问、外部服务之间允许怎样调用。
4. **业务不变量**：无论怎样修改都必须成立的资金、权限、状态、数据归属、幂等或一致性规则。
5. **副作用边界**：数据库、网络、文件、消息、缓存和第三方调用在哪里发生，失败如何传播。
6. **公开契约**：API、事件、schema、SDK、共享类型和存储格式的兼容责任。
7. **运行与发布边界**：哪些模块独立构建、部署、回滚和版本化。
8. **Legacy 边界**：旧入口、旧实现、兼容层和废弃计划，明确哪些内容不得作为新代码样板。
9. **质量属性与取舍**：只记录需求或风险实际需要的属性；每项绑定业务影响、适用范围、可观察目标、验证方法、owner、约束／依赖和已接受折衷。无法测量或验证时标为假设／未决，不用统一数字制造伪精确。
10. **原则落地证据**：高内聚、低耦合、依赖方向、信息隐藏和单一所有权如何由目录、接口、测试或检查命令体现。

不要为了画图而画图。小型文本表和依赖方向说明通常比一张无法校验的大图更有价值。架构文档必须与真实路径、配置和发布单元相符。

可从 `assets/architecture-governance/ARCHITECTURE_CONTRACT.template.md` 复制项目模板。

## 5. 架构变更触发契约

以下变化在编码前必须做影响说明；G3-G4 或项目声明的关键模块还应建立 ADR 或等价决策记录：

- 新增、拆分、合并或移动模块／服务。
- 改变依赖方向或允许原本禁止的跨层访问。
- 新增公共 API、事件、schema、共享包或跨模块状态。
- 新增数据库表、破坏性迁移或数据所有权变化。
- 新增第三方依赖、基础设施组件、框架或长期后台进程。
- 用新实现替代旧实现，但旧入口、旧数据或旧消费者仍然存在。
- 为解决局部问题引入全局状态、缓存、重试、异步或兼容分支。

最小影响说明回答：

- 为什么现有模块或能力不能满足？
- 已搜索哪些同类实现，如何确认不会创建第二套能力？
- 影响哪些模块、公开契约、数据、部署和发布单元？
- 新依赖方向是什么，是否违反现行架构契约？
- 怎样测试、迁移、观测和回滚？
- 这是永久设计还是已登记的临时技术债？

ADR 记录决策、背景、替代方案、后果和替换条件；不要把每个小实现细节都升级成 ADR。

能力替代应作为一个变更单元收口：同步处理旧状态、UI／入口、路由／事件／过滤链、数据／消费者、测试和现行文档。确需暂留的兼容面必须登记替代对象、owner、退出条件和验证，并明确不得作为新实现样板。

## 5.1 技术一致性自查

普通技术规划和实现前自查由 Engineering 主责，对照 REQ／验收标准、TD／ADR、任务阶段和真实代码边界检查：需求是否有设计承接、设计对象是否有需求来源、任务是否覆盖必要实现与验证、术语和数据实体是否一致、依赖顺序是否可执行，以及是否出现计划外模块、接口、数据或基础设施。

自查结论进入 `TECHNICAL_REVIEW.md`、TD 或项目既有工程评审 owner，不另建第二份技术计划。实现者自查只能标为 evidence-based self-review；负责人要求独立结论、存在跨领域争议或 G3-G4 需要正式独立放行时，交由 Assurance 按冻结对象和证据范围审查，修订仍由 Engineering 完成。

## 6. 变更预算与任务拆分

项目应在 `CODE_QUALITY.md` 中声明自己的变更预算或升级条件，不在通用 Skill 中机械规定统一行数。可使用以下信号：

- 涉及的模块、发布单元或公开接口数量。
- 新增依赖、迁移、配置和运行服务的数量。
- diff 文件数、行为变化范围和回滚复杂度。
- 是否同时包含行为修改、机械格式化、目录移动和依赖升级。
- 是否超出一名评审者或一个 AI 能完整理解和验证的范围。

超过项目预算时，AI 不得用“已经能运行”继续扩大 diff，应暂停并执行以下一项或多项：

- 先提交技术设计或 ADR。
- 按可独立验证和回滚的行为拆分任务。
- 把机械修改与行为修改分开。
- 增加独立 AI 或人工架构复核。
- 明确负责人批准的例外、风险和收口条件。

## 7. 架构与退化门禁

项目根据语言和框架选择工具，但正式项目必须明确哪些架构事实由机器检查、哪些只能语义评审。

优先建立以下检查：

- 禁止依赖和层级方向检查。
- 循环依赖检查。
- 重复代码、重复实现和废弃入口检查。
- 未使用代码、未使用依赖和孤立模块检查。
- 公共 API、schema、迁移和共享类型兼容检查。
- 复杂度、超大文件／函数和高扇入扇出热点趋势。
- 架构文档、policy、目录和实际依赖的一致性 validator。

门禁原则：

- 项目已声明为禁止的依赖、循环依赖、跨发布单元内部引用和破坏性契约变化属于 Hard Gate。
- G3-G4 新增模块、公共接口、数据库或基础依赖但没有影响说明、必要测试和回滚依据时，不得宣称完成。
- 复杂度、重复率、文件大小等指标默认看趋势和热点，不用统一数字机械否决合理实现。
- 老项目先记录基线；新增和修改代码不得让已选指标继续恶化。历史债务单独登记，不能用全局忽略制造绿色。
- 自动检查通过不能替代职责、业务不变量、异常语义和重复实现的人工或 AI 语义评审。

统一质量命令应明确包含或调用适用的架构检查；无法自动化的项目必须保留可重复的人工检查表和证据位置。

## 8. 测试与架构保护

测试应与变化类型对应：

- 业务规则变化：单元或领域行为测试。
- 模块公开接口变化：契约或接口测试。
- 数据库 schema 与数据所有权变化：迁移、兼容和回滚验证。
- 修复历史复杂模块：先补特征测试或回归测试，再拆分实现。
- 跨服务或发布单元流程：集成测试和必要真实流程验证。
- 替换旧实现：证明新入口可用且唯一、旧入口不可达，状态、数据、消费者和事件／过滤链已经收口；暂留兼容边界有 owner、退出条件和验证。

不要用大量针对私有实现的脆弱测试锁死重构，也不要只测成功路径而遗漏权限、部分失败、重复执行和旧数据兼容。

## 9. 技术债登记与偿还

技术债可以被有意识地接受，但不能隐形存在。G2-G4 项目发现会持续增加修改成本或风险的已知问题时，应写入 `engineering/TECH_DEBT.md`、项目 issue 系统或等价权威台账。

最小字段：

- 债务 ID、标题和状态。
- 位置与影响模块／发布单元。
- 形成原因和当前症状。
- 对开发速度、正确性、安全、数据或发布的影响。
- 为什么现在接受，哪些方案已经排除。
- 责任归属、偿还触发条件或目标版本。
- 验收和移除方式。

规则：

- 临时补丁、全局忽略、兼容分支和 TODO 如果代表真实债务，应引用债务 ID 或在附近写明收口条件。
- 不把普通待办全部包装成技术债；只登记会持续产生维护成本或风险的问题。
- 每次涉及债务所在模块时，检查是否已触发偿还条件。
- 正式发布前报告新增、偿还和继续接受的债务，不要求为了清零而阻塞所有发布。
- 债务状态只有在代码、测试、文档和旧入口确实收口后才能改为已偿还。

可从 `assets/architecture-governance/TECH_DEBT_REGISTER.template.md` 复制项目模板。

## 10. 现有系统工程治理与技术债审查

审查默认先只读，不把“发现问题”自动扩展为重构授权。按以下顺序执行：

1. 确认负责人认可的权威项目根、Git 根、当前分支、发布单元和正式运行入口。
2. 检查工作区、最近提交、VERSION、changelog、tag、权威文档适用版本和实际运行版本。
3. 盘点语言、框架、模块、入口、数据库、依赖、后台任务、外部服务和部署单元。
4. 读取项目现有需求、技术设计、代码质量、测试、部署、版本和工作日志，不用文档替代真实代码核对。
5. 先运行项目已经声明的只读质量、测试、构建和架构命令；失败时记录原始结果，不静默修复基线。
6. 检查模块职责、依赖方向、数据所有权、重复实现、循环依赖、复杂度热点、超大文件／函数、宽泛异常、死代码、测试缺口和 legacy 入口。
7. 默认 `risk_based` 模式对核心业务路径做语义抽样，确认业务不变量、权限、事务、幂等、失败补偿和数据一致性是否在正确边界实现；用户明确要求逐文件／函数／注释全量审查时，切换为 Assurance `exhaustive_source` 模式和稳定完成账本，不得用语义抽样宣称完成。
8. 把发现分为代码质量、架构、技术债、测试门禁、版本发布治理，以及需要另行开展的业务正确性或安全风险。
9. 按 P0-P3 排序，给出文件位置、证据、影响、建议和验证方式；不要用笼统的“建议重构”代替可执行结论。
10. 先提交审查报告和分阶段整改计划；没有负责人授权时，不做全仓格式化、大规模移动、框架替换或业务重写。

建议报告路径：

```text
engineering/audits/ENGINEERING_GOVERNANCE_AND_TECH_DEBT_AUDIT_<YYYY-MM-DD>.md
```

严重程度：

- **P0**：可能造成生产事故、数据／资金／权限错误、无法发布或无法回滚，立即阻断相关发布。
- **P1**：架构边界明显失控、核心模块无法安全修改或版本事实冲突，应优先治理。
- **P2**：持续增加维护成本的质量和技术债问题，纳入近期迭代。
- **P3**：可选优化、风格统一或低风险长期改进，不冒充阻断问题。

风险抽样可使用 `assets/architecture-governance/ENGINEERING_AUDIT_TASK.template.md`；穷尽式源码治理使用 `assets/architecture-governance/EXHAUSTIVE_SOURCE_REVIEW_TASK.template.md`，并由 Assurance 控制记录裁决完整性。

## 11. 审查输出与整改闭环

审查报告至少包含：

- 审查范围、权威根、分支、commit、发布单元和未覆盖范围。
- 实际执行的命令、退出结果和证据路径。
- 当前架构和版本治理事实，而不是只复述文档。
- 按严重程度排序的问题清单。
- 当前质量与技术债基线。
- 立即阻断项、近期治理项和长期改进项。
- 建议新增或校准的项目内架构契约、质量命令、测试和台账。
- 未验证盲区和需要业务负责人确认的事项。

整改必须另行分阶段执行：先用测试保护关键行为，再处理高风险边界和重复实现，最后清理低风险结构与风格。每阶段运行匹配门禁、更新技术债状态和工作日志；不要一次性重写整个系统来追求“看起来干净”。

## 12. 降噪与例外

- 小型原型可以把架构契约合并进 `TECHNICAL_DESIGN.md`，技术债写入一个短表，不要求建立复杂委员会或大量文档。
- 不用统一的文件行数、复杂度或覆盖率阈值替代项目判断；要求项目声明自己的基线、趋势和关键路径。
