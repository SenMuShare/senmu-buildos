# 项目工程规范发现方法

本方法用于从成熟代码库的真实工程证据中提炼项目自己的编码、架构、测试和工具链规范。目标是让后续实现延续项目有效做法并识别需要治理的缺陷，而不是把“现有代码就是正确规范”或把 BuildOS 的语言偏好强加给项目。

## 1. 选择代表性证据

先确定当前发布单元和任务切片，再按实际技术栈选择少量代表性材料：

- 公开入口、核心业务路径和常改模块。
- 构建、格式化、lint、类型检查、测试和依赖配置。
- 正常路径、错误路径、边界处理和持久化实现。
- 单元、集成、端到端测试及 fixtures。
- 架构、ADR、代码质量、贡献和发布文档。
- 能说明规则形成原因的近期提交或已验证事故记录。

排除生成代码、vendor、缓存、归档、demo、已退役实现和与当前发布单元无关的 worktree。不要机械规定固定文件数量；证据应足以覆盖目标决策，又不要求全文读取仓库。

## 2. 值得提炼的模式

- 模块职责、依赖方向、公共接口和副作用边界。
- 命名、类型、错误处理、日志、配置和数据迁移方式。
- 框架组件、项目封装、标准库、依赖和复用顺序。
- 测试层级、真实依赖与替身边界、测试数据和质量命令。
- 安全、权限、隐私、支付、生产数据和发布相关的工程约束。
- 与通行默认不同但在项目中稳定、合理且会影响实现的选择。

常识性语言语法、只出现一次且无理由的风格、明显缺陷和互相矛盾的旧实现不提升为规范。

## 3. 候选判定

为每个候选记录证据位置，并判断：

| 判定 | 含义 | 处理 |
| --- | --- | --- |
| 正式规则 | 已有权威文档或机器配置，且与生产实现一致 | 保持原 owner，加入短索引 |
| 稳定实践 | 多处一致并有测试、工具或历史理由支撑 | 经确认后写回最接近的工程 owner |
| 待确认候选 | 有迹象但理由、例外或有效性不清 | 保持 candidate，不约束实现 |
| 工程缺陷 | 重复、耦合、过时或与质量目标冲突 | 进入技术债或当前授权修复，不包装成规范 |
| Legacy | 只为兼容、回滚或迁移保留 | 标注边界和替代项，不作为新实现样板 |

单一文件的写法、代码出现频率和提交时间先后都不能单独证明规范成立。

## 4. 写回与索引

完整规则按语义写回项目已有的 CODE_QUALITY、ARCHITECTURE、TESTING_STRATEGY、TECHNICAL_DESIGN、ADR、工具配置或等价 owner；必要时同时修正代码、配置或统一质量入口，使文档和真实执行一致。

Project Map 或成熟项目映射的短索引只登记领域、适用信号、决策摘要、权威路径和状态。索引不得复制示例、长规则或命令清单。工程规则变化时先改专业 owner，再更新索引。

项目工程规范本身应保持可扫描、可执行：

- 先写规则和适用条件，再补必要理由；不要用背景长文掩盖实际约束。
- 只记录非显而易见、项目特有且会改变实现决策的内容；语言常识和代码已经自解释的事实不重复写。
- 一个条目只负责一个概念，优先使用短条目和最小正反例；示例用于消除歧义，不发展成教程。
- 同一规则只保留一个正文 owner；入口和索引只说明何时读取、影响什么以及正文在哪里。
- 机器能够稳定执行的规则进入现有 formatter、lint、类型、测试或架构配置，文档解释语义、例外和验证入口，不复制配置明细。

## 5. 使用边界

- 项目当前语言、框架和工具链优先于个人偏好；除非任务明确批准迁移，不发起技术栈重写。
- 发现现有做法有缺陷时，优先修复原 owner，不另建一套“更理想”的平行代码或规范。
- 外部官方文档和开源实践可以帮助判断，但不会自动成为该项目已采纳规则。
- 只加载当前模块、风险和变更范围直接相关的规范；全仓重构、迁移或正式审查才扩大证据范围。
- 需要独立判断证据是否充分或存在争议时交给 `senmu-build-assurance`；普通发现和一致性自查仍由 Engineering 负责。
