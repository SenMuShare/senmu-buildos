# Python 工程编码规范

本规范用于 Python 项目的开发、重构、代码评审、质量工具配置和 AI 自查。先遵守项目内 `AGENTS.md`、`engineering/CODE_QUALITY.md`、`engineering/languages/PYTHON.md` 和现有 `pyproject.toml`；项目未落地这些文件时，使用本规范生成适合当前仓库的本地规则。

它是 Senmu BuildOS 的 Python 项目默认基线，不是 Python 教程，也不要求所有项目采用完全相同的目录、框架或严格度。通用职责、依赖、变化成本、评审和验证原则由跨语言规范统一定义；本页只保留 Python 特有的工程落地。

## 1. 适用边界与规则优先级

涉及 `.py`、`.pyi`、Python Notebook、`pyproject.toml`、Python 依赖文件或 Python 服务时读取本规范。若任务只涉及其他语言，不要加载本文件。

按以下顺序解决规则冲突：

1. 安全、隐私、生产数据、支付、权限和正式发布 Hard Gate。
2. 项目内现行规则、支持的 Python 版本和工具配置。
3. 本规范。
4. PEP 8、PEP 257 和所选工具默认值。

PEP 8 明确允许项目制定自己的风格，并强调项目内部一致性。不要为了形式合规破坏兼容性、制造大面积无关 diff 或降低可读性。

## 2. Python 版本、项目结构和依赖

- 在 `pyproject.toml` 或项目权威文档中声明最低 Python 版本，不按 AI 当前环境猜测。
- 新代码只使用最低支持版本可用的语法和标准库；升级版本时同步 CI、镜像、类型检查、部署和文档。
- 可安装的库或需要稳定导入边界的新项目优先采用 `src/` 布局；单文件工具、框架已有目录或历史应用可以保持更合适的结构。
- 让包和模块围绕领域职责组织，不建立长期堆放杂项的 `utils.py`、`helpers.py` 或 `common.py`。
- 将依赖及其版本范围放在项目统一清单中；不要在多个 requirements 文件和 `pyproject.toml` 之间维护互相冲突的事实。
- 新增第三方依赖前检查标准库和现有依赖，说明用途、维护状态、许可证、安全和部署影响。
- 将运行依赖和开发／测试依赖分组，锁定方式由项目选择并在 README 或开发文档中写清楚。

推荐结构思想：

```text
project-root/
  pyproject.toml
  src/
    package_name/
      __init__.py
      domain/
      application/
      infrastructure/
      api/
  tests/
    unit/
    integration/
```

目录名称不是硬规定。关键是让业务规则、应用编排、外部 I/O 和入口边界可辨认，并与实际规模匹配。

## 3. 格式、命名和导入

### 3.1 自动格式化

- 默认使用 Ruff formatter 和 Ruff linter；项目已稳定使用 Black、isort、Flake8 或 Pylint 时，先评估迁移成本，不在无关任务中擅自替换。
- 把行宽写入工具配置。新项目默认可使用 Ruff/Black 常见的 88 字符；项目选择 PEP 8 的 79、团队允许的 99 或其他值时保持全仓一致。
- 不用人工评审争论空格、引号和换行；让格式化工具生成唯一结果。
- 不把自动格式化和业务行为修改混在大规模迁移提交中。

### 3.2 命名

- 模块、函数、方法和变量使用 `snake_case`。
- 类和异常使用 `PascalCase`；异常类以 `Error` 结尾。
- 常量使用 `UPPER_CASE_WITH_UNDERSCORES`。
- 内部实现使用单前导下划线表达非公开接口；不要自行发明双下划线命名。
- 布尔变量和判断函数优先使用 `is_`、`has_`、`can_`、`should_` 等能够读成条件的名称。
- 使用完整领域词汇；只保留项目和行业公认缩写。
- 避免覆盖 `list`、`dict`、`str`、`id` 等内置名称，也避免难辨认的单字符 `l`、`O`、`I`。

### 3.3 导入

- 每行导入一个模块，按标准库、第三方、本项目分组，并由项目 lint 的 import 规则排序。
- 默认使用清晰的绝对导入；包内部短而明确的显式相对导入可以由项目统一采用。
- 禁止普通业务代码使用 `from module import *`。
- 导入放在文件顶部；为解决循环依赖、可选依赖或启动成本而局部导入时，用中文注释说明真实原因。
- 不通过修改 `sys.path` 掩盖错误的包结构；测试和运行入口应使用正确安装或明确模块路径。
- 导入模块不应启动服务、访问网络、写文件或执行其他业务动作；可执行脚本把入口放进 `main()` 并使用 `if __name__ == "__main__"` 保护。

## 4. 函数、类和数据模型

### 4.1 函数

- 让函数承担一个清晰职责并保持相近抽象层次；不设置机械的最大行数。
- 用动词或动宾结构命名动作，用返回对象表达查询意图。
- 让输入、返回值、异常和副作用可见；不要把数据库或网络写入藏在看似纯计算的函数中。
- 禁止可变默认参数，例如 `items=[]`；使用 `None` 后在函数内部创建对象。
- 参数过多或成组出现时使用 `dataclass`、Pydantic 模型或有含义的数据对象。
- 避免用多个布尔参数切换完全不同的模式；使用枚举、配置对象或不同入口函数。
- 业务计算尽量写成无 I/O 的纯函数，把事务、持久化和第三方调用放在明确边界。
- 返回结构固定的数据，不让调用方猜测同一函数在不同路径返回 `dict`、元组、`None` 或其他不兼容类型。
- 简单转换可以使用推导式；包含多层条件、副作用、异常处理或难以命名的复杂推导应改为普通循环或小函数。

### 4.2 类和抽象

- 只有状态、生命周期、多态或明确的领域对象需要时才使用类；简单转换和计算优先使用函数。
- 优先组合而不是深层继承；避免把 Java 的 Interface/Impl、Factory、Manager 仪式机械移植到 Python。
- 需要替换能力时优先使用结构清晰的 `Protocol`、可调用对象或小接口；只有确实共享实现和状态时才使用抽象基类。
- 使用 `dataclass` 表达轻量值对象；需要输入验证、序列化或外部边界时再评估 Pydantic 等成熟工具。
- 不让 ORM 模型、API 模型、领域模型和第三方数据对象长期承担同一个角色；项目规模增长时明确转换边界。
- 属性访问应保持廉价、可预测且没有重要副作用；昂贵 I/O、可能失败的远程调用或改变状态的动作使用明确方法。
- 不为减少少量重复使用元类、动态注入、描述符或运行时猴子补丁；只有框架契约或可验证收益成立时采用，并隔离在明确边界。

## 5. 类型标注

- 为所有公开模块边界、公共函数、类方法、数据模型和外部接口编写准确类型。
- 新项目和新模块默认启用静态类型检查；历史项目先覆盖新增代码和核心边界，再逐步收紧。
- 避免无理由使用 `Any`。确实无法精确表达第三方或动态边界时，将 `Any` 限制在适配层并说明原因。
- 不用 `cast()` 或 `# type: ignore` 隐藏真实不一致。必须忽略时写具体错误码、原因和最小范围。
- 使用项目最低 Python 版本支持的现代类型语法；不要为了追求新语法破坏运行兼容性。
- 区分“可能为 `None`”和“参数缺失／使用默认值”，不要让 `None` 同时代表多个业务状态。
- 使用 `Enum`、`Literal`、值对象或受约束模型表达有限状态，减少散落的魔法字符串。
- 类型只证明结构，不证明业务合法性；金额范围、状态迁移、权限和数据归属仍需运行时校验和测试。

默认可使用 Pyright。项目已使用 mypy 或框架提供的类型插件时保持一致，不要求同时运行两套类型检查器制造重复噪声。

## 6. 中文注释与 docstring

内部项目采用以下明确覆盖项：

- 代码标识符使用规范英文；业务注释和 docstring 默认使用简体中文。
- 对公共模块、类、函数和方法编写 docstring；私有且自解释的短函数不为满足形式添加无价值文字。
- 使用 `"""` 编写 docstring，并遵守 PEP 257 的单行摘要、空行和多行结束位置。
- 项目默认可采用 Google 风格章节名 `Args`、`Returns`、`Raises`，章节内容使用中文；项目已采用 NumPy 或 Sphinx 风格时保持一致。
- 不在 docstring 中重复类型标注已经完整表达的内容，重点说明业务语义、前置条件、返回契约、副作用、幂等性和异常。
- 对复杂分支、兼容处理、事务、并发、重试、性能和安全取舍，用中文解释原因与不可随意改变的约束。
- 修改实现时同步更新或删除注释；不要保留注释掉的旧实现。

示例：

```python
def settle_order(order_id: str) -> SettlementResult:
    """结算指定订单。

    同一订单重复调用不会重复记账；只有已支付订单能够进入结算流程。

    Args:
        order_id: 订单唯一标识。

    Returns:
        本次结算结果；已经结算的订单返回原结果。

    Raises:
        OrderNotFoundError: 订单不存在。
        InvalidOrderStateError: 订单状态不允许结算。
    """
```

推荐的行内注释：

```python
# 支付平台可能重复投递同一回调；先按 transaction_id 去重，避免重复入账。
if payment_exists(transaction_id):
    return
```

不推荐的注释：

```python
# 遍历订单
for order in orders:
    ...
```

PEP 8 对面向全球的开源代码倾向英文注释；本规范把中文定义为内部项目的项目级选择。若项目转为国际开源、公共 SDK 或跨国协作，在项目规则中明确切换为英文或双语，不在同一模块随机混用。

## 7. 异常、日志和资源

- 避免可变模块全局状态；常量可以放在模块级，缓存、连接、配置和运行状态应有明确 owner、生命周期、并发与测试重置方式。
- 捕获能够处理的具体异常，禁止裸 `except:`。
- 仅在进程、任务、HTTP 等明确边界捕获宽泛 `Exception`；必须记录上下文，并重新抛出、转换或返回明确失败状态。
- 转换异常时使用 `raise NewError(...) from exc` 保留原因链；不要泄露密钥、令牌、个人数据或内部堆栈给外部用户。
- 不用 `return None`、空集合或成功状态静默代替真实错误，除非接口契约明确将“未找到”定义为正常结果。
- 在最合适的一层记录一次异常，避免每层重复打印同一堆栈。
- 使用标准 `logging` 或项目统一日志设施，使用参数化日志；不要在库代码中使用 `print()` 代替日志。
- 为日志附带可关联的业务 ID，但不要记录敏感内容。
- 使用 `with`、`async with` 或框架生命周期管理文件、连接、事务、锁和会话。
- 仅在程序入口使用 `sys.exit()`；业务模块返回结果或抛出领域异常。

## 8. 并发、时间、金额和边界数据

- 不在 `async` 路径中直接执行阻塞网络或文件操作；使用异步客户端、线程边界或任务队列并说明取舍。
- 并发任务明确超时、取消、重试、幂等和部分成功策略，不创建无人等待或无人回收的后台任务。
- 使用带时区的时间处理跨地区和持久化数据；项目应明确数据库和接口采用的时区标准。
- 金额使用 `Decimal` 或整数最小货币单位，不使用二进制浮点直接执行财务结算。
- 对外部 JSON、消息、文件和数据库数据先验证再进入领域逻辑；不要把任意 `dict` 直接传遍系统。
- 对路径操作优先使用 `pathlib`；对用户输入路径做目录穿越和权限边界校验。
- 对回调、消息和任务执行设计幂等键；重试不得造成重复扣费、重复写入或重复通知。

## 9. 测试规则

- 默认使用 pytest；项目已有稳定测试框架时保持一致。
- 将测试放在独立 `tests/` 目录，命名为 `test_*.py`，让测试位置与模块职责容易对应。
- 新项目可采用 `--import-mode=importlib` 和 `src/` 布局减少导入路径歧义；历史项目先验证插件和导入行为再切换。
- 测试公共行为、业务契约和有意义的状态，不依赖私有实现顺序。
- Bug 修复先建立能失败的回归测试，再确认修复后通过；无法自动化时记录复现与真实验证步骤。
- 使用 fixture 管理可复用前置状态，避免 fixture 隐藏大量业务动作或跨测试泄露可变状态。
- 单元测试不访问真实网络、生产数据库或付费服务；集成和端到端测试使用明确标记、隔离环境和授权。
- 测试关键边界：空值、重复请求、非法状态、超时、外部失败、权限、事务回滚和资源清理。
- 不追求单一覆盖率数字。为支付、权限、数据迁移和核心业务规则建立更高的场景覆盖与真实流程门禁。

## 10. 默认工具链与配置

新项目或尚无稳定工具链的项目，默认采用：

- Ruff formatter：统一格式。
- Ruff linter：PEP 8 基础、Pyflakes、导入、常见 Bug 和现代化规则。
- Pyright：静态类型检查。
- pytest：测试。
- pre-commit：可选的提交前快速门禁。
- CI：运行完整检查和测试。

`wemake-python-styleguide` 可用于对复杂度和严格规则有明确需求的成熟团队，但其规则高度主观且严格。先在试点模块评估误报和改造成本，不作为本规范的默认 Hard Gate。

项目可以从以下 `pyproject.toml` 片段起步，必须根据最低 Python 版本、源码目录、既有规则和框架调整：

```toml
[tool.ruff]
line-length = 88
target-version = "py310" # 替换为项目最低支持版本

[tool.ruff.lint]
select = ["E4", "E7", "E9", "F", "I", "B", "UP", "SIM"]

[tool.ruff.format]
quote-style = "double"
indent-style = "space"

[tool.pyright]
typeCheckingMode = "standard"
include = ["src", "tests"]

[tool.pytest.ini_options]
addopts = "-ra --import-mode=importlib"
testpaths = ["tests"]
```

默认质量命令：

```bash
ruff format --check .
ruff check .
pyright
python -m pytest
```

另提供自动修复命令，但不要在未检查 diff 的情况下批量修复并提交：

```bash
ruff format .
ruff check --fix .
```

项目应把这些命令封装成一个快速入口和一个完整入口，并让本地、提交前检查和 CI 复用同一配置。工具未安装或命令无法运行时，AI 必须说明环境限制，不能伪造通过结果。

## 11. AI 开发与评审清单

编码前检查：

- [ ] 已确认目标 Python 版本、框架、源码路径和依赖管理方式。
- [ ] 已读取项目 `AGENTS.md`、质量规范、技术设计和测试说明。
- [ ] 已搜索同类实现和现有抽象，没有重复发明另一套模式。
- [ ] 已确认本次改动的输入、输出、副作用、异常和兼容边界。

完成前检查：

- [ ] 命名表达业务意图，没有泛化 helper/manager 或魔法字符串扩散。
- [ ] 函数、类和模块职责清楚，I/O 与业务规则边界可辨认。
- [ ] 公共边界有准确类型，`Any`、ignore 和宽泛异常都有理由。
- [ ] 关键业务约束、幂等、事务、兼容和副作用有准确中文注释。
- [ ] 注释、docstring、测试和相关技术文档与代码同步。
- [ ] 已检查安全、权限、敏感日志、资源释放、并发和外部失败。
- [ ] 已审查完整 diff，没有无关格式化或依赖变化。
- [ ] 已运行与治理等级匹配的 Ruff、类型检查和 pytest 命令。

评审时先报告正确性、安全、兼容性、数据和测试问题，再报告可维护性建议。仅有风格差异且工具配置未禁止时，不将个人偏好标成缺陷。

## 12. 旧项目迁移和例外

- 先运行工具形成基线，统计规则类型和影响模块，不立即对全仓执行自动修复。
- 先要求新文件和修改范围通过最低规则，历史问题进入独立治理清单。
- 将全仓格式化、导入排序和大规模类型补全拆成独立提交，避免与行为变更混在一起。
- 从 API、领域模型、支付、权限和核心数据开始增加类型和回归测试。
- 对 `# noqa`、`# type: ignore[...]` 和 per-file ignore 使用最小范围、具体规则码和中文原因。
- 禁用规则前确认是项目不适用、工具误报还是代码确有设计问题；不要为让 CI 变绿而全局关闭未知告警。
- 例外应声明原因、作用域和收口条件。长期合理的例外写入项目规范，临时例外写入任务或工作日志。

## 13. 规范维护

- 项目工具配置是机械风格和版本能力的执行事实；本规范只提供没有稳定项目基线时的默认判断。
- 具体工具选项、Python 版本能力或框架 API 可能变化时，按需查询当前官方资料，不靠本页保存易过期参数全集。
- 外部规范的新内容先进入 Learning 的工程知识蒸馏批次，查重、裁决后更新本页；不追加来源目录、原文摘录或第二套 Python 手册。
- 多次出现且只属于某个框架的规则应进入项目或框架 owner，不继续膨胀 Python 通用 Profile。
