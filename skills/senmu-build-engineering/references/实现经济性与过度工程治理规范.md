# 实现经济性与过度工程治理规范

本规范用于在保持需求语义、质量属性和风险门禁的前提下，减少不必要的代码、抽象、依赖、文件和维护面。它适用于功能实现、Bug 修复、重构、技术方案评审和只读工程审查；不把“代码行数最少”当作正确性或工程质量的替代指标。

## 1. 判断顺序

先理解真实需求、现有调用链、数据和失败语义，再按以下顺序寻找满足要求的最小正确方案：

1. 需求是否已经由现有行为满足，或者属于尚未批准的假设性需求；不需要的能力不实现。
2. 项目是否已有明确 owner、公共入口或可安全扩展的实现；有则复用或修正源头，不另建平行能力。
3. 当前语言标准库、平台原生能力或已安装依赖是否完整满足所需语义、兼容性和质量属性。
4. 成熟、持续维护的开源方案、框架、组件或服务是否能以低于自研的总拥有成本补足真实缺口。
5. 以上均不满足时，编写边界清楚、可验证且维护面最小的自有实现。

每一级都先经过语义契合与风险门禁，再比较实现成本。标准库、原生能力和现有依赖只是候选来源，不因“已经存在”而自动获得采用资格。

## 2. 最小正确实现

- 优化目标是满足当前已批准需求和质量属性的最小正确变更，不是机械追求最少行数、最少测试或最少文件。
- 优先删除失效分支、合并重复 owner、缩短调用链和扩展现有职责；删除前证明行为、消费者、数据和兼容边界已收口。
- Bug 修复处理制造问题的源头，并检查同类调用路径；不在症状外再包一层补丁或复制一个“新版本”实现。
- “完美”“长期”“通用”“一定不能影响其他功能”等质量目标只约束当前结果，不授权扩大产品或实现范围。只实现当前已批准需求、必要质量属性和风险保护；没有已批准路线、真实消费者或第二用例、已证明瓶颈，以及明确替换、隔离、复用或测试压力时，不新增平台、抽象层、插件／规则系统、通用 DSL、配置面、兼容模式、空目录／占位模块或计划外功能。一个实现的接口、一个产品的工厂、只转发调用的包装器和把静态配置变成动态框架，都按上述证据裁决。
- 用户明确指出方案过度、太重或“绣花”时，立即停止扩展并回到满足当前需求的最小方案；删除未授权部分，但保留安全、隐私、权限、支付、数据、法规、不可逆操作、发布完整性和已批准兼容边界所必需的保护，不为原方案辩护。
- 真实世界输入、设备、网络或硬件存在不可消除差异时，保留必要校准、容错和观测入口；不要以简化为由硬编码偶然样本。

## 3. 价值优先的分阶段实现

- 每个动作先判断它是在改变可交付结果、证明结果正确，还是只在维护内部哈希、回执、仪表盘或进度记录。前两类按需完成；纯记账不得阻塞主链路、否定已确认成果或制造重做，除非该记录本身承担产品功能、法规审计、安全、授权、外部副作用核账或发布事实。
- 在实施前定义本阶段最小价值切片：从权威输入经过真实核心路径，到可观察结果、匹配验证和可交付输出形成闭环。只完成底层脚手架、抽象层、通用平台或检查体系，不等于形成价值切片。
- 每一阶段都应处于可运行、可验证、可接力的状态，并在涉及数据、部署或外部副作用时具备明确恢复方式。不要把大量未闭合分支同时铺开，再依赖下一次长会话统一收口。
- 不以“工程治理”为理由先堆叠大量 validator、清单、审批和报告。先修正生产路径并让正确做法成为默认，再为无法消除的重大剩余风险保留最小可执行门禁。
- 重复读取、重复失败或范围扩大却没有产生新证据时，停止当前做法，重新确定根因、最小下一步和停止条件；不建立运行时计数台账或固定工具／Token 限额。
- 安全、隐私、权限、支付、生产数据、不可逆操作和发布完整性保护必须随首个相关价值切片一起成立，不得被解释为以后再补的装饰性工作。
- 多阶段任务在项目声明的 Durable Task State Owner 中记录每阶段完成定义、当前状态、证据和恢复入口；状态记录服务交付，不制造与专业事实平行的正文。

### 3.1 G1 契约保持型变更快通道

`契约保持型局部变更（contract-preserving local change）` 指影响范围已知且本地可逆，同时保持以下既有约束的变更：产品语义与验收、用户动作与信息层级、交互可供性与可访问性、状态与数据、权限、接口、跨步骤流程、外部副作用以及交付／运行边界。它按契约是否变化判定，不按文件数、代码行数或“看起来只是界面”判定。

`表现层等价变更（presentation-equivalent change）` 是其中一个子类：可以调整样式、措辞或局部布局，但调整前后在上述契约上等价。只要语义、信息优先级、操作方式、响应式／可访问性结果或明确验收发生变化，就不再属于该子类。

快通道还要求已知单一 owner／发布单元，且不涉及安全、隐私、权限、支付／计费、生产数据、外部付费副作用、破坏性操作或正式发布。命中任一排除项就退出快通道。

- Engineering 是唯一 BuildOS 主 Skill；不因对用户可见、代码将来可能提交或代码里有步骤而组合 Product、Delivery 或 Workflow。
- 只读受影响代码、项目本地规则和最近匹配测试；不为重述本地契约读取不相关 reference、完整产品体系或发布规范。
- 只修改实现与最贴近的有价值测试；不新建 Task、TD、ADR、PRD、Changelog 或发布记录，G1 默认不写 Work Log。
- 每轮只运行直接证明当前受影响行为的最小充分检查；同一契约下的连续表现层等价调整作为一个批次，方向确认或准备交接时再统一构建、可见验证、日志和提交收口。

## 4. 语义契合门禁

采用“现有／标准／原生”方案前至少确认：

- 它覆盖的是所需契约，而不是名称相似的局部能力。解析器不等于验证器，格式化器不等于清洗器，组件默认行为也不等于产品验收规则。
- 错误、边界、国际化、可访问性、兼容性、性能和数据语义满足当前项目要求。
- 调用方式没有绕过项目的权限、事务、状态、所有权和发布边界。
- 当前版本和运行环境确实提供该能力；具体 API、版本和平台清单在任务发生时读取项目依赖与官方资料，不固化为通用 Skill 快照。
- 框架已有公开扩展点时先验证其真实契约和失败路径。绕过公开 API、监听内部 DOM、调用私有接口或复制框架状态 owner 只能作为有证据的最小适配，并说明隔离、兼容风险和退出条件；自定义实现测试通过本身不能证明方向优于框架能力。

如果成熟能力只覆盖一部分需求，应明确保留的小范围适配代码，而不是为了“零自研”扭曲业务契约。

## 5. 不得以简化绕过的内容

以下内容按项目风险保留必要保护，不纳入单纯删行目标：

- 安全、隐私、权限、支付、生产数据和不可逆操作；
- 数据完整性、事务、幂等、兼容迁移、失败补偿和回滚；
- 可访问性、法规、明确验收条件和对外公开契约；
- 已知关键边界、回归测试、运行观测和发布门禁。

验证遵循风险匹配的“最小充分”原则。低风险直观变更可以只有一个可见检查；高风险或跨边界变更可能需要多层测试与真实流程验证，不能套用固定的“只留一个测试”。

## 6. 有意简化与技术债

当团队有意识地选择当前较小实现、但已知存在适用上限时，应把事实写入项目现有的 `engineering/TECH_DEBT.md`、issue 系统或等价权威位置：

- 当前简化边界与影响；
- 可观察的升级或偿还触发条件；
- 责任归属和验收方式；
- 代码中的 TODO、兼容分支或说明应引用稳定债务 ID。

不要为这种记录另建只属于某个 Skill 的注释格式或第二套债务账本。没有真实上限和持续维护成本时，也不要把普通设计说明包装成技术债。

## 7. 实现与审查输出

日常实现无需输出冗长评分表，但应能说明：复用了什么、为什么没有新增平行能力、验证了哪些语义和风险。只读审查可以增加独立的“实现经济性”视角：

- 可安全删除的未使用代码、依赖、文件和旧入口；
- 可由现有 owner、标准／平台能力或已安装依赖替代的重复实现；
- 没有真实变化压力的抽象、包装、配置和脚手架；
- 可在保持契约前提下缩短的实现和调用链。

这类发现应标为复杂度改进机会，并与正确性、安全和业务风险分开。只有基于实际 diff、依赖图或可复查路径时才估算可删除行数、文件数或依赖数；不得用通用基准推导当前项目“节省了多少代码或 Token”。复杂度审查通过也不代表整体代码审查通过。
