# 后端服务与数据契约规范

本规范用于项目缺少、冲突或正在改变服务端工程契约时，校准 API、领域服务、数据、事务、缓存、队列和后台任务。已有项目规则足以指导普通实现时直接遵守项目；具体框架、数据库、支付或迁移方法由命中的专项 Skill 或项目 owner 负责。

## 1. 先确认事实与边界

读取真实入口、调用方、接口、schema、迁移、权限、任务运行器、配置、日志和测试。明确请求／事件从哪里进入，哪个领域 owner 可以改变核心事实，哪些系统只是读取、派生、缓存或投递。

API 与事件契约至少说明输入、输出、错误、权限、兼容、幂等、超时和可观察结果。校验不可信输入并在真实信任边界执行授权；前端隐藏、按钮禁用或调用方约定不能代替服务端保护。

## 2. 一致性与副作用

- 一个业务事实只有一个可写 owner；跨服务协作通过显式 API、事件或文件契约，不直接依赖对方内部代码或随意共写核心表。
- 事务只覆盖需要原子成立的状态变化。数据库提交与外部副作用无法同一事务完成时，明确顺序、幂等键、重试、补偿和部分失败可见性。
- 把重复请求、并发更新、乱序、超时、消费者重复投递和进程重启视为可发生条件；用约束、版本、锁或幂等语义保护真实不变量。
- 缓存是可重建派生层，不成为唯一事实 owner；失效、回源、陈旧容忍和故障降级必须与业务风险相称。
- 队列和后台任务明确投递语义、去重、重试上限、死信／人工恢复、进度与结果 owner；进程内变量不能冒充可恢复运行状态。

## 3. 数据演进

Schema、索引和迁移先服务当前查询、约束与生命周期。破坏性变更说明兼容窗口、读写顺序、回填、验证与回滚边界；生产数据修改、删除或不可逆迁移需要独立授权和证据。

日志、指标和追踪只记录定位结果与失败所需信息，避免密钥、令牌和不必要的个人数据。可观察性不能补救含混的业务状态；先让状态机、错误和恢复语义可判定。

## 4. 验证

按风险组合单元、契约、集成、迁移和真实依赖测试。关键路径应验证成功、校验失败、无权限、重复、并发、超时、部分失败、重试和重启恢复中实际相关的条件；mock 调用次数不能代替数据库状态、响应、事件或外部可观察结果。

验证必须绑定真实接口／schema／任务版本和测试数据边界。未运行真实数据库、队列、缓存或第三方沙箱时，明确这是静态或替身证据，不宣称生产行为已证明。
