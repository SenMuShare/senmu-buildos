# Ant Design 前端实践规范

本规范用于指导 React/Web/SaaS/后台/工具型产品的通用前端实现。目标是减少重复造轮子，降低 AI 生成成本，让项目界面长期保持稳定、清晰、可维护。

本规范优先级：

1. 明确产品需求、业务规则和后端权限边界。
2. 项目内技术设计、前端规范、组件封装规则和既有实现。
3. Ant Design、Ant Design X、Ant Design Charts、Ant Motion 等官方 MCP/CLI/文档。
4. 少量业务自定义 UI、图表或动效。

除非有明确设计稿、既有产品规范或业务交互要求需要还原，否则不得绕过成熟组件库从零手写通用组件、AI 对话组件、基础图表或通用动效。

## 本页导航

1. 来源与适用范围；2. 总体原则；3. 设计范式；4. 布局与尺度；5. 组件选择；6. AI 交互范式；7. 页面类型；8. 自定义边界；9. 后续 AI 执行。

## 1. 来源与适用范围

本规范提炼自以下官方设计体系：

- Ant Design 设计体系：`https://ant.design/docs/spec/introduce-cn`
- Ant Design X RICH 设计范式：`https://1x-ant-design-x.antgroup.com/docs/spec/introduce-cn`
- Ant Design X 当前文档：`https://ant-design-x.antgroup.com/docs/spec/introduce-cn`

适用范围：

- React/Web/SaaS/后台/工具型产品。
- 管理后台、运营后台、配置中心、数据看板和业务工作台。
- AI 助手、智能导入、智能检查、智能生成、智能分析等 AI 交互界面。
- 官网、营销页、品牌页可参考组件复用和一致性原则，但视觉表达可以比后台更偏品牌展示。

如果项目已经有更具体的 `FRONTEND_GUIDE.md`、设计系统、组件封装规范或设计稿，应优先遵守项目内规范；本文件只作为补齐和校准依据。

## 2. 总体原则

### 2.1 企业级产品优先

企业级 Web、SaaS、后台和工具型页面应优先保证清晰、稳定、可扫描、可重复操作。界面首先服务用户任务，而不是展示视觉技巧。

默认页面气质：

- 安静、克制、专业。
- 信息密度适中，优先让用户快速找到任务、状态和操作入口。
- 少用装饰性大图、夸张渐变、营销式大标题和无业务意义的视觉元素。
- 复杂信息优先使用表格、标签页、筛选、分组、详情区和状态标识组织。

### 2.2 项目版本优先

Ant Design 的核心价值是把企业级产品中高频出现的界面、组件和模式抽象成稳定资产。前端开发应优先复用成熟组件：

- 通用 UI：项目已安装的 Ant Design 主版本；新项目可优先评估最新稳定版。
- AI 交互：Ant Design X。
- 图表：Ant Design Charts 优先，ECharts 兜底。
- 动效：Ant Motion、组件库内置动效或 CSS transition 优先。

不得把某个固定 Ant Design 版本写成所有项目的永久默认。写代码前应先检查项目 `package.json`、锁文件和既有组件用法；需要官方 API 时，通过 Ant Design MCP 或 `@ant-design/cli --version <antd-version>` 按项目版本查询。

只有在现有生态无法满足明确业务交互、性能要求、可访问性要求或设计稿还原时，才允许少量自定义。

### 2.3 业务规则不下放给 UI 库

组件库只负责呈现和基础交互，不负责平台业务判断。

以下逻辑必须以后端接口、业务规则和安全边界为准：

- 登录、权限、角色和管理边界。
- 组织、空间、项目、资源或数据归属。
- 计费、订单、余额、额度、审批、审计等核心业务规则。
- 文件上传、导入、导出、转码、异步任务和失败重试状态。
- AI 模型调用、审计、安全、限流和敏感数据处理。

前端可以做体验层校验，但不能把后端必需校验改成只靠组件状态、按钮隐藏或路由跳转控制。

## 3. Ant Design 范式

Ant Design 面向企业级产品，强调自然、确定性、意义感和生长性。落到项目时，按以下方式执行。

### 3.1 自然

让界面符合用户对后台系统和工作工具的直觉。

- 表格页保持表格页，不随意改成卡片瀑布流。
- 创建、编辑、删除、导入、导出等操作位置稳定。
- 相近信息放在一起，不相关信息拉开距离或分区。
- 项目、客户、订单、文件、任务、账单、配置等实体使用用户能理解的名称，不把内部技术字段直接暴露给普通用户。

### 3.2 确定性

让用户知道当前在哪里、正在发生什么、下一步能做什么。

- 每个异步动作都要有明确状态：待处理、处理中、成功、失败、可重试。
- 危险操作使用确认弹窗或二次确认，不能依赖误触后撤销。
- 重要表单和流程的关闭、取消、保存按钮语义明确。
- 表格筛选、分页、排序和查询范围要可见，不能隐藏关键条件。
- 不为了视觉效果引入不稳定布局，避免内容跳动、按钮换位、列宽失控。

### 3.3 意义感

界面元素必须服务用户任务。

- 工作台突出任务、状态、关键指标、最近更新时间和可执行操作。
- 详情/工作区突出当前业务对象、关键上下文、处理状态和下一步动作。
- Admin 后台突出运营对象、业务指标、系统状态、配置入口和风险提示。
- 图表必须回答明确问题，例如趋势、占比、对比、排行、分布或异常，而不是为了“看起来丰富”增加。

### 3.4 生长性

界面结构要支持后续功能增加。

- 新功能优先扩展现有 Shell、导航、表格、标签页、详情页、弹窗和抽屉结构。
- 避免每个功能做一套独立视觉系统。
- 重要页面保留清晰模块边界，后续可以加字段、筛选、批量操作和状态列。
- 自定义组件只封装稳定业务模式，不封装一次性样式。

## 4. 布局、间距和视觉尺度

默认使用 Ant Design 的布局和间距思路。

- 页面使用稳定 Shell：顶部/侧边导航 + 主内容区。
- 后台页面优先左侧导航 + 右侧工作区；营销或官网页面可使用上下布局。
- 间距优先使用 8 的倍数，常用 8、16、24。
- 相关元素距离更近，不相关模块距离更远。
- 主内容区域宽度、表格列宽和工具栏高度要稳定，避免 hover、加载、长文本导致布局抖动。
- 卡片只用于独立对象、弹窗、重复项或确实需要框定的工具区域；不要把整页分成嵌套卡片。

## 5. 组件选择规则

### 5.1 通用界面

优先使用项目已安装版本中的 Ant Design 组件；新项目可优先评估最新稳定版。

- `Table`：列表、明细、运营对象、资源管理、记录查询。
- `Form`、`Input`、`Select`、`DatePicker`、`Upload`：录入、筛选、上传和配置。
- `Modal`、`Drawer`、`Popconfirm`：确认、编辑、详情和侧向任务。
- `Tabs`、`Segmented`、`Menu`：分区和导航。
- `Pagination`：分页。
- `Alert`、`Result`、`Empty`、`Spin`、`Skeleton`、`Progress`：反馈、空态和加载。
- `Tag`、`Badge`、`Tooltip`：状态和辅助说明。

禁止为了普通表格、普通弹窗、普通表单、普通分页重写一套基础组件。

### 5.2 图表

优先级：

1. Ant Design Charts。
2. Ant Design 生态内其他展示组件。
3. ECharts。
4. 自定义图形或 canvas。

图表必须先明确“数据要回答什么问题”，再选择图表类型。

- 趋势：折线图、面积图、柱状趋势。
- 对比：柱状图、条形图、双轴图。
- 占比：饼图、环图、堆叠图。
- 分布：散点图、热力图、箱线图、直方图。
- 流程/关系：桑基图、流程图、网络图、树图。

不得在前端编造假趋势、假波动、假占比或仅为美观而生成业务数据。

### 5.3 动效

动效优先使用 Ant Motion、Ant Design 组件内置动效或 CSS transition。

允许的动效目标：

- 帮助用户理解状态变化。
- 降低等待焦虑。
- 表示元素进入、退出、展开、收起。
- 增强反馈，但不抢占工作注意力。

避免：

- 长时间循环的装饰性动画。
- 影响表格扫描、表单录入和高频操作的动效。
- 为了酷炫手写复杂动画。

复杂时间线、滚动驱动、SVG/path/text 动画或高质量营销动效，按 `技术路线与组件选型.md` 判断是否加载 GSAP 相关 skill。

## 6. Ant Design X / RICH 范式

当功能涉及 AI 交互时，遵循 Ant Design X 的 RICH 范式：Role、Intention、Conversation、Hybrid UI。

### 6.1 Role：角色

AI 需要有清晰、稳定的角色。

AI 不应被设计成泛泛的聊天机器人，而应围绕具体任务出现：

- 导入助手。
- 检查/审核助手。
- 分析/洞察助手。
- 配置/生成助手。
- 导出/发布前检查助手。
- Admin 运营或系统维护助手。

角色要求：

- 名称、语气、能力边界一致。
- 不夸大能力，不承诺无法确认的结果。
- 普通用户侧偏任务协助，Admin 侧偏运营分析、系统维护和风险提示。

### 6.2 Intention：意图

AI 界面必须帮助用户表达明确意图。

优先使用 Ant Design X 的 `Welcome`、`Prompts`、`Suggestion`、`Sender`、`Attachments` 等组件组织输入。

要求：

- 给用户可点选的推荐问题或快捷指令。
- 支持文件、项目、记录、配置、订单、客户等上下文输入时，要展示上下文来源。
- 输入框附近应提示 AI 能处理什么，不要让用户猜。
- 高风险动作必须先确认，不允许 AI 直接执行不可逆操作。

### 6.3 Conversation：会话

AI 会话要围绕任务闭环，而不是无限闲聊。

优先使用 Ant Design X 的 `Bubble`、`Conversations`、`Think`、`ThoughtChain` 等组件。

要求：

- 展示用户输入、AI 回复、生成中、失败、重试等状态。
- 流式回复要有可理解的生成状态。
- 需要追问时，明确告诉用户缺少什么信息。
- 错误时说明原因和可执行下一步。
- 任务完成时给出可应用的结果操作，而不是只输出文本。

### 6.4 Hybrid UI：混合界面

AI 不替代图形界面。优先让 AI 和 GUI 配合。

适合混合界面的场景：

- AI 给出审核或配置建议，用户在表格、表单或弹窗中确认。
- AI 检查异常，用户跳转到具体记录、文件、任务或配置项处理。
- AI 分析指标变化，用户进入看板、明细表或筛选视图继续验证。
- AI 生成发布、导入或导出前检查结果，用户点击修复或继续执行。

要求：

- AI 输出结果应尽量变成按钮、表格、列表、引用、文件卡片或可跳转对象。
- 重要结论要能追溯来源，例如项目、客户、订单、记录、文件、账单或配置。
- 不要把所有交互都塞进聊天窗口；能用表格、表单、弹窗和详情页完成的任务，继续使用 GUI。

## 7. 页面类型落地

### 7.1 列表页

- 顶部放标题、主操作、搜索和筛选。
- 主体优先使用 `Table`，服务端分页优先。
- 行操作保持稳定，危险操作放二次确认。
- 状态用 `Tag`、`Badge`、进度或文本组合，不只靠颜色。

### 7.2 详情/工作区

- 保持主任务在第一屏可见。
- 当前业务对象、上下文、状态、历史记录和操作区边界清晰。
- 不随意改变项目既有工作区骨架。
- 对长文本、长名称、长备注、长路径或长编号做换行或省略，不覆盖邻近内容。

### 7.3 表单页/弹窗

- 简单编辑用 `Modal`。
- 多步骤或长表单可以用 `Drawer`、`Steps` 或独立页面。
- 必填、错误、帮助文本要靠 Ant Design 表单能力承载。
- 关闭、取消、保存按钮语义明确。

### 7.4 Admin 看板

- 先展示关键指标，再展示趋势和明细。
- 图表和表格必须口径一致。
- 默认时间范围、筛选条件和统计口径要可见。
- 指标数据不得前端造假；mock 数据必须明确标注且不得作为验收依据。

### 7.5 AI 助手界面

- 用 Ant Design X 组件搭建会话、输入、快捷指令和结果反馈。
- AI 输出必须带状态、来源和可执行动作。
- 高风险动作进入确认流程。
- AI 功能失败时，用户仍能用原 GUI 流程完成任务。

## 8. 允许自定义的边界

允许自定义：

- 与业务强绑定的组合组件。
- 明确设计稿要求且组件库无法覆盖的局部视觉。
- 高密度工作区、专用编辑器、播放器、时间轴、画布、地图、流程图等特殊交互。
- 性能、可访问性、合规或安全要求必须定制的局部组件。

自定义要求：

- 优先组合现有组件，而不是重写底层控件。
- CSS 范围收敛到当前组件或模块。
- 不破坏 Ant Design 的主题、字体、间距和交互习惯。
- 不引入与项目主视觉冲突的大面积新风格。

## 9. 后续 AI 执行规则

后续 AI 写前端代码前，先判断任务类型：

- 普通后台/项目页面：读项目内前端规范、技术设计和既有实现，优先使用项目已安装版本的 Ant Design。
- AI 交互页面：读项目内前端规范，优先评估 Ant Design X。
- 图表页面：读项目内前端规范，优先评估 Ant Design Charts；复杂图表再评估 ECharts。
- 动效页面：读项目内前端规范，常规动效优先组件库内置能力、Ant Motion 或 CSS transition。

涉及 Ant Design 官方知识时，优先按需调用官方 MCP 或 `@ant-design/cli`，不要凭记忆臆造 API：

- 组件 props/API：查 `antd_info`，或运行 `antd info <Component> --format json`。
- 可运行示例：查 `antd_demo`，或运行 `antd demo <Component> [name] --format json`。
- 设计语言、颜色、字体、间距、圆角和原则：查 `antd_design_md`，或运行 `antd design.md --format json`。
- 全局或组件级 Design Token：查 `antd_token`，或运行 `antd token [Component] --format json`。
- 样式覆盖、`classNames` / `styles`、DOM 结构和样式钩子：查 `antd_semantic`，或运行 `antd semantic <Component> --format json`。
- 版本差异、废弃 API 或迁移风险：查 `antd_changelog`，或运行 `antd changelog ... --format json`；修改后优先运行 `antd lint` 检查。

如果项目已安装特定 Ant Design 版本，应在 CLI 查询中加 `--version <antd-version>`，或优先使用 MCP/CLI 对项目版本的查询能力。

只有以下情况需要进一步回读官方文档或临时外部快照：

- 不确定组件 API、版本差异或废弃项。
- 要使用新的 Ant Design X / Charts / Motion 组件。
- 组件行为与预期不一致，需要查 FAQ 或示例。
- 项目内规范没有覆盖的新页面类型。
- MCP/CLI 不可用、工具结果不足，或需要固定版本快照复现；固定快照不得长期混入通用 skill 包。

实现完成后检查：

- 是否复用了成熟组件。
- 是否遵守项目已安装 Ant Design 版本和项目内封装规则。
- 是否减少了自定义 UI、CSS、动画和图表代码。
- 是否符合 Ant Design 的企业级后台气质。
- AI 交互是否符合 RICH 的角色、意图、会话、混合界面。
- 是否保留后端业务规则和权限边界。
