# 源代码工程质量与 AI 协作规范

本规范是 Senmu BuildOS 跨语言工程质量标准，用于把“代码应当易读、可维护”从口头要求落成长期有效的设计判断、项目规则、工具配置、自动检查和评审证据。它适用于项目初始化、老项目质量治理、AI 编码、代码评审、合并门禁和重复返工后的治理校准。

本规范只定义跨语言的共同规则与加载方式。架构、变更预算、技术债和现有系统审查继续读取 `架构约束与技术债治理规范.md`；根据实际代码只加载 Python、TypeScript、Go、Java 或命中的框架专项。其他语言在真实项目需要时再建立 reference，不预先塞进上下文。

## 1. 治理目标与边界

把代码质量理解为以下能力的组合，不要把“符合格式”误判为“质量合格”：

- 在代码预期寿命、团队规模和风险条件下，能够持续响应需求、依赖和技术变化。
- 人类和后续 AI 能快速理解模块职责、业务意图、依赖和风险。
- 局部修改不会无意破坏其他模块、公开接口、数据或部署行为。
- 功能能够被替换和删除，临时兼容、旧入口和技术债有明确退出机制。
- 格式、静态检查、类型和测试可以由同一组命令重复验证。
- 评审结果能够指出问题位置、影响、证据和残余风险。
- 规范能够随项目留存，不依赖聊天历史或某一个 AI 产品。

把规则分为三种约束强度：

- **Hard Gate**：安全、隐私、生产数据、支付、权限、不可逆操作、正式发布，以及项目已声明为合并阻断项的质量检查。未通过时不得宣称完成，除非项目负责人明确豁免并记录原因。
- **Soft Gate**：类型覆盖、独立评审、覆盖率目标、复杂度收敛等默认应做但可按项目阶段说明不适用的规则。
- **Guidance**：函数大小、抽象方式、工具偏好等需要结合上下文判断的实践，不使用机械数字替代工程判断。

## 2. 四层规范模型

按以下四层组织规则，避免每种语言重复一整套工程手册：

1. **跨语言通用层**：职责、命名意图、依赖方向、副作用、异常、注释、测试、评审和完成证据。
2. **语言层**：语言惯例、类型系统、包结构、格式化、静态检查和语言特有反模式。
3. **框架层**：Django、FastAPI、Spring、React 等框架的目录、生命周期和 API 约束。
4. **项目层**：当前项目的业务词汇、模块边界、允许修改路径、实际命令、例外和兼容要求。

工程规则的默认适用顺序为：

```text
安全与 Hard Gate
  > 项目内现行规则和机器配置
  > 当前语言／框架专项规范
  > 本通用规范
  > 社区默认惯例
```

项目规则可以覆盖一般风格选择，但不得静默降低安全、隐私、生产数据、支付、权限和正式发布门禁。发现项目文档与工具配置不一致时，把它记录为治理缺陷并修正，不允许 AI 任意选择其中一套。

## 3. 项目内落地与权威关系

初始化或治理校准后，把适用规则写入项目，不让日常开发持续依赖本 Skill。复用项目现有 owner；没有时可从 `assets/code-quality/` 裁剪模板：

- 根 `AGENTS.md` 或等价文件只作短入口，声明读取顺序、作用域、禁止事项、质量命令和完成输出。
- `CODE_QUALITY` 保存质量决策、约束强度、统一命令和例外；`ARCHITECTURE`／技术设计保存职责、依赖、数据所有权、契约与不变量。
- 语言文件只保存该语言的项目覆盖项；真实技术债进入既有 issue／`TECH_DEBT`，没有债务不建空台账。
- 工具配置是机械规则的执行事实；本地、提交前检查和 CI 复用同一底层命令，不另建配置副本。
- 不同 AI 入口引用同一组项目权威文档，不复制完整手册。正式文档声明适用范围和版本；小型原型可以合并文件，但入口、命令和最低规则不能消失。

## 4. 按需加载规则

进入代码任务时先读当前作用域入口，确认仓库、发布单元、允许路径和非目标，再读取项目质量、技术设计／架构、债务和测试 owner。根据本次实际读取或修改的扩展名、清单和配置加载对应语言；只有任务确实涉及已确认框架时才加载框架规范。多语言仓库不连带加载无关语言，纯问答或不改代码的 G0 任务不默认加载语言细节。

如果项目未提供某语言规范，先保持现有语言和运行基线，遵守通用层、项目构建配置、既有代码惯例和当前框架官方规则；不得因为 Senmu BuildOS 只有 Python 详细 Profile 就迁移到 Python。只有形成稳定、可执行且会重复使用的项目决策后才补 `engineering/languages/<LANGUAGE>.md`，不要预建所有语言手册。

## 5. 治理等级与质量门禁

复用 `治理强度分级与门禁规范.md`，不要另建平行等级体系：

| 等级 | 代码质量最小动作 |
| --- | --- |
| G0 | 只读和解释；说明依据，不强制运行代码检查。 |
| G1 | 读取当前文件和局部规则；运行目标文件可用的格式、lint 或可见验证；说明未运行项。 |
| G2 | 读取通用与语言规范；运行格式检查、lint、适用的类型检查和匹配测试；审查完整 diff。 |
| G3 | 运行项目声明的完整质量命令、测试和构建；CI 通过；记录发布影响和残余风险。 |
| G4 | 在 G3 基础上增加安全、数据、权限或真实主流程验证；高风险变更采用独立 AI 或人工复核。 |

把以下规则作为代码任务 Hard Gate：

- 不提交密钥、隐私、真实生产数据或未经授权的敏感材料。
- 不以 mock、语法通过或工具返回成功替代受影响真实路径的必要验证。
- 不在项目声明的阻断检查失败时宣称完成。
- 不静默忽略失败命令；记录命令、退出结果、失败原因和影响。
- 修改行为时同步必要测试、注释和权威文档；无法同步时记录例外与后续收口点。
- 不违反项目已声明的禁止依赖、发布单元边界和破坏性契约门禁；确需改变时先更新架构契约并完成影响说明。

## 6. 跨语言代码质量原则

### 6.1 长期健康与变化成本

- 正确性、安全和业务契约优先于技巧、简短或局部美观；代码只能“碰巧跑通”时不算完成。
- 让开发者尽量通过当前模块及其公开依赖形成正确心智模型；小改动需要理解大量无关模块是边界退化信号。
- 让一个业务变化集中在拥有该知识的模块；同一判断、状态或兼容逻辑散落多处时，先找唯一 owner，避免霰弹枪式修改。
- 每个业务事实、可变状态、副作用和不变量应有明确权威所有者；缓存、派生数据和 UI 状态不能静默成为第二事实源。
- 把依赖、失败和副作用显式化；调用者不应通过阅读实现才能发现数据库、网络、文件、全局状态或不可逆动作。
- 抽象服务于已知变化压力、隔离或测试价值；相似代码不自动要求抽象，假设性未来不自动要求扩展点。
- 设计增加、迁移、替换和删除的完整生命周期；暂留兼容面必须说明消费者、退出条件和验证，不能成为新实现样板。
- 用时间、规模、风险和可逆性裁决实践强度；短期脚本和十年服务不机械采用同一流程，但安全和授权边界不因寿命短而消失。

### 6.2 命名和结构

- 使用领域词汇表达意图，避免 `data`、`info`、`helper`、`manager`、`handle`、`process` 等缺少上下文的泛化名称。
- 让一个函数或方法表达一个可命名的职责；不要用固定行数机械判定质量。
- 让同一函数内部保持相近抽象层次，分离业务规则、I/O、持久化和外部服务调用。
- 让输入、输出、副作用和失败方式可发现；不要把网络、数据库或文件写入隐藏在看似纯计算的接口中。
- 参数过多或长期一起出现时，使用有含义的数据对象；不要用多个布尔参数控制互不相同的行为模式。
- 只有确实存在替换、隔离、扩展或测试边界时才增加抽象，不为“企业级”制造只有一个实现的空接口层。

### 6.3 依赖和边界

- 遵守项目技术设计声明的模块方向，核心业务逻辑不要反向依赖 UI、HTTP、数据库驱动或具体第三方 SDK。
- 优先通过公开接口访问其他模块，不跨层读取内部状态。
- 新增依赖前检查标准库和项目现有依赖能否满足需求，并说明新增依赖的维护、安全和部署成本。
- 不在无关任务中大面积重排目录、替换框架或升级依赖。

### 6.4 错误、状态和资源

- 捕获能够处理的具体错误；不能恢复时保留原始原因并在合适边界转换。
- 不静默吞错，不用成功返回值伪装失败，不在多个层级重复记录同一异常造成日志噪声。
- 跨进程调用必须有与上游总预算相容的有界期限；分别确认连接、DNS／TLS、连接池、请求和响应读取是否被实际超时覆盖。流式或离线任务采用不同期限模型时，也必须有取消、资源上限和停止条件。
- 重试只处理已分类的可恢复失败，由一个明确层级在总尝试／时间预算内负责；优先复用已验证的客户端能力，采用封顶退避、抖动和必要配额，避免调用链多层重试、同步风暴和依赖故障时的负载放大。
- 可能产生副作用的可重试操作使用稳定的调用方意图标识建立幂等契约，并原子关联请求意图与结果；同键不同参数必须拒绝或显式裁决。结果不确定且无法证明幂等时，先查询、核账或人工恢复，不盲目重发。
- 明确事务、取消和部分成功语义；支付、任务、回调和消息处理尤其要说明重复执行、迟到请求和预算耗尽后的影响。
- 使用语言或框架提供的资源管理机制关闭文件、连接、锁和会话。

### 6.5 测试和可验证性

- 测试可观察行为和业务契约，不把私有实现细节写死在测试中。
- Bug 修复应增加能复现问题的回归测试；如果无法自动化，记录真实复现和验证步骤。
- 覆盖成功路径、关键边界和有业务意义的失败路径。
- 对远程调用按风险验证连接／请求超时、可重试错误、尝试与时间预算、调用放大、退避抖动、重复／迟到请求、同幂等键不同意图和结果未知后的核账路径。
- 不把单一覆盖率数字当作质量结论；按资金、权限、数据完整性和用户主流程提高关键路径要求。

## 7. 中文注释与文档字符串

内部项目默认采用以下语言约定：

- 使用英文命名代码标识符，保持生态工具、API 和搜索兼容性。
- 使用 UTF-8；业务注释和文档字符串默认使用简体中文。
- 面向国际开发者的开源库、公共 SDK 或跨国协作项目可以由项目规则改为英文或中英双语。
- 使用注释解释“为什么、有什么约束、不能怎样改”，不要逐行翻译代码。
- 为复杂业务规则、兼容方案、事务边界、幂等、并发、安全、性能取舍和非显然副作用补充注释。
- 修改代码时同步更新或删除过时注释；与代码矛盾的注释比没有注释更危险。
- 不保留大段被注释掉的废弃代码，不在注释中放聊天过程、密钥、个人信息或生产数据。
- 对自解释的简单代码不强制添加噪声注释。

示例：

```text
不推荐：# 遍历所有订单
推荐：  # 支付平台可能重复投递回调；按 transaction_id 去重，避免重复入账。
```

注释语言和价值属于语义门禁。工具可以检查公开接口是否缺少文档字符串，但不能可靠判断中文注释是否正确、是否解释了真实约束；必须由 AI 或人工评审补足。

## 8. 可执行工具契约

每个正式代码项目至少声明：

- 一个自动修复或格式化命令。
- 一个快速质量命令，用于开发过程中检查受影响范围。
- 一个完整质量命令，用于 CI、合并和发布。
- 一个测试命令，以及集成或真实流程测试的单独入口。
- 各命令适用路径、预计成本、是否访问网络或外部服务。

优先使用语言生态标准配置，例如 `pyproject.toml`、`pom.xml`、`build.gradle`、`package.json` 和 `tsconfig.json`。统一命令可以由 Make、Task、项目脚本或包管理器提供，但不得把真实检查逻辑只写在文档里。

CI 至少执行项目声明的完整质量命令。对 G2-G4 项目，逐步增加以下机器检查：

- 格式与 lint。
- 静态类型或编译检查。
- 单元和接口测试。
- 依赖与安全检查。
- 构建或打包检查。
- 必要的架构边界、文档版本或策略一致性 validator。

项目已经声明模块边界、禁止依赖或结构基线时，完整质量命令必须包含对应架构检查，或明确调用一份可重复、有证据输出的语义评审契约。具体检查、变更预算、技术债增量规则和现有系统审查流程按 `架构约束与技术债治理规范.md` 落地。

不要让 CI 和本地命令使用互不相同的规则。任何忽略或禁用检查都要靠近配置或代码记录规则 ID、原因和范围；高风险或长期例外还要记录责任人或到期条件。

## 9. AI 编码工作流

AI 修改代码时执行以下闭环：

1. **预检**：读取项目入口、作用域、代码质量规范、语言规则、技术设计和测试说明；检查工作区与同类实现。
2. **计划**：说明行为变化、影响模块、架构影响、测试策略和需要同步的文档；搜索现有同类能力，避免创建第二套实现；定位缺陷由哪个生产环节制造，小任务保持轻量。
3. **分段实现**：优先修正产生缺陷的需求契约、职责归属、架构、接口、默认值或代码路径，使正确路径成为默认路径；不得用追加提示词、检查清单或 validator 代替已可实施的根因修复。复杂任务一次只完成当前上下文能够实现、验证和交接的阶段结果，不固定套用 Setup、Foundation、Core 或 Polish。
4. **局部验证与记录**：在实现过程中运行快速格式、lint、类型或目标测试，及时修正问题；完成有意义阶段后，把结果、证据、未完成项和下一步写回项目声明的 Durable Task State，不为每个微小文件变化刷新状态。
5. **变化回写**：实现发现改变用户行为、范围或验收时回写 REQ／PRD；改变模块、接口、数据、依赖或长期技术路线时回写 TD／ADR；只改变执行顺序时更新 Task。不得只修改代码或聊天结论，让正式文档继续描述旧系统。
6. **实现后简化**：只审视本次已稳定的代码及必要接口缝，分别检查复用、可维护性和效率；只应用能够证明行为不变且收益明确的调整，不用删行数衡量成功。
7. **完整自查**：审查完整 diff，检查正确性、兼容性、异常、副作用、安全、注释、测试、无关改动，以及需求、设计、任务与实现是否仍然一致。
8. **质量验证**：运行与治理等级匹配的统一命令；不得只口头声称遵守规范。
9. **结果移交**：报告改动、命令和结果、未验证项、例外与残余风险；Engineering 只能确认 `implemented`，不能代替 Product 宣称 `accepted` 或代替 Delivery 宣称 `released`。

现存代码、历史页面、旧测试和旧文档只能证明能力曾经存在，不能反向定义当前需求。纯布局／样式任务只排列当前需求 owner 已批准的用户可见能力；发现无现行需求依据的控件时，报告需求—实现冲突并交 Product 判断，不得自行决定新增、恢复、保留或移除，也不得为适配残留实现而改写 PRD 或测试。

技术机制不得静默改写产品行为。若缓存、批处理、事务、队列、版本或性能方案需要新增／删除用户动作或可见状态，改变生效、持久化、撤销、退出、切换、失败恢复或验收结果，先比较“维持已批准行为的工程方案”和“改变行为的产品方案”，向 Product 交接原行为、技术约束、用户影响、替代与验证条件。未经产品决定，不得直接实现后再同步修改 PRD 和测试来完成自我授权。

AI 的完成输出至少包含：

- 实际修改范围。
- 实际运行的命令及结果。
- 未运行或失败的检查及原因。
- 发现并处理的关键风险。
- 尚存风险、例外和下一步。

### 9.1 实现后简化收口

实现已经满足当前需求、准备进入最终评审时，对本次实质代码变化做一次有边界的简化检查。用户指定范围优先；否则使用当前分支相对基线的变化。纯文档、生成文件、vendor、锁文件和机械格式变化不触发代码简化。

从三个视角检查：

- **复用**：是否重复了项目已有 helper、公共接口、标准库、运行时或框架已经保证的能力；只有语义、错误、副作用和顺序等价时才替换。
- **质量**：是否出现重复状态、参数膨胀、轻微变体复制、泄漏内部细节、无必要的字符串协议、过深条件、复述代码的注释、已验证无调用的死代码，或者仅为本次未发布迭代保留的兼容壳。
- **效率**：是否存在重复计算／读取／请求、N+1、可安全并行却串行的独立操作、启动或请求热路径新增阻塞、无变化更新、先检查再操作的竞态、未清理资源、无界缓存，或为找少量结果读取全部数据。

只修改当前范围和维持接口所必需的缝合点；范围外发现进入技术债或后续任务，不顺手扩张。每项调整必须保持可观察输出、错误、状态、副作用和顺序；无法证明等价时不改。不得删除安全、权限、数据保护、信任边界校验、可访问性或恢复能力，也不得通过放宽类型、断言或测试来换取“更简洁”。完成后运行与影响范围匹配的测试和质量命令；没有可用检查时明确报告。简化成功以理解成本、重复工作和资源浪费下降为准，不以净删除行数、抽象数量或评审意见数量为准。

普通任务由当前 Engineering 自查完成，不固定启动多个审查 Agent；只有用户要求独立结论或风险等级需要职责分离时才交给 Assurance。

### 9.2 缺陷判断、修复与验证闭环

Bug／Hotfix 不因紧急而跳过事实判断，也不要求另建三份阶段报告。产品影响以 `defect` 类型 REQ 或项目既有缺陷系统为 owner，跨步骤进度使用项目声明的 Durable Task State，代码、测试、工作日志和发布记录继续保存各自事实。

1. **判断**：记录实际现象、期望行为、影响范围、环境／版本和可用复现入口，并区分 `confirmed`、`likely_unreproduced`、`expected_behavior`、`duplicate`、`out_of_scope`。无法复现时把根因写成有置信度的假设，不冒充已确认事实。
2. **修复**：针对已证实或有足够证据的根因做最小改动，检查同类调用路径并补回归保护；发现原判断错误或范围必须实质扩大时停止原方案，更新 Task 和对应 REQ／TD 后再继续。
3. **验证**：优先重新执行原始复现或其等价自动化，再运行新增／修改测试和受影响回归检查。原始现象未实际覆盖、真实环境不可达或关键检查未运行时，结论只能是 `partial` 或 `not_run`，不能写 `verified`。
4. **收口**：记录修复 commit、验证证据、未覆盖环境和残余风险。修复和验证完成只形成工程事实；合并、版本、Tag、部署和上线仍遵守 Delivery 授权与 Hotfix 门禁。

## 10. AI 与人工评审契约

评审目标是让候选在整体上明确改善或至少不降低代码健康，同时保持合理推进速度；不是追求不存在的完美代码。技术事实、项目契约和可复查证据高于个人偏好。纯风格问题由项目格式化／lint 和已选规范裁决；未被项目规则覆盖且不影响健康的偏好不得阻断。

评审时先找行为和风险问题，再看风格。按以下顺序检查：

1. 需求和业务逻辑是否正确，边界和失败路径是否遗漏。
2. 安全、权限、隐私、数据完整性和不可逆操作是否受保护。
3. 公开接口、存储结构、兼容性和部署行为是否意外变化。
4. 并发、事务、幂等、超时、重试和资源释放是否正确。
5. 模块职责、依赖方向、副作用、重复实现和技术债是否恶化。
6. 类型、异常、日志、测试、中文注释和文档是否与实现一致。
7. 格式和命名是否已由工具或项目规则统一。

评审输出使用以下结构：

- 先列问题，按严重程度排序，并给出文件、位置、触发条件和影响。
- 区分确定缺陷、需要确认的风险和可选改进，不把偏好包装成 Bug。
- 只有会降低正确性、安全、契约、可维护性或验证可信度的问题才阻断；教育性建议和细小润色明确标为可选，不让低价值意见无限拖延候选。
- 评论说明“为什么会造成什么影响”，并给出足够修正方向；评价代码和决策，不评价开发者能力。
- 没有发现问题时明确说明，同时列出已检查范围和未验证盲区。
- 不以“测试通过”替代语义评审，不以“AI 评审通过”替代自动检查。

G3-G4 或高风险变更优先由与实现上下文相对独立的 AI 或人类复核，减少同一执行者重复遗漏同一假设。独立复核仍应读取原始需求、diff、工具输出和测试证据，不接收预设结论。

### 10.1 日常代码变更审查

日常代码质量以“准备进入集成基线的完整变更集”为审查单位，不对开发分支的每个 WIP commit 重复启动独立审查。开发者可先产生范围清楚、可恢复的本地 commit；但任何第一方代码进入主线、受保护集成线或发布基线前，必须审查冻结的 `base_commit..head_commit` 完整差异。

审查契约：

- 实现者先完成完整 diff 自查和匹配质量命令；自查是候选准备，不代替需要职责分离的合并批准。
- 审查者核账每个变更文件、变更函数／方法／顶层执行单元和被修改的现有注释，理解分配给自己的每一行人工代码；生成物、vendor 和纯数据只能按项目规则登记排除。
- 变更单元沿用本规范的函数九维和注释四维检查，并关联 Finding、整改 commit、原问题复核和匹配回归证据。
- G2-G3 第一方代码由与作者分离的同行、人类或独立审查 Agent 批准；G4 使用 independent review。只有纯文档／配置、生成物或项目明示例外可使用自查，例外必须记录 owner、理由和失效条件。
- 批准必须绑定精确 `head_commit`。审查后新增任何 commit 都使旧批准过期；只需重新审查新差异及其影响链，不机械重跑全项目审查。

项目可沿用既有 PR／MR／审批系统保存等价证据；没有远程平台或等价系统时，可使用 Delivery 的 `CHANGE_REVIEW_CONTROL.template.json` 和 `validate_change_review.py`。Engineering 负责语义标准和 Finding 复核，Delivery 只负责在合并时核对候选身份、审查完整性和状态。

项目已有穷尽式源码治理账本时，日常变更审查要使修改单元的旧指纹／结论失效，复核通过后回写新指纹和结论；未变单元不重复审查。

### 10.2 穷尽式函数与注释审查

用户明确要求老项目逐系统、逐文件、逐函数或逐条现有注释治理时，由 Assurance 按 `exhaustive_source` 冻结范围和保持完成账本，Engineering 提供以下语义标准：

- 每个函数／方法分别审查职责是否可命名且单一、抽象层次是否一致、输入输出和副作用是否可发现、失败与资源边界是否正确、依赖是否遵守架构、是否重复现有 owner 或制造无价值抽象、关键行为是否有匹配测试、注释／文档是否足够且正确。
- 每条现有注释／文档字符串必须审查是否与当前代码和业务契约一致、是否解释非显然约束、是否过时，以及是否暴露密钥、隐私或生产数据。
- 没有注释不自动构成问题；复杂规则、不可见副作用、兼容／事务／并发／安全取舍缺少必要说明时，才登记发现。
- 每个单元必须有结果、证据和发现关联；不得将 lint、测试绿灯、覆盖率或文件级摘要替代函数级语义审查。

这一契约保证“每个已登记单元都有审查结果”，不保证代码绝对无 Bug。整改后是否符合标准，还要依据冻结后代码、原 Finding 复核、匹配回归和未评估运行环境限制裁决。

## 11. 旧项目渐进治理

为已有大量 AI 代码的项目采用“先基线、后收紧”的方式：

1. 先盘点语言、框架、模块边界、现有工具、失败数量、技术债和核心业务路径。
2. 冻结统一工具和配置，不在同一功能分支中顺带全仓格式化。
3. 先要求新增和修改代码不增加违规；为历史问题建立单独治理任务。
4. 如需全仓格式化或批量重命名，使用独立提交或分支，避免行为变化混入机械 diff。
5. 按模块逐步启用类型和更严格规则，先覆盖接口边界、资金、权限和核心数据。
6. 为暂时无法修复的例外记录规则 ID、原因、范围和收口条件，禁止用全局忽略隐藏未知问题。
7. 用真实开发任务验证规范是否减少返工；规则造成普遍无价值噪声时，调整项目配置而不是让 AI 反复绕过。
8. 对职责混乱、循环依赖、重复实现和复杂度热点建立证据化债务项；先用测试保护，再按模块偿还，不一次性全库重写。

## 12. 例外、维护与 Skill 反哺

- 让项目个性化选择留在项目文档，不把客户、路径、账号、服务器或业务私有规则写回通用 Skill。
- 只有问题跨项目高概率复现、能够用项目无关语言表达、确实减少返工且不会让小任务变重时，才反哺本 Skill。
- 优先修改已有通用或语言 reference；新增语言文件必须从 `SKILL.md` 和 `项目实践指南.md` 建立直接路由。
- 外部网页、PDF、书、仓库或第三方 Skill 需要吸收到 BuildOS 时，由 Learning 按 `工程知识蒸馏与标准晋级规范.md` 建立临时候选批次；本规范只接收裁决后的 Senmu 规则，不保存教材、来源清单或逐条出处。
- 当语言和框架 reference 明显增多、维护节奏独立或开始让 `senmu-build-engineering` 过度触发时，把专项内容拆为独立代码工程 Skill，由本 Skill 保留治理原则和路由。
