# 软件测试与质量验证规范

本规范定义跨语言的软件测试与质量验证方法。它不要求所有项目采用同一种测试金字塔或覆盖率数字，而是根据行为、风险、边界和失败代价选择最小充分验证。产品验收由 Product 负责，真实发布由 Delivery 负责；测试证据支持这些决定，但不能单独替代它们。

## 1. 测试策略的输入

建立或修改测试策略前确认：

- 需求、业务不变量和可观察验收标准。
- 模块、公开接口、数据所有权和依赖方向。
- 关键副作用：数据库、文件、网络、消息、支付、权限和外部服务。
- 运行环境、支持版本、兼容边界和发布／回滚方式。
- 失败影响、发生概率、可检测性和恢复成本。
- 项目已有测试、CI、真实环境能力和历史缺陷。

测试类型由风险决定，不为形式填满所有层级。纯函数可能只需单元和性质验证；跨服务交易、权限或数据迁移需要契约、集成、回滚和真实路径证据。

版本级 `TEST_CASES.md` 直接从该版本 PRD 的页面／功能／能力、产品行为、交互、异常、边界和验收产生，并沿用相同内容结构。关联通过共同版本和章节即可，不另建追踪矩阵；项目已有测试管理系统时继续使用原 owner。用例模板是可裁剪提纲，低风险小改只保留最小匹配用例，不因模板存在而填满全部测试类别。

## 2. 测试层级与职责

| 层级 | 主要证明 | 不应承担 |
| --- | --- | --- |
| 单元测试 | 局部规则、边界条件和确定性计算 | 证明数据库、网络或部署真实可用 |
| 模块／组件测试 | 一个模块通过公开入口完成职责 | 穿透内部实现形成脆弱断言 |
| 契约／API 测试 | 请求、响应、事件、schema、错误和兼容语义 | 代替消费者真实流程 |
| 集成测试 | 数据库、队列、文件、第三方适配和事务协作 | 用大量 mock 冒充真实依赖 |
| 端到端／真实流程 | 用户或系统主链在接近真实环境下可完成 | 覆盖所有细枝末节或精确定位根因 |
| 产品验收 | 需求与验收标准是否满足 | 证明已经部署上线 |
| 发布验证 | 制品、部署、版本、流量和回滚事实 | 重复全部开发阶段测试 |

层级可合并，但职责不能消失。同一业务不变量由最接近“不可信输入转为可信状态”的边界拥有验证，下游复用该结果，只验证本层新增风险，不复制同一探测、错误码表或需人工对账的平行状态。跨信任域、独立消费者契约、安全纵深或无法共享可信结果时，保留必要复核并明确各层证明什么。小脚本可用输入输出样例完成模块和端到端验证；大型服务应避免把所有验证都压在慢而脆弱的 E2E 上。

## 3. 测试设计维度

对受影响行为按需覆盖；不存在的风险不生成章节或用例：

- 正常路径和核心业务结果。
- 空值、最小／最大值、格式、国际化和时间边界。
- 非法状态、重复请求、乱序、超时、取消和部分成功。
- 权限、租户、数据归属、敏感信息和越权访问。
- 事务提交／回滚、幂等、并发竞争和重试副作用。
- 外部依赖失败、降级、恢复、补偿和资源释放。
- schema、API、配置、文件格式和版本兼容。
- legacy 入口、迁移前后等价和回滚路径。

缺陷修复至少包含能在修复前失败、修复后通过的回归测试，或说明为什么只能采用其他可重复证据。不要为了增加数量复制等价用例。

完整替代的回归测试应同时证明新入口可用且唯一、旧入口不可达；经当前需求明确批准的兼容面，则证明其范围受控、不是默认入口且满足退出条件。只断言旧控件或旧入口仍存在的历史测试不能作为需求依据，应按当前需求契约删除或改写。

## 4. 测试替身与真实依赖

- 在自己拥有的边界使用 fake、stub 或 mock；不要模拟到已经脱离真实第三方或框架契约。
- mock 只证明调用方行为，不证明依赖真实兼容。关键集成需要契约测试、沙箱或受控真实服务验证。
- 缺陷涉及身份、支付、存储、队列、协议或第三方 SDK 时，先保存能触发原问题的最小生产形态样例，包括会改变行为的字段、密钥类型、顺序、状态和错误；简化 fixture 不得删掉本次风险所在的差异。
- 时间、随机数、网络、文件系统和环境变量通过明确边界注入或固定，避免测试依赖机器偶然状态。
- 不在测试中复制生产算法作为期望值；优先使用业务规则、固定样例、独立 oracle 或性质约束。
- 测试替身与真实 schema／接口发生漂移时，先修复契约 owner，不用继续堆 mock 掩盖。

## 5. 测试数据与环境

- 测试数据说明来源、构造方式、隐私边界、隔离和清理策略。
- 默认不复制真实个人数据、密钥、生产数据库或受限素材到测试环境。
- 测试独立、可重复、可并行；依赖顺序时应把顺序建模为一个场景，而不是依靠用例执行先后。
- 数据库测试明确事务、迁移、时区、编码、约束和清理行为。
- 需要真实凭据、付费调用或外部写入的测试必须显式启用，并遵守授权和停止条件。

## 6. 非功能验证

只有需求或风险存在时加载相应验证：

- 性能：代表性数据、基线、指标、环境、重复次数和接受阈值。
- 可靠性：超时、重试、故障恢复、降级、容量和资源耗尽。
- 安全：认证、授权、输入、敏感数据、依赖和供应链；专项安全审计另行开展。
- 可访问性：键盘、语义结构、焦点、标签、对比度和辅助技术。
- 可观测性：关键成功／失败信号、结构化日志、指标、追踪和告警入口。

一次本地快跑不能推广为生产容量结论。记录环境和限制，区分测量事实与推断。

## 7. 变更影响与回归选择

先从 diff、调用链、公开契约、数据和配置判断受影响面，再选择测试。至少检查：

1. 修改的直接行为。
2. 调用者和消费者。
3. 共享数据、状态和副作用。
4. 兼容、迁移和回滚路径。
5. 同类实现和历史缺陷。

小改动运行目标测试和匹配检查；跨模块、公共接口、schema、依赖或发布单元变化运行完整质量命令及相关真实路径。只运行一个新用例不能证明没有影响旧行为。

验证顺序先回答“原问题是否真的被修复”：用修复前可失败、修复后可通过的原始路径或等价生产形态测试闭合根因，再运行受影响回归，最后只在候选冻结时运行项目完整门禁。通用回归数量再多，也不能替代关键依赖形态和本次主链；反过来，关键路径通过也不能替代其真实影响面需要的回归。

同一契约下的连续表现层等价调整先按一个交互批次选择回归：每轮只运行能及时暴露当前回退的最便宜局部检查；在用户确认方向、批次准备提交或进入候选前，再统一运行一次匹配构建和可见交互验证。若语义、信息层级、操作方式、状态、可访问性或验收发生变化，重新评估影响面和回归范围。不得因批次策略跳过安全、数据、权限、计费、生产或不可逆边界的即时检查。

## 8. Flaky、跳过与失败治理

- Flaky test 是质量缺陷，不允许无期限重跑直到变绿。
- 同一候选的一次后续通过不能抹去先前尚未解释的失败；聚合结论保持“不稳定”，直到根因已修复，或测试已按 owner、风险和退出条件完成隔离。
- 隔离或跳过必须记录 owner、原因、风险、触发条件和恢复期限。
- CI 绿色但关键测试被跳过、未发现或未连接真实依赖时，必须报告实际覆盖，不能称为完整通过。
- 保留首次失败的原始输出；修复测试基础设施时区分产品缺陷、测试缺陷和环境缺陷。
- 不为了通过测试降低断言、删除用例或把失败改成 warning，除非契约确实改变并同步权威文档。

## 9. 质量入口与证据

项目本地 `engineering/TESTING_STRATEGY.md` 至少登记：测试层级与目录、关键风险映射、测试数据和替身边界、统一命令、CI job、真实流程、跳过项和发布阻断规则。

统一命令应尽量复用同一底层配置：

- 快速检查：受影响文件的格式、lint、类型和目标测试。
- 完整质量：全量 lint、类型、单元／集成测试和构建。
- 架构／契约：依赖方向、API/schema 和迁移兼容检查。
- 真实流程：受控环境中的主链、权限、数据和恢复验证。

最终报告记录实际命令、结果、失败／跳过、环境、未覆盖范围和残余风险。工具返回成功不等于产品验收、部署或发布成功。

## 10. 旧项目渐进落地

先建立当前基线和关键路径，不要求一次补齐所有历史测试：

1. 锁定现有行为和高风险不变量。
2. 新改代码必须增加匹配验证，不继续扩大无测试区域。
3. 按缺陷频率、变更频率和失败影响补回归保护。
4. 收敛重复测试入口、过度 mock 和长期跳过项。
5. 将测试策略、命令和真实能力写入项目权威，而不是只留在 CI 或聊天中。
