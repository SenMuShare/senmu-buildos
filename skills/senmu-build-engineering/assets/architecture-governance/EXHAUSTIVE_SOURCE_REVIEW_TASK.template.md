# 穷尽式源码治理任务

请使用 `$senmu-build-assurance` 的 `exhaustive_source` 审查模式，并按实际语言和架构读取 `$senmu-build-engineering` 的质量、架构、测试与语言规则。目标不是抽样找几个问题，而是对冻结范围内每个第一方源码文件、每个可执行单元和每条现有注释／文档字符串建立可复核结论。

本轮默认只读。允许读取代码、文档、Git 和项目配置，运行非破坏性的符号扫描、静态检查、测试和构建，以及编写审查记录；未经再次授权，不修改业务代码、数据、版本或生产状态。

## 必须冻结

- 权威项目根、Git 根、commit／树身份、工作区状态和正式运行入口。
- 发布单元、系统／模块、包含根、语言、生成物／vendor／外部镜像等排除规则。
- 项目内实际生效的需求、架构、代码质量、测试、安全和注释规则。
- 审查身份、只读边界、允许命令、证据等级、P0-P3 和停止条件。

## 完整性要求

1. 从 `EXHAUSTIVE_SOURCE_REVIEW_CONTROL.template.json` 创建控制记录，在项目现有审计 owner 中保存；已有等价系统时沿用它，不建平行台账。
2. 用项目跟踪文件、语言清单和入口核账文件清单。排除文件也要逐个登记理由；不允许用“非核心”笼统排除第一方源码。
3. 用匹配语言的 AST／编译器／索引能力清点函数、方法、构造器、属性访问器和具有独立行为的 lambda／顶层可执行单元。正则搜索可作交叉检查，不单独作为跨语言完整性证明。
4. 每个可执行单元完成九个审查维度；每条已存在注释／文档字符串完成准确性、必要性、时效性和安全性检查。
5. 每个单元保留稳定 ID、限定名、行范围、内容指纹、证据和 Finding 双向引用。不适用必须有理由，pending／blocked 必须计入未完成数。
6. 分开交付审查结果和整改结果：`review_complete` 代表全量单元已审；`verified_complete` 还要求冻结整改后目标、所有必须整改项已复核、原失败路径与匹配回归通过。

## 完成门禁

- 所有第一方源码文件均已登记为纳入或有理由排除。
- 纳入文件的 symbol scan 和 comment scan 全部 complete，每个单元的审查维度完整。
- 控制记录校验通过，审查报告列出总数、完成数、排除、阻塞、发现和未评估运行环境。
- 任何一个未清点文件、未审函数、未审现有注释或缺失维度都不得宣称穷尽式审查完成。

## 最终输出

- 冻结目标、实际清点方法和限制。
- 系统／模块／文件／可执行单元／现有注释的核账统计与控制记录路径。
- 按 P0-P3 排序的 Finding，包含位置、证据、影响、整改目标、owner 和复核条件。
- 审查完整性结论与整改后符合性结论，两者不混同。
- 明确尚未验证的真实环境、残余风险和不可能承诺的“绝对无 Bug”边界。
