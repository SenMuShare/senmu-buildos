# 工程治理与技术债审查任务

请使用 `$senmu-build-assurance`，并按需读取 `$senmu-build-engineering` 的权威工程规则，对当前项目执行一次“工程治理与技术债审查”。本轮默认只读审查：允许读取代码、文档、Git 状态、配置、测试和构建信息，允许运行非破坏性的检查命令并编写审查报告；未经我再次授权，不要重构业务代码、全仓格式化、升级框架、迁移数据库、修改生产环境或发布版本。

> 审查模式：`risk_based`。本模板允许对明示关键路径抽样，不产生“每个函数／每条注释都已审查”的结论。需要该结论时改用 `EXHAUSTIVE_SOURCE_REVIEW_TASK.template.md`。

## 审查目标

判断当前项目是否正在出现以下问题：

- 模块职责混乱、跨层调用、循环依赖或依赖方向失控。
- 同一能力存在多套实现，旧入口、旧缓存或 legacy 代码仍被新功能误用。
- 超大文件／函数、复杂度热点、重复代码、宽泛异常、死代码或无测试保护的核心逻辑。
- 数据所有权、事务、幂等、权限、状态流转和失败补偿放在错误边界。
- 质量命令、CI、测试和架构检查无法阻止新增问题。
- 技术债没有登记、没有责任归属或没有收口条件。
- 已有 owner、标准／平台能力或当前依赖可以满足需求，却仍存在重复实现、无真实变化压力的抽象、转发包装、脚手架、无用文件或无用依赖。
- 权威项目根、发布单元、VERSION、CHANGELOG、tag、文档适用版本和实际运行版本不一致。

## 执行要求

1. 先确认权威项目根、Git 根、当前分支／commit、发布单元和正式运行入口；检查工作区，不覆盖现有改动。
2. 审查跨越多个模块、阶段或会话时，在项目声明的 Durable Task State Owner 登记只读边界、覆盖计划、当前进度和恢复入口；只有采用 BuildOS 新项目默认实例时才使用 `governance/tasks/TASK-<NNNN>-<slug>.md`。
3. 读取当前作用域的 `AGENTS.md`、README、PRD、技术设计、代码质量、测试、部署、版本、changelog 和工作日志；以真实代码、配置和运行事实校验文档。
4. 盘点语言、框架、模块、入口、数据存储、后台任务、第三方服务、构建和部署边界。
5. 先运行项目已有的非破坏性格式检查、lint、类型、测试、构建和架构检查；失败时保留原始证据，不为了让报告变绿而顺手修代码。
6. 搜索重复实现、跨层依赖、循环依赖、复杂度热点、超大文件／函数、宽泛或静默异常、无用代码、无用依赖、缺失回归／契约／迁移测试和 legacy 入口。
7. 对核心业务路径做语义抽样，说明抽样范围和盲区；不要把工具通过当成业务或架构正确。
8. 把代码质量、架构、技术债、测试门禁、版本发布治理分别报告；安全和业务正确性风险单独标注是否需要专项审计。
9. 按 P0-P3 排序，每项给出文件位置、触发条件、影响、证据、建议和验证方式；另列“实现经济性改进机会”，不把可选删减冒充缺陷或整体审查通过。
10. 给出“立即阻断／近期治理／长期改进”三阶段方案，不提出一次性全项目重写。
11. 将报告保存到 `engineering/audits/ENGINEERING_GOVERNANCE_AND_TECH_DEBT_AUDIT_<YYYY-MM-DD>.md`；如果项目已有审计目录或命名规范，遵守现有规范。

## 最终输出

- 审查范围、治理等级和未覆盖范围。
- 实际执行的命令及结果。
- P0-P3 发现摘要。
- 当前架构、质量、技术债和版本治理基线。
- 有证据支持的复用、删除、依赖收敛和抽象简化机会；只在实际路径或 diff 可核查时估算规模，不套用通用基准宣称节省。
- 建议优先修正的需求、架构、接口、默认值、实现或生产流程，以及确有剩余风险时才需补充的最小机器门禁。
- 本轮只读审查中未修改的内容。
- 下一阶段建议；等待负责人授权后再整改。
