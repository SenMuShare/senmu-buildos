# 工程治理与技术债审查任务

复制当前请求需要的部分，删除不适用字段。局部技术诊断由 `$senmu-build-engineering` 主责；需要冻结对象并形成证据化审计结论时，使用 `$senmu-build-assurance` 并按需读取 Engineering 的规范。审查身份与范围分别说明，同一执行者只能称有证据的自审，不能冒充独立评审。

本轮只读：可读取批准范围的代码、文档、Git、配置及已有测试结果，运行获准的非破坏性检查并形成报告。发现问题不授予重构、全仓格式化、框架升级、数据库迁移、生产操作或发布权限。已有整改授权仍须核对其具体范围，不要求每一步重复批准。

## 先确定范围

- **已指定模块或问题：** 从 `<模块／现象>` 及其相关合同、调用方和依赖开始，不先盘点无关技术栈、部署或历史债务。
- **没有指定模块：** 用近期改动、重复故障和返工选择检查重点；历史不可用时说明缺口。热点只是取样线索，安全和正确性风险优先，不以修改次数直接判定缺陷。
- **明确要求全局体检：** 盘点约定仓库的模块、语言、入口、数据、依赖、构建、部署、版本与治理边界，不以局部样本冒充整仓结论。

> 默认 `risk_based`，说明取样与盲区。只有要求逐文件／逐函数／逐注释覆盖时，才采用 `EXHAUSTIVE_SOURCE_REVIEW_TASK.template.md` 的穷尽覆盖要求；不得以局部路径缩小用户已要求的范围。

## 执行要求

1. 确认权威根、Git 根、分支／commit、工作区与允许操作，复用仍有效的基线，不覆盖他人工作。
2. 多模块、多阶段或跨会话审查沿用现有任务状态位置保存范围、证据和恢复点；一次小型局部诊断不新建任务台账。
3. 读取作用域内有效的项目指令、需求、设计、代码质量和验证入口。仅当与问题或全局审查相关时，补读部署、版本、日志和其他技术栈。
4. 选择能观察问题的已有只读检查，保留失败证据。无关构建不一律运行；付费、生产和破坏性检查仍需相应权限。
5. 按实际问题检查职责、依赖方向、重复能力、旧入口、复杂度、异常、所有权及测试缺口。不要只依据文件大小、方法数量或代码外形下结论。
6. 证据指向相邻调用方或共享边界时扩展，并说明原因。局部范围不能排除与当前问题相连的支付、权限、事务或数据风险；不能访问的证据记为缺口，不擅自操作。
7. 代码质量、架构、技术债、检查能力、版本发布治理分别下结论。真正的缺陷按 P0-P3 排序，可选简化与尚待证据的候选单列，不把猜测或风格偏好当阻断项。
8. 回答当前问题和已约定覆盖后结束取证。只提出与证据相关的后续动作，不把发现报告扩大成全项目重写计划。

## 最终输出

先说明范围、审查身份、结论和盲区，再列少量有证据的发现。小型诊断可在现有任务或对话中完成；需要持久报告时沿用现有审计位置，没有约定才使用 `engineering/audits/ENGINEERING_GOVERNANCE_AND_TECH_DEBT_AUDIT_<YYYY-MM-DD>.md`。

每个候选按需保留这些内容，不另建报告系统：

- **问题与证据：** 真实位置、原始症状、调用关系和已运行检查。
- **前后变化：** 哪些职责集中或分开，哪些调用方改变；一句话、短差异或小图任选。
- **收益与代价：** 减少哪种已发生的摩擦，增加哪些迁移或维护成本，哪些约束必须保留；未知数字不编造。
- **建议与验证：** 优先处理、值得进一步验证或证据不足，并说明验证入口、未覆盖项和恢复方式。

### 局部建议示例（虚构，不是项目事实）

问题：网页入口和后台任务各自复制价格范围校验，规则变更需要在两处修改。

```text
修改前：网页 → 自有范围校验 → 计算
        任务 → 另一份范围校验 → 计算
修改后：网页／任务 → 既有价格模块（范围校验＋计算）
```

建议：在确认两处业务语义相同后，把重复业务规则归入现有价格模块；各入口的身份与租户校验仍留在各自信任边界。保留已有错误语义和兼容约束，不新增服务或通用插件层。

验证：通过两个调用入口验证合法价格、越界拒绝和原有错误；复用已有权限测试。潜在代价是调整调用和兼容错误映射，工作量需读到真实调用方后再判断。若规则看似重复但实际业务含义不同，保留差异，撤回合并建议。
