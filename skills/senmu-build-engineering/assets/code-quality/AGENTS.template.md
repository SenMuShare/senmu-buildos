## 开工读取顺序

1. 阅读 `README.md`，确认项目、发布单元和本地启动方式。
2. 阅读 `engineering/CODE_QUALITY.md` 和 `engineering/ARCHITECTURE.md` 或技术设计中的架构契约。
3. 如本次涉及已登记技术债，阅读 `engineering/TECH_DEBT.md` 或等价台账。
4. 根据本次涉及的文件读取 `engineering/languages/<LANGUAGE>.md`。
5. 只有任务实际涉及某框架时，读取 `engineering/frameworks/<FRAMEWORK>.md`。
6. 阅读受影响模块的需求、技术设计和 `engineering/TESTING_STRATEGY.md`。
7. 检查当前分支、工作区和同类实现，再开始修改。

## 稳定规则

- 项目权威规则优先于通用惯例；安全、隐私、生产数据、支付、权限和正式发布 Hard Gate 不得静默降低。
- 代码标识符使用规范英文；内部业务注释和 docstring 默认使用简体中文。
- 注释解释原因、约束、边界和副作用，不逐行翻译代码。
- 不覆盖他人未提交改动，不夹带与任务无关的格式化、重构或依赖升级。
- 行为变化必须同步匹配测试，以及受影响的需求、技术设计和注释。
- 不违反架构契约声明的模块职责、禁止依赖、数据所有权和发布单元边界。
- 新模块、公共接口、数据库 schema、基础依赖、跨模块状态或第二套同类能力必须先做影响说明；超过项目变更预算时先拆分或复核。
- 临时补丁、长期忽略或兼容分支如形成真实技术债，必须登记债务 ID 和收口条件。
- 工具或测试失败时不得宣称完成；无法运行时必须说明命令、原因和风险。

- 修改范围和行为变化。
