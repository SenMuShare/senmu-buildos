## 2. 通用代码规则

- 使用领域词汇命名，避免职责不明的 helper、manager、data 和 process。
- 让函数、类和模块职责清楚，使输入、输出、副作用和失败方式可发现。
- 遵守技术设计声明的依赖方向，不绕过公开接口跨层访问内部状态。
- 不为形式制造无实际替换或隔离价值的抽象。
- 选择现有、标准、平台或依赖能力前验证其完整语义；优先最小正确实现，不以最少代码绕过契约、风险和必要测试。
- 捕获能够处理的具体异常，不静默吞错，不用成功状态伪装失败。
- 行为变化同步测试、注释和受影响权威文档。
- 永久取消功能时完整删除入口、路由／接口、后台触发、服务分支、开关配置、权限暴露和失效测试／文档；不得只隐藏前端或保留可重新接线的运行时代码。历史数据、兼容和回滚保留范围另行决定并记录退出条件。
- 本次实现稳定后，只在变化范围内检查复用、可维护性和效率；只做可证明行为不变且收益明确的简化，不以删除行数为目标，不削弱安全和必要验证。

## 3. 中文注释规则

- 代码标识符使用规范英文，内部业务注释和 docstring 默认使用简体中文。
- 解释业务原因、约束、幂等、事务、兼容、安全和非显然副作用，不复述代码。
- 对自解释的简单代码不强制添加注释。
- 修改实现时同步更新或删除过时注释。
- 面向国际开发者的公开库或 SDK：`<英文 / 中英双语 / 不适用>`。

## 5. 治理等级与门禁

- G1：运行受影响文件可用的格式、lint 或可见验证。
- G2：运行格式检查、lint、适用类型检查和匹配测试，审查完整 diff。
- 风险决定证据深度，开发／集成／发布阶段决定检查时机；项目明确批准的更严格政策继续执行。
- G3：开发切片先做影响分析、匹配测试和受影响架构检查；在集成／发布收口运行项目声明的完整质量、测试、构建与 CI，不因等级自动把开放切片视作发布候选。
- G4：在首个受影响切片验证安全、权限、数据和真实风险路径，不延后必要保护；独立 AI 或人工复核由实际风险、职责分离或项目明确政策触发。

## 7. 代码评审输出

- 审查触发：每个准备进入集成基线的代码变更集，不对每个 WIP commit 重复审查。
- 冻结对象：`<base_commit..head_commit>`；新 commit 使旧批准失效。
- 审查者：`<按实际风险、职责分离及项目明确政策确定；普通自审不冒充独立审查>`。
- 审查记录 owner：`<PR／MR／项目审批系统／change-review.json>`。
- 合并门禁入口：`<受保护分支必需检查／本地 merge 命令>`。
- 职责分离适用时，实现者先交付实际改动、测试、偏差和已知缺口；审查 Finding 必须包含位置、触发、影响、严重度和复核条件。返修后复核原 Finding 与受影响链，最终批准绑定完整 `base..head`；普通低风险变更不强制额外 Agent 或固定轮次。

- 先报告正确性、安全、数据、兼容性和测试问题，再报告可维护性和风格建议。
- 每个问题说明文件、位置、触发条件、影响和建议。
- 区分确定缺陷、待确认风险和可选改进。
- 没有发现问题时仍列出检查范围和未验证盲区。
- 明确说明模块职责、依赖方向、重复实现、技术债和版本发布事实是否恶化。
- 功能永久退役时，明确检查直接入口、后台触发、配置／开关和旧测试是否仍可恢复旧能力；数据销毁不从代码删除任务中推导授权。
