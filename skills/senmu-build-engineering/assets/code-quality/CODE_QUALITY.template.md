## 2. 通用代码规则

- 使用领域词汇命名，避免职责不明的 helper、manager、data 和 process。
- 函数、类和模块按实际责任命名；名称、签名与邻近说明应让读取、计算、提交和应用结果的差异可发现。不要把网络、写入或取消隐藏在看似纯计算的接口中，也不机械拆成四层。
- 关键业务参数与结果使用准确类型和明确字段；固定业务结构不藏进无约束字典。互斥阶段用明确状态及相应载荷表达，真正独立的布尔属性不强制合并。外部输入仍需运行时校验。
- 涉及事务时保留同一业务操作的原子提交／回滚；拆模块不拆坏事务。持锁期间不随意等待慢外部调用；调整调用顺序时同步验证一致性和未知结果恢复。
- 涉及客户端异步状态时使用当前框架的请求与生命周期机制；React 客户端 render／memo 不执行请求取消或资源清理。旧任务的结果、错误与收尾不得污染另一个实体或已替代的请求，不能只依靠 abort 判断结果有效。
- 遵守技术设计声明的依赖方向，不绕过公开接口跨层访问内部状态。
- 不为形式制造无实际替换或隔离价值的抽象；简单且只用一次的逻辑优先留在调用处，明确概念、复杂边界或真实复用／隔离价值除外。
- 不为没有可说明触发路径的假想边界增加防御、重试或兼容机制；在负责边界校验未知数据，内部复用仍成立的保证，新信任边界、状态变化或不同业务约束仍需检查。类型标注或转换不等于运行时校验。
- 选择现有、标准、平台或依赖能力前验证其完整语义；优先最小正确实现，不以最少代码绕过契约、风险和必要测试。
- 捕获能处理或恰当转换的异常并保留原因。恢复选择不同时区分明确拒绝、已知失败和外部结果未知；超时或取消请求不是未执行的证明。恢复、回滚或清理再次失败时保留两层原因，不宣称已经恢复，不盲目重发未知效果。
- 行为变化同步测试、注释和受影响权威文档。
- 永久取消功能时完整删除入口、路由／接口、后台触发、服务分支、开关配置、权限暴露和失效测试／文档；不得只隐藏前端或保留可重新接线的运行时代码。历史数据、兼容和回滚保留范围另行决定并记录退出条件。
- 本次实现稳定后，只在变化范围内检查复用、可维护性和效率；只做可证明行为不变且收益明确的简化，不以删除行数为目标，不削弱安全和必要验证。
- 公网服务、不可信输入、上传／远程取文件和付费后台任务，主动核对服务端授权、输入／资源边界与费用上限；采用框架和平台的成熟控制，实施规则与实际部署验证分别归属原技术和运维文档。
- 以相同验收下完成任务的总成本评价效率；实测输入／输出／缓存 Token 与找路、重复读取、返工分别记录，缺少宿主用量时不填估算为实测。

## 3. 注释书写与治理

### 书写

- 沿用项目语言；无另行规定时，英文标识符配简体中文业务注释。公开库／SDK 的说明语言：`<英文 / 中英双语 / 项目约定>`。
- 不复述显而易见的动作，不要求每个函数都写。保留代码难以表达的原因、内部业务约束和必要算法解释；公共接口说明用途、用法、结果、错误和副作用。
- 补足影响正确使用或安全修改的缺失信息；重要理由链接原需求或设计，不编造历史。临时办法说明原因、范围和退出条件，不用说明掩盖缺陷。
- 版权、工具指令、文档生成内容和类型负例测试单独核查实际用途，不按关键词批量删除。检查豁免须有范围和理由，临时豁免还须有退出条件。

### 治理

- 普通开发检查本次修改和受影响的邻近注释；专项治理按约定范围执行。只读审查不修改，文字清理不自动授权业务重构。
- 分别判断说明与实现：删除无效内容、修正错误、补齐缺失、保留必要理由；暴露的实现问题在授权内修复并验证，不能只删说明就称修好。
- 原因未明时保留必要警告并标明待核实，不把旧说法当事实；只暂停依赖它的关键修改，不阻塞无关工作。
- 优先改善正确默认实现，按真实缺口补必要保护；先验证替代保护，再移除警告。有测试不等于设计理由不再需要。
- 核验受影响的行为、工具和文档；不以注释密度或删除数验收。规范失效时修原规则、入口或实现，不另建台账或逐事故追加规则。

## 5. 治理等级与门禁

- G1：运行受影响文件可用的格式、lint 或可见验证。
- G2：按实际影响与项目已声明门禁选择适用的格式、lint、类型和测试检查，审查完整 diff；只读审查不修改被审对象，文档工作不机械触发无关代码检查。
- 风险决定证据深度，开发／集成／发布阶段决定检查时机；项目明确批准的更严格政策继续执行。
- G3：开发切片先做影响分析、匹配测试和受影响架构检查；在集成／发布收口运行项目声明的完整质量、测试、构建与 CI，不因等级自动把开放切片视作发布候选。
- G4：在首个受影响切片验证安全、权限、数据和真实风险路径，不延后必要保护；独立 AI 或人工复核由实际风险、职责分离或项目明确政策触发。

## 7. 代码评审输出

- 审查触发：每个准备进入集成基线的代码变更集，不对每个 WIP commit 重复审查。
- 冻结对象：`<base_commit..head_commit>`；新 commit 使旧批准失效。
- 审查者：`<按实际风险、职责分离及项目明确政策确定；普通自审不冒充独立审查>`。将适用要求写到既有合并入口，交付校验使用同一要求；被审记录不得自行放宽它。
- 审查记录 owner：`<PR／MR／项目审批系统／change-review.json>`。
- 合并门禁入口：`<受保护分支必需检查／本地 merge 命令>`。
- 职责分离适用时，实现者先交付实际改动、测试、偏差和已知缺口；审查 Finding 必须包含位置、触发、影响、严重度和复核条件。返修后复核原 Finding 与受影响链，最终批准绑定完整 `base..head`；普通低风险变更不强制额外 Agent 或固定轮次。

- 先报告正确性、安全、数据、兼容性和测试问题，再报告可维护性和风格建议。
- 每个问题说明文件、位置、触发条件、影响和建议。
- 区分确定缺陷、待确认风险和可选改进。
- 没有发现问题时仍列出检查范围和未验证盲区。
- 明确说明模块职责、依赖方向、重复实现、技术债和版本发布事实是否恶化。
- 功能永久退役时，明确检查直接入口、后台触发、配置／开关和旧测试是否仍可恢复旧能力；数据销毁不从代码删除任务中推导授权。
